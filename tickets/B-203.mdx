drew.

### What to build

1. **The listing ledger**, written into this ticket's PR body and checked by a test: for each key
   of `uiState().needs_you` — `unconfirmed`, `attempts`, `held_items`, `regressed`,
   `stale_skills`, `fence_pending`, `bars_mismatch`, `unacknowledged_releases`, `policy` (claims;
   `policy` the legs waiting on a required bar),
   `blocked_capability`, `instances_unknown` (blocks), `no_owner_channel`, `pool_unclaimed`
   (notices), `course_changed` (stations), `adoptions`, `courses_refused`, `ontologies_refused`,
   `keys`, `scope`, `questions` — the V2 screen that shows it: a `baton.<sub>` condition on
   Conditions (B-57's work, B-195's screen) for the claims', blocks', notices' and stations'
   listings, the refused courses and ontologies and the keys notice; adoptions on Sync (B-220);
   scope findings on the ticket page (B-210, B-222); questions on Conditions (B-219). A key B-57 did
   not make a condition and no screen shows is a gap: file it as a ticket in this project
   before removing the route — this ticket does not finish with a listing lost. The test
   asserts the ledger's keys equal `needs_you`'s at the moment of removal.
2. **Retire `GET /v1/ui/state`**: the route and `ui.state`'s §14 row; every query it composed
   is behind an entity read. `uiState()` itself stays, serving `GET /v1/admin/state`, and B-216
   renames it `stateView()` (Decision 4a) — one ticket renames, this one removes a route.
3. **The `/v1/ui/*` routes.** Keep every write route V2 calls (`/v1/ui/messages`,
   `/v1/ui/overrides/{ticket}`, `/v1/ui/conditions/{condition}/resolve`, `/v1/ui/resync`,
   `/v1/ui/board/accept`, `/v1/ui/scope/{id}/resolve`, `/v1/ui/claims/{id}/reap`,
   `…/fence-clear`, `…/confirm`, `…/release`, `/v1/ui/cutover`, `/v1/ui/adoptions/{claim}/confirm`,
   `/v1/ui/logout`): they are the session's write surface, with R-BTN-16's `Origin` rule and
   R-BTN-155's codes. Remove `POST /v1/ui/claims/{id}/resolve`, which V1 alone called and which
   B-222's `…/confirm` and `…/release` replaced (it has no §14 row); the `@model` annotation
   moved with them. `check:actions` and `model:links` green.
4. **Docs.** `docs/context/design-brief.mdx`'s "Where to look" names `src/dashboard/` and the
   entity reads and drops V1; the README's Layout and Commands are current;
   `BATON_SPEC_HISTORY.md`'s Migrations list the retired view names (Needs you, Running, Ready,
   Timeline, Instances, Capacity, Discrepancies, Resolve as a bare path) with the screens that
   replaced them, as R-BTN-127 does for command names. B-17's PR is merged or the owner closes
   it; this ticket touches it not.

### What not to do

- Do not retire `ui.state` while a listing has no home (item 1).
- Do not touch `GET /v1/admin/state`'s shape (B-216) or any workflow (B-193 made the one change).
- No new screen or control: a gap is filed, not built.

### Trust

Removal adds no input. The ledger test is the trust statement: nothing a person needed to see
in V1 is silently gone.

### Invariants

- **No listing lost** (R-BTN-163).
- **One check** (R-BTN-129): `check:actions` green, no route outside the registry.
- **Both hosts** (R-BTN-55).

### Tests

The ledger test (item 1); `check:actions`; a unit test that no file under `src/` references
`/v1/ui/state` or `/v1/ui/claims/{id}/resolve`; the full suite green on both hosts.
