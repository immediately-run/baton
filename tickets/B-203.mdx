### What to build

1. **Every listing accounted for.** Before removing V1, list what its Needs you drew
   (`uiState().needs_you`: the claims', blocks', notices', stations', adoptions, refused courses
   and ontologies, the keys notice, scope findings, questions) and find each on a V2 screen: a
   condition on Conditions (R-BTN-163), an adoption on Sync, a refused course on Courses, the
   keys notice and seed owners on the tenant screens. A listing with no home is a gap: file it
   as a ticket (B-56 and B-57 own the moves into conditions) and keep V1 serving until it has
   one — this ticket does not finish with a listing lost.
2. **Remove V1.** Delete `src/ui/index.html`, `app.css` and `app.js`; the front's `STATIC` map
   serves only the V2 bundle (B-193); the README's `src/ui/` row describes `src/ui-v2/` (or the
   directory is renamed to `src/ui/` in the same PR, with B-193's paths updated — the
   implementer's choice, stated in the PR body).
3. **Retire `GET /v1/ui/state`.** Remove the route, `uiState()`'s assembly and `ui.state`'s
   §14 row; every query it composed is now behind an entity read (B-192 to B-202). Remove each
   `/v1/ui/*` route whose action has an `http` route the dashboard now calls directly, and keep
   the `ui` routes R-BTN-129 still names (`/v1/ui/resync`, `/v1/ui/overrides/{ticket}`,
   `/v1/ui/conditions/{condition}/resolve`, `/v1/ui/messages`, the claim and adoption
   confirmations, cutover, logout) — or, where B-192's registry work gave each of them an
   `http` row a session may call, retire the `ui` route and amend R-BTN-129's `ui` bullet to say
   `route` is gone; `check:actions` decides which, and the §14 Dashboard rows follow.
4. **Settle `GET /v1/admin/state`** (B-118, R-BTN-57): it stays, as the one-request answer a
   terminal reads — the union of `repo.list`, each repository's `board`, `tickets`, `runners`,
   `conditions`, `sync` and the tenant reads, by the same functions — so the dashboard and a
   terminal cannot drift (R-BTN-179), and S-BTN-170 asserts the union equals the parts.
5. **The scenarios.** S-BTN-76 (hostile values rendered) and G-BTN-13 run against the V2
   renderer: markup and `javascript:` in a ticket title, a hold reason, an activity label, a
   reading detail and a condition's detail reach each screen as text; a link to an unlisted host
   is text. G-BTN-100's renderers row names the V2 bundle. B-191's scenario (the screen draws
   only its caller's actions) runs on every screen with a control.
6. **The deploy.** `baton-deploy.yml` builds the bundle before `wrangler deploy` (B-193's step,
   confirmed here on staging): `baton-staging.immediately.run` serves V2 at `/`, every tree path
   deep-links, and `/login` signs an administrator in; the production deploy follows on merge.
   A CI change: in an owner-approved PR, named in its body.
7. **Docs.** `docs/context/design-brief.mdx`'s "Where to look" names `src/ui-v2/` (or `src/ui/`)
   and the entity reads; the README's layout table and Commands (`build:ui`) are current;
   `BATON_SPEC_HISTORY.md`'s Migrations list the retired view names (Needs you, Running, Ready,
   Timeline, Instances, Capacity, Discrepancies as views) with the screens that replaced them,
   as R-BTN-127 does for command names.
8. **The project page.** `tickets/projects/baton-ui-v2.mdx`'s Done when is checked against the
   deployed instance, and B-17 is closed if it still stands open.

### What not to do

- Do not remove V1 while a Needs-you listing has no V2 home (item 1).
- Do not keep `GET /v1/ui/state` "for compatibility": nothing but V1 reads it, and a second
  source of truth drifts (R-BTN-179's reason).
- Do not rewrite `admin.state` as a new query: it is the union of the entity reads' functions.
- No new screen or control: gaps found here are filed, not built.

### Trust

- **Removal** adds no input. `admin.state` is answered to an administrator's key only
  (R-BTN-57), built from functions already bounded by their reads' callers.
- **The scenarios** are the trust statement: every value that reached V1 as `textContent`
  reaches V2 as a text node, proven on both hosts.

### Invariants

- **No listing lost** (R-BTN-163): what Needs you showed, Conditions or another screen shows.
- **Readable with a key** (R-BTN-179): `admin.state` equals the union of the reads.
- **Text, never markup** (§12.3, G-BTN-13, S-BTN-76).
- **One check** (R-BTN-129): `check:actions` is green with no route outside the registry.
- **Both hosts** (R-BTN-55).

### Tests

S-BTN-76, S-BTN-170 and G-BTN-13 amended and green against V2; B-191's scenario over every screen;
a unit test that no file under `src/` references `/v1/ui/state` or `src/ui/`; `check:actions`
green; a staging run noted in the PR body with the paths exercised.

### Exit criteria

- [ ] Every V1 listing has a V2 home or a filed ticket; V1's files and `GET /v1/ui/state` are
      gone; the `ui` routes are as `check:actions` and R-BTN-129 settle them.
- [ ] `admin.state` is the union of the entity reads, asserted by S-BTN-170.
- [ ] Staging serves V2 for every tree path; the deploy builds the bundle (owner-approved
      workflow change).
- [ ] Brief, README, history Migrations and the project page current; `npm test`,
      `npm run typecheck`, `npm run lint`, `npm run check:actions`, `npm run check:wiki` and
      `npm run check:tickets` are green.
