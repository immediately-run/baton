**Brief:** the owner, 2026-10-22: "how can a leg indicate that it requires a singleton within
the runner's VM. For instance, a chrome MCP session which can only be used by a single agent
session… Similar: I want one instance of a leg being completed by all runners at any time (eg:
the leg required RDP access to a machine which can only be controlled by a single client at a
time)." And: "specific capabilities used by the leg about to be completed should travel with the
claim request: the runner in the vm is authoritative about this… if they make the claim first,
the later claim can fail."
**Spec:** §6.11 R-BTN-178 (rewritten 2026-11-02 by the spec restructure's part 4, B-166), with
the rules it touches: §6.6 rule 11 and step 4, R-BTN-75's why-not table (`full`), R-BTN-99's
instance view, R-BTN-127's `admin capacity set`, §13 (`capability_capacity`) and §14 (`PUT
/v1/admin/capacities`). The history is in `BATON_SPEC_HISTORY.md` (Changelog, 2026-10-22, §6.11;
and "the restructure, part 4", which replaced seats on resource instances, `bills`, `claim_bills`
and the `host` scope by B-165's review default).

### What to build

1. **Registration.** A migration adds `capability_capacity (capability, capacity, set_by,
   set_at)`. Add `baton admin capacity set <capability> <n> | --clear`, the registry action
   `admin.capacity.set` and `PUT /v1/admin/capacities`, logged `admin`.
2. **Seats.** A claim holds a seat on each capability with a capacity that its running leg
   requires among those rule 4 matched — the claim's leg until its first `advance`, then the
   leg the latest `advance` started. Seats are computed from claims and their legs, never stored
   apart.
3. **Rule 11.** In the claim's and advance's committing transaction, count the seats other
   active or fence-pending claims hold on each such capability and refuse `capacity-full` past
   capacity, naming the holders only where the caller may see them. Never a failed attempt; a
   `prefer` claim moves to its next candidate. Add the rule to the matching code and the model
   (R-BTN-68).
4. **Release.** An `advance` into a leg not requiring the capability, the claim's end and a reap
   release the seat; a fence-pending reap releases at `fence-cleared` or the fence deadline.
5. **Recommendations and why-not.** Skip a leg requiring a full capability; `baton leg why`
   answers `full`. The instance view serves each capacity and the claims holding its seats.
6. **One machine's singleton** is the runner's: document, in the runner's configuration help, a
   capability whose check takes a lock the runners on that machine share (R-BTN-121, R-BTN-178).

### Tests

S-BTN-21 (rewritten) and G-BTN-162, green in `npm test` on both hosts.

### Exit criteria

- [ ] one capability with capacity 1 has at most one holder across every host and repository
- [ ] a seat refusal is `capacity-full`, never a failed attempt, and a reap releases every seat
- [ ] recommendations do not offer a leg whose required capability is full

## Status

- 2026-11-02: rewritten by the spec restructure's part 4 (B-166, B-165's review default): the
  capacity is a capability's, not a resource instance's. Where the old plan's items went: 1
  (resource `--capacity`, `host` scope) → item 1, a capability's capacity; the `host` scope is
  gone, one machine's singleton being a runner-side lock (item 6). 2 (host instances) → nowhere:
  no per-host instance. 3 (rule 11 on bills, per-candidate `bills`) → item 3, on the leg's
  requirements; no `bills`. 4 (release) → item 4. 5 (recommendations, why-not, instance view)
  → item 5, `full` in place of `busy`. 6 (the runner names its bills) → nowhere: the seat
  follows from the leg. Exit criteria: the first → two runners on one VM sharing a device is
  the runner's lock; the rest as above.
