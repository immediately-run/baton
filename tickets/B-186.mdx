**Brief:** the owner, 2026-11-08: "I've noticed that failed leg runs often leave almost completed
work as filesystem changes in their git worktrees which the next attempt should have access to so
it can continue from there."

**Spec:** [BATON_SPEC §9.3](../spec/BATON_SPEC/09-claims.md#sec-9-3) ([R-BTN-44](../spec/BATON_SPEC/09-claims.md#sec-9-3)),

**Depends on:** B-185 (the run id that names a draft).
**Used by:** B-184 (its executor interface gains `salvage`), any executor that discards a leg's environment (Fieldhouse's sandbox executor).

### Why

- Every leg runs in the runner's one home checkout (R-BTN-131, `src/runner/home.ts`); the runner
  neither cleans nor preserves it between legs. A retry on the same runner may find the previous
  attempt's changes; a retry anywhere else finds nothing.
- The leftovers leak: the next leg on that runner may be another ticket's, and starts in a dirty
  tree. create-pr's implement instructions work around it ("the checkout may hold other work").
- §9.4 already promises that a release pushes the work done so far; nothing but the agent does it,
  and R-BTN-44 exempts a lost lease and a supersession from the hand-off entirely.
- Under B-184 with an executor that discards a leg's disk (FLDH-52), the work is always lost.

### What to build

1. **Capture at every leg end where the checkout exists** — a failed or timed-out `run`, a stop
   or release (R-BTN-119, before `close` and `handoff`, so the hand-off can cite the draft), a
   context refresh (R-BTN-123, before the fresh session starts), a suspension, and at runner start
   for a checkout left dirty by a runner that died (its lock names the last claim and run id).
   Not after a leg that finished cleanly with nothing uncommitted. The runner, never the agent:
   - a temporary index (`GIT_INDEX_FILE` under the git dir), never the leg's own;
   - `git add -A` into it under the runner's usual `-c core.hooksPath=/dev/null
     -c core.fsmonitor=false`: untracked files included, ignored files not, `node_modules` and the
     install roots' links never;
   - `git write-tree`, then `git commit-tree` with the checkout's `HEAD` as parent and trailers
     `Baton-Ticket`, `Baton-Run-Id`, `Baton-Leg`, `Baton-End` (the end reason);
   - nothing to capture (the tree equals `HEAD`'s) writes nothing.
2. **Bounded and masked.** A file over 5 MB, or files past 50 MB in total, are left out and listed
   in the commit message. A file containing any literal in R-BTN-144's masking set (computed for
   that leg) is left out and named, never pushed. A binary file is captured within the bounds.
3. **Pushed to a draft ref, never a branch:** `refs/baton/wip/<tenant host>/<local ticket id>/<run_id>`
   on the home's remote (B-185 item 5), with the runner's own credential and a 60-second bound. A
   failed push keeps the commit in the local git dir under the same ref name and records
   `salvage-push-failed`; the next salvage on that runner retries it.
4. **Recorded as resume data.** The runner reports activity `salvaged` whose detail's `resume`
   carries `{draft: {ref, sha, base, files, bytes, left_out}}`; R-BTN-24 carries it into the resume
   record, `previous_attempts` and `BATON_RESUME` unread. A draft Baton never heard of (a lost
   lease, a dead runner) is still found by listing `refs/baton/wip/<tenant host>/<local ticket id>/*`.
5. **The checkout is reset after capture**: `git reset --hard HEAD` and `git clean -fdx` outside the
   install roots, so the next leg — any ticket's — starts clean. The implement instructions' "the
   checkout may hold other work" line is removed.
6. **create-pr resumes from the newest draft.** At the start of an implement or fix leg the leg
   script, not the agent, looks for the newest draft of this ticket (resume record first, then the
   ref listing): if its `base` is the branch's tip or an ancestor of it and it applies cleanly
   (`git checkout <draft> -- .` over the branch, or `git apply --3way` of `base..draft` when the
   branch moved), it applies it **uncommitted** and the instructions tell the agent: "an earlier
   attempt left these uncommitted changes (run `<run_id>`, ended `<reason>`); they are a draft
   from a failed run — review them before you commit any". If it does not apply, nothing is
   applied and the agent is told the ref. Review, adjudicate and merge legs never apply a draft.
7. **Retention.** When a writing leg of the ticket ends with its work pushed to the branch, or the
   ticket closes, the runner deletes that ticket's draft refs; otherwise the newest 3 per ticket
   are kept, and a runner deletes drafts older than 14 days on its home when a claim ends.
8. **Agents still push early.** create-pr's implement and fix instructions gain one line: commit
   and push to the branch whenever the repository's checks pass. Salvage is for the ends where the
   agent never gets to.

### What not to do

- **No push of a draft to the ticket's branch**, which would run CI, enter review and mix a
  failed run's work into the PR.
- **No draft for a leg that does not write:** review, adjudicate and `reads_only` legs are not
  salvaged and never receive one.
- **No core change beyond what B-185 adds:** core reads no `draft` field; `salvaged` is an activity
  like any other.
- **No capture by running repository code:** no hooks, no fsmonitor, no `npm` script.

### Trust

- **The draft** — written by a leg that failed, which may be a compromised one. It reaches only
  the next writing leg of the same ticket, which runs that branch's code anyway (R-BTN-183: no new
  taint), as uncommitted changes the agent is told to review. It never reaches a review leg.
- **`refs/baton/wip/*`** — writable by anyone who can push the home; outside every guarantee, and
  nothing a trusted leg acts on is read from it (Decisions 2026-10-30). A forged draft under a
  ticket's prefix is at worst bad starting work offered to an implementer, as a forged branch
  commit is today. On a public repository a draft is publicly readable, which is why item 2 drops
  files holding known credentials.
- **The `salvaged` activity's `resume`** — the runner's word (R-BTN-46), returned as data in
  `BATON_RESUME`, never inside instructions (R-BTN-144).

### Invariants

- **The audit window** (§12.9): the salvage push is the runner's own, made after the leg's window
  closes, and is not reported as the leg's push.
- **Legs are stateless at their boundaries** (R-BTN-38): the draft is in git, where any runner
  finds it; nothing travels through a session's context.
- **Idempotent side effects** (R-BTN-25): a ref per run id; re-running capture for one run
  rewrites nothing that differs.
- **One runner per home checkout** (R-BTN-131) holds; the reset makes it also one ticket's tree.

### Tests

- A leg that writes files and exits 1: a draft ref exists with those files, the checkout is clean,
  and the next implement attempt's checkout holds the files uncommitted with the instruction line.
- An untracked ignored `.env` is not captured; a tracked file holding a masked literal is left out
  and named.
- A branch that moved so the draft conflicts: nothing applied, the agent told the ref.
- A runner killed mid-leg: on restart it salvages the dirty checkout under the dead claim's run id.
- A review leg after a failed implement leg starts with no draft applied.
- Retention: a successful implement leg deletes the ticket's drafts.
- Each behaviour change names its `S-BTN-n` scenario (R-BTN-31).
