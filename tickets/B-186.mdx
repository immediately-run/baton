**Brief:** the owner, 2026-11-08: "I've noticed that failed leg runs often leave almost completed
work as filesystem changes in their git worktrees which the next attempt should have access to so
it can continue from there."

**Spec:** [BATON_SPEC §9.3](../spec/BATON_SPEC/09-claims.md#sec-9-3) ([R-BTN-44](../spec/BATON_SPEC/09-claims.md#sec-9-3)),

**Depends on:** B-185 (the run id that names a draft).
**Used by:** B-184 (its executor interface gains `salvage`), any executor that discards a leg's environment (Fieldhouse's sandbox executor).

### Why

- Every leg runs in the runner's one home checkout (R-BTN-131, `src/runner/home.ts`); the runner
  neither cleans nor preserves it between legs. A retry on the same runner may find the previous
  attempt's changes; a retry anywhere else finds nothing.
- The leftovers leak: the next leg on that runner may be another ticket's, and starts in a dirty
  tree. create-pr's implement instructions work around it ("the checkout may hold other work").
- §9.4 already promises that a release pushes the work done so far; nothing but the agent does it,
  and R-BTN-44 exempts a lost lease and a supersession from the hand-off entirely.
- Under B-184 with an executor that discards a leg's disk (FLDH-52), the work is always lost.

### What to build

1. **Capture at every leg end where the checkout exists** — a failed or timed-out `run`, a stop
   or release (R-BTN-119), a suspension — after `close` and `handoff` have run, so the capture falls outside the leg's audit
   window (§12.9) and is reported as the runner's own push; and at runner start for a checkout left
   dirty by a runner that died (its lock names the last claim and run id), unless that leg is still
   running and reattachable (B-188). Every checkout the runner prepared for the leg is captured,
   the home's and those of the ticket's other `repos:`. Not at a context refresh (R-BTN-123): the
   fresh session continues in the same checkout, so its work is neither captured nor reset there
   (B-12 overlaps).
   Not after a leg that finished cleanly with nothing uncommitted. The runner, never the agent:
   - a temporary index (`GIT_INDEX_FILE` under the git dir), never the leg's own;
   - `git add -A` into it under the runner's usual `-c core.hooksPath=/dev/null
     -c core.fsmonitor=false`: untracked files included, ignored files not, `node_modules` and the
     install roots' links never;
   - `git write-tree`, then `git commit-tree` whose parent is the **remote** tip the leg started
     from (the ticket branch's remote tip, else the default branch's) — never the checkout's
     `HEAD`, so commits the leg made and never pushed are not pushed with the draft; they are folded
     into the draft's single diff instead, where masking sees them — with trailers `Baton-Ticket`,
     `Baton-Run-Id`, `Baton-Leg`, `Baton-End` (the end reason);
   - nothing to capture (the tree equals the parent's) writes nothing.
2. **Bounded and masked.** A file over 5 MB, or files past 50 MB in total, are left out and listed
   in the commit message. A file matching any of R-BTN-144's seven masking classes (computed for
   that leg: the literals and the patterns, Baton's bearer prefixes and private-key blocks among
   them) is left out and named, never pushed: the whole diff from the parent is scanned, unpushed commits
   included. A left-out tracked file keeps the parent's blob in the draft tree, so applying the draft
   never deletes it. A binary file is captured within the bounds.
3. **Pushed to a draft ref, never a branch:** each checkout's capture to its own repository's
   remote, at `refs/baton/wip/<tenant host>/<local ticket id>/<run_id>` (B-185 item 5) — never one
   repository's tree to another's remote, so a private repository's work never lands in a home
   that may be public — with the runner's own credential and a 60-second bound. A
   failed push keeps the commit in the local git dir under the same ref name and records
   `salvage-push-failed`; the next salvage on that runner retries it.
4. **Recorded as resume data — a core change, larger than one kind.** Activity kinds and their
   detail keys are closed lists (`src/core/validate.ts`), the code accepts no `resume` detail key
   yet, and `resumeRecord` (`src/core/attempts.ts`) copies no `resume` object — R-BTN-24 specifies
   that carrying; the code does not do it. In scope here: a new activity kind `salvaged`; the
   `resume` detail key §12 already specifies (flat values, at most 2 KB); `resumeRecord` copying
   each activity's `resume` as R-BTN-24 says. The `salvaged` activity's `resume` carries flat keys
   per checkout repository: `draft_repo`, `draft_ref`, `draft_sha`, `draft_base`, `draft_files`,
   `draft_bytes`, `draft_left_out` (a count; names in the draft's commit message), one activity per
   repository. The resume record, `previous_attempts` and `BATON_RESUME` then carry it unread. A draft Baton never heard of (a lost lease, a
   dead runner) is found by listing `refs/baton/wip/<tenant host>/<local ticket id>/*` — and only
   shown, never applied (item 6).
5. **The checkout is reset after capture**: `git reset --hard HEAD` and `git clean -fd` (not `-x`:
   ignored files, which capture leaves out, are kept) outside the install roots, so the next leg — any ticket's — starts clean. The implement instructions' "the
   checkout may hold other work" line is removed (both copies: `.baton/courses/create-pr/legs/implement.md` and
   `src/defaults/courses/create-pr/implement.md`).
6. **create-pr resumes from the newest draft Baton recorded.** At the start of an implement or fix
   leg the leg script, not the agent, takes the newest draft named in this ticket's resume records
   (`draft_ref` and `draft_sha`, and only if the ref still points at that sha). If its `base` (the
   remote tip it was parented on) is the branch's tip or an ancestor of it and it applies cleanly
   (`git checkout <draft> -- .` over the branch, or `git apply --3way` of `base..draft` when the
   branch moved), it applies it **uncommitted** and the instructions tell the agent: "an earlier
   attempt left these uncommitted changes (run `<run_id>`, ended `<reason>`); they are a draft
   from a failed run — review them before you commit any". If it does not apply, nothing is
   applied and the agent is told the ref. A draft found only by listing refs is named to the agent
   as unverified and never applied: `refs/baton/*` is open to every writer (§12.8), so applying it
   would let a writer the forge restricts feed the implementer. Review, adjudicate and merge legs never apply a draft.
7. **Retention.** When a writing leg of the ticket ends with its work pushed to the branch, or the
   ticket closes, the runner deletes that ticket's draft refs; otherwise the newest 3 per ticket
   are kept, and a runner deletes drafts older than 14 days, in each repository it pushed drafts
   to, when a claim ends.
8. **Agents still push early.** create-pr's implement and fix instructions gain one line: commit
   and push to the branch whenever the repository's checks pass. Salvage is for the ends where the
   agent never gets to.

### What not to do

- **No push of a draft to the ticket's branch**, which would run CI, enter review and mix a
  failed run's work into the PR.
- **No draft for a leg that does not write:** review, adjudicate and `reads_only` legs are not
  salvaged and never receive one.
- **No core reading of a draft:** core validates the new activity kind, the `resume` key and its
  flat values, carries them, and reads none of them; nothing places a ticket or passes a gate on a draft.
- **No capture by running repository code:** no hooks, no fsmonitor, no `npm` script.

### Trust

- **The draft** — written by a leg that failed, which may be a compromised one. It reaches only
  the next writing leg of the same ticket, which runs that branch's code anyway (R-BTN-183: no new
  taint), as uncommitted changes the agent is told to review. It never reaches a review leg.
- **`refs/baton/wip/*`** — writable by anyone who can push the home; outside every guarantee, and
  nothing a trusted leg acts on is read from it (Decisions 2026-10-30). A forged draft under a
  ticket's prefix is at worst bad starting work offered to an implementer, as a forged branch
  commit is today. On a public repository a draft is publicly readable, which is why item 2 drops
  files holding known credentials.
- **The `salvaged` activity's `resume`** — the runner's word (R-BTN-46), returned as data in
  `BATON_RESUME`, never inside instructions (R-BTN-144).

### Invariants

- **The audit window** (§12.9): under `builtin` the salvage push is the runner's own, made after
  `close` and `handoff` and so after the leg's window closes, and is not reported as the leg's
  push. Under an executor that salvages itself (B-184's `salvage`), the push is the executor's
  act with the credential it chooses — Fieldhouse's pushes with the leg's own token and counts it
  as the leg's push (FIELDHOUSE_SPEC R-FH-80). R-BTN-72's
  "The runner writes nothing to git itself" is amended in the spec PR to name this one write.
- **Legs are stateless at their boundaries** (R-BTN-38): the draft is in git, where any runner
  finds it; nothing travels through a session's context.
- **Idempotent side effects** (R-BTN-25): a ref per run id; re-running capture for one run
  rewrites nothing that differs.
- **One runner per home checkout** (R-BTN-131) holds; the reset makes it also one ticket's tree.

### Tests

- A leg that writes files and exits 1: a draft ref exists with those files, the checkout is clean,
  and the next implement attempt's checkout holds the files uncommitted with the instruction line.
- An untracked ignored `.env` is not captured; a tracked file holding a masked literal is left out
  and named.
- A branch that moved so the draft conflicts: nothing applied, the agent told the ref.
- A runner killed mid-leg: on restart it salvages the dirty checkout under the dead claim's run id.
- A leg with an unpushed local commit holding a credential: the draft's parent is the remote tip,
  the commit is not pushed, and the credential-bearing file is left out with its parent blob kept.
- A context refresh captures nothing and resets nothing.
- A ticket with two repositories pushes each capture to its own repository's remote.
- A runner restarted while its leg still runs and is reattachable (B-188) salvages nothing.
- A draft found only by listing refs is named to the agent and not applied.
- A review leg after a failed implement leg starts with no draft applied.
- Retention: a successful implement leg deletes the ticket's drafts.
- Each behaviour change names its `S-BTN-n` scenario (R-BTN-31).
