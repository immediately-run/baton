**Brief:** the policy a repository stores and the policy the spec describes are two documents.
`PolicyDocument` and `KNOBS` in `src/core/policy.ts` carry knobs and values §12.8's table does
not have, and lack four it has (the table below, read from both on 2026-11-20). Every consumer of
the policy read (`GET …/policy`, the claim response's hashes, `baton owner policy …` in
`cli/baton.mjs`, whose own `KNOBS` copy at line 978 matches the code) therefore sees knob names
the spec does not define. The spec simplification left this as found
([the review](../docs/review/spec-simplification-review-2026-11-19.mdx), *Where the spec and
the code disagree*).

| In the code | In §12.8 |
|---|---|
| `approvers.trust` | `approvers.roles` |
| `grants.default_trust`, `grants.one_per_domain`, `grants.trusted_domain` | no knob: a grant has a role, a domain and the checker mark (R-BTN-180) |
| `refs.baton`, `refs.legs` | `refs.default_branch`, `refs.tags`, `refs.other` only |
| `courier` in `REF_WRITERS` and in an outbox route's `deliverers` | writers `runner`, `trusted-runner`, `mirror`, `human`; deliverers `runner`, `trusted-runner` |
| an outbox route's `trust` and `min_release` | a route is its `deliverers` alone |
| `merge.reviews.distinct` | `merge.reviews` is its `count` alone |
| `authorship`, `leg_state`, `inputs.answers` | absent |
| preset `protected-signed` | preset `protected-hardware` |
| floors as rows of `policy_floors` (`name`, `guarantees`, `remove_by`), written by `POST …/policy/floors` | `floors`, a knob of the document listing guarantees by name |
| `policy_pins` and `PolicyPin` (a runner's pinned hash and floors hash) | "a trusted runner pins nothing" |
| absent | `outbox.source`, `repos.unlisted`, `approvers.roles`, the `floors` knob |

## Plan

1. **Rule on the rows, in a spec PR, before any code.** The default for every row is "the code
   moves to the spec": the spec was just rewritten to what the owner ruled, and the code is
   older. For each row the PR either confirms that, or amends §12.8 to keep the code's knob.
   The rows where the code may be right and the owner decides:
   - **floors.** The old removal path checks both `remove_by` and `approvers.policy`.
     Shortening `floors` needs the prior `approvers.policy`; R-BTN-189 refuses conversion
     if that gate cannot preserve the old restriction across later versions.
   - **pins.** `policy_pins` records what a runner last saw; R-BTN-188 says a runner pins
     nothing. Remove the table and the pin check, or state what the pin is for.
   - **`leg_state`** (R-BTN-190, where leg state lives) and **`refs.legs`**, which the `branch`
     leg-state design used; that design is on `spec/proposals/courses.md`.
   - **`authorship`**: signed authorship was retired with signed control (B-263), and the
     guarantee `signed-authorship` goes with it.
   - **the guarantees.** `trusted-domain-separate` and `human-gates-hardware` are in the code
     and not in R-BTN-189's table. A floor may name either today (`POST …/policy/floors`
     validates against `GUARANTEE_NAMES`), so removing a name needs the stored floors read
     first. Use R-BTN-189's successor mapping and refusal rules; a floor without a successor
     stops the migration.
   - **the signed read.** B-160 item 3 removes the signature, the hashes and `policy_pins`
     on the owner's ruling of 2026-11-01. [B-160](archive/B-160.mdx) has landed; do not
     reintroduce the removed fields or add the migration's effective hash to claims.
   - **preset apply.** Decide whether an apply replaces the document, as the code does, or
     merges, as the rule says. The rule's version is the safer one: a whole-document apply
     drops a `service:` writer and any knob the owner set outside the preset. Recommended:
     build the merge.
   B-165 lists several of these as constant knobs; this ticket takes its policy-knob half and
   leaves a note there.
2. **`repos.unlisted` is B-264's**; this ticket does not build it. `outbox.source` is built
   here as a stored and validated knob only; what delivers a source entry is B-64's.
3. **Code.** Change `PolicyDocument`, `KNOBS`, `REF_WRITERS`, `OutboxRoute`, the validators
   (`checkOutboxRoute` and the rest of the document check), `PRESETS`, `policyForPreset`,
   `guaranteesFor` and the unsatisfiable-list and could-not-work refusals to the ruled table.
   Rename the preset; `baton owner policy apply` accepts `protected-hardware` and refuses
   `protected-signed` with one line naming the new word. Update `cli/baton.mjs`'s `KNOBS`.
4. **Stored versions.** `repository_policies` is an append-only log of documents with their
   hashes. A new migration (number from `node cli/baton.mjs tickets next migration --for
   B-293`) does not rewrite a stored version. Project only the current legacy version as in
   R-BTN-188, dropping `courier` rather than changing it to `runner`. The next policy write stores the
   new shape. The policy read's effective hash is recomputed over the new shape in one place
   and the change is logged as an `admin` event per repository. Stored hashes and links remain
   unchanged. Keep live `policy_floors` backing rows until the new document is materialized;
   preserve them through export and import as required by R-BTN-88.
5. **Tests.** S-BTN-197 (the policy scenario, formerly numbered S-BTN-189), S-BTN-190 and
   S-BTN-192 are rewritten to the ruled names. New cases:
   every preset's document validates and yields the guarantees R-BTN-189's table says;
   exercise the R-BTN-188 and R-BTN-189 migration checks in table-driven fixtures (each old
   preset and a document per removed knob), asserting either preservation of held comparable
   guarantees and the required audit or atomic refusal with the expected reason. Check
   historical reads against the stored history, not against the projection. An old knob name
   on `PUT …/policy` is `invalid-params` naming the knob.

### Trust

The policy is the input every authority rule reads, so the reader's mapping is the risk here.
Its writers do not change: a `PUT …/policy` signed by a credential on `approvers.policy` as the
list stood before the change (R-BTN-188), validated in `policy.ts` before any SQL. New input:
the `outbox.source` knob, written the same way. The mapping of a stored version is Baton's own
code, run on documents their approvers wrote; it may drop or rename, and must never widen: no
mapped document admits a writer, a deliverer or an approver the stored one did not. The PR
shows this with the table-driven test of step 5 and a dry run on an owner-supplied offline copy
of the reference deployment's log and backing data. For each current legacy version, check no
new authority, no loss of a held comparable guarantee, and all floor and approver checks;
record report-only guarantee losses and any repository that blocks migration. Verify every
stored version's original hash and chain links stay intact. An implement leg does
not read a live deployment or use its administrator key. This ticket changes no key, grant,
floor or approver list on any live repository.

### Invariants

- BATON_SPEC [R-BTN-188](../spec/BATON_SPEC/12-security.md#sec-12-8): every policy change needs an approver on `approvers.policy` as it stood
  before. The migration and the reader write no policy version; the first new-shape version of
  a repository is written by its approver.
- BATON_SPEC [R-BTN-189](../spec/BATON_SPEC/12-security.md#sec-12-8): a floored guarantee is never broken by a change. The mapping is checked
  against each repository's floors in the migration's transaction, and a repository whose
  mapped policy would break a floor stops the migration with its name, rather than being
  mapped.
- BATON_SPEC [R-BTN-188](../spec/BATON_SPEC/12-security.md#sec-12-8), *No gate without a key to open it*: re-checked on the mapped lists
  (`listSatisfiable`), under the repository's `human_key` ([R-BTN-185](../spec/BATON_SPEC/12-security.md#sec-12-8)).
- BATON_SPEC [R-BTN-180](../spec/BATON_SPEC/12-security.md#sec-12-8): a grant's role, domain and mark keep their meaning; removing the
  `grants.*` knobs changes no stored grant.
- Migrations are append-only; `repository_policies` stays append-only too.
