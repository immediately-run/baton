**Brief:** the owner, 2026-10-24: "I would like both the implement and fix legs to be followed
by a run – test leg, which execute an NPM script to run deterministic tests and linting" and
"I would like the course to explicitly specify that the third round of reviews should trigger a
human in the loop request if they continue to find blockers."
**Spec:** §5.8 (R-BTN-131, the standard courses — create-pr's graph and stubs), §5.2 (R-BTN-69,
the course file: `test_script`), §2f (R-BTN-74, the `pr` station function's forge facts and
comment markers), §6.1 (R-BTN-120's `why` table gains nothing — run-tests' waits are readiness,
not blocks), §16 S-BTN-1 (the course scenario) and its trace.

### The design (decided with the owner, 2026-10-24)

1. **`run-tests` is a leg of the graph, and deterministic.** `from: ['pr-open', 'fixed']`,
   `to: ['pr-open', 'fixed']` — a self-loop, so the claim's path can walk it while the posted
   station stays forge-computable. **A red gate routes to `fix`, never back to `implement`**
   (the owner, 2026-10-24: the missing edge is `implement → run-tests → fix`) — making the
   tests green is fixing, wherever the push came from — and the loop it forms
   (`implement → run-tests → fix → run-tests → …`) is bounded generously: `run-tests` and
   `fix` both `max_runs: 30`, the review rounds staying at 3 (the gate is deterministic and
   cheap; spending retries there harms nothing the way a wasted review round does). The generated stub runs **no agent**: it is new stub kind
   beside `stubSource`, executing `npm run <test_script>` (the course file's new field,
   default `test`) in the checkout, bounded and non-interactive exactly as B-94 bounds git —
   `npm` inherits `GIT_NONINTERACTIVE_ENV` and a `RUN_TESTS_TIMEOUT_MS` of its own, its lease
   arithmetic named and pinned like `CLOSE_TIMEOUT_MS`'s (one run, synchronous, under the
   lease's margin).
2. **The gate's state is Baton's traversal record — the server already knows the history
   (the owner, 2026-10-24, and §4's rule of the same day: "Baton's traversal record counts").**
   Repeated entry into a leg is counted from `claim_legs` and confirmed arrivals, never from a
   forge; and run-tests' *outcome is its advance*: the leg that follows it names it — `review`
   means green, `implement`/`fix` means red — so `claim_legs` already records the gate's last
   answer, forge or no forge. A push after the gate opens it again the way any push re-readies
   a fix (R-BTN-63's arrival counting; plain git included). The close's marker line remains
   what it always was — evidence in git (`markers_seen`, R-BTN-46), the sync's placement
   input, never the counter. Routing at `pr-open`/`fixed`:
   - **no marker** → `run-tests` ready (the gate before every review round);
   - **green** → the path gains its `run-tests` step and `review` queues, `ci`-waited as today;
   - **red** → `fix`, ready, wherever the push came from (the `implement → run-tests → fix`
     edge) — the deterministic gate refuses to spend a review round on red checks, and the
     red-fix loop runs to its generous budget of 30.
   The stub reads `ctx.claim.station` (already in the leg context) for its return position and
   names the failing script's last lines in its red marker.
3. **The third round's blockers are the owner's.** The round count needs no forge either:
   review's runs are the traversal record's (`max_runs` already reads it — §4). Today
   round-3-changes queues `adjudicate` *ready* — a fresh agent reproducing findings. The
   change is one routing word and a changed contract: `adjudicate` queues **`waiting`,
   `waiting_on: 'owner'`** — the human in the loop, carried by Needs you (§14) asking exactly
   the owner's question (2026-10-24): *"3 failed reviews — manual review or start a 4th
   round?"* — and the leg's instructions become the owner's: answer with
   `Baton-Adjudicated: merge|owner|round` as a trailer on a commit pushed to the branch (git,
   like every durable record — the forge-comment spelling of `adjudicationOf` joins the
   adapters as one reader, not the record; `merge` → `adjudicated`, merge ready; `owner` →
   parked; `round` → exactly one more review round, its run budget granted by the owner
   override that carries the answer, §6.8). No agent reproduces anything: the third pair of
   eyes is the person's.
4. **Docs and course file follow**: §5.8's create-pr description and graph,
   `docs/standard-courses.mdx`'s diagram, the shipped `run-tests.md` instructions (one screen:
   what the script is, that no agent runs, where the marker goes), and `baton repo init`
   scaffolding the new leg beside the others (the committed `.baton` stubs regenerate).

### What not to do

- Do not run the deterministic script through an agent: the whole point is a gate whose outcome
  never depends on a model, and B-94's bounds already make it safe unattended.
- Do not add a station for `verified`: the posted station must stay forge-computable; the
  self-loop plus the marker is the sound encoding.
- Do not build §7's `hitl` for this: the owner wait plus the trailer is today's
  human-in-the-loop, git-native and dashboard-visible.
- Never a forge comment as the durable record of a leg's outcome or re-entry: Baton serves
  plain-git repositories (R3-1265), where comments do not exist. Counting and the gate's state
  are Baton's traversal record (§4, 2026-10-24); git (the close's marker, a trailer beside it
  if useful) is the evidence; the forge adapters are readers.

### Tests

- `course-pr.test.ts`: the routing table — gate open/green/red at `pr-open` and at `fixed`,
  read from the traversal record (which leg run-tests advanced into); red routes to `fix` from
  both edges of the loop; a push after a green gate re-opens it; the red-fix loop counted to
  30, the review rounds to 3; round-3 `changes` — counted from the same record — →
  `adjudicate` waiting on the owner with the owner's question; the owner's `merge`/`round`
  answers → merge ready / a fourth round budgeted.
- `defaults-cli.test.ts`: the scaffold carries `run-tests.mjs`/`run-tests.md`; the generated
  stub runs the script itself (a fixture `npm run` that fails/succeeds, asserting the marker
  text and the return position); `test_script` defaults to `test`.
- The plain-git variant: no forge adapter, the trailers read from the branch's commits —
  the gate and the owner round work identically with `gh` nowhere in sight.
- S-BTN-1's steps gain the gate and the owner round.

### Exit criteria

- [ ] no review round starts on red checks, and a red gate routes to `fix` from either edge
      of the loop with the failure named — without an agent in the path, the loop free to run
      to 30
- [ ] the third round's blockers arrive in Needs you naming them, and the owner's marker
      resolves them — no agent reproduction
- [ ] the graph, the docs and a fresh scaffold agree
