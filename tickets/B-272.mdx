**What:** replacing SQLite with PostgreSQL is feasible for one instance and large: the `Store`
port is synchronous (about 2,000 call sites) and 894 SQL statements sit in 29 core files. Nothing
stops that cost growing. Keep the move possible without making it.

From the architecture review of 2026-11-19 (`docs/review/architecture-review-2026-11-19.mdx`, on the branch `review/architecture-2026-11-19` until it lands).

### What to build

1. A dialect lint in `npm test` that fails on new uses of `last_insert_rowid`, `changes()`,
   `rowid`, `INSERT OR`, scalar `MAX(a, b)`, `IS ?`, `COLLATE NOCASE` and `PRAGMA`, beyond an
   allowlist that may only shrink.
2. A `Store` conformance test run on both hosts: nested rollback, `one()`, `rowsWritten`,
   integers above 2^53, unique-violation detection, a write followed by a throw outside a
   transaction.
3. Replace the six `last_insert_rowid()` reads with `RETURNING id`; give the five `rowid`
   orderings a column; read the stored number in `Sequences.next` inside its transaction (it is
   read outside it today).
4. One `Db` helper replacing the 23 private `rows` wrappers; then a repository per aggregate
   for the four files that hold 501 of the 894 statements.
5. Record on the architecture page whether the synchronous store and the single writer are
   permanent decisions. This is the owner's sentence to write; the leg proposes it.

Several instances on one shared database is out of scope: correctness rests on a single writer.

**Done when:** steps 1 to 3 are in `npm test` and green on both hosts; step 4 may be a second
pull request.

### Trust

No new input. The SQL changes keep every value bound as a parameter; no statement is built from
a runner- or owner-supplied string.
