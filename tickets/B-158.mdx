**Brief:** the owner, 2026-11-01, on the whole-spec review they commissioned ("assess it for …
can any vocabulary, core concepts or actors be simplified … is the user experience intuitive …
are the security guarantees … truly guaranteed and … do they matter"), asked for its findings
to be filed as tickets. Source: `docs/review/spec-simplification-review-2026-11-01.mdx`.
The review's claims are a reviewer's, checked against the spec where they cite it; this ticket
verifies each against the text before changing anything.

### Why

Review finding 2 and F3, the owner's own example: R-BTN-66 ("An agent can change every byte of
a registered repository") lets any pusher re-file a held ticket under a new id (admitted in
R-BTN-12), change `course:`, add an edge or an `arrives` leg, or rename a leg to dodge a bar
(R-BTN-142). The vocabulary still calls holds and bars "limits agents cannot change".

### Decided (the owner)

**Rulings of 2026-11-01** (the owner, answering each question in the session that continued
immediately-run/baton#150; the restructure, B-166, writes them into the spec):

- "Remove it": under `cooperative` Baton's state is a coordination record, not a boundary, and
  the adversary-only mechanisms are removed outright; `std:git.implied@1` stays as a dashboard
  hint only.

### What to build

1. **A spec PR first**, under the babysit skill's *Spec PRs*: two fresh reviewers, the impact list,
   every rule restating the same fact changed with it.
2. State in R-BTN-39, R-BTN-66 and the vocabulary that under `cooperative` Baton's owned state
   is a coordination record, not a boundary; under `protected` control paths make it one.
3. Remove, or limit to `protected`, each mechanism whose only purpose is detecting an adversary
   under `cooperative`, listing each in the PR with what it caught.
