**Brief:** the owner, 2026-10-27: "Baton as currently designed is completely unprotected against
scenarios where a runner is compromised (and this will happen sooner or later)", then, on the
security model's hardening option 8: "file it now".

**Spec:** R-BTN-106 (independence by credential), R-BTN-139 (whose words count), R-BTN-58 and
R-BTN-146 (grants and capabilities), R-BTN-131 (the standard courses' legs), R-BTN-66;
`docs/security-model.mdx` (what a push can reach, 4; hardening option 8).
**Depends on:** none.
**Waits on:** R3-1266 (Baton claims its own tickets), for item 4.

### Why

Every VM shares one GitHub identity with `write` on the home and every output repository. A
compromised runner can therefore approve its own PR (B-119 counts a verdict from anyone who can
push) and merge it, and Baton's independence rule binds runner keys inside claims, not what that
identity posts outside them. Every other hardening option bounds or detects this. Only this one
makes a single compromised runner unable to land code alone.

### What to build

1. **Two GitHub identities per fleet**, at two credential sets: an **implementer** (pushes
   branches, opens PRs) and a **reviewer** (posts verdicts, approves, merges). A runner holds one
   set, never both, and declares which by a holding (B-104) or a granted capability
   (`forge-implementer`, `forge-reviewer`).
2. **The courses route by it.** `create-pr`'s `implement` and `fix` legs require
   `forge-implementer`; `review`, `adjudicate` and `merge` require `forge-reviewer`. The same for
   `review-pr`. A ticket's review is never run by a runner holding the implementer set.
3. **GitHub enforces it.** On each home and output repository, a branch ruleset on the default
   branch:
   - requires a pull request with one approval;
   - requires approval of the most recent push by someone other than the pusher;
   - lets neither identity bypass.

   So the implementer cannot merge, and the reviewer cannot push the code it approves. Baton's
   sync counts a verdict only from the reviewer identity, or an owner (R-BTN-139's
   `trusted_identities`, narrowed for these repositories).
4. **Ticket moves off direct pushes to main.** The ticket commands push straight to main today,
   which the ruleset forbids. With R3-1266 claims happen in Baton and no ticket write needs a
   direct push; until then, decide between a pushable `tickets/**` exemption (a push ruleset
   allowing only that path, private repositories only) and ticket writes by PR.
5. **Control paths stay owner-only** (security model A or B, or B-127), so the reviewer identity
   cannot change `.baton/` or workflows either. Then reaches 1, 2 and 5 also need two
   compromises.
6. **The reviewer identity never executes code under review** (security model, OWASP ASI05 and
   ASI07). A review that runs the PR's tests (B-110's run-tests leg) executes the implementer's
   code; on a runner holding the reviewer set, a compromised implementer would gain the
   reviewer's credentials and undo the split. Tests run in a credential-free sandbox (no forge
   credential, no Baton key with review rights), whose results the reviewer reads; or on the
   implementer's side, with the results reproduced by a check the reviewer does not execute.
   **Decide** which; the scenario proves the reviewer runner never runs PR code.

**After the adversarial review** (2026-10-27, `docs/security-model.mdx` *Review*):

- **What this buys, stated exactly** (finding 7): one compromised runner cannot land code
  without either a second compromise or a successful injection of the reviewer model, which reads
  attacker-written code, comments and PR text. So merges also need deterministic checks
  (Fieldhouse's fourth practice) run by the executor, not only a model verdict.
- **Two Apps, not one** (with B-131): if both roles mint tokens from one GitHub App they are one
  identity, and the rule collapses. Separate Apps, separate broker keys.
- **The implementer cannot approve at all** on GitHub: required reviews come from a team only the
  reviewer identity (and the humans) belong to, so the implementer's approval of a reviewer's push
  does not satisfy "someone other than the pusher".

### Tests

- A scenario (the next free S-BTN number): a runner with only `forge-implementer` is never
  offered `review` or `merge`; a verdict posted by the implementer identity does not count; the
  review leg's claim on a reviewer runner moves the ticket.
- A drill on a scratch repository, scripted: the implementer identity's attempt to merge, or to
  approve its own PR, is refused by GitHub; the reviewer identity's push to the PR branch is not
  counted as approved.
