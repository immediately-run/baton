granted here: alive/dead, claim held, current activity; the per-runner page carries the 24h
timeline." The mockup's Workers page — a card per runner with its name, state mark (● Working,

### What to build

The §14 rows first, then the code.

1. **`GET /v1/repositories/{repository}/runners`** (`repo.runners`, read; callers the repository
   reads' principals and a session): every runner holding an accepted grant on the repository
   (R-BTN-146), alive or dead within the retention `workersView` uses today: `name`
   (hostname and session name), `alive`, `last_seen_at`, `last_activity_at`, `harness`, `kind`,
   `isolation`, `tier_ceilings`, `capabilities` (declared) and `granted` (this repository's
   grant, R-BTN-174), `tags`, `courses` (ids and versions for this repository), `lease_timeout_s`,
   `credential` (kind, registering token id if any, role and domain from the grant), and
   `claim` — null, or this repository's claim it holds: ticket, station, leg, run id, claimed at,
   lease ends, deadline, attempt n of `max_runs`, `session_url`, `leg_log.dir`, and the current
   `activity` (kind, label, started). A runner's claim on another repository shows as
   `busy_elsewhere: true` with no detail. What `/v1/runner/fleet` shows a machine key for the
   repository (R-BTN-99), from `workers.workersView` and `claims.running`.
2. **`GET /v1/repositories/{repository}/runners/{name}`** (`runner.show`, read; same callers):
   the runner's row plus `?since=` (default 24 hours, at most 7 days) of its timeline on this
   repository: `claims` (id, ticket, leg, started, ended, end reason — released, silent, reaped,
   done, suspended), each with its `activities` (id, parent, kind, label, source, started,
   ended, outcome, detail as the validated object, R-BTN-3 and §9.9), `session_url` and
   `log_dir`; and the runner's earlier attempts on its live ticket (the attempts table's rows for
   that ticket, each with end reason and detail). From `claims.timeline`.
3. **`/repositories/{r}/runners`**: the mockup's cards, alive first, then silent (alive but
   `last_activity_at` old — the Running view's "stalled" rule), idle, dead; each card the
   runner's line (name, state mark and text, harness, kind, tier ceiling, last report), its
   capability chips (granted ones marked), and its claim block from `claim`, with the mockup's
   lease bar (claimed at to lease ends, now marked), attempt and backoff; a dead runner's card
   says what its reap did ("its claim on … was reaped; retries …") from the read, as text. The
   card's controls, from `ui.view`: **Status** (`runner.message` `status_request`), **Wind
   down** (`wind-down`), and on the claim **Stop** (`leg.stop`, destructive, through the confirm
   dialog, R-BTN-119); **Open session** only where `session_url` passed `session_hosts`
   (R-BTN-113), as a link with the host shown. The mockup's "Stream stdout / stderr" is not
   built: a leg's log is read from its directory by `baton leg log` (R-BTN-128), which the card
   names as text beside `log_dir`.
4. **`/repositories/{r}/runners/{name}`**: the card, then the timeline: one lane, the window's
   claims as bars coloured and labelled by end (released, silent, reaped, running), activities
   nested under each by kind, failed ones marked by shape; hovering or focusing a segment shows
   its label, detail, session link and log directory as text; `?since=` as a URL query (24 h
   default, 7 d max); then the earlier attempts. A `<table>` of the same claims and activities
   below the drawing, for screen readers and phones.
5. **The fleet line.** The sidebar's Runners count is alive/total from `repo.runners`; the root
   screen's `runners_alive` agrees.
6. **Phone.** The cards stack at 375 px with the controls under the claim; the timeline is the
   table.

### What not to do

- No tenant-wide fleet here: an owner's session sees the runners granted on its repositories,
  an administrator's the same screen per repository; a runner's work elsewhere is
  `busy_elsewhere`, no more (R-BTN-155).
- No log streaming, no new runner-side channel: logs are R-BTN-128's directory, read by the CLI.
- No message kind beyond the registry's: `status_request`, `wind-down` and `release` (Stop) as
  `POST /v1/ui/messages` admits them, each its own action by `match`.
- No capability meaning: a chip is a name (R-BTN-174); nothing in the screen says what a
  capability is for.

### Trust

- **The two reads** — Baton's rows; hostnames, session names, labels, detail, harness and
  capability names are a runner's own statements (R-BTN-3, §12.3), validated on the heartbeat
  and drawn as text; `session_url` is a link only because R-BTN-113 already checked its host.
- **Status, wind-down and Stop** — registry actions through `authorize`; Stop refuses a ticket
  the runner does not hold (`forbidden`); an owner's session reaches only runners holding its
  repositories' claims.
- **`?since=`** — validated on the server (`invalid-params` over 7 days).

### Invariants

- **Capabilities are the runner's statement** (R-BTN-174): drawn, matched by name, never judged.
- **Log directories as text** (R-BTN-128); **session links only from `session_hosts`**
  (R-BTN-113).
- **Stop is one click plus `confirm: true`** (R-BTN-119, §12.2), never a confirm code
  (R-BTN-155).
- **Text, never markup** (§12.3).
- **An owner's session, its repositories** (R-BTN-155).

### Tests

Scenarios numbered at merge, on both hosts, with a fixture of two granted runners (one holding a
claim with two activities, one dead after a reap) and one granted elsewhere:

- `repo.runners` lists the two with `alive`, `granted`, the claim's lease and activity, the dead
  one's reap; the third is absent; a runner busy on another repository is `busy_elsewhere`;
- `runner.show` returns the 24-hour claims with nested activities and refuses `?since=` over 7
  days;
- under `test/ui/`: the cards order alive, silent, idle, dead; Stop sends `release` with
  `confirm: true` and draws the refusal for a runner not holding the ticket; a `session_url`
  on an unlisted host is text; the timeline table lists what the drawing draws; a hostile
  activity label is text.
