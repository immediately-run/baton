### What to build

1. **`stateView()`** in core: `uiState()` renamed, its body unchanged in shape, serving `GET
   /v1/admin/state` only (R-BTN-57), built from the same functions the entity reads use
   (`readyRows`, `claims.running`, `workersView`, `history.view`, …) so the two cannot drift.
   Its §14 row reads "the state in one request for a terminal, built by the functions the
   entity reads use". S-BTN-170 is rewritten: with the fake clock held, for each registered
   repository r, each section of `stateView()` filtered to r equals r's entity read followed
   over every page — `repositories[r]` to `repo.list`'s row, `ready` and `running` to
   `repo.tickets?state=ready|running`, `workers` (granted on r) to `repo.runners`, `timeline`
   to each runner's `runner.show` window, `discrepancies` and `held` to `repo.sync`, `limits[r]`
   to `owner.grant.list`, `blocked` to `blocked`, `needs_you`'s keys to the homes B-203's ledger
   names — and the tenant-wide sections equal the tenant reads: `resources` to
   `admin.instance.list`, `workers` as a whole to the union of `repo.runners` over every
   repository plus the runners granted nowhere; `ready_by_tier` is the board's — asserted on both
   hosts.
2. **The renderer scenarios.** S-BTN-76 and G-BTN-13 amended to name the V2 renderer and run
   against it: fixture rows carrying `<img onerror>`, `{{x}}`, backticks and a `javascript:`
   link in a ticket title, a hold reason, an activity label, a reading `detail`, a condition
   `detail` and an attestation `value` are drawn on the ticket page, the Tickets table, the
   runner page, `/instances`, the Resolve page and `/attestations` as text, in the `ui` vitest
   project against the screens' components, and a link whose host is not in `link_hosts`,
   `session_hosts` or under `web_base` is text. G-BTN-100's renderers row names
   `src/dashboard/` and the source gate. B-191's scenario (the screen draws only its caller's
   actions) runs on every screen with a control: the ticket page, Conditions and the Resolve
   page, the runner screens, Sync, Attestations.
3. **Production check.** After this PR's merge deploys (the workflow B-193 changed deploys on
   every push to `main`), the agent opens `https://baton.immediately.run/` — production, the
   one deployment anyone uses; the owner ruled this project needs no staging (B-191's Decision
   7c) — and every path of `src/core/screens.ts` with a real id, read-only: the owner runs
   `baton admin open` and binds the code (an administrator key is the owner's to use, never the
   agent's), the agent drives only the browser and presses no control, and records in the PR
   body the paths exercised and the console clean of errors. The agent triggers no deploy
   (`workflow_dispatch` is the owner's) and changes no workflow.
4. **The project page.** `tickets/projects/baton-ui-v2.mdx`'s Done when is checked line by line
   against the deployed instance and marked in its Status.

### What not to do

- Do not reshape `GET /v1/admin/state` into a union of paged reads (Decision 4a) or a second
  query.
- No deploy triggered, no workflow edited, no control pressed on production during the check,
  no staging check (Decision 7c).
- No new screen or control.

### Trust

- **`stateView()`** is answered to an administrator's key only (R-BTN-57), built from functions
  already bounded by their reads' callers.
- **The scenarios** are the trust statement of the whole project: every value that reached V1
  as `textContent` reaches V2 as a text node, proven on both hosts and in the DOM project.

### Invariants

- **Readable with a key** (R-BTN-179): `stateView()` equals the entity reads, by test.
- **Text, never markup** (§12.3, G-BTN-13, S-BTN-76).
- **One check** (R-BTN-129); **both hosts** (R-BTN-55).

### Tests

S-BTN-170 rewritten and green; S-BTN-76 and G-BTN-13 amended and green; B-191's scenario over
every screen with a control; the production check's record in the PR body.
