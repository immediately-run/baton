## The organizing rule

**Brief:** the owner, 2026-11-09: "I want the V2 API to be organized along the same concepts as
the REST API, CLI and MCP. Under that assumption the dashboard becomes a walk down the same tree
the URLs already draw — sign in, pick a repository, and every screen after that is one entity.
Every screen = one entity's REST reads, with its controls the registry actions placed there by
`ui.view` — so 'what I see' and 'what I can do' come from the same definition." The owner chose
React and TypeScript, which replaces the brief's dependency-free rule; noted that this flips the
earlier task-view decision — Running and Ready collapse into Board and Tickets, Needs you into
Conditions, with one overview strip per repository ("running now · ready · needs you") so the
task answers stay one glance away; and ruled on the transition: "Nobody is using the V1 Baton
UI, so the transition doesn't need to be smooth" — V2 replaces V1 at `/` as soon as its shell
lands.

The tree, as the owner drew it:

- **Root `/`** — the caller's repositories (an administrator's all, an owner's theirs): head,
  mode, ready count, open conditions. Sign-in at `/login`; nothing else is tenant-scoped for an
  owner.
- **One repository, `/repositories/{r}/…`**: **Board** `/board`; **Tickets** `/tickets`,
  `/tickets/{t}`; **Goals** `/goals`; **Courses** `/courses`, `/courses/{c}`; **Conditions**
  `/conditions`, `/conditions/{id}` (the Resolve page); **Runners** `/runners`,
  `/runners/{runner}` (keyed by the runner's id); **Credentials** `/grants`, `/owners`,
  `/tokens`, `/mcp-keys`, `/sync-keys`, `/check-runners`; **Governance** `/policy`,
  `/settings`, `/bars`, `/consents`, `/attestations`; **Sync** `/sync`.
- **Tenant screens, an administrator's** — `/repositories` (the registry), `/instances`,
  `/resources`, `/capacities`, `/settings`, `/state`, `/sessions`.

The mockup draws the *content* of these screens — the Needs-you list, the timeline, the ticket
table with its state column and reasons, the runner cards with lease bars and attempts, the course
graph with queue depths, discrepancies, capacity — and its visual language (calm, dense, status by
shape and label before colour, exceptions first). Its navigation (Overview, Tickets, Workers,
Courses, Schemas) is *not* the design: the tree above is, and the mockup's sections are placed on
the entity screens the tickets name. What the mockup draws and the tickets do not build, each
with its reason, is recorded once in B-191's Decisions: Schemas (no read exists; B-54's
renderers), Providers and Suspensions (B-142 retired their tables; a provider's availability is a
reading on `/instances`), Accept history (R-BTN-85 adopts git's value at once), Stream
stdout/stderr (R-BTN-128: a log is its directory), the runner's model (R-BTN-3 names none), the
fleet-wide timeline (the owner's tree puts it on the runner page), "Workers" (B-68: runners);
its Limits block is split across the credential screens (B-199), Governance (B-200) and
`/resources` (B-214, where probe keys are listed).

## The owner's six answers

B-191's Decision needed packet was answered on 2026-11-09 ("I take your recommendations"), (a)
in each: (1) the tenant screens are read-only, (2) route and adopt stay the CLI's, (3) Stop is
one click, (4) `GET /v1/admin/state` keeps its shape as `stateView()`, (5) the held post's
Accept stays on Sync, (6) no ESLint — a source test over `src/dashboard/**` is the gate. The
tickets are written against exactly these; each remains a two-way door for a later spec ticket.
