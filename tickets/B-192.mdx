**Brief:** the owner, 2026-11-09 (B-191): "Every screen = one entity's REST reads."

**Spec:** [BATON_SPEC §11.3](../spec/BATON_SPEC/11-people.md#sec-11-3) ([R-BTN-129](../spec/BATON_SPEC/11-people.md#sec-11-3):
`callers`; a session authorizes as `session` with its role), [§11.4](../spec/BATON_SPEC/11-people.md#sec-11-4)
([R-BTN-155](../spec/BATON_SPEC/11-people.md#sec-11-4): an owner's session only its repositories),
[§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1) (the session row; [R-BTN-179](../spec/BATON_SPEC/12-security.md#sec-12-1):
the state readable with a key), [§12.4](../spec/BATON_SPEC/12-security.md#sec-12-4) ([R-BTN-16](../spec/BATON_SPEC/12-security.md#sec-12-4):
same-origin JSON, the `Origin` and `Sec-Fetch-Site` checks), [§14](../spec/BATON_SPEC/14-api.md#sec-14)
(the repository reads; `children`, `courses`), [§4.6](../spec/BATON_SPEC/04-tickets-syncs-board.md#sec-4-6)
([R-BTN-86](../spec/BATON_SPEC/04-tickets-syncs-board.md#sec-4-6): children),
[§5.2](../spec/BATON_SPEC/05-courses.md#sec-5-2) ([R-BTN-69](../spec/BATON_SPEC/05-courses.md#sec-5-2):

**Depends on:** B-191 (the screens and the session paths are specified), B-10 (`prerequisites`),

**Used by:** B-194, B-196, B-197, B-202, B-204, B-205, B-206, B-213.

### What to build

The §12.1 and §14 rows first, then the code.

1. **The front resolves a session on any admitted GET** (`src/core/front.ts`): a request carrying
   the `__Host-baton_session` cookie to a route whose registry entry lists `session` is the
   session's, with R-BTN-16's `Origin`/`Sec-Fetch-Site` checks as on `/v1/ui/*`; a request that
   carries a signature or a bearer is that key's and its cookie is ignored. Until B-25's registry
   drives the router, the front holds the same fact as a list in `src/core/screens.ts`'s
   neighbour `sessionReads.ts`, deleted when B-25 generates it.
2. **Session callers** — `{principal: "session", roles: ["administrator", "owner"], scope:
   "repository"}` — on `GET /v1/repositories/{repository}/board`, `…/tickets/{ticket}/blocks`,
   `…/prerequisites`, `…/history`, `…/children`, `…/legs/{leg}/runs` (its callers are owner and
   admin: a session of either role), `blocked`, `conditions`, `courses`, `stats`, `policy`, and
   `GET /v1/owner/{repository}/grants`, `…/policy/log`. The core's `authorize` answers an owner's
   session on the repositories its key still owns, an administrator's everywhere, a target
   elsewhere `forbidden` (R-BTN-155, R-BTN-129). The scope check runs on the server; nothing is
   filtered in a client.
3. **`GET /v1/repositories/{repository}/tickets/{ticket}/children`** (`ticket.children`, read;
   the repository reads' principals and a session): `{children: [{ticket_id, station, blocked,
   closed?}]}` as §14 states it, from the tickets whose `parent` is the ticket (R-BTN-86) joined
   with `stations.ts` and `blocks.ts`.
4. **`GET /v1/repositories/{repository}/courses`** (`repo.courses`, read; same callers): each
   course file as last accepted — id, version, the file as an opaque blob, its capability types
   and roles (R-BTN-121, R-BTN-157) — and `refused: {version, reason}` where a newer file was
   refused (R-BTN-69), from `courses.ts`.
5. **§12.1 and R-BTN-16** as B-191 words them: the session row names the reads; R-BTN-16 says a
   session's reads outside `/v1/ui/*` are Baton's to authenticate.

### What not to do

- No new write caller: the confirmed-action list (R-BTN-155) and every write's callers are
  untouched.
- No read built here beyond `children` and `courses`: the ticket list and detail (B-194), the
  runner reads (B-196), `course.show` (B-197), `sync` (B-201), the tenant reads (B-202) and
  `attestations` (B-213) are their tickets'.
- No `GET /v1/ui/state` change: it keeps answering until B-203.
- No ETag or cursor here: B-205.

### Trust

- **A session's read** — the cookie is the credential (R-BTN-155), checked on every request
  against its role and repositories; a read on a repository the key no longer owns is
  `forbidden`, the same answer as for one that does not exist.
- **A request with both a key and a cookie** — the key's; the cookie decides nothing, so a page
  cannot borrow a key's reach and a key cannot borrow a session's.
- **`children` and `courses`** — Baton's rows and an opaque blob (the course file, §12.3),
  answered to the repository reads' principals.

### Invariants

- **One check** (R-BTN-129): `authorize` decides every added caller.
- **An owner's session reaches only its repositories** (R-BTN-155).
- **Readable with a key** (R-BTN-179): a session read is the same entry, query and JSON a key gets.
- **Same-origin** (R-BTN-16) on every session request.
- **Both hosts** (R-BTN-55).

### Tests

Scenarios numbered at merge, on both hosts:

- an owner's session reads each listed read on its repository and is `forbidden` on another's;
  an administrator's reads both; a runner key's answers are unchanged;
- a request with a cookie and a valid signature is the key's (an owner key's session cookie
  plus a runner's signature answers the runner's view);
- a session request with a foreign `Origin` is refused as `/v1/ui/*` refuses it today;
- `ticket.children` lists a fixture parent's children with station and blocked; `repo.courses`
  returns the accepted file and the refused newer version.

### Exit criteria

- [ ] §12.1's session row, R-BTN-16's paragraph and the §14 rows amended; `spec:index` current.
- [ ] The front resolves sessions on admitted GETs; every read above admits a session;
      `children` and `courses` exist.
- [ ] The scenarios pass; `npm test`, `npm run typecheck`, `npm run check:wiki` and
      `npm run check:tickets` are green.
