**Brief:** the resumed acceptance run, 2026-10-21, twice. The first `reaped:silent` (the
morning's hung `opencode` leg) was written off as unreproducible; the second is fully
observed: B-83's implement agent finished its session at 16:09, the runner's heartbeats
stopped at 17:28 with the process still alive, the leg's result file landed at 18:09 — a
two-hour close — the server reaped the claim (`leg-abandoned review, reaped:silent`), and
the runner process then died with no log line and no crash report. The close is
`commitMarker` + `git push origin HEAD` (`src/defaults/course-markers.ts`): an unbounded
push — no timeout, `GIT_TERMINAL_PROMPT` unset, no terminal to answer an ssh prompt or
wait out a dead connection — is the prime suspect for the wedge.
**Spec:** §5.8 (R-BTN-131: the stubs' close), §6.3 (R-BTN-6: the lease), §6.13 (R-BTN-72:
the runner); `src/defaults/course-markers.ts` (`markerClose`), `src/runner/runner.ts`
(the heartbeat timer and the leg-wait race).

### Why

Two failures compound. A leg's close can block for hours on one unbounded git call — the
claim is doomed from that moment whatever the agent achieved. And the runner went silent
with it: the heartbeat timer is independent of the claim loop by design, so a silent
runner means its event loop was blocked — something in the runner's own path runs
synchronously alongside the leg — and when the loop unblocks the process dies without a
trace (no log line, no crash report), which is the worst possible post-mortem.

### What to build

1. Every git call the stubs and the runner make is bounded and non-interactive:
   `GIT_TERMINAL_PROMPT=0`, `GIT_SSH_COMMAND` with `BatchMode=yes` and a connect timeout,
   and an explicit kill on timeout — a wedged push fails the leg in seconds, not hours.
2. The runner's silence is reproduced or excluded: an audit (and test) that nothing on
   the heartbeat path — spool writes, `ensureSha`, `fetchMain`, `holdHome` — can run
   synchronously against git or the filesystem unboundedly; whatever blocked it is named.
3. A runner's death leaves a line: SIGTERM/SIGINT handlers and an `exit` hook log the
   last state (claim id, last beat, in-flight leg) before the process goes, so "died
   tracelessly" cannot happen again.

### Do not

- Move the close off the leg: the marker's commit is the leg's evidence; bound it, don't
  detach it.

### Tests

- Unit: a `git` stand-in that never returns fails the close within the bound (fake clock
  or short timeout), and the leg reports the timeout as its failure.
- Unit: the runner's shutdown hook writes its last line on SIGTERM.

### Exit criteria

- [ ] no git call in stubs or runner can outlive a bounded timeout
- [ ] a wedged close fails its leg while the worker keeps heartbeating
- [ ] a runner's death always leaves a log line

### Work (2026-10-22, implement leg)

**Built.** (1) `src/defaults/course-markers.ts`: `exec` — what every standard course's `close`
runs — now passes `timeout: CLOSE_TIMEOUT_MS` (120 s) and `killSignal: 'SIGKILL'` to
`execFileSync`, and `GIT_NONINTERACTIVE_ENV` (`GIT_TERMINAL_PROMPT=0`,
`GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=20"`) is merged into its env. (2)
`src/runner/home.ts`: the runner's own git (`ensureSha`, `courseOf`, `loadCourse`) is bounded at
`GIT_TIMEOUT_MS` (30 s, under a beat) and carries the same environment; `fetchMain`
(`src/runner/main.ts`) gains that environment beside its existing 20 s bound. (3)
`src/runner/runner.ts`: `Runner.lastLine(why)` names the claim, the leg in flight and the last
beat; `work()` installs one process-wide pair of `uncaughtException`/`unhandledRejection`
handlers that log that line and exit 1. `src/runner/main.ts`: `stopLine` and `exitHook` are the
SIGTERM/SIGINT and `exit` lines `runMain` writes. Spec: §8.3 R-BTN-72 gains "a wedged git never
holds a claim" and "a runner's death always leaves a line"; S-BTN-41's row gains B-94's cases.

**Audit (item 2) — what was found.** The heartbeat timer fires independently, so a silent
runner is a blocked event loop. The unbounded work on the runner's *own* path is the synchronous
`git` in `home.ts` (`ensureSha`, `courseOf`, `loadCourse` — `execFileSync`, no timeout), called
from `runClaim`/`beatOnce`; `fetchMain` already had a bound and `holdHome` does two small reads
under `git rev-parse`, now bounded too. The `spool` writes in `beatOnce` are `appendFileSync`
on a file the runner itself spent; the runner cannot bound the kernel's write, and they are not
the suspect. **The close's `execFileSync` (unbounded, in `src/defaults`, in the runner's process
when `callClose` runs it) is the named suspect:** a push whose remote stops answering held the
runner's event loop, so its beats stopped, the claim was reaped, and when the push returned the
unblocked loop ended with Node's default fatal path and no handler — the traceless death. With
the close bounded, that path ends in a thrown, logged `close` failure, not a wedge; with the
fatal hooks, a death leaves a line.
