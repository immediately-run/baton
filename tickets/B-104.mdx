**Brief:** the owner, 2026-10-22: "credentials are capabilities: an anthropic api key is what
enables a runner to execute an opus review." "Course legs specify a high-level capability like
code-generation-llm, while the runners know they have an API key for OpenCode Go and DeepInfra
and an instance of OpenCode 2 installed in the VM. Baton should never store the credentials,
but it needs to keep track of the ontology of how credentials map."
**Spec:** §5.9, R-BTN-174 (the ontology, its merge, matching, storage, why-not) and
R-BTN-175 (the language, its validation, bounds, evaluator, narrowing and conformance), with the
rules it amends: R-BTN-121 (types; `human-operator` self-declared), §6.6 rule 4 and the pipeline, R-BTN-75's
`fleet_capabilities`, and R-BTN-126's dead-holding end (a leg's environment stays R-BTN-144's). The data model is in §13: `ontologies`,
`runner_derived` (no `ontology_proofs`: why-not is computed on read). The API is §4.4's board-post `ontology` field and §6.2's `not-derived` answer. How the design got here,
and the review that shaped it, are in `BATON_SPEC_HISTORY.md` (Changelog, 2026-10-22; Review
record).

### What to build

1. **`src/core/ontology.ts`** (pure): parse, validate, stratify and evaluate R-BTN-175's
   fragment exactly as its evaluator bullet fixes it, with its bounds as counters and each
   atom's canonical proof recorded. It is about 300–400 lines.
2. **Accepting a unit.** The board post's `ontology` field (§4.4) carries the merged program, or
   the merge's `error`. Core computes the digest, accepts or refuses the unit (program, course
   entries' `route_choices`) whole at each post, and stores `fixed_json`.
3. **Derived sets, current by input digest.** Evaluate a runner's sets in the transaction of a
   heartbeat or end that changes its holdings. At any read, re-evaluate the reader's sets that
   are not current. Store a crossed evaluation as `limited`. Run the alarm cycle after program
   and grant changes. Bump `fleet_version` on change. Rule 4 is `gatesFor` (`src/core/gates.ts`):
   check the grant against H, then requirements against H ∪ D(H). Update the model (R-BTN-68)
   to match.
4. **Why-not.** Compute `not-derived` and `not-derivable` on read from the maximal evaluation,
   memoised by digest.
5. **Course code.** `src/defaults/ontology/baton@1.json` (the first built-in: its `derived`
   list, model facts, `offers`, `usable_with`, the binding idiom), the file's JSON Schema, the
   sync's merge by id with `ontology: {error}` on failure, and `repo init` scaffolding a
   `.baton/ontology.json` that names it.
6. **Removals the advisory model asks for.** Delete §11.1's refusal of a heartbeat declaring an
   ungranted capability. Make `human-operator` grantable like any capability, retire rule 6, and
   drop the vendored library's `ROLES['human-operator']` expansion in docs first, then `npm run
   vendor`.
   Let R-BTN-126 accept any declared capability as a `capability` ref.
7. **Conformance.** The translator `src/defaults/ontology-asp.ts`, fixtures under
   `test/fixtures/ontology/`, `test/unit/ontology-conformance.test.ts` on `clingo-wasm@0.6.0`
   (an exact devDependency, in the Node project), and the strict-syntax test.
