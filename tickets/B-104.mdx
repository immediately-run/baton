**Brief:** the owner, 2026-10-22, across the credential-capability discussion: "credentials
are capabilities: an anthropic api key is what enables a runner to execute an opus review."
"We need a hierarchy for capabilities… course legs specify a high-level capability like

### The three layers, and who owns each

| Layer | Owner | Example |
|---|---|---|
| Requirements | course legs (course files, posted by syncs) | implement requires `capability:code-generation-llm`; a review round may require `model:claude-opus-5-5` directly |
| Holdings | the runner, in its heartbeat, bounded by its grant | `credential:OPENCODE_GO_API_KEY`, `credential:DEEPINFRA_API_KEY`, `dependency:opencode-v2` |
| The ontology | the repository: `.baton/ontology.json`, posted by the sync from the default branch's accepted snapshot | the rules below |

Every capability is R-BTN-121's `<type>:<value>` with a declared type, so `credential:` values
are environment-variable names (`^[A-Z0-9_]{1,64}$`) — never `credential:opencode-go-api-key`.
A course declares the types the ontology derives with a new key, `"derived": true`:

```json
"capability_types": {
  "credential": {"description": "a named secret in the runner's env", "values": "^[A-Z0-9_]{1,64}$"},
  "dependency": {"description": "a harness or tool installed on the runner", "values": "^[a-z0-9.-]{1,64}$"},
  "model":      {"description": "a model the runner can reach", "values": "^[a-z0-9.-]{1,64}$", "derived": true},
  "capability": {"description": "an abstract ability a leg requires", "values": "^[a-z0-9-]{1,64}$", "derived": true}
}
```

`derived` is refused on a type named `credential` (R-BTN-144 keys the leg environment on it).
The built-ins `runner` and `human-operator` are never derived. A derived type may still be
declared directly, so a human-operator machine can simply *have*
`capability:code-generation-llm`. The ontology translates; it does not gatekeep. Roles
(`capability_roles`) expand before the ontology sees anything. Rules never name a role.

### The language: one sentence, then its rules

> **A Baton ontology is a safe, stratified ASP-Core-2 program of facts and normal rules over
> string and integer constants, with default negation and the comparison built-ins, and with
> no disjunction, function symbols, arithmetic terms or aggregates. It is the fragment whose
> programs have exactly one answer set, computed bottom-up, stratum by stratum.**

B-105 adds one construct to it, preferences, as ASP-Core-2's choice rule and weak constraints
in a separate stratum. Nothing else is added without a ticket that names the ASP-Core-2
construct it adopts.

- **Atoms.** A predicate name matches `^[a-z][a-z0-9_]{0,31}$`. Arguments are constants or
  variables. A string constant matches `^[A-Za-z0-9:._/@-]{1,128}$`. An integer constant is a
  32-bit signed integer, which is clingo's range. Predicates have fixed arity, and binary
  predicates with variables in argument positions (`offers(K, M)`) are ordinary first-order
  Datalog, not a second-order language.
- **Safety** (ASP-Core-2's): every variable of a rule occurs in a positive body literal that
  is not a comparison. This covers variables in the head, in a negated literal and in a
  comparison.
- **Comparisons.** `<, <=, >, >=` take integer operands only, and `=, !=` take two integers or
  two strings. Validation types every variable from the literal that binds it (B-105 types
  reading atoms by predicate) and refuses an ill-typed comparison. So the TypeScript evaluator
  and clingo never meet a mixed-type comparison, and ASP-Core-2's cross-type term order is
  never exercised.
- **Recursion and cycles.** Cycles are judged on the **predicate** dependency graph. Positive
  recursion is allowed, so generic transitivity
  (`implies(A, C) :- implies(A, B), implies(B, C).`) is legal. A cycle **through negation** is
  refused, and the refusal names the cycle. That is the stratification test, and it is the only
  cycle that is refused. A cycle among ground facts (`a ⇒ b ⇒ a`) is harmless, since the
  closure is a set.
- **Integrity constraints** (`:- body.`) are allowed only over predicates that do not depend on
  a core-formed atom. They are checked at post, and a violated constraint refuses the file and
  names it. The built-in uses one to make bindings functional. That rule used to be hard-coded
  validation; now it is ontology.
- **Core-formed atoms.** Core supplies them, and a rule may never use them as its head. In the
  gate stratum the only one is `holds(K)`: a holding in (declared ∩ grant). B-105 adds the
  preference stratum's own.
- **The output** is `derived(K)`. The runner's capability set for the repository is its
  holdings ∪ every K with `derived(K)`.

### What a repository may and may not derive

Each of these is checked at post, and a refusal names the rule:

1. **Heads.** No rule's head is a core-formed predicate. A `derived(K)` must name a capability
   of a type that a course of the repository declares `derived: true`. A rule that could
   derive `credential:`, `dependency:` (unless declared derived), `runner:` or
   `human-operator` is therefore refused. The check runs on the program's maximal input (item 3
   below), so a variable head is covered too.
2. **`holds` is never negated** in the gate stratum. Every variable in a `holds` literal also
   occurs in a positive literal of a non-core predicate, which binds it to a constant the
   program names. So more holdings never lose a capability, and holdings the program does not
   name cannot take part.
3. **Monotone, therefore bounded at post.** By rules 1 and 2, the gate stratum's result only
   grows with holdings, and only holdings named in the program matter. So validation evaluates
   it once on the **maximal input**, with every capability constant the program names held,
   and that evaluation bounds every runner's.
4. **The gate stratum reads nothing else.** `derived` and everything it depends on may not
   depend on B-105's reading, time or preference atoms (B-105 § Strata). Advice never becomes
   refusal (value 2).

### Bounds (validated at post; enforced again at evaluation)

| Bound | Limit |
|---|---|
| File size | 64 KB serialized |
| Entries (facts + rules + constraints, merged) | 512 |
| Body literals per rule | 8 |
| Distinct variables per rule | 4 |
| Derived atoms per evaluation | 20 000 |
| Join steps per evaluation (body-literal matches, counted) | 1 000 000 |

The two evaluation bounds are counters, never wall-clock time, so both hosts fail at exactly
the same point (value 9). Validation evaluates the gate stratum on the maximal input, and a
file whose maximal evaluation crosses either bound is refused. The counter still runs at
every evaluation. If it is crossed anyway (B-105's preference stratum has no maximal input),
that evaluation yields no derivations, raises `baton.ontology-limit`, and leaves the runner
with its holdings alone. That fails closed for gates and empty for advice, and it never stalls
a tenant: each runner's evaluation is bounded, and a recompute runs in alarm batches (below).

### The evaluator: in core, bounded, honest about its size

`src/core/ontology.ts`, pure, no dependency. It parses the JSON, validates everything above,
stratifies (SCCs of the predicate graph, in topological order) and evaluates semi-naively,
stratum by stratum. Each rule's body is reordered once at validation: positive literals first,
as written, then comparisons and negated literals as soon as their variables are bound. Order
is deterministic, and so is the first-found derivation that explanations use. The honest size
is **~300–400 lines**, not the addendum's 50–100. This is a general join engine with
stratified negation, and the review was right that graph reachability plus first-match cannot
express the owner's join. Core does parse the ontology. It does not run a solver.

**Why this is not "running repository code" (value 4):** the program is total and
terminating, has no I/O, and is bounded by the counters above. It is data that core
interprets, as it interprets a course file's state machine. The decision row records this.

**Where it runs: at heartbeat, not at claim.** A runner's derived set for a repository is
recomputed when its inputs change: a heartbeat that changes its declared capabilities, a grant
change, or an accepted ontology for the repository. It is stored in
`runner_derived(runner_id, repository_id, capability, via_json, ontology_digest)`, created by
a new append-only migration. Rule 4's SQL and `fleet_capabilities` read declared ∪ derived, so
claim-time matching does no evaluation and the §6.6 pipeline keeps its shape. An accepted
ontology recomputes the granted live runners of its repository in the alarm, 50 per turn.
Until a runner is recomputed, its previous set stands under the digest it names. This is the
same posture as any course-file change.

### Serialization: `.baton/ontology.json`

Every entry has an `id` (`^[a-z][a-z0-9-]{0,63}$`, unique in the file). Variables are written
`$name`. The owner's worked example, in full:

```json
{ "version": 1,
  "entries": [
    { "id": "offers-ocg-deepseek",  "fact": ["offers", "credential:OPENCODE_GO_API_KEY", "model:deepseek-v4.1-flash"] },
    { "id": "offers-di-deepseek",   "fact": ["offers", "credential:DEEPINFRA_API_KEY",   "model:deepseek-v4.1-flash"] },
    { "id": "offers-anth-opus",     "fact": ["offers", "credential:ANTHROPIC_API_KEY",   "model:claude-opus-5-5"] },
    { "id": "usable-oc-deepseek",   "fact": ["usable_with", "dependency:opencode-v2",   "model:deepseek-v4.1-flash"] },
    { "id": "usable-oc-opus",       "fact": ["usable_with", "dependency:opencode-v2",   "model:claude-opus-5-5"] },
    { "id": "usable-cc-opus",       "fact": ["usable_with", "dependency:claude-code",   "model:claude-opus-5-5"] },
    { "id": "model-from-credential",
      "head": ["derived", "$m"],
      "body": [["offers", "$k", "$m"], ["holds", "$k"]] },
    { "id": "codegen",
      "head": ["derived", "capability:code-generation-llm"],
      "body": [["model_for", "coding", "$m"],
               ["offers", "$k", "$m"], ["holds", "$k"],
               ["usable_with", "$d", "$m"], ["holds", "$d"]] }
  ] }
```

A body literal is `[pred, args…]`. A negated literal is `{"not": [pred, args…]}`. A comparison
is `{"cmp": [lhs, op, rhs]}`. A constraint is `{"id", "constraint": [body…]}`. The format is
pinned by a JSON Schema in `src/defaults/` and by the validator in core. The
two-level chain `credential:ANTHROPIC_API_KEY → model:claude-opus-5-5 →
capability:code-generation-llm` is these two rules. `model:` capabilities are derived
in their own right, so a leg may require either altitude.

### Bindings: narrowing by default negation, the ASP idiom

A binding is a fact. Positive Datalog cannot narrow: an unconditional rule beside a binding
rule only ever adds derivations, which is what the review found. So narrowing uses **default
with exception**, which is ASP's own idiom and stays inside the fragment:

```json
{ "id": "model-for-bound",   "head": ["model_for", "$c", "$m"], "body": [["binding", "$c", "$m"]] },
{ "id": "bound",             "head": ["bound", "$c"],           "body": [["binding", "$c", "$m"]] },
{ "id": "model-for-default", "head": ["model_for", "$c", "$m"], "body": [["model_class", "$c"], ["model", "$m"], {"not": ["bound", "$c"]}] },
{ "id": "binding-functional", "constraint": [["binding", "$c", "$m1"], ["binding", "$c", "$m2"], {"cmp": ["$m1", "!=", "$m2"]}] }
```

With no binding for `coding`, every model the ontology lists serves the codegen rule. A
repository that writes `{"id": "coding-model", "fact": ["binding", "coding",
"model:claude-opus-5-5"]}` narrows it to Opus. The binding's value is the capability string
itself, so there is no `model_name` mapping and one naming scheme. `bound` depends only on
facts, so negating it respects rule 2. B-105's preferences choose *among* what this stratum
allows. They never stand in for it.

### The built-in ontology, and override by id

Baton ships a reasonable ontology as course code: `src/defaults/ontology.json`, scaffolded by
`repo init` (the facts above, the binding idiom, `model_class("coding")`, and
`model(...)` facts for the models it lists). **Merging is the sync's job, in course code.** The
CLI sync takes the built-in entries, removes the ids listed in the repository file's
`"retract": [id…]`, replaces any built-in entry whose id the repository file reuses, adds the
rest, and posts **one merged program** with its digest. There is one granularity: the entry
id. Core never merges. It validates and evaluates what was posted. A repository that posts no
file gets the built-in.

**Snapshot and timing.** The file is read from the default branch's accepted snapshot, like
course files (R-BTN-74). A refused file keeps the previous one in force and raises
`baton.ontology-refused` (R-BTN-69's posture). A claim and each advance check rule 4 against
the runner's stored derived set. An ontology change mid-ticket therefore takes effect at the
next advance, as a course file's `requires` change does.

### Matching, and the answers it gives

- **Rule 4 becomes** `capabilitiesOf(ticket.requires ∪ leg.requires.capabilities) ⊆ H ∪
  derived(H)`, with `H = declared ∩ grant(repository)`. The closure runs over the granted
  holdings, never the other way round. Derived capabilities need no grant of their own, and a
  grant naming a derived capability still admits a runner that declares it directly. Open
  decision 1's lean is adopted: tight concrete grants, stable abstract requirements.
- **`fleet_capabilities`** counts declared ∪ derived, so a `capability` block (R-BTN-75)
  clears when a derivation, not only a declaration, supplies the capability.
- **The why-not chain** comes with the blocks index's `missing-capability` answer. It is
  defined, not left to the implementer. The validator's maximal evaluation records, per derived
  atom, its first four derivations in body-reordered, rule-id order. For a runner,
  `missing(a)` is ∅ when `a` is in H ∪ derived(H) or is a fact, and `{a}` when `a` is an
  unheld holding. For a derived atom it is the derivation whose union of `missing` over its
  positive body literals is smallest, ties broken by the lexicographic order of the sorted set,
  then by rule id. Negated literals contribute nothing, because they range over facts. The
  answer is canonical and deterministic. It is an explanation, not a guaranteed minimum (the
  general problem is set cover), and the spec says so. Example: *"requires
  `capability:code-generation-llm`; missing `credential:ANTHROPIC_API_KEY` (rule `codegen` via
  `model-from-credential`)."*
- **The leg environment (R-BTN-144, amended).** The runner keeps `credential:<NAME>` when the
  leg's `requires` names it, **or** when it is in the `via` of a required capability that was
  derived for this runner. `via` is the set of holdings in the derivations recorded for that
  capability, at most 16, stored in `runner_derived.via_json` and returned in the claim answer
  per leg. Otherwise a leg that requires `capability:code-generation-llm` would have every
  credential stripped and could not run its own route.

### What Baton never does

Baton never stores a credential: holdings are labels, never material. It never learns a
vocabulary: `anthropic` is an opaque string to core. It never calls a provider: preflight is
course code. A leg verifies the credentials it will use, and a failing preflight retracts the
declaration and fails the leg, naming the credential. The ontology maps claims, and preflight
tests truth.

### Conformance: the fragment checked against clingo (built here)

B-104 builds the harness, and B-105 adds fixtures to it.

- **The translator**, `src/defaults/ontology-asp.ts`, emits ASP-Core-2 text from a merged
  program. Every constant becomes a quoted string (`"credential:OPENCODE_GO_API_KEY"`; the
  constant pattern admits no quote or backslash), an integer stays an integer, `$m` becomes
  `V_m`, and `{"not": …}` becomes `not …`. The emitter is a closed set of templates, and its
  output contains no gringo-only syntax (no `#show`, pools, intervals or scripts).
- **The conformance suite** is `test/unit/ontology-conformance.test.ts`, an ordinary vitest
  file in `npm test`. It needs no separate CI job, no Python and no network, and runs the same
  on a contributor's machine. It uses **`clingo-wasm`**, pinned exactly as a devDependency
  (`"clingo-wasm": "0.6.0"`, which bundles Clingo 5.8.1; Node ≥ 22, the repository's engine).
  For every fixture under `test/fixtures/ontology/` it runs the translated program, the
  fixture's holdings as `holds/1` facts, and a harness-only `#show derived/1.`, kept apart so
  `#show` never enters the translation, through `clingo.run(text, 0)`. It asserts `Result` is
  `"SATISFIABLE"` with exactly one witness, which is the stratified fragment's guarantee, and
  that the witness's `derived/1` atoms equal `src/core/ontology.ts`'s result. The `Warnings`
  must hold nothing but clingo's "atom does not occur in any rule head" info for prelude
  predicates a fixture leaves empty. A refused fixture must be refused by the validator. Heavy
  tooling stays in tests, never hosted (the R-BTN-68 posture). Upgrading `clingo-wasm` is a
  deliberate commit that re-runs every fixture.
- **The strict-syntax lint** backs the "standard" claim, since clingo accepts a superset of
  ASP-Core-2. A unit test parses every emitted fixture with a small recursive-descent parser for
  exactly the ASP-Core-2 productions the emitter uses, and fails on anything else.
- **Recorded rejections:**
  - clingo-wasm in the Worker: megabytes against the size budget, a cold start per isolate,
    NP machinery for a polynomial need. It is adopted in tests only.
  - A `pip`-installed clingo CI job: Python in a TypeScript repository, and an oracle that
    contributors do not run locally.
  - Another Datalog dialect with its own engine (Nemo, Soufflé, Logica, Mangle). None is a
    standard, none has a preference construct (so B-105 would leave the language), and none
    offers better TypeScript tooling than clingo-wasm. The owner, 2026-10-22, would replace
    ASP-Core-2 only for a dialect with better TypeScript tooling.
  - A clingo sidecar: core egress, and a Baton that needs infrastructure beside it (value 11).
  - An N3/RDF mapping: the first addendum's demotion, completed. The facts read naturally as
    triples if a consumer ever needs that. It is not built, tested or promised.

### Decided defaults (reversible, recorded)

1. **Grant level:** grants bound concrete holdings, and the closure runs over (holdings ∩
   grant). This is now normative, in § Matching.
2. **`dependency:` verification:** heartbeat self-report plus the leg's preflight, and nothing
   stronger until a fleet lies about it.
3. **Name scope:** the built-in uses shared names (`capability:code-generation-llm`, the
   `model:` values), and repository-local names are permitted beside them. Each repository's
   program is its own, so no cross-repository merge is needed.

### Tests (each names its scenario)

- **S-BTN-139 — closure.** The owner's chain derives `capability:code-generation-llm` from
  `credential:ANTHROPIC_API_KEY` + `dependency:claude-code`. The conjunction is required, since
  the credential alone does not derive it. A generic transitive rule derives across three hops.
- **S-BTN-140 — refusals at post**, each naming the rule or cycle: a cycle through negation; an
  unsafe rule; an ill-typed comparison; a head deriving `credential:X`, `runner:x` or
  `human-operator`; a negated `holds`; a `holds` variable bound only by `holds`; a violated
  constraint (two bindings for `coding`); each bound in the table crossed; an unknown
  capability type. Positive recursion is accepted.
- **S-BTN-141 — bindings narrow.** No binding: a DeepSeek-holding runner satisfies codegen.
  `binding(coding, model:claude-opus-5-5)`: it no longer does, and an Opus-holding one does.
- **S-BTN-142 — grant order.** A runner declaring `credential:ANTHROPIC_API_KEY`, granted
  `credential:*` and `dependency:*` but not `capability:*`, matches a leg requiring
  `capability:code-generation-llm`. Ungranted on `credential:ANTHROPIC_API_KEY`, it does not.
- **S-BTN-143 — matching.** A leg requiring the capability is recommended to a runner whose
  holdings derive it and not to one whose holdings do not. A direct declaration satisfies with
  no derivation. `fleet_capabilities` clears a `capability` block on a derivation.
- **S-BTN-144 — why-not.** The answer names `credential:ANTHROPIC_API_KEY` and the rule chain,
  and with two alternative missing sets it names the smaller (ties broken lexicographically).
- **S-BTN-145 — environment.** A leg requiring `capability:code-generation-llm`, derived via
  `credential:DEEPINFRA_API_KEY`, receives `DEEPINFRA_API_KEY` and no other declared credential.
- **S-BTN-146 — timing and bounds.** An accepted ontology recomputes runners in alarm batches,
  and a claim in between matches under the previous digest. An evaluation crossing the step
  counter yields holdings only and raises `baton.ontology-limit`, identically on both hosts.
- **Conformance.** The clingo-wasm suite is green in `npm test` on every fixture, including the worked example, the
  binding idiom and a recursive one. The strict-syntax lint passes on all emitted text.

### Exit criteria

- [ ] legs require at any altitude; runners declare holdings; the closure of (holdings ∩
      grant) under the repository's posted ontology derives, server-side, materialized at
      heartbeat and read by rule 4 and `fleet_capabilities`
- [ ] the fragment is stated in one sentence in §5.9 (R-BTN-175), with its safety,
      stratification, typing, head, monotonicity and bounds rules, each refused at post with
      the rule named
- [ ] bindings narrow by default negation, built-in and overridable by entry id; the sync
      merges, core never does
- [ ] a missing capability's why-not names the missing holding and the rule chain, by the
      specified canonical choice
- [ ] a derived capability's credentials reach the leg's environment, and no others
- [ ] the ASP-Core-2 translator, the clingo-wasm conformance suite and the strict-syntax lint
      are green in `npm test`
- [ ] no credential material, provider call or vocabulary word ever enters core
