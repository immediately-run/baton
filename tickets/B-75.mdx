**Brief:** the owner, 2026-10-20, closing the open question "Handlers that answer core
conditions": go with owner-signed answers for now, and "persist the stations and legs traversed by
a ticket over a course in Baton, so even if an agent modified the record in git, we still have a
Baton record which would be authoritative if there is disagreement. The number of times a
particular station / leg has been traversed by the given ticket is really all the state we need for
the retry logic."
**Revised** the same day after the adversarial review (adv-2 B1): the sync that would verify a
signature is code agents can change, so the owner chose that a core condition is answered only
through Baton's own authenticated surfaces, the handler delivering a deep link to its resolve page.

### Requires

None: a checkout and a terminal.

### Why

A retry hold exists so that agents cannot burn quota by retrying forever. If an answer in git
could clear it, any agent that can push could; and if `max_runs` counted from the posted path, an
agent that rewrote a ticket's history could buy its legs more runs.

### What to build

1. **Answers only in Baton.** Core never reads a core condition's handler output or file answer
   for the condition. The outbox's `handler` entry for a `baton.*` condition carries the
   condition id, and the handler's input and message carry `resolve_url`
   (`https://<origin>/conditions/<condition_id>`). The dashboard's Resolve page shows the condition
   and its restarts; choosing one is `owner.resolve` for a signed-in owner of the repository or an
   administrator, through `authorize` (R-BTN-129); signed out, it asks for sign-in and returns.
2. **Traversal record.** Counts of each leg run and station arrival per ticket, under resolved
   names, maintained in the transactions that record `claim_legs` and confirm sync-posted
   arrivals (a new table or columns on the ticket's history — one new numbered migration). The
   `advance` gate for `max_runs` and the retry policy read it. A snapshot whose path implies fewer
   runs logs `path-rewritten` with both counts and changes nothing.
3. The dashboard shows a held ticket's counts beside `baton.retries`.

### Do not

- Read anything from git (a handler's `answer`, its output, a signature) as an answer to a
  `baton.*` condition.
- Let a posted path lower a count, or a count move a ticket: git still places it (R-BTN-35).

### Tests

- S-BTN-131 extended: a bound `baton.retries` answered `retry` in its handler's file (read for
  nothing, the hold kept); the handler's message links `/conditions/<id>`; resolved there by a
  signed-in owner; the page refused to a runner key and to another repository's owner.
- Unit: the traversal counts across a course rename; a force-pushed history with fewer runs logs
  `path-rewritten` and the leg is still refused at `max_runs`.
