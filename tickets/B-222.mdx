### What to build

The §14 rows exist for every route; the code first for the two that lack it, then the controls.

1. **`POST /v1/ui/claims/{id}/confirm` and `…/release`** (`claim.confirm`, `claim.release`; an
   administrator's session; `{}`; `202 {confirm_code}` per R-BTN-155): built over
   `claims.resolve`'s `confirm | release` (today's `POST /v1/ui/claims/{id}/resolve`, which V1
   called with `{action}` and which B-203 removes once these exist), keeping its `@model`
   annotation so `model:links` still names the implementation; `ui.view` on
   `repository/tickets/{ticket}` for both; a scenario on both hosts for each, with the code
   confirmed by the minting key.
2. **The controls** (`src/dashboard/screens/tickets/TicketControls.tsx`) through B-207 by
   `ui.view` with context `{repository, ticket_id, claim_id: claim.claim_id, to_runner_id:
   claim.runner_id, condition_id}` (the last set only when exactly one condition is open):
   - **hold** and **cancel** (cancel through the confirm dialog), **expedite** and **clear
     expedite** (the code dialog), **unhold** (the code dialog; drawn only where `ticket.show`'s
     `allowed` names `ticket.unhold`, R-BTN-186);
   - **resolve**: where exactly one open condition offers restarts, its restart buttons inline
     (`ticket.resolve` through B-56's route); otherwise "resolve on the condition's page" linking
     each condition;
   - **Stop**: one click, no dialog (Decision 3a), `leg.stop` through `POST /v1/ui/messages` with
     `to_runner_id`, `kind: release` and a payload of the ticket id and `reason: requested`;
   - **acknowledge** on each open scope finding (`scope.resolve`, `POST
     /v1/ui/scope/{id}/resolve`, one click, §12.9; its `ui.view` from B-204);
   - for an administrator's session: **force-reap** (`claim.force-reap`, the code dialog),
     **clear fence** where `fence_pending` (`claim.fence-clear`, B-171's, the code dialog),
     **confirm completion** and **release completion** where the state is `unconfirmed`
     (item 1's routes, the code dialog).
   Each refusal is drawn beside its control as text.
3. **Phone.** The controls row wraps under the head at 375 px.

### What not to do

- No route or adopt button (Decision 2a); no dialog on Stop (Decision 3a); no control the
  registry does not place here.
- No permission logic: unhold follows `allowed`; everything else is drawn from the session's
  entries and refused by the server if need be.

### Trust

- **Every control** is a registry action through `authorize`; the page sends the context and the
  form and draws a refusal as text.
- **`claim.confirm` and `claim.release`** — an administrator's session, confirmed by the minting
  key (R-BTN-155); the same core function V1 called.

### Invariants

- **R-BTN-155's confirmed list**: unhold, expedite, the completion's confirm and release,
  force-reap and the fence clear go through the code dialog; hold, cancel, Stop, resolve and the
  acknowledgement do not.
- **Destructive takes `confirm: true`** (§12.2) except Stop (Decision 3a). **One check**
  (R-BTN-129). **Both hosts** (R-BTN-55) for the two routes.

### Tests

Scenarios numbered at merge, on both hosts: `claim.confirm` and `claim.release` answer `202`
to an administrator's session and act on confirmation, `forbidden` to an owner's. Under
`test/ui/` with a fixture `GET /v1/actions` and `ticket.show`: the owner's entries draw hold,
cancel, Stop, resolve and not force-reap, the administrator's force-reap, clear fence, confirm
and release too (B-191's scenario on this screen); unhold appears only with `allowed`; Stop sends
with `to_runner_id` and no dialog; cancel opens the confirm dialog; expedite opens the code
dialog; the acknowledgement sends one click.
