### What to build

The §14 Requests paragraph first, then the code.

1. **ETag on every session-readable GET.** One function in the front wraps the JSON answer of a
   read whose entry lists `session`: the ETag is a strong SHA-256 of the body with the top-level
   `server_time` key removed (the body itself keeps `server_time`, so the CLI's and runners'
   contracts are unchanged); `If-None-Match` matching answers `304` with the ETag and no body.
   `GET /v1/runner/fleet` and `…/instances` keep their own (R-BTN-99). The ETag is per response,
   never cached across callers.
2. **The cursor convention**, stated once in §14's Requests paragraph and used by every new list
   read: `?cursor=` in, `next_cursor` out (absent on the last page), 100 items a page unless the
   row says otherwise; the cursor is opaque, HMAC-bound under `CursorKey` (R-BTN-55) to the
   caller's credential or session, the action id and the other query parameters, as R-BTN-130's
   list tools bind theirs; a cursor from another caller, action or filter is `invalid-params`.
   A pure helper in `src/core/cursor.ts` mints and checks them; the list reads B-194, B-195,
   B-196, B-197, B-201, B-202 and B-213 add use it.
3. **Existing reads keep their paging**: `history` stays `?before=<id>&limit=`; `board`,
   `grants`, `blocked` (which already has its own `?cursor=`), `conditions` (its own `?cursor=`)
   stay as §14 states them. No existing row changes shape.
4. **Response convention for new reads**, stated in the same paragraph: `{<items>: [...],
   next_cursor?, counts?}`, timestamps as epoch milliseconds as today, filters as query
   parameters with `invalid-params` for an unknown one.

### What not to do

- No change to any existing read's body or paging (R-BTN-179 fixes the board's shape for keys;
  `baton ticket history` reads `before`).
- No shared cache: an ETag compares one caller's last answer with its next; nothing is served
  from a cache to another caller.
- No `Cache-Control` beyond `no-store`, which the front sets today.

### Trust

- **ETag** — a hash of the caller's own answer; it reveals nothing the body did not and is
  compared per request.
- **Cursors** — opaque and HMAC-bound; a forged, foreign or re-filtered cursor is
  `invalid-params`, so a cursor cannot widen a read beyond what the first page authorized.

### Invariants

- **Existing contracts unchanged** (R-BTN-179, the CLI's reads).
- **One check** (R-BTN-129): `authorize` runs before the ETag is compared; a `304` is never
  answered to a caller the read would refuse.
- **Both hosts** (R-BTN-55): `CursorKey` and the hash are available on both.

### Tests

Scenarios numbered at merge, on both hosts:

- two reads of an unchanged board one second apart differ only in `server_time` and carry the
  same ETag; the second with `If-None-Match` is `304`; a changed row changes the ETag;
- a `304` is never answered to a session the read refuses (a revoked owner's session with the
  old ETag is `forbidden`);
- a cursor minted for one session, action and filter is `invalid-params` for another session,
  another action, or the same action with a different `?state=`; a tampered cursor is
  `invalid-params`;
- `history` with `?before=` and `board` answer exactly as before this ticket.
