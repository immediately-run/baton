**What:** nothing says which rules of the spec are built. The marks live in section headings
("proposal — B-106"), and 90 of 192 scenarios have no test while [BATON_SPEC §15](../spec/BATON_SPEC/15-verification.md#sec-15) ([R-BTN-30](../spec/BATON_SPEC/15-verification.md#sec-15)) says
scenarios are required. Make a rule's status data, and check it.

From the architecture review of 2026-11-19 (`docs/review/architecture-review-2026-11-19.mdx`, on the branch `review/architecture-2026-11-19` until it lands).

### What to build

1. One status token per rule — `built`, `partly`, `specified`, `retiring` — with the tickets
   that build it, replacing the heading marks.
2. `npm run spec:index` emits a ledger: rule, status, the modules that cite it, the scenario
   tests that name it.
3. For scenarios without a test, a pending list that may only shrink.
4. `check:spec` fails on: a rule without a status; a `built` rule no source file cites; a
   `specified` rule whose tickets are all archived; a scenario with neither a test nor a pending
   entry.
5. Amend R-BTN-30 to say what is true: required, or pending by name.

**Done when:** CI runs the four checks and the ledger is generated, not hand-kept.

### Trust

No new input: the ledger is computed from the repository's own files. A status token is a claim
by whoever wrote it, which is why the check compares it with the code's citations instead of
trusting it.

### Invariants

- One home per statement (`docs/context/spec-writing.mdx`): a rule's status is written once,
  beside the rule, and the ledger is generated from it.
- R-BTN-31: every behaviour change names its scenario; the pending list never grows.
- The generated index stays generated: `spec/BATON_SPEC.md` is written only by `spec:index`.
