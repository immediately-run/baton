**What:** the `Runner` class in `src/runner/runner.ts` is about 2,440 lines and reaches each
claim's state through `AsyncLocalStorage` proxies. Put per-claim behaviour on a per-claim object.

From the architecture review of 2026-11-19 (`docs/review/architecture-review-2026-11-19.mdx`, on the branch `review/architecture-2026-11-19` until it lands).

### What to build

1. `ClaimRun`: owns its slot and holds `runClaim`, `runLeg`, the close and handoff calls and the
   verify methods. No proxy: the claim's state is `this`.
2. `Sidecar`: the heartbeat and the spool.
3. `runClaim` split into prepare, the leg loop and settle.

**Done when:** the runner uses no `AsyncLocalStorage`; no function exceeds about 120 lines; the
runner scenarios pass unchanged.

### Trust

No new input. The runner still checks what it reads from the checkout (the ticket's schema after
every leg, the pull request before `pr-open`, the answer line before the verdict); the move must
keep each of those checks on the path it guards.

### Invariants

- [BATON_SPEC §9.1](../spec/BATON_SPEC/09-claims.md#sec-9-1) ([R-BTN-4](../spec/BATON_SPEC/09-claims.md#sec-9-1)): a runner may hold several claims, each in its own session and
  checkout. Two `ClaimRun`s share no mutable state.
- [BATON_SPEC §8.3](../spec/BATON_SPEC/08-runners.md#sec-8-3) ([R-BTN-107](../spec/BATON_SPEC/08-runners.md#sec-8-3)): how a leg runs is the executor's; `ClaimRun` hands the leg to the
  `Executor` contract and knows no executor by name.
- Fencing (R-BTN-6): a heartbeat's refusal stops that claim's legs and no other's.
