**Spec:** R-BTN-155 (*dashboard sign-in is a code a key holder confirms*, steps 3 and 4,
*Limits*), §14's rows for `POST /v1/admin/login-links` and `POST /v1/owner/login-links`, the open
question *Confirmation by keys a same-user process can reach*, S-BTN-124. Source:
`docs/review/security-review-2026-11-02.mdx`, finding S7, checked against the text in PR #165.

### Why

R-BTN-155 says a process that asks for a code of its own "gets nothing unless a key holder types
that code, read from Baton's own page". Against an attacker who starts a sign-in and relays the
code ("type this into `baton owner open`"), that holds only if the holder sees whose row the code
binds — which step 3 promises (`owner session for <address>, <n> s old`) and the API cannot
deliver: both login-links routes take `{code}`, bind at once and answer `{ok: true}`. A CLI built
to the routes binds first and can show the row only afterwards, when it no longer helps.

### Spec (written 2026-11-03)

The spec half is written: R-BTN-155 step 3 (preview, then `{code, confirm: true}`), its closing
sentence, §14's two login-links rows and S-BTN-124's cases, in PR `claude/baton-spec-review-2fwiga`
at the owner's request ("Please ensure all tickets required to implement the spec are ready to be
picked up for implementation"). The open question on `sk-`-only binding stays the owner's and is
untouched.

### What to build

1. Both login-links routes: without `confirm`, answer `{role, client_addr, age_s}` for the
   unbound, unexpired row of the route's role and bind nothing; with `confirm: true`, bind as
   today. `not-found` at either step as R-BTN-155 says.
2. `baton admin open` and `baton owner open`: send the preview, print `owner session for
   <address>, <n> s old` (or the administrator form), ask `bind? [y/N]` defaulting to no, refuse
   `--yes`, and on yes send the confirm. An `sk-` key touches for each request.
3. The tests.
