**Brief:** the first acceptance round (the lessons page): the review agent reviewed PR #81
but ended its output with prose around the verdict; the stub refuses the round on the last
line's shape. PR #82 hardened the instructions; prompts drift, and a round is expensive.
**A second failure, B-71's first review round, bounds this ticket honestly:** the client
process exited mid-review (B-84's client/server split) and the stub read *truncated*
stdout — no verdict line existed yet to be tolerant of. The backward scan below saves the
round only when the client outlives the session; the completion signal is B-84's, not
this ticket's. **Spec:** §5.8 (R-BTN-131: `Ask` — "the agent's last line, checked against
the course's values"), `src/defaults/courses.ts`'s stubs.

### Why

A machine parses the answer; the machine should read like one. The strict last-line rule
loses whole rounds to a trailing sentence — B-80's review burned its claim on exactly this.

### What to build

1. The answer check scans backwards for the last line that begins with one of `ask.values`
   (the value word as a whole word), taking any PR URL that follows it on that line; extra
   prose before or after no longer fails the leg.
2. The instructions keep demanding the bare line (a tolerant reader is no excuse for a
   sloppy answer); the `.md` templates stay as PR #82 wrote them.
3. The same scan serves `review` and `adjudicate` (and any future `Ask` leg) through one
   helper, with the strict behaviour kept behind a flag for the kit's tests.

### Tests

- Unit: a table of agent outputs — bare word, word plus URL, prose before, prose after,
  trailing blank lines, the word mid-line only (still refused) — against the helper.

### Exit criteria

- [ ] a verdict with prose around it no longer loses the round
- [ ] a missing or misspelled verdict still fails, naming what was read
