**Brief:** the owner, 2026-11-09, after a runner-trust audit (three reviewers over BATON_SPEC,
FIELDHOUSE_SPEC and `docs/security-model.mdx`): "no-runner-lands is a vestigial structure from
when the runner was assumed to be untrusted because it executed repository code unsandboxed.
This is not the case any longer, as we have transitioned to keeping the runner outside the
sandbox." On legs and the forge: "'Legs never hold a forge write token.' Agree"; on "plain Baton
under builtin makes no security promises at all": "Ok". The owner, 2026-11-24, on review
independence by domain: "This provision seems to be a vestigal structure from the time when
baton's runner was executing within the sanbox. The runner is now a trusted component, executing
on the host, and all course legs including implement and review are sandboxed (each leg
receiving a blank-state separate sandbox). In addition, each leg receives transient local-only
git and llm api keys which they can use to communicate with the local proxy backed by llm
providers and the git forge. The contamination risk is therefore no longer something that
warrants any extra complexity"; asked whether those proxies replace forge actions a runner
performs for a leg: "Proxy replaces it"; and "Every leg should get leg-duration keys to be used
by sandboxed code." The audit's list (2026-11-09) is the map for this ticket.

The spec half is its own spec PR, landing first with the owner's approval: §12.8, R-BTN-180,
R-BTN-188 and R-BTN-189 as `spec/BATON_SPEC_HISTORY.md`'s entry of 2026-11-24 records.
This ticket builds it.

### What to build

1. **The policy document loses the runner-distrust knobs.** `src/core/policy.ts` and
   `cli/baton.mjs`'s `KNOBS` drop `refs.*` (`default_branch`, `tags`, `other`, and the legacy
   `baton` and `legs`), `approvers.roles` (the code's `approvers.trust`), the legacy `grants.*`,
   `outbox.git`, `outbox.forge-check` and `inputs.board`, with every refusal that reads them
   (the `outbox.git`-against-`refs` refusals, the `git` repository's `ci-identity` and
   `forge-check` refusals) and `REF_WRITERS` and `BOARD_INPUTS`. `outbox.source` stays,
   `[runner]` or `[]`. `paths.control`'s value `trusted-runner` becomes `approval`. The presets
   and `plain-git` become §12.8's columns. A `PUT …/policy` naming a retired knob or value is
   `invalid-params` naming it, and so is `merge.trusted` with `tickets.created: filed`, a new
   refusal of R-BTN-188's.
2. **The guarantees rebase; `no-runner-lands` retires.** `guaranteesFor` computes R-BTN-189's
   ~~five~~ six: each but ~~`human-gates`~~ `human-gates` and `human-gates-hardware` rests on the landing condition (`merge.trusted`,
   `tickets.created: proposed`, `paths.control` not `any`) where it named `no-runner-lands`; `independent-review`
   holds on `merge.reviews.count` ≥ 2 and `attestations` admitting only `baton` for
   `std:review@1` and `std:wrote@1`; `human-gates` reads `approvers.members` and
   `approvers.policy`; `board-from-trusted` reads `attestations` alone. A floor naming
   `no-runner-lands` (or the code's `trusted-domain-separate`) is dropped by the migration in
   whichever form it is stored when this lands — a `policy_floors` row (the built form, while
   B-293 has not landed) or a version's `floors` (after it) — by a new version without the name, logged `admin` with both hashes and naming the
   owner's ruling of 2026-11-09 — never a silent edit of a stored version, whose hash chain
   stays; a change naming either afterwards is `invalid-params`. (This is the owner's ruling for
   these two names; B-293's rule that a floor without a successor stops the migration applies
   to every other name.) A version or `floors` entry naming any guarantee R-BTN-189 does not
   define is refused `invalid-params`. (Review counting — `std:review@1` superseding per run id,
   a rejection voiding a head's approvals — is B-146's store and B-140's gate, not built here.)
3. **The protection report retires.** The heartbeat's `protection` is accepted and ignored, so
   an older CLI keeps working, until no request has carried it for 30 days, then refused
   `invalid-params` (the history's *Migrations the implementation still carries*); the
   `protection_reports` table (§13's `repositories.protection_json`), the 24-hour lapse check and
   `baton.unprotected` go, a migration closing every open `baton.unprotected` condition with a
   logged reason. `baton repo protect --print | --check`, when built
   ([proposed](../spec/proposals/security.md)), stays a tool a person runs that Baton reads
   nothing from.
4. **Grant trust columns go.** A new migration drops `runner_grants.trust_level`,
   `trust_domain`, `role`, `trust_set_by` and `model_family` (§13's `role`, `checker`, `domain`, `set_by`) and
   `claim_legs.domain` if present, after one release in which nothing reads them; the grants
   read (§14, S-BTN-295) stops answering `role`, `domain` and `set_by`, and an owner-state
   import (R-BTN-88, `src/core/ownerState.ts`) accepts an older export carrying them and ignores
   them. A trusted leg
   is routed by the capability its course requires (R-BTN-174), which the owner admits on the
   grants of runners whose host holds its credential (R-BTN-180, R-BTN-182); rule `trusted`, as
   the security proposal's part 7 now defines it over capabilities, is B-140's, and no role
   route is built.
5. **The executor's brief carries the claim's reach.** The runner adds to R-BTN-107's `brief`
   the claim's `scope` (§12.9, the claim answer's) and the ticket's `branches`: its course's
   `branch_pattern` with the ticket's id in place and its leg-state branch (R-BTN-190).
   `executor_api` stays 1 (an added field). The `builtin` executor ignores them; a deployment's
   executor mints leg-duration credentials bounded by them (Fieldhouse: its git/forge proxy).
   Legs keep ordinary `git` and `gh`; no forge-action protocol is built.
6. **Kept as cheap defence in depth**, unchanged: R-BTN-144's credential stripping and masking,
   per-key limits (R-BTN-187), fencing, §12.9's audit and cross-check, and `no_chain_from` as a
   course rule no guarantee requires.
7. **Docs.** `docs/security-model.mdx`'s remaining text about reach 1 under a kept duty, the
   runbooks that name a protection checker or `inputs.board`, and `AGENTS.md` follow the spec;
   the spec PR marked the superseded options (4, 5, 8, 16, and the runner halves of 3 and 17).

### What not to do

- **No isolation vocabulary in Baton.** The duty is the deployment's (§12.8); Baton names no
  proxy, sandbox or key format and checks nothing about them (R-BTN-107).
- **Do not weaken R-BTN-183.** Every check of the merge gate stays.
- **Do not build forge actions** (a leg returning push, PR and comment requests for the runner to
  perform): the owner ruled on 2026-11-24 that the deployment's proxies replace them.
- **Do not reopen signed authorship** (the owner, 2026-11-09: not now).

### Trust

- **The executor brief's `scope` and `branches`** — Baton's claim answer and the course's
  `branch_pattern`, read from the course file as every course field is (a control path,
  R-BTN-184); the runner writes the brief, a leg never does. An executor that trusts them trusts
  Baton and the course, as the runner already does.
- **The migration's dropped knobs and floor names** — Baton's own code, run over documents their
  approvers wrote. It loosens on the owner's ruling, and says so: a repository whose policy
  excluded `machine` from `inputs.board` lets machine keys post its board, one whose `refs.*`
  named writers loses a statement only the forge enforced, and a floor on `no-runner-lands` is
  dropped. Each is logged `admin` per repository with the knob named. Two more: a repository
  floored today on a guarantee that included `no-runner-lands` is broken now (no checker report
  can exist) and resumes taking claims when this lands if its landing condition holds; and a
  policy whose `approvers.roles` was stricter than its `approvers.members` loses that
  difference, a trusted leg's capability being a grant's, under `approvers.members`. Three more:
  `independent-review` keeps its name but no longer requires distinct domains, so a deployment
  floored on it accepts one key writing and reviewing; with `outbox.git` gone any runner
  declaring the class delivers git entries; and a stored version with `merge.trusted` and
  `tickets.created: filed` stays in force until its next change, which the new refusal then
  binds. The migration names each per repository in its
  `admin` event.
- **A heartbeat's `protection`** — ignored; nothing stores or reads it.

### Invariants

- **R-BTN-183's merge gate** keeps every check but independence, which now counts `reads_only`
  review runs of the exact head with no rejection there.
- **Baton runs no repository code** (R-BTN-98).
- **Migrations are append-only** (one new numbered file per change); stored policy versions and
  their hashes are never rewritten, only followed by a new version.
- **Validate before you write**: a policy change still passes `src/core/validate.ts` and
  `policy.ts`'s checks before any SQL.
- **Filter fields only** (R-BTN-33): no new stored text.
- **One clock** (R-BTN-32): the migration's version time comes from `this.now`.

### Tests

- Every preset's document validates and yields R-BTN-189's guarantees: `protected` holds all
  but ~~`human-gates`~~ `human-gates-hardware`, `protected-hardware` ~~all five~~ the same until a key can meet `hardware`, with no grant role, checker or report.
- A `PUT …/policy` naming `refs.default_branch`, `approvers.roles`, `inputs.board`,
  `outbox.git` or `paths.control: trusted-runner` is `invalid-params` naming it, as is a new
  `merge.trusted` with `tickets.created: filed`; a stored one stays in force and is named.
- A stored version floored on `no-runner-lands` gets one new version without it, logged
  `admin`; the stored version and its hash are unchanged; a later change naming it is refused
  (S-BTN-190).
- A heartbeat carrying `protection` is accepted and stores nothing (and is refused once the
  30-day sunset passes); an open
  `baton.unprotected` is closed by the migration.
- A test executor records the brief: `scope` and `branches` match the claim answer and the
  resolved `branch_pattern`.
- Each behaviour change names its `S-BTN-n` scenario (R-BTN-31).
