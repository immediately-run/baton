**Brief:** the Baton project; filed by R3-1253 (docs#217).
**Spec:** `spec/BATON_SPEC.md` §3.3 R-BTN-94 (runners, the spool), R-BTN-97 (a sync off a CI sandbox); §3.4 R-BTN-96 (fact adapters, the `branch` course), R-BTN-139 (trusted facts); §5.1 R-BTN-134 (course directories and sources, `facts`, `baton repo init`, `--defaults-only`); §4.2 R-BTN-74; §15 S-BTN-54 and S-BTN-56's `--defaults-only` cases
**Depends on:** R3-1263, R3-1249, B-43 (course directories: `branch` is one)

### Requires

- none — the harness runs a bare repository with a `post-receive` hook and a fake GitLab/Gitea API.

### Why

A plain git server needs a runner and a course whose facts come from git alone; GitLab and
Gitea need the PR facts `create-pr` and `review-pr` read. Tier: judgement — the station rules are fixed by the spec.

### What to build

1. `baton repo sync --if-wanted` and `baton repo mirror --if-wanted` (one signed request when nothing is
   wanted), `baton repo spool <repository>` for `post-receive` hooks and the sync account's loop
   that records the want and runs the sync.
2. `baton repo sync --defaults-only`: no repository code; refuses to start when the resolved CLI or
   a module it loads lies inside the checkout.
3. **Fact adapters** (R-BTN-96) for GitLab merge requests and approvals and Gitea pull requests
   and reviews, chosen by the repository's `forge`, mapped to the facts the GitHub adapter
   gives (a PR's head branch, state, head checks and verdicts on the head, each with
   `repository`, fork-ness and `trusted`, R-BTN-139). Every course whose `entry.json` declares
   `facts: ["prs"]` — today `create-pr` and `review-pr` — reads them unchanged.
4. **The `branch` course** as a course directory `src/defaults/courses/branch/` in the baton
   repository (R-BTN-134: `course.json`, `entry.json` with `facts: ["branches"]`, `sync.mjs`,
   `legs/<leg>.mjs` and `legs/<leg>.md`), read from its source like any other course;
   `baton repo init --course branch` writes only the source
   `github/immediately-run/baton/<commit>/src/defaults/courses/branch` and the entry. Its
   station function: stations `filed` → `pushed` → `reviewed` → `merged` with `fixed` between
   `reviewed` and the next review; merged first by a `Baton-Ticket` trailer on the default
   branch's first-parent history; a ticket's branch is a ref matching the current or previous
   `branch_pattern` with a commit off the default branch; empty verdict commits with
   `Baton-Verdict` and `Baton-Reviewed`; legs `implement`, `review` (`max_runs` 4), `fix`
   (`max_runs` 3) and `merge`, whose leg script writes `git merge --no-ff` with the trailer.
5. `baton repo init` writes CI configuration whose sync key only default-branch runs can read.

### Architecture — the decisions, named

- **The station rules are written once** over forge-neutral facts.
- **Do not**: let a `post-receive` hook read the sync key or wait for a sync; bar identities in
  the `branch` course.

### Tests

- Integration: S-BTN-54, both hosts; S-BTN-56's `--defaults-only` cases.
- Unit: the `branch` station function over constructed histories (no branch, a branch at the
  tip, verdicts naming older commits, a fix after a verdict, a squash merge, a deleted branch, a
  trailer on a merged-in commit); each fact adapter over recorded GitLab and Gitea answers,
  mapped to the GitHub adapter's facts.

### Exit criteria

- [ ] S-BTN-54 passes on both hosts
- [ ] the `branch` station function's and the adapters' unit tests pass
- [ ] `src/defaults/courses/branch/` passes `baton course test`, and `baton repo init --course branch` writes a source, never a course file
- [ ] `npm run typecheck` green
