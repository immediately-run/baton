### Why

- **Ticket edits under a claim.** R-BTN-5 checks the ticket's version once, before the first leg
  runs. After that, R-BTN-35's "progress is not staleness" leaves the claim alone for anything but
  a withdrawal or a re-tier. A ticket rewritten in git, or edited in a tracker behind
  `.baton/tickets.mjs` (B-183), is worked to the end of the leg on the old text. B-183's version
  contract already makes the signal exact: a ticket's version changes exactly when something a
  runner reads of it changes. Baton sees the change in the snapshot it accepts. Nothing passes it
  on.
- **Stops from the dashboard.** R-BTN-119 stops a leg at once for `requested` (Stop leg),
  `owner-cancel` (Cancel) and `superseded`. A leg script only sees `ctx.signal` abort with reason
  `release`, and a session sees only SIGINT. The leg cannot tell a cancelled ticket (nothing to
  hand off) from a paused one (hand off carefully), even though the runner knows the reason.

### Decisions (the session's recommendations; the owner settles them in the spec PR)

1. **The name.** The vocabulary defines a condition as something "a running leg raises".
   Inbound events are not conditions. Their only handler is the running leg, so there is no
   binding, no handler ticket, no Needs-you entry, no `conditions` row and no quota. They share
   the condition **type grammar** (R-BTN-160: dotted, at most 64 characters, a core-reserved
   namespace). Recommended: a sibling noun, **leg event**, with its own vocabulary sentence.
   Alternative: "inbound condition".
2. **The undeclared default for `ticket.changed`** is `continue`, today's behaviour, so no
   existing course changes. Alternative: `restart`, which is safer when a task is rewritten but
   changes every course at once.
3. **No mid-leg adoption of the new body.** A ticket is a task, not authority. Handing a running
   agent new text after the claim's tier check, readiness check and signed-control check
   (R-BTN-5, R-BTN-133) would be a new injection surface. `restart` gets the new text through the
   existing re-verification instead. A later ticket may add an `adopt` choice that re-runs
   R-BTN-5's checks before the leg sees the text.
4. **A leg's own edits.** A leg that changes its own ticket also moves its version. The runner
   suppresses the event where it can prove the change is the leg's own: for the markdown source,
   when the commit that moved the ticket's file on the default branch is one the leg's window
   pushed (the reflog the scope audit already reads, R-BTN-106). For any other source the event
   is delivered. Under `continue` it is a harmless notice, and a leg that declared `restart` and
   writes its own ticket through a tracker must listen and decide itself.
5. **`release` is not negotiable.** It carries R-BTN-119's reason before the stop and gives the
   leg no new way to delay or refuse. The 10 s and 25 s escalation and the 2-minute `close` and
   `handoff` bounds are unchanged.

### What to build

**First PR: the spec amendment** (new rule R-BTN-196, the next free id at merge), with
`npm run spec:index` and a `spec/BATON_SPEC_HISTORY.md` entry recording the owner's answers to
the decisions above.

1. **R-BTN-196 (leg events), in §7** as a new subsection after §7.8, or wherever the owner places
   it. It states:
   - A leg event is a typed event Baton tells a running leg about. Its type follows R-BTN-160's
     grammar.
   - The standard types are `ticket.changed` and `release`. Both are core's alone, and the
     validator refuses a course that declares either as a condition, as it does for `baton.*`.
   - A leg event is delivered by the heartbeat and the doorbell, and never stored as a condition.
2. **R-BTN-35.** "Progress is not staleness" gains one sentence: a version change on a held
   ticket is delivered to the holder as `ticket.changed` (R-BTN-196), and the claim stays.
3. **§8.1, the heartbeat response.** The active claim carries `version`, the held ticket's version
   in the latest accepted snapshot.
   **R-BTN-91** gains the ring kind `ticket`. In the transaction that accepts a snapshot, Baton
   rings the holder of every held ticket whose posted version differs from the version it had
   cached. The ticket's history (R-BTN-81) logs `ticket-changed {claim, from_version,
   to_version}`. Versions are opaque filter fields (R-BTN-33). They are compared for equality
   only, never ordered (values 4).
4. **R-BTN-69, the course file.** A leg field
   `"on_ticket_changed": "continue" | "restart"`, defaulting to decision 2's answer.
5. **The runner (§8.3).**
   - **Detection.** The runner compares each heartbeat's `version` with the version the claim was
     decided on, or with the last version it delivered. It applies decision 4's suppression, then
     delivers `ticket.changed {from_version, to_version, snapshot_sha}` once per change.
   - **`continue`.** The event is delivered and the leg goes on. A later `advance` in the same
     claim re-runs R-BTN-5's version check before the next leg starts, so a chained leg never
     starts on a version the board has moved past.
   - **`restart`.** The event is delivered. Then the runner stops the leg at its next safe point
     (§9.4) with `ctx.signal` reason `release`, calls `close` and `handoff`, and ends the claim
     `released:ticket-changed`. The next claim re-reads the ticket and passes R-BTN-5 again.
   - **`release`.** The runner delivers `release {reason}` (`requested`, `owner-cancel`,
     `superseded`, `floor`, a bar's reason, `leg-timeout`) before the stop. R-BTN-119 is
     otherwise unchanged.
6. **The leg's side (R-BTN-72, R-BTN-106).**
   - `ctx.on(type, listener)` receives events by type, a prefix included (`on('ticket', …)`).
     `ctx.events` is an async iterator over the same events. `ctx.signal` and its three reasons
     stay as they are, so existing scripts keep working.
   - The channel gains `baton leg events [--wait <s>]`, which prints the leg's undelivered events
     as JSON lines. Like `baton leg await`, a harness that bounds tool calls calls it again.
   - A leg that wants to restart on a `continue` course calls the existing
     `baton leg release --reason ticket-changed`.
7. **§9.4's end table.** Add `released:ticket-changed` (status `released`, not a failed attempt).
   The run counts toward the leg's `max_runs` (R-BTN-63), so a ticket edited over and over is
   bounded and ends in the existing hold.
8. **The agent stubs** (`src/defaults/cli.ts`, after B-227 lands). They pass each event to the
   agent at its next tool boundary, as a message saying what changed and that the leg may
   release. That means a hook for Claude Code and the closest equivalent for opencode. The
   message never includes ticket text. The agent reads the new version itself, from git or
   through the source, if the course lets it continue.
9. **§15.** Scenario S-BTN-223 (the next free number at merge):
   - a snapshot moves a held ticket's version, and the holder is rung and the event delivered
     once;
   - `continue`: the leg runs on, and the next `advance` re-verifies;
   - `restart`: the claim ends `released:ticket-changed`, unpenalised, and the next claim reads
     the new version;
   - the leg's own push to its ticket raises no event (markdown source);
   - Stop leg delivers `release {reason: "requested"}` before the stop, and Cancel delivers
     `release {reason: "owner-cancel"}`.
10. **The vocabulary** (`docs/context/vocabulary.mdx`): one sentence for decision 1's noun.

**Second PR: the build**, items 3 to 8 in the code, with the scenario as a test.

**Done when** S-BTN-223 passes as a scenario test, `npm test` and `npm run typecheck` are green,
`baton course test` prints `on_ticket_changed` in a leg's signature, and an edit to a held
ticket's file on the default branch reaches a running leg's `ctx.on('ticket.changed')` within
one doorbell ring of the snapshot's acceptance.

### Out of scope

- **How quickly an external tracker's edits are seen.** Baton learns of a version change at the
  next accepted snapshot. For the markdown source that follows the forge's notification
  (R-BTN-73). An edit in a tracker such as Linear raises no want (R-BTN-94) until something else
  does, or until a relay calls `POST /v1/sync/want`. Making that prompt is a separate ticket.
- **Mid-leg adoption** of the new body (decision 3).
- **Other leg events** (an owner bar set, a prerequisite lapsing). The grammar admits them, and
  each needs its own rule.

### Trust

- **The version** comes from the sync's post, an attestation weighed by its writer as every
  snapshot is (R-BTN-35, R-BTN-93). A forged version change can at worst make a `restart` leg
  release unpenalised, and that is bounded by `max_runs`. It never changes what the leg runs:
  the next claim re-verifies through the source itself.
- **No ticket content crosses Baton.** The event carries two opaque versions and a sha. Ticket
  text reaches the leg only through the source's own `read` under R-BTN-5's checks, or not at
  all.
- **The stub's message to the agent** is runner-written text naming the change. It never quotes
  the ticket, so an edit cannot use the event to put text in front of a running agent.
- **The release reason** is Baton's own, from the message the runner already acknowledges
  (§6.9).

### Invariants

- **R-BTN-33:** nothing new is stored but opaque versions in a history event.
- **R-BTN-5 and R-BTN-133:** no leg ever acts on ticket text that skipped re-verification.
  `restart` and the re-check at `advance` are the only paths to a new version.
- **R-BTN-119:** the stop's timing and escalation are unchanged. The event is delivered before
  the stop, never in place of it.
- **R-BTN-160 to R-BTN-163:** conditions, bindings, handlers, Needs you and their quotas are
  untouched. A leg event is never a condition row.
- **Values 4:** versions are compared for equality only.
- **The architecture page, "Replies stay replies":** the ring carries no effect, and delivery and
  acknowledgement stay on the heartbeat.
