**What:** the three event lookups behind `/v1/ui/state` scan the whole, never-pruned `events` table.

- Add `CREATE INDEX events_by_kind_at ON events(kind, at)`.
- Recreate `events_unsigned_control` (0040:61), silently lost when 0043 rebuilt `events` (0043_part4_resources.sql:95-98 restores four indexes).
- Make the queries index-friendly: `claims.ts` 'bars-mismatch', `baton.ts` 'unsigned-control', `history.ts:117/121` 'discrepancy' — order by `at` (not `seq`) so the planner uses the index rather than walking rowids.
- Add the indexes to §13's index list.

**Target:** ui/state's events share drops from ≈3·E to the matching rows (tens).

**Why:** on 2026-11-14 production exceeded Cloudflare's free-tier Durable Objects limit of
5,000,000 `rows_read`/day at 21:41Z; every runner call returned 500 until the 00:00Z reset.
Measured on a production-sized local state (180 tickets, 600 claims, ~3k events) with
workerd's `SqlStorageCursor.rowsRead`: `GET /v1/ui/state` ≈ 14.4k rows per 10 s poll
(≈ 3·events + 2–5k), recommendations ≈ 3.7k, claim ≈ 3.8–4k, alarm ≈ 0.8–1.3k per minute,
`POST /v1/sync/board` 4–5k rows over ~2.5k statements. This ticket is one of B-235–B-243,
the owner's 2026-11-15 plan to bound what each read costs.

**Done when:** the named calls' rows_read, measured the same way in a test (cloudflare host),
is at or below the target, `EXPLAIN QUERY PLAN` shows the intended index where one is named,
and behaviour is unchanged (the existing scenarios pass).

### Trust

No new input: indexes, tables and queries over data Baton already stores; no field, file, commit trailer or request is added.

### Invariants

- R-BTN-81 (history) and the Needs-you lists: the same rows in the same order; only the query plan changes. The existing scenarios and an EXPLAIN QUERY PLAN test check it.
