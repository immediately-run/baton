**Brief:** the owner, 2026-11-23, asked for this ticket ("yes, file the ticket") after signing in to `baton.immediately.run` with Cloudflare Access failed with the sentence above. The cause was that production had no `ACCESS_TEAM_DOMAIN` or `ACCESS_AUD`: `wrangler.toml` sets neither, and a deploy rewrites the Worker's variables from that file. Setting both as secrets fixed it. The page gave no hint of that. It shows the same sentence for every `unauthenticated` answer to `POST /v1/login {access: true}` (`src/dashboard/app/SignIn.tsx`).

**Spec:** [BATON_SPEC §11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) ([R-BTN-155](../spec/BATON_SPEC/11-people.md#sec-11-4), *Sign-in through Cloudflare Access*). The rule lists the refusals and says each is `unauthenticated` and sets no cookie. This ticket amends it to name a `reason` with each.

**Depends on:** none.

### What to build

Today the five causes become one answer in two places:

- `verifyAccess` (`src/core/auth.ts`) returns `null` when the Worker has no `ACCESS_TEAM_DOMAIN` or `ACCESS_AUD`, when the request has no `Cf-Access-Jwt-Assertion`, and when the assertion does not verify or carries no usable email. The front (`src/core/front.ts`, the `/v1/login` branch) then forwards the request with no email.
- `login` (`src/core/admin.ts`) answers `unauthenticated` with the same message for no email, an email with no line, and a line naming a key that is not an administrator's.

The change:

1. **`verifyAccess` says why it found no email.** It returns the email or one of three refusals:
   - `not-configured`: the Worker has no `ACCESS_TEAM_DOMAIN` or no `ACCESS_AUD`.
   - `no-assertion`: the request has no `Cf-Access-Jwt-Assertion`, so Access does not cover `/v1/login` on this hostname.
   - `unverified`: the assertion failed verification (signature, issuer, audience, expiry), or its `email` claim is missing or not ASCII.

   A failure to fetch the team's keys stays `unavailable`, as now. Its other caller, the legacy `verifyOwner`, keeps its behaviour: it reads only whether there is an email.
2. **The front refuses those three itself.** In the `/v1/login` branch, a request with `access: true` and no email is answered `unauthenticated` with `{reason}` in the error body (`BatonError`'s `extra`), without forwarding to the core. A `{token}` login is unchanged.
3. **The core names the binding refusal.** In `login`, both binding refusals (no line for the email, or a line naming a key not in `BATON_ADMIN_KEYS`) answer `unauthenticated` with `{reason: "not-bound"}`. They stay **one** reason: the caller must not learn whether an email has a line (S-BTN-308). A malformed `ACCESS_IDENTITIES` stays `unavailable`.
4. **The page draws one sentence per reason**, in `SignIn.tsx`, as text (§12.3). The one-time link stays offered under every one. The wording is the implementer's, in this sense:
   - `not-configured`: this Baton has no Cloudflare Access settings, `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD`, so whoever deploys it sets them, as secrets so a deploy keeps them.
   - `no-assertion`: no Cloudflare Access token reached Baton, so Access does not cover `/v1/login` on this hostname.
   - `unverified`: the Access token did not verify. `ACCESS_AUD` or `ACCESS_TEAM_DOMAIN` may not match the Access application, or the Access session has ended and you sign in to Access again.
   - `not-bound`, or no reason (an older Baton): today's sentence, adding that the binding is a line of `ACCESS_IDENTITIES` naming a key in `BATON_ADMIN_KEYS`.
5. **Amend R-BTN-155** in `spec/BATON_SPEC/11-people.md`: the refusal carries `reason`, with exactly these four values, and `not-bound` covers both binding failures. Then run `npm run spec:index` and record the amendment in `spec/BATON_SPEC_HISTORY.md` as its other entries are.
6. **Runbook.** In `docs/runbooks/register-baton.mdx` step 2, say to set `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` with `wrangler secret put`. That is the cause this ticket came from: `wrangler.toml` sets neither, and each deploy rewrites the Worker's variables from it.

Out of scope: owners' sign-in and sign-in by code (B-76, B-206), and any change to what a session authorizes.

### Trust

- **No new input.** The reason is computed from the request and the Worker's own configuration. No header carries it from the front to the core, so `PRINCIPAL_HEADERS` gains nothing. The front answers the first three refusals itself.
- **What an unauthenticated caller learns.** Anyone can click the button. `no-assertion` and `unverified` describe the caller's own request. `not-configured` says the Worker has no Access settings. That is configuration, not a secret, and Access's own redirect already shows whether a hostname is behind Access. `not-bound` is one value for both binding failures and echoes no email, so the answer still says nothing about which emails have a line or what key a line names.
- Nothing about a refusal is stored. The sign-in event (`{act: "login", via: "access"}`, the email's SHA-256) is written only on success, as now.

### Invariants

- [R-BTN-155](../spec/BATON_SPEC/11-people.md#sec-11-4): a refusal sets no cookie, the email is never stored and never echoed, and a malformed `ACCESS_IDENTITIES` is `unavailable`.
- R-BTN-16: inbound principal headers are still stripped, and `/v1/login` still requires a state-changing request from this Baton's own page (`checkStateChanging`).
- §12.3: the dashboard draws every value as text, with no `innerHTML`.
- `verifyOwner`'s legacy path, used while `BATON_ADMIN_KEYS` names no key, is unchanged.

### Tests

Take a new scenario id with `baton tickets next scenario` and name it in each test.

- `verifyAccess`, with the test key set (`TEST_ACCESS_JWKS`): no team domain or audience gives `not-configured`, no header gives `no-assertion`, a wrong audience or an expired token gives `unverified`, a token with no email gives `unverified`, and a good one gives the email.
- `POST /v1/login {access: true}` through the front gives each of the four reasons in the error body, and sets no cookie for any of them.
- `not-bound` comes back the same for an email with no line and for a line naming a non-administrator key, with the same message. Neither answer contains the email.
- `test/ui/shell.test.tsx`: each reason draws its sentence, the one-time link is offered under each, and S-BTN-308 still passes. A refusal with no `reason` draws today's sentence.

### Exit criteria

- [ ] R-BTN-155 names the reasons, and the index and history are updated.
- [ ] The runbook says to set both Access values as secrets.
- [ ] `npm test` and `npm run typecheck` pass.
