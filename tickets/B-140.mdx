> **The specification is BATON_SPEC §12.8 (R-BTN-180 to R-BTN-189, baton#134, baton#145).** Where
> this ticket and the spec differ, the spec wins. The plan below was rewritten on 2026-10-31 for
> the repository policy; the brief and the owner's statements are kept as written.

**Brief:** the owner, 2026-10-28, on keeping runners from writing Baton's state on every forge and
on plain git, without a git proxy or per-worker forks: "explore with me the idea of having a
protected main branch … a dedicated runner type, which runs only deterministic code, picks up
tickets on a merged main leg and merges them when they are ready. It's essentially taking the merge
approval logic out of GitHub and placing it into Baton at the cost of having a deterministic
trusted runner executing somewhere." Then: "What I like about this design is that the PR branch
merge leg can be customized as necessary. On a per project or per course basis."

**The model** (`docs/security-model.mdx`, *The core guarantee*), now stated as the repository
policy's knobs (R-BTN-188) rather than a mode: runners propose and the merge runner lands
(`refs.default_branch`, `merge.trusted`); what Baton's state depends on lands as `paths.control`
and `paths.tickets` say; status, claims and course history live in Baton.

**Spec:** R-BTN-180 (refs, `baton repo protect`, the protection checker, proposals and the
proposal merge), R-BTN-182 (trusted runners: the role, no repository code, pins, the refusal-only
override), R-BTN-183 (what the merge runner merges), R-BTN-184 (protected paths), R-BTN-187 (what a
trusted leg reads), R-BTN-188 (`merge.*`, `paths.*`, `authorship`, `refs.*`, `grants.trusted_domain`),
R-BTN-189 (pins); R-BTN-131 (the standard courses' `merge` leg), R-BTN-134 (sources); B-136, B-138,
B-139, B-141; FLDH-37, FLDH-43.
**Depends on:** B-145 (the policy the merge runner reads), B-146 (attestations it acts on), B-147
(the trusted-runner role and trust domains).
**Waits on:** R3-1266 (Baton holds claims and status, so no runner needs to push the default
branch).

### What to build

1. **The merge runner** is a grant with the trusted-runner role (B-147). It claims only legs its
   course marks `trusted: true` (the standard courses' `merge`; rule `trusted`), runs a CLI release
   installed by tarball integrity (B-138), and executes nothing from the repository: no install,
   build, hook or repository script; it reads git objects and Baton's records only (R-BTN-182).
2. **What it merges** (R-BTN-183), at the PR's exact head `H`, every rule read from the policy:
   - `merge.reviews`: `count` `std:review@1` at `H`, each from a trust domain other than every
     writer domain of `H` (`std:wrote@1`, `std:ran@1`), from a review claim that started at `H`,
     differing in each field `distinct` names; null domains and families never count as distinct;
   - `merge.checks: required`: a `std:checks@1` at `H`, or check runs whose workflow file is on the
     protected default branch with the same blob as at merge time;
   - `authorship: signed`: every commit in every attested range signed by its leg's key;
   - continuity: a writing claim's start head is the last attested head; a commit no claim
     reported resets the branch and raises `baton.foreign-commit`;
   - paths: `git diff-tree -r -z --no-renames --name-only` from the default branch's tip to the
     merge result plus each `merge-base --all` diff; a symlink, submodule or `.gitmodules` change
     refused; matched case-folded and NFC-normalised against `paths.protected` plus the computed
     floor (R-BTN-184);
   - control paths as `paths.control` says: `human` ends the leg at `human-merge` and recognises
     the human's merge from the forge; `trusted-runner` merges with a `std:approval@1`; `any` merges
     as any path does;
   - tickets and goals, under `paths.tickets: approval`, only with a `std:approval@1` at `H` whose
     `paths` and `blobs` cover every protected path changed; a leg's own progress after `## Status`,
     by R-BTN-184's grammar, needs none;
   - leg state (R-BTN-190): a work branch whose merge result, or any commit in the ticket's ranges,
     holds a path segment at any depth that after NFC normalisation and case folding is
     `.baton-legs` is refused; it never merges a `baton-legs/*` branch, and a push there is no
     write (no range, no foreign-commit reset);
   - how: squash or merge at exactly `H` with the base pinned (a compare-and-swap push), a commit
     message it writes itself; a branch that moved since an attestation was made is refused.
   Every attestation is fetched, verified against the pins, its subject compared with the exact
   object, and a `once` attestation consumed by compare-and-swap (R-BTN-182).
3. **The proposal merge** (R-BTN-180): it merges `baton/proposed/<ticket>` when every commit on it
   since the merge base is a deliverer's template write for that ticket's outbox entries (B-64),
   touching only the paths they name, and one `std:approval@1` whose subject is that ticket at that
   commit covers exactly those paths and blobs; R-BTN-183's paths, protected-path and leg-state
   refusals apply (a control path never lands this way), and `merge.reviews`, `merge.checks`,
   `authorship` and continuity do not. The ticket merge (R-BTN-183's built-in trusted leg
   `baton.ticket-merge`, a marker course's work branch on the owner's approval) is B-149's, built
   on this runner.
4. **The course override** `legs/merge.run.mjs` only adds refusals: it runs in a sandbox with no
   network, no credential, a private PID namespace, the computed diff as its only input and a fixed
   time, and returns `{refuse, reasons}` from a closed list; where no sandbox is available it is
   refused, not run (R-BTN-182).
5. **Pins** (R-BTN-182, R-BTN-189): its own configuration pins the `human_only` public keys, Baton's
   attestation key, the tenant signing keys, and the hashes of the policy and its floors. It reports
   its pins in each heartbeat and acts on nothing in the repository while one differs from Baton's
   (`baton.policy-unpinned`); it verifies signed policy reads against its pinned keys, checking
   `repository` and `tenant`.
6. **`baton repo protect`** (R-BTN-180): `--print <forge>` derives the forge setting from the
   policy's `refs.*` and `paths.control`:
   - GitHub (an organisation): branch and tag rulesets whose only bypass actors are the trusted
     runners' dedicated App and a team holding only the human-only identity; `refs/baton/*` cannot be
     restricted;
   - GitLab protected branches and tags (a deploy key on GitLab Free); Gitea and Forgejo protected
     branches with a whitelist; plain git a `pre-receive` hook on a server that knows the pusher
     (`baton repo hook pre-receive`), keeping a pusher log, and refusing default-branch updates
     that add such a segment, and admitting `baton-legs/*` as the policy's `refs.legs` says
     (R-BTN-190);
   - the protection checker mode also reads the default branch's tree for such a segment and reports
     it as `legs: {count, tickets}` in its heartbeat's `protection`, the reading that alone raises and closes `baton.leg-state-landed` where a checker exists
     (B-148).

   `--check <forge>` reads it back and returns `{matched, reading_hash}`; it does not match while a
   class the forge cannot restrict excludes any writer. On GitHub it needs the credential that reads
   `bypass_actors`, which can also write rulesets: it runs only in the **protection checker** mode
   (`baton run --role protection-checker`, a trusted runner named by `approvers.trust`, claiming no
   leg and holding no merge credential), never as a workflow and never beside the merge runner; that
   mode reports in its heartbeat's `protection` at least hourly. Verify whether a narrower GitHub App
   permission suffices.
7. **Where it runs**: a GitHub Actions workflow on the default branch (its credential in an
   environment limited to the default branch, without reviewers), or a process in a trust domain of
   its own (`baton run --role merger`); under `grants.trusted_domain: separate` that domain is shared
   with no other grant (B-147). Where no agent session runs is the deployment's duty (FLDH-43).
8. **The secrets rule is a precondition** (FLDH-37): where any `refs.*` admits `runner`, no
   repository-level secrets; every secret, the merge runner's included, in an environment limited to
   the default branch (R-BTN-180).

### Do not

- Read a merge criterion from a course file, a PR comment, a trailer or a board post: they are the
  policy's and git's (R-BTN-183, R-BTN-187).
- Hold the protection checker's credential in the merge runner, or run the checker as a workflow.
- Load `.baton/tickets.mjs` or any repository code, delivering proposals included.
- Merge a commit other than the exact head, or a proposal carrying anything but template writes.

### Tests

- **S-BTN-183** (what merges), **S-BTN-184** (protected paths under `paths.control: human` and
  `paths.tickets: approval`), **S-BTN-182** (trusted runners), **S-BTN-180** (refs from the policy,
  `--check` and `baton.unprotected`), and S-BTN-191's proposal-merge and checker cases, on both hosts.
- A drill per environment, scripted: a runner identity's push to the default branch is refused by
  the GitHub ruleset, by a Gitea protected branch, and by the `pre-receive` hook; `--check` matches
  each, and stops matching after a hand edit.

- [ ] the scenarios pass on both hosts; the drills pass

  human-only identity, and a protection checker reporting
- [ ] `npm test`, `npm run typecheck` and `npm run check:spec` green; merged under the review gate
