**Brief:** the owner, 2026-11-08, ruled that Fieldhouse's first edition does not guard against a
compromised runner whose legs all run in sandboxes, and agreed to count review independence by a
label the runner attests for each leg's sandbox, over a second dispatcher or over dropping the domain rule
(FIELDHOUSE_SPEC R-FH-80, R-FH-82 and its Decisions, 2026-11-08). With one runner credential,
today's rules refuse that runner its own review legs.

This is a proposal: the spec half lands first, as its own spec PR, with the owner's approval.

**Spec:** [BATON_SPEC §12.8](../spec/BATON_SPEC/12-security.md#sec-12-8) ([R-BTN-180](../spec/BATON_SPEC/12-security.md#sec-12-8),
[R-BTN-181](../spec/BATON_SPEC/12-security.md#sec-12-8), [R-BTN-183](../spec/BATON_SPEC/12-security.md#sec-12-8),
[R-BTN-189](../spec/BATON_SPEC/12-security.md#sec-12-8): `independent-review`, `merge.reviews`),
[§8.3](../spec/BATON_SPEC/08-runners.md#sec-8-3) (`no_chain_from`), [§1](../spec/BATON_SPEC/01-what-baton-is.md#sec-1)
([R-BTN-46](../spec/BATON_SPEC/01-what-baton-is.md#sec-1)).
**Depends on:** B-185 (the run id a per-run label is bound to). Works with any executor; what a label stands for (a sandbox, a VM,
a container, nothing) is the deployment's, and Baton never learns it.
**Used by:** FIELDHOUSE_SPEC R-FH-82 (its section 5), FLDH-53's findings.

### What to build

1. **A grant may be `domain: per-run` — a policy change.** Marking a grant `per-run` changes what
   `independent-review` means for its work, so it is a change to the repository policy, governed
   by `approvers.policy` (R-BTN-186), not a role setting: the policy gains `domains.per_run:
   [fingerprints]`. `independent-review`'s *holds when* gains "and `domains.per_run` is empty", so a
   floor on it refuses the change. A new, weaker guarantee `independent-runs` promises the same
   two reviews with per-run domains admitted, and states what it does not withstand: a
   compromised runner of a per-run grant, and — under `builtin`, where any leg can read the runner's
   key (R-BTN-144) — a hostile leg acting as that runner; it holds only as far as the deployment
   keeps runs apart from each other and from the runner; a
   deployment that accepts per-run domains floors `independent-runs` instead. Such a grant's runner reports a `run_label`
   once per run, on the `advance` that starts it (the run's label is then stored; the finishing
   `advance` or `end` needs none, and an `advance` that both finishes one run and starts the next
   carries the new run's label); a missing label is refused `invalid-params`. A refresh (R-BTN-123)
   keeps its run's label. The label comes only from the runner's own call, never through a leg's
   channel (B-184 item 2).
2. **The per-run domain** is `<grant fingerprint>/<run label>`, the label 1–128 characters of
   `[A-Za-z0-9_.:-]` (opaque: an executor's per-run `instance`, B-184 item 7 — not its `environment`, which may
   repeat across runs). It is stored on the run's
   `claim_legs` row beside B-185's `run_id`.
3. **A label is used once.** Baton refuses (`invalid-params`, rule `label-reused`) a label any
   earlier run of the same grant reported, on any ticket, so a label that named one run cannot
   name another.
4. **Attestations carry the per-run domain.** `std:wrote@1`, `std:ran@1` and `std:review@1`
   (R-BTN-181) from a per-run grant carry the run's domain; R-BTN-183's independent review
   compares those, unchanged otherwise: each review from a domain other than every writer domain
   of `H`, no two from one domain.
5. **`no_chain_from` compares per-run domains** for a per-run grant: a review leg is refused only
   when its run's domain is one that ran a named leg of the ticket, which a fresh label never
   is. For every other grant it compares credentials, as today.
6. **Shown on the record.** The ticket's history (R-BTN-81) and the dashboard show a run's per-run
   domain, so an owner sees that a review ran under a label no writer used.

### What not to do

- **No verification Baton cannot do:** Baton checks a label's shape and its single use, never that
  it names anything real or fresh (R-BTN-46; R-BTN-180: "Baton compares domains as labels and
  verifies nothing about them").
- **No isolation vocabulary:** the API, the schema and the dashboard say `run_label`, never
  sandbox, VM or container (B-184's agnosticism).
- **No pretence about `no_chain_from`:** for a per-run grant it can never refuse — labels are
  single-use and the claim-time check runs before a label exists — so marking a grant per-run
  disables `no_chain_from` for it; independence then rests on per-run domains and the policy's
  guarantees alone, and the policy view says so.
- **No change for grants not marked `per-run`.**
- **No per-run marking of a `trusted-runner` grant** (the merge runner stays one labelled domain).

### Trust

- **`domains.per_run`** — a policy knob, changed only through `approvers.policy` and checked
  against the floors (R-BTN-189).
- **The `run_label`** — the runner's word. Marking a grant `per-run` is the owner's statement
  that the runner is trusted to report it honestly (FIELDHOUSE_SPEC R-FH-80); a compromised
  per-run runner can forge independence, which is exactly the risk that ruling accepts.

### Invariants

- **R-BTN-189's guarantees keep their meaning for labelled grants.** For a per-run grant only
  `independent-runs` can hold, and only as far as the deployment keeps runs apart from each other
  and from the runner — Baton cannot tell — never against a compromised runner. The spec PR
  amends R-BTN-189's "Every guarantee holds against a compromised runner" and §12.8's *Outside
  every guarantee* list to say so, and the policy view shows it beside the guarantee.
- **`independent-review` is unchanged in strength:** it is never held while a grant is per-run.
- **Validate before you write:** the label goes through `src/core/validate.ts` before SQL.
- **Migrations are append-only:** one new file for the column.
- **Filter fields only** (R-BTN-33).

### Tests

- A per-run grant implements and then reviews one ticket under two labels: the review is admitted,
  and two such reviews satisfy `merge.reviews {count: 2}`.
- The same grant reporting a label twice is refused `label-reused`.
- With `domains.per_run` non-empty, `independent-review` computes as broken and `independent-runs` as
  held; with it empty, both behave as `independent-review` does today.
- A floor naming `independent-review` refuses the policy change that adds a per-run grant; a floor
  naming `independent-runs` admits it.
- A per-run grant omitting the label on `advance` is refused.
- A labelled grant behaves exactly as today (the existing scenarios pass unchanged).
- Each behaviour change names its `S-BTN-n` scenario (R-BTN-31).
