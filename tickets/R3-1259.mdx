**Brief:** [the Baton project](projects/baton.mdx); the owner, 2026-10-15: recurring jobs such as the
decision-packet routine as Baton courses, one child ticket per run; legs that time out or are
cancelled administratively.
**Spec:** `docs/content/specs/BATON_SPEC.mdx` §2j (R-BTN-89, R-BTN-90), R-BTN-69
(`max_duration`), R-BTN-74 and §7.1 (`not_before`), R-BTN-83 (the closing marker's
`not_before=`), §4 (`ticket_next_legs.not_before`, `ticket_next_legs_due`, `claims.deadline_at`,
`claims.cancel_at`, the `leg-timeout` and `not-before-invalid` events), §3 (the alarm), §6.5, §6.6, §6.10,
§9, §11, R-BTN-68 (the model), §13a S-BTN-51, -52; §16 G-BTN-79, -80
**Depends on:** R3-1257 (positions and closing markers, which carry `not_before`), R3-1258
(child tickets, which series use)

### Requires

- none — every case runs in the integration harness with fixture course files and a fake
  clock.

### Why

A recurring job — the decision-packet routine, a weekly audit — should run on a course like any
other work, with Baton's leases, history and dead-ticket queue, which needs a leg that waits
for a time. A leg that overruns, or an owner who wants work stopped at a set time, needs a
deadline Baton enforces by taking the claim away. Tier: critical — the deadline and its reap
change the lease paths.

### What to build

1. **Migration** (one new numbered file): `ticket_next_legs.not_before` and the
   `ticket_next_legs_due` index (`state = 'waiting' AND waiting_on = 'time'`); `claims.deadline_at`,
   `claims.cancel_at`; the events CHECK's `leg-timeout` and `not-before-invalid`.
2. **Time waits** (`src/core/time.ts`): validate `not_before` on a ticket and on a station's
   queued leg, and on `end`, in `src/core/validate.ts` (RFC 3339 with `Z` or an offset, at most
   `NOT_BEFORE_HORIZON_DAYS` (400) after `now`, the one constant shared with `baton/leg`;
   otherwise logged and a posted `ready` leg waits on `not-before-invalid`, under Needs you); a past value stored as NULL; the station's value wins over the ticket's; store `waiting` on `time` only over a posted `ready`, in every transaction that
   writes next legs, exempt from `waiting_since` and Needs you, `time` reserved; the alarm, set
   early to the earliest pending instant, readies due legs (`ready_since` = `not_before`,
   `not_before` cleared), drops the repository's cached recommendations and queues `unblocked`
   with `cleared: [{kind: 'time'}]` to the idle workers the ticket would pass the gates for, with
   no workflow dispatch (the ring once R3-1260 lands); `not_before?` in the `next` entries of the
   heartbeat, claim, adopt and advance responses; the dashboard's "waiting until" and the
   Courses view's list of pending waits.
3. **The CLI**: `nextFire(cron, tz, after)` and `writeSuccessor(ctx, {schedule})` in the
   leg-script module `baton/leg`, with `NOT_BEFORE_HORIZON_DAYS`, which both enforce;
   `writeSuccessor` commits the next run's ticket file on the default branch before the run's
   closing commit, with the same `parent`, `run: <n+1>`, the id `<series>-<n+1>` and its
   `not_before`, and `depends_on` naming the current run; it writes nothing if that file exists
   as this series' run (`parent`, `run`), and fails `cannot-finish:spec` on a foreign file or an
   over-long id; `not_before?` in the leg result,
   validated by the runner, written by `close` and reported on the `end`; the default
   markdown ticket source's `not_before` field and the default `locate`'s decoding and posting
   of the closing marker's `not_before=`; the default
   `series` course (`active`, `retired`, leg `retire`); the runner suspending on a `time` wait
   more than 30 minutes away and waiting under the claim otherwise.
4. **Deadlines** (`src/core/deadlines.ts`): `max_duration` validated in the course file (60 to
   604,800); `deadline_at` set at each `advance`, re-armed to now + 40 minutes by the
   heartbeat's `leg_finished` (the runner sends an immediate heartbeat when the leg's `run`
   returns; it withdraws a still-pending `leg-timeout` release, the message `expired` with
   `withdrawn: 'leg-finished'`), cleared by the next advance and the end; the alarm
   queuing `release` `leg-timeout`, reaping an unacknowledged one with a fence after 15 minutes
   (actor `alarm:leg-timeout`, a failed attempt), and running a scheduled Cancel at
   `cancel_at`; `released:leg-timeout` as a failed attempt.
5. **Owner route and display**: `POST /v1/owner/{repository}/claims/{id}/deadline`,
   `baton owner deadline` (`extend_to` refused with no deadline or once the release is queued;
   `cancel_at` within 7 days, lapsing with the claim, logged); `deadline_at` and `cancel_at` in
   the heartbeat's claim and on the dashboard's claim row.
6. **The model** (R-BTN-68): `model/` in the same PR — the `leg-timeout` release and its fenced
   reap as Baton actions, `leg_finished` clearing the deadline, and the properties that every
   fence clears and no leg finished inside its budget is timed out *(review gate round 1)*.

### Architecture — the decisions, named

- **Time is git data**: Baton reads `not_before` from what the sync posts and never computes a
  schedule; a leg script turns cron into instants.
- **One clock**: every comparison uses `this.now` (R-BTN-32); tests set it with `setClock`.
- **Do not**: loop a ticket through a timed leg; complete a leg from Baton; count a `time` wait
  toward `baton:stalled`; refuse a claim for a `time` wait beyond what rule 1 does for any
  waiting leg.
