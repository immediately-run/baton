**Brief:** the owner, 2026-10-31, in a design session on Fieldhouse's courses, on being shown that
the marker courses cannot run under the strong policy: "This seems like a pretty serious issue.
Please address this now."

**Spec:** `spec/BATON_SPEC.md` §5 R-BTN-131 (*One ticket, one PR, one merge*, the course table,
`spec-to-tickets`, `build-app`), R-BTN-5, R-BTN-116 (the answer as output), R-BTN-192
(`merged-by-hand`'s `pr-merged`); S-BTN-104, S-BTN-107, S-BTN-194.

**Depends on:**
- B-120: course history in Baton, and fact legs.
- B-140: the fact reader, which attests `pr-merged` under `protected`.
- B-7: person legs (`decision`'s `answer`).
- B-62: call legs (`build-app`'s `stages`, `file`, `verify`).

Under `cooperative` the sync attests `pr-merged`, so the PR courses can be built and tested before
B-140.

### Why

The five marker courses cannot run on a home whose default branch is protected.

- **The code.** Every marker leg's `close` commits the ticket on the default branch and pushes it
  (`src/defaults/ticket-state.ts`, `PUSH_TRIES`), retrying only a refusal because the branch moved.
  Each leg also commits its own work there under its `## <leg>` heading; `build-app` writes
  `product/<ticket>/`; `bug-report`, `draft-ticket` and `spec-to-tickets` file new ticket files.
- **The spec.** Under `merge.trusted`, "no course commits to the default branch" (R-BTN-188,
  R-BTN-180). R-BTN-180 routes what a runner's action *creates* through proposals, but gives no
  route for a marker leg's record, `build-app`'s documents, or the tickets these courses file.
  `create-spec`'s `converse` and `address` no longer write frontmatter (B-120 moves their state to
  course history), so they need nothing here.
- **The ticket that held it.** B-130 item 4: "No course writes main directly …", with the exit
  criterion "the standard courses file tickets by PR; no course commits to a default branch".
  B-130 was superseded on 2026-10-31 without it. This ticket takes item 4 back.
- **Who it hits.** Under the `protected` and `protected-signed` presets every marker leg fails at
  its close once the rulesets `baton repo protect` prints are applied. FLDH-42 applies them to
  `fieldhouse`, `docs` and `baton`; docs runs `bug-report`, `draft-ticket` and `decision`.

### What the owner has decided

- **2026-10-31:** the standard courses must run under Baton's strongest preset; no hardened
  copies in other homes.
- **2026-11-01,** after four drafts and five review rounds on routes that kept a "marker"
  course: "Would it be possible to simplify the spec by eliminating this type of course entirely
  and tying every course to a ticket file in Git?" The owner then agreed to one ticket, one PR,
  one merge, with `build-app` as a parent ticket. The earlier choices still hold:
  - a PR under every policy;
  - `decision` answered in Baton, then merged;
  - each approval a merge.

  The history entries dated 2026-10-31 and 2026-11-01 in `spec/BATON_SPEC_HISTORY.md` record
  each draft and why it was dropped.

### What to build

1. **The close commits on the ticket's branch.** The close of each leg of `bug-report`,
   `draft-ticket`, `decision`, `spec-to-tickets` and `draft-doc`:
   - commits the ticket and its outputs on the ticket's branch, the first push opening the PR
     (as `create-pr`'s `implement` does);
   - never pushes the default branch, and writes no `status:` (`src/defaults/ticket-state.ts`);
   - validates against `item.schema.json` read from the default branch.
2. **The course files** (`src/defaults/courses.ts`), as R-BTN-131's table gives them:
   - `merged-by-hand` on each PR course;
   - the send-back edge with `max_runs` 3 on each last writing leg;
   - `decision`'s `answer`, its `carried` (settled) route and its re-ask route;
   - the new `draft-doc` course;
   - `build-app` as `stages`, `file`, `verify`.
3. **Reading at the branch head.** The runner reads the body and inputs at the ticket's branch
   head (R-BTN-5), and so do the station functions. The applied answer is the person leg's output
   `answer`.
4. **`build-app`'s `stages` script.** It files the four `draft-doc` children, one per document,
   each `depends_on` the one before. `file` reads the merged `PLAN.md`.
5. **Leg instructions.**
   - Every leg's `.md` commits to the ticket's branch, never the default branch, and sets no
     `status:`.
   - `draft-doc`'s `write` carries `build-app`'s four drafting instructions, chosen by the
     document the child names, and its *The conversation* ends with the owner's merge, not
     `answer:`.
   - `decision`'s `prepare` asks through Baton and reports `carried` when the question is
     settled.
   - `carry-out` reads its input `answer`, only records and files, and reports `asked` to re-ask.
6. **Migration**, tested on a fixture per row:
   1. Land the new course files. A live ticket whose queued leg the new file lacks waits on
      `course-changed` (R-BTN-83).
   2. Place each such ticket with `baton owner ticket adopt`:
      - `decision` at `asked`: `answer` queued.
      - `build-app` at `requested`, `defined`, `designed`, `architected` or `planned`: to
        `requested` with `stages` queued. Its script skips any stage whose document the default
        branch already holds and that the git `answer:` approved.
   3. Records already on the default branch stay, and the ticket's next leg opens its branch.

   If R-BTN-64's course test refuses the new file while such tickets are live, place them first
   on a transitional file that keeps the old edges beside the new ones, then remove those edges.
7. **The docs.** In `docs/standard-courses.mdx`, *How each course finds where a ticket is* and
   *`build-app`, step by step*.

### Tests

### Do not

- Push the default branch from any leg of a standard course, under any policy.
- Give one ticket a second approval: a course that needs several is several tickets.
- Copy the standard courses into Fieldhouse or any other home as hardened variants.
