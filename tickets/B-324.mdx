**Found by:** the supervising session, 2026-11-23–24 (handover `docs/plans/supervisor-handover-2026-11-24.mdx`, open investigation 1). This is a defect report, not an owner brief.

**Spec:** [BATON_SPEC §5.3](../spec/BATON_SPEC/05-courses.md#sec-5-3) [R-BTN-63](../spec/BATON_SPEC/05-courses.md#sec-5-3) (`max_runs` bounds the runs made without a person), [§5.8](../spec/BATON_SPEC/05-courses.md#sec-5-8) (the standard courses' stubs); B-110 (the round that reaches the file's `max_runs` queues `adjudicate`).

**Depends on:** none.

### What is wrong

The `create-pr` review stub decides when the review rounds run out from a number baked in when the stub was generated, not from the course file in force:

- `src/defaults/courses.ts` builds the review leg's `position` from `CREATE_PR_COURSE.legs.review.max_runs` — 3, in `src/defaults/course-pr.ts` — and writes the literal into the stub.
- `.baton/courses/create-pr/legs/review.mjs` therefore hard-codes `(ctx.run ?? 1) >= 3 ? { suspend: true } … 'adjudicate'`.
- On 2026-11-22 (`d8b3fdf3`) the owner raised `review.max_runs` to 8 in `.baton/courses/create-pr/course.json` only.

So every third round that asks for changes ends the claim `suspended:reviewed`, next `adjudicate`, waiting on the owner, while Baton — which reads 8 from the file — shows `fix` next. This is the main reason the course merges almost nothing on its own: tickets park at round 3 for an owner answer the owner did not ask to give.

### What to build

1. The review stub reads the bound from the course in force — the leg context's course graph (`review.max_runs`) where the runner passes it, else the course file beside the stub — and falls back to the default only when the file names none. No round count is a literal in a generated stub.
2. Regenerate `.baton/courses/create-pr/legs/review.mjs` (and any other stub that bakes a `max_runs`: check `review-pr` and `create-spec`).
3. A test, under the scenario that covers B-110's adjudication bound (or a new `S-BTN-n` if none fits): a course file with `review.max_runs: 8` and a changes verdict at run 3 queues `fix`, not `adjudicate`; at run 8 it suspends and queues `adjudicate`.
4. A check — in `npm test` or the course check — that fails when a stub's bound and its course file's `max_runs` can disagree.

### Exit criteria

- With `course.json`'s `review.max_runs: 8`, round 3's changes verdict queues `fix` and round 8's queues `adjudicate`.
- No generated stub carries a `max_runs` literal.
- `npm test` and `npm run typecheck` green.

### Not in scope

Clearing the tickets already parked at `adjudicate` by round 3: that is the owner's `resolve`/route, listed in the handover.

### Trust

No new input. The bound is read from the course file in force, which Baton already reads from git and which only reviewed pushes change; the stub reads nothing a runner or ticket author supplies beyond what it reads today.

### Invariants

- R-BTN-63: `max_runs` bounds the runs made without a person; the stub and Baton now read the same number, so the stub's `adjudicate` and Baton's station agree.
- R-BTN-37: no vendored copy is edited by hand; any vendored stub source changes at its source, then `npm run vendor`.
