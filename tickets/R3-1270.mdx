**Brief:** the Baton project; the owner, 2026-10-16: runners are fully trusted to sync the tickets from git, none of it required of them.
**Spec:** `spec/BATON_SPEC.md` §8.2 R-BTN-102 (sync under a machine key, `posted_by`, `baton.machine-post`) and R-BTN-146 (active grants, span), §3.2 R-BTN-93 (one verifier for sync routes), §12.1 (principals), §13 (`board_snapshots.posted_by`, `repositories.machine_sync`), §14, §15 S-BTN-59
**Depends on:** R3-1263 (pulled syncs: `/v1/sync/want` and `/v1/sync/wanted`), R3-1269 (the migration this extends)

### Requires

- none.

### Why

Today a board can be posted only under a sync key or a CI identity token
(`verifySyncCredential` in `src/core/auth.ts`, R3-1262's sync keys). A plain git server should
need no server-side component, so a runner that already holds a grant must be able to post its
repository's board. The owner accepted that any agent on such a machine can then post a board
that matches no commit; the spec bounds it by recording and listing, not refusing. Tier:
critical — authentication.

### What to build

1. `/v1/sync/observation`, `/v1/sync/board`, `/v1/sync/want` and `/v1/sync/wanted` accept a request signed by a machine key (credential kind `runner`, still `worker` in the code until B-68) with `?repository=<id>` in the signed query, no runner secret, role `sync` only; `/v1/sync/events` and the mirror's routes refuse it `forbidden`.
2. Refused `forbidden` when the key holds no unrevoked grant on the repository, or the repository policy's `inputs.board` excludes `machine` (R-BTN-93, R-BTN-188), read through `src/core/policy.ts` (B-145; until it lands, `inputs.board` defaults to the `cooperative` preset's, which admits `machine`).
3. No settings route: whether a machine key may post is a policy change, made by an approver on `approvers.policy` (B-145).
4. Every accepted or held board post stores `posted_by` (the credential's fingerprint, or the CI identity), and its `snapshot-accepted` event names it.
5. A machine-key post that closes a ticket another runner holds, drops a posted bar, lowers a tier, drops a `requires` clause (or, during R-BTN-132's window, `operator_only`), or removes a `ticket` block or a decision raises `baton.machine-post` naming the tickets and the key — through today's `needsYou()` path if this lands before B-57, which converts it.

### Architecture — the decisions, named

- **One verifier still answers every sync route**: extend the existing path that turns a sync request into `{repository, role}` so a machine key is one more credential kind it tries; no route checks keys itself (R-BTN-93's rule).
- **The loosening check is a pure function** `loosenedBy(before, after)` in `src/core/board.ts`, comparing the outgoing and incoming `TicketRow`s the snapshot transaction already holds; it returns the ticket ids and what loosened. The transaction calls it only when the poster is a machine key.
- **Owner and administrator keys stay out**: a key that is both granted as a runner and listed in `repository_owners` or `BATON_ADMIN_KEYS` is already impossible (R-BTN-57); do not relax that check.
- **Do not**: let a machine key mirror; accept `?repository=` from an unsigned part of the request; refuse a loosening post (it is raised, by the owner's decision); require a runner secret on sync routes.

### Tests

- `test/unit/auth.test.ts`: a machine key with a grant passes as `sync` for that repository and fails for another; with `machine` out of the policy's `inputs.board` it fails; at `/v1/sync/events` it fails.
- `test/unit/board.test.ts` (new): `loosenedBy` over fixture rows built from the real `rowForTicket`, one case per loosening and one that tightens (no entry).
- Integration: `test/integration/S-BTN-59.passive-plain-server.test.ts` — the board-posting half (the `ls-remote` trigger half is R3-1272's); S-BTN-55 still green.
