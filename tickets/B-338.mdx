**Brief:** the owner, 2026-11-23: "the dashboard should also be available for repo owners and
regular users as well (naturally only allowing the actions these user types may perform)", and,
asked who a regular user is, chose a repository member: "a person an owner adds to a repository
(bound by Access email or key). Reads everything in that repository and answers person legs whose
`asks:` label is assigned to them; cannot grant, hold, resolve or change policy."

**Spec:** [BATON_SPEC §11.2](../spec/BATON_SPEC/11-people.md#sec-11-2) ([R-BTN-204](../spec/BATON_SPEC/11-people.md#sec-11-2)),

[§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1) (the principal row; one role per key),

### What to build

Everything below is R-BTN-204 and the rules it cites; where this list and a rule differ, the
rule wins.

1. **The role and the table.** `repository_members` (one append-only migration); `member` in the
   one-role-per-key check across `credentials`, `repository_owners`, `repository_members`,
   `sync_keys` and the administrator set (§12.1), refused `conflict` without naming the role.
2. **Owner routes and commands.** `POST /v1/owner/{repository}/members` — add `{public_key,
   answers[]}`, change `{fingerprint, answers[]}`, remove `{fingerprint, remove: true, confirm:
   true}` — each an `approvers.members` action (R-BTN-188); `answers` labels validated against
   R-BTN-116's `asks` pattern. `baton owner member add|answers|remove` (R-BTN-127).
   `GET /v1/owner/{repository}/grants` lists `members`.
3. **Reads.** A member key is a *reader* of its repositories (§14), and reads the board and a
   leg's runs, which §14 lists for a member; `GET /v1/repositories` lists its own. Not the owners'
   grants or policy log, which list the repository's credentials and the policy's history
   (R-BTN-204; the owner's brief said "reads everything", and the owner accepted this narrowing
   on 2026-11-23). Nothing else: every owner, administrator and runner
   route is `forbidden` to it.
4. **The answer.** `POST …/attestations` takes a member key's or member's session's
   `std:decision@1` for a person leg whose `asks` label is in its `answers` (R-BTN-116 says
   which legs take an answer), as writer `member`; another label, or any other type, is `forbidden`. The `cooperative` and default
   policies admit `member` for `std:decision@1`; `protected` admits `human` alone (R-BTN-188's
   table), which a member's session meets and a member key does not (R-BTN-185). The conditions read's `answerable` (`src/core/reads/conditions.ts`, `answerWord`)
   says yes for such a member and names the label otherwise.
5. **Revocation.** `admin key revoke` of a member key removes it from every repository in the
   same transaction and ends its sessions (R-BTN-57).
6. **The dashboard.** A member's session (B-76) is drawn the repository screens with no controls
   but the answer on the person legs it may answer (S-BTN-307's rule: only the caller's actions).

### Trust

- **A member's key and `answers`** — written only by an owner's `approvers.members` action
  (R-BTN-188), validated in `src/core/validate.ts` before any SQL: the public key by R-BTN-13 or
  R-BTN-159, each label by R-BTN-116's `asks` pattern.
- **A member's answer** — authenticated by the request (its signature, bearer or session,
  R-BTN-155), admitted only where the policy's `attestations` entry names `member` and its
  `answers` hold the leg's label; the `std:decision@1` value validated as any answer.

### Invariants

- **One role per key** (§12.1): a member key holds no other role; the check runs in the
  transaction that adds it.
- **R-BTN-186**: a member does the same on the CLI and the dashboard, and nothing more on either.
- **R-BTN-181, R-BTN-188**: whose answer counts is the policy's; a member writes only as `member`.
- **Both hosts** (R-BTN-55); migrations append-only.

### Do not

- Give a member any action R-BTN-204 does not list, on any surface.
- Let a member's answer count where the policy does not admit `member`.
