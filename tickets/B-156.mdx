**Brief:** the owner, 2026-11-01, on the whole-spec review they commissioned ("assess it for …
can any vocabulary, core concepts or actors be simplified … is the user experience intuitive …
are the security guarantees … truly guaranteed and … do they matter"), asked for its findings
to be filed as tickets. Source: `docs/review/spec-simplification-review-2026-11-01.mdx`.
The review's claims are a reviewer's, checked against the spec where they cite it; this ticket
verifies each against the text before changing anything.

### Why

Review finding 6: "MCP is specified twice and contradictorily". R-BTN-130 / R-BTN-154 ("its
only writes add a hold and stop a leg") and R-BTN-186 ("Tightening ... is open to any owner
credential, MCP keys included. This replaces R-BTN-130's closed list") are both in force;
R-BTN-163 already assumes the latter. An MCP agent can hold but not unhold, stop but not restart,
and read `leg.why` but neither route nor adopt.

### Decided (the owner)

**Rulings of 2026-11-01** (the owner, answering each question in the session that continued
immediately-run/baton#150; the restructure, B-166, writes them into the spec):

- "Tighten, and undo own": an MCP key may make any tightening and undo what it tightened itself
  (unhold its own hold, restart a leg it stopped); loosening others' limits, routing and adopting
  stay with owner keys.

### What to build

1. **A spec PR first**, under the babysit skill's *Spec PRs*: two fresh reviewers, the impact list,
   every rule restating the same fact changed with it.
2. One rule for what a delegated key may do, cited by R-BTN-130, R-BTN-154, R-BTN-163,
   §12.2, §14 and G-BTN-144.
3. The action registry's MCP entries (R-BTN-129) generated from that rule.
