**Brief:** the owner, 2026-10-20, closing the open question "Watching for owners' dashboard
sessions": "Sounds useful."
**Spec:** [BATON_SPEC §11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) [R-BTN-155](../spec/BATON_SPEC/11-people.md#sec-11-4) (sign-in by a confirmed code, now for owners too),
[§12.2](../spec/BATON_SPEC/12-security.md#sec-12-2) (destructive actions), [§12.4](../spec/BATON_SPEC/12-security.md#sec-12-4) [R-BTN-16](../spec/BATON_SPEC/12-security.md#sec-12-4)
(cookies, origin checks), [R-BTN-129](../spec/BATON_SPEC/11-people.md#sec-11-3) (the registry decides each action's callers); [§11.2](../spec/BATON_SPEC/11-people.md#sec-11-2) [R-BTN-57](../spec/BATON_SPEC/11-people.md#sec-11-2)
(`admin.key.revoke`: an owner key from every repository, never an administrator's); [§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1) (one
role per key: `baton admin keys set` and `baton.admin-key-conflict`).
**Depends on:** B-25 (the registry, which scopes a session's actions).
**Used by:** B-206 (the V2 shell signs in per role).

### Requires

None: a checkout, a terminal and a browser.

### What to build

1. Sign-in by code, the role the binding key's (R-BTN-155: authentication first, then the
   role): `/login` sends `POST /v1/login {code_request: true}`, writing a `login_codes` row with
   no role; `baton admin open`, `baton owner open` or `baton member open` binds it through
   `POST /v1/admin/login-links`, `/v1/owner/login-links` or `/v1/member/login-links` signed by a
   key of that role, and the session is that key's, in R-BTN-155's two steps: `{code}` answers
   `{role, client_addr, age_s}` — the role the binding would give — and binds nothing, the
   command prints it and asks `bind? [y/N]` (no `--yes`), and `{code, confirm: true}` binds. The administrator's route
   and `baton admin open` take the same two steps (B-172's items, folded in here), replacing
   today's one-time login link (`src/core/admin.ts` `loginLink`). A `not-found` at either step
   is no failed verification. S-BTN-124's preview cases.
2. `dashboard_sessions` gains `role` and `key_fingerprint` (one new migration, with item 8's);
   an owner's session reads its key's repositories on every request, so it drops a repository
   its key stops owning and ends when none remains, or
   when an administrator revokes the key (R-BTN-57); `POST /v1/owner/sessions/revoke`
   (`owner.sessions.revoke`, destructive).
3. The `session` principal carrying its key's role in `authorize` (R-BTN-129): an owner's or
   member's session takes only the actions its role's key may, on its key's repositories, at
   their key routes (item 9); never an administrator's action. The `/v1/ui/*` rows §14 narrows
   to `session (administrator)` or `(administrator, owner)` refuse the others; each id-taking
   `/v1/ui/*` route acts only within the session's repositories and answers another
   repository's id as an unknown one.
4. Confirmation by the session's key only, through another channel: `baton owner confirm` and
   `POST /v1/owner/confirm`, `baton admin confirm` and `POST /v1/admin/confirm` (and a member's
   when one of its acts needs it), the confirming key the session's own; the acts R-BTN-155's
   *Authority-changing acts* names.
5. The V2 dashboard's shell does this (BATON-UI-V2: B-206 draws by the session's role, B-207
   draws only the session's registry entries); no V1 change — B-193 removes V1.
6. **Revoking keys** (R-BTN-57, adv-4 M1): `admin.key.revoke` (`revokeKey` in
   `src/core/admin.ts`) removes an owner key from every repository it owns, the last owner
   included, and ends its dashboard sessions and MCP keys in the same transaction; naming a key
   listed in `BATON_ADMIN_KEYS` it answers `invalid-params` and changes nothing — an
   administrator's key ends only by leaving the secret.
7. **One role per administrator line** (§12.1, adv-4 m4): `baton admin keys set` (`cli/baton.mjs`)
   refuses a line whose key holds another role in the tenant, without naming the role; a host
   that loads such a line anyway (`src/cloudflare/baton.ts`, `src/local/host.ts`, through the
   admin-key reader in `src/core/auth.ts`) treats that key as no administrator and raises
   `baton.admin-key-conflict` (R-BTN-163) for the administrators.

8. **Every person role, the key chosen after authenticating, one session per tab** (R-BTN-155
   as amended 2026-11-23). `ACCESS_IDENTITIES` binds an email to several keys, one line per
   pair; `{access: true}` opens the one key an email opens, or answers `choose` and sets
   nothing; `{access: true, key}` opens the chosen key's session. `dashboard_sessions` is
   re-keyed by a public `session_id` with `browser_hash`, `role` and `key_fingerprint` (one
   migration, with item 2's columns); `POST /v1/login` answers `session_id`, the shell keeps it in
   `sessionStorage` and sends `Baton-Session` on every request, and the front authorizes a
   session request only when the header names a live session bound to the cookie. Every sign-in
   sets a new cookie value and rebinds the browser's live sessions to it (`dashboard_cookies`,
   §13.2); the cookie lives as long as its longest session; a request carrying a replaced value
   ends every session of that browser. A tab with no session id signs in; nothing lists sessions to it.
   `ui.logout` ends the tab's session; `{all: true}` ends every session bound to the cookie and
   clears it. Members' sessions land with B-320; build the role as data, not an owner special
   case.
9. **A session calls its actions at their key routes** (R-BTN-155 *Where a session calls*,
   R-BTN-16, §14's *Routes a session shares with the keys*). The front resolves the cookie and
   `Baton-Session` on any `/v1/` route carrying no signature and no bearer, and the core
   authorizes the session as its key's role through the same check as the key. Refuse R-BTN-186's
   key-only acts to every session (login links, code binding, confirmations, minting an API key,
   a registration token or an MCP key, export and import). An act an `approvers.*` list governs,
   or that changes an owner, a member, a grant or a credential, answers `202 {confirm_code}` and
   waits for the key's confirmation (item 4); until item 4 lands, it is refused to a session and
   its control is drawn disabled, naming the command. S-BTN-315 and G-BTN-174.

### Do not

- Give an owner session any administrator action, or another repository's rows.
- Let any route remove an administrator's key from Baton's side; only the secret does.

### Tests

- S-BTN-124's owner-session cases (a foreign repository and an administrator route
  `forbidden`, an owner code typed into `baton admin open` `not-found`, another key's
  confirmation `not-found`, removal and `owner sessions revoke` ending the session); S-BTN-32's
  revoked owner key (removed from every repository, its sessions and MCP keys dead) and
  `admin.key.revoke` on an administrator line (`invalid-params`); S-BTN-126 extended: an owner signs in, sees only its repositories, and a
  confirmed action needs its code.
- Unit: `baton admin keys set` refuses a line whose key is an owner key; a host started with
  such a line refuses that key's administrator requests and raises `baton.admin-key-conflict`.

- S-BTN-314 (the role choice and per-tab sessions) and S-BTN-315 for the owner role (every owner
  action through a session, a person leg's answer with B-195's route included); G-BTN-174's
  check over §14's rows.
