**Brief:** the owner, 2026-10-20, closing the open question "Watching for owners' dashboard
sessions": "Sounds useful."
**Spec:** `spec/BATON_SPEC.md` §11.4 R-BTN-155 (sign-in by a confirmed code, now for owners too),
§12.2 (destructive actions), §12.4 R-BTN-16
(cookies, origin checks), R-BTN-129 (the registry decides each action's callers); §11.2 R-BTN-57
(`admin.key.revoke`: an owner key from every repository, never an administrator's); §12.1 (one
role per key: `baton admin keys set` and `baton.admin-key-conflict`).
**Depends on:** B-25 (the registry, which scopes a session's actions).

### Requires

None: a checkout, a terminal and a browser.

### What to build

1. Sign-in per role: `/login?as=administrator|owner`, `POST /v1/login {role}` writing a
   `login_codes` row with its `role`; `baton owner open` and `POST /v1/owner/login-links {code}`
   signed by an owner key bind only an owner row (`POST /v1/admin/login-links` only an
   administrator row; any other code `not-found`); the CLI shows the row's role, address and age.
2. `dashboard_sessions` gains `role`, `key_fingerprint` and `repositories` (one new migration);
   an owner's session drops a repository its key stops owning and ends when none remains, or
   when an administrator revokes the key (R-BTN-57); `POST /v1/owner/sessions/revoke`
   (`owner.sessions.revoke`, destructive).
3. The `owner-session` principal in `authorize` (R-BTN-129): only entries whose `callers` list
   it, on its repositories; never an administrator's action. `GET /v1/ui/state` filtered to its
   repositories; `/v1/ui/messages` (only `release` and `status_request`, holder checked) and
   `/v1/ui/resync`, `/v1/ui/overrides/{ticket}` and `POST /v1/ui/conditions/{condition}/resolve`
   on its repositories; the administrator-only `/v1/ui/*` routes refuse it.
4. Confirmation by the minting key only: `baton owner confirm` and `POST /v1/owner/confirm`
   (`baton admin confirm` likewise restricted to the administrator key that minted the
   session); R-BTN-155's one confirmed-action list.
5. The dashboard hides what the session may not see, and draws no administrator control for it.
6. **Revoking keys** (R-BTN-57, adv-4 M1): `admin.key.revoke` (`revokeKey` in
   `src/core/admin.ts`) removes an owner key from every repository it owns, the last owner
   included, and ends its dashboard sessions and MCP keys in the same transaction; naming a key
   listed in `BATON_ADMIN_KEYS` it answers `invalid-params` and changes nothing — an
   administrator's key ends only by leaving the secret.
7. **One role per administrator line** (§12.1, adv-4 m4): `baton admin keys set` (`cli/baton.mjs`)
   refuses a line whose key holds another role in the tenant, without naming the role; a host
   that loads such a line anyway (`src/cloudflare/baton.ts`, `src/local/host.ts`, through the
   admin-key reader in `src/core/auth.ts`) treats that key as no administrator and raises
   `baton.admin-key-conflict` (R-BTN-163) for the administrators.

### Do not

- Give an owner session any administrator action, or another repository's rows.
- Let any route remove an administrator's key from Baton's side; only the secret does.

### Tests

- S-BTN-124's owner-session cases (a foreign repository and an administrator route
  `forbidden`, an owner code typed into `baton admin open` `not-found`, another key's
  confirmation `not-found`, removal and `owner sessions revoke` ending the session); S-BTN-32's
  revoked owner key (removed from every repository, its sessions and MCP keys dead) and
  `admin.key.revoke` on an administrator line (`invalid-params`); S-BTN-126 extended: an owner signs in, sees only its repositories, and a
  confirmed action needs its code.
- Unit: `baton admin keys set` refuses a line whose key is an owner key; a host started with
  such a line refuses that key's administrator requests and raises `baton.admin-key-conflict`.

### Exit criteria

- [ ] the extended scenarios pass on both hosts, S-BTN-32's administrator-line case included;
  G-BTN-57 and G-BTN-144 hold
- [ ] `npm test`, `npm run typecheck`, `npm run check:spec` and `npm run check:wiki` green
