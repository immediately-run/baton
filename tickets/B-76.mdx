**Brief:** the owner, 2026-10-20, closing the open question "Watching for owners' dashboard
sessions": "Sounds useful."
**Spec:** `spec/BATON_SPEC.md` §11.4 R-BTN-155 (sign-in by a confirmed code, now for owners too),
§8 R-BTN-118 (streaming; owner sessions watch), §12.2 (destructive actions), §12.4 R-BTN-16
(cookies, origin checks), R-BTN-129 (the registry decides each action's callers).
**Depends on:** B-9 (leg streams), B-25 (the registry, which scopes a session's actions).

### Requires

None: a checkout, a terminal and a browser.

### What to build

1. `baton owner open` and `POST /v1/owner/login-links {code}` signed by an owner key, binding the
   pending sign-in as the administrator's route does; the session row records the owner's
   credential and its repositories.
2. Every `/v1/ui/*` read and action authorizes an owner session against its repositories and the
   registry's `owner.*` actions; destructive ones need a confirmation code as an
   administrator's do.
3. `GET /v1/ui/stream` admits an owner session for a claim of one of its repositories.
4. The dashboard hides what the session may not see.

### Do not

- Give an owner session any administrator action, or another repository's rows.

### Tests

- S-BTN-126 extended: an owner signs in, sees only its repositories, and a destructive action
  needs its code; S-BTN-70 extended: an owner session watches its repository's leg and is refused
  another's.

### Exit criteria

- [ ] the extended scenarios pass on both hosts; G-BTN-144 holds
- [ ] `npm test`, `npm run typecheck`, `npm run check:spec` and `npm run check:wiki` green
