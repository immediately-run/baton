**Brief:** the Baton project.
**Spec:** `spec/BATON_SPEC.md` §16.2 step 1 (exit), §11.4 (the dashboard's Ready view, R-BTN-155 sign-in), §15 (staging; S-BTN-13, G-BTN-10)
**Depends on:** R3-1207, R3-1208

### Requires

- `human-operator` — exit criteria 1–2: signing in to the dashboard as the owner.

### Why

Step 1's exit (§16.2) is that, for each tier, the live Ready view's order equals the course's
own claim order on the same snapshot (Baton applies the expedite bound from its own claims, so
git's withholding is not compared — docs#205's review). Only a deployed Worker behind its real
sign-in proves it.

### What to build

A verification sitting (about 15 minutes), no code.

### Architecture — the decisions, named

- Compare on one snapshot: read the sha the dashboard shows, then run the course's own
  claim-order tool at that sha (docs: `node scripts/baton-sync.mjs --compare`, or its successor
  once R3-1216's sync swap lands).
- No provider view: R3-1237 removed the provider tables, and provider state is docs'
  `roadmap-pr` course's (R3-1235).
- **Do not:** fix a difference here; file a BUG item against R3-1206 or R3-1207 instead.

### Tests

None to write. The automated half is S-BTN-13 on `baton-staging` after each deploy.

### Exit criteria

- [ ] **live leg** (`human-operator`): `https://baton.immediately.run/` asks for the owner's sign-in (Access where configured, then R-BTN-155's code) and then shows the Ready view; another account is refused
- [ ] **live leg** (`human-operator`): the Ready view's snapshot sha equals `git rev-parse origin/main` within one sync, and for `routine`, `judgement` and `critical` its order equals the course's own claim order at that sha (the compare tool exits 0)
- [ ] the latest `baton-deploy` run shows staging `S-BTN-13` green
- [ ] `npm run verify` green
