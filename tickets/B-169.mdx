### What to build

1. **Masking.** The runner's class-5 pattern matches `brt_`, `bak_`, `bmcp_`, `bps_`, `bds_`,
   `bmo_`, `bmr_` and `bor_`, each followed by `[A-Za-z0-9_-]*`; the archiver's transcript
   masking uses the same pattern (one shared definition, not two lists).
2. **The checks map.** `PUT /v1/owner/{repository}/settings` refuses a `checks` course map that
   does not name exactly one end station `success`, exactly one `failure` and at most one
   `timed_out` (`invalid-params`, naming the course; `neutral` is not a conclusion, the owner's
   ruling of 2026-11-02 on B-175). A station newly mapped to `success`, or a removed or renamed
   course entry, is a loosening: it needs an approver on `approvers.policy` (R-BTN-186); any other
   change is a tightening, open to any owner credential but a delegated key, which `checks`
   refuses as before. (B-175 builds the same validation: build it once, in whichever lands
   first.) Registering a check-runner stays `approvers.members`'s (R-BTN-188).
3. **Notification body caps.** `POST /v1/github/webhook` and `POST /v1/forges/{repository}/notify`
   refuse a body over 26,214,400 bytes `too-large` on `Content-Length`, or once that many bytes
   have been read (chunked bodies), before any MAC is computed. Both stay outside the per-IP
   rule.
4. **Headers.** Every response to a request a credential or a dashboard session authorizes, and
   every response that sets a cookie or carries a sign-in code, carries `Cache-Control: no-store`
   (one place in `src/core/http.ts`, not per route).
5. **The pending cookie** is `__Host-baton_pending` wherever B-46's sign-in builds it.
6. **Supersession.** Where B-146's attestation store supersedes the sync's attestations, it does
   so across a sync key, the CI identity and a machine key alike (R-BTN-191); if B-146 has not
   landed, this item moves to it.
