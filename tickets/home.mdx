## How tickets work

- A ticket is one `.mdx` file in this folder, named after its id. New tickets are `B-1`,
  `B-2`, and so on; tickets that moved here from the immediately.run docs roadmap keep their
  `R3-NNNN` ids. [How tickets work](HOW-TICKETS-WORK.md) is the generated conventions page —
  `baton repo init` writes it, `baton tickets check` reports it when it drifts.
- Its frontmatter is what Baton reads: `status`, `depends_on`, `order`, `tags`, `prs` and
  `repos`. `item.schema.json` is its shape, and `npm run check:wiki` checks every ticket
  against it. The body is for people and agents; Baton never stores it.
- A finished ticket moves to `archive/` with `status: done`.

## Claiming a ticket

**Ask Baton first (B-129).** A ticket's frontmatter is written by whoever can push, including a
session releasing its claim in a hurry; Baton's record of where a ticket stands comes from
claims, advances and the forge's PR facts, and the owner has ruled that about a ticket's position
Baton wins over git (B-120). Before claiming, read Baton's board —
`node cli/baton.mjs board baton` (or `node cli/baton.mjs ticket history baton:B-129`) — and trust
its station over the frontmatter: a ticket at a station past `filed` already has work and a PR to
continue, and you take it over there, on its branch —
`node cli/baton.mjs tickets check <id> --claimable` prints where. Never `checkout -b` a new
branch for a ticket Baton holds past its start.

Ticket files are Dibber's to write (B-326); Baton reads them, hands out their numbers and holds
the claims. `dibber` writes your working tree: commit and push what it wrote — a new ticket alone,
on its own `baton-ticket/<id>` branch, through a pull request. Before a claim,
`tickets check <id> --claimable` reads the ticket from Baton with the session's key (`-i KEY`,
else `BATON_KEY_FILE`) and writes nothing; an unanswered read exits 2 — pass `--offline` only when
Baton is unreachable and git's word is all there is. A ticket that is not available or whose
dependencies are not all done is not claimable — Baton's position overrides only a false
`available`, never `in-progress`, `in-review` or a parked or closed status — nor is a ticket
another claim holds, named with its holder and its lease.

```sh
node cli/baton.mjs board baton                                        # Baton's station for every ready ticket, first
node cli/baton.mjs tickets check B-110 --claimable -i ~/.config/baton/worker   # may it be claimed? the takeover, if any
dibber claim B-110                                                    # available → in-progress
dibber set B-110 in-review --pr https://github.com/immediately-run/baton/pull/40
dibber set B-110 available --note "review round 2 next"               # a release, with what is left
dibber done B-110 --pr https://github.com/immediately-run/baton/pull/40
dibber set B-110 --note "rules re-read: R-BTN-33, R-BTN-50"           # once the amended rules it cites are re-read
dibber new --title "…" --depends-on B-110 --order 1100 --body-file F  # the next B-n, from Baton
node cli/baton.mjs tickets --help                                     # the checks, the tags Baton reads
```

`check --claimable` says a ticket that cites a rule `spec/BATON_SPEC_HISTORY.md` amended after
the ticket was filed is not claimable, naming each; re-read them, rewrite what they contradict,
and record the re-read with the `dibber set … --note` it prints. A new migration number or scenario id comes from
`node cli/baton.mjs tickets next migration|scenario` — Baton's sequence (B-176, R-BTN-199); with
Baton unreachable the command prints the next free number by the scan and says so, and then the
old rule applies: merge main before merging, and renumber if main took it. A ticket filed from
2026-11-03 carries `### Trust` and `### Invariants`
(`check.sections_since` in `.baton/baton.json`), and every ticket from B-176 on carries the
`_filed` Status line, by which CI's shallow clone judges it (`check.sections_from_id`).
