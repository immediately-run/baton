## How tickets work

- A ticket is one `.mdx` file in this folder, named after its id. New tickets are `B-1`,
  `B-2`, and so on; tickets that moved here from the immediately.run docs roadmap keep their
  `R3-NNNN` ids. [How tickets work](HOW-TICKETS-WORK.md) is the generated conventions page —
  `baton repo init` writes it, `baton tickets check` reports it when it drifts.
- Its frontmatter is what Baton reads: `status`, `depends_on`, `order`, `tags`, `prs` and
  `repos`. `item.schema.json` is its shape, and `npm run check:wiki` checks every ticket
  against it. The body is for people and agents; Baton never stores it.
- A finished ticket moves to `archive/` with `status: done`.

## Claiming a ticket

**Ask Baton first (B-129).** A ticket's frontmatter is written by whoever can push, including a
session releasing its claim in a hurry; Baton's record of where a ticket stands comes from
claims, advances and the forge's PR facts, and the owner has ruled that about a ticket's position
Baton wins over git (B-120). Before claiming, read Baton's board —
`node cli/baton.mjs board baton` (or `node cli/baton.mjs ticket history baton:B-129`) — and trust
its station over the frontmatter: a ticket at a station past `filed` already has work and a PR to
continue, and `baton tickets claim` takes it over there, on its branch. Never `checkout -b` a new
branch for a ticket Baton holds past its start.

Until Baton claims this repository's tickets itself (R3-1266), git is the lock, and the
commands are the CLI's — the same ones docs and fieldhouse run (B-112). Each is one commit
pushed straight to `main` from a fresh checkout of it; if someone else pushed first, it retries
on the new head. `claim` reads the ticket from Baton with the session's key (`-i KEY`, else
`BATON_KEY_FILE`) before it writes, and refuses — rather than trust the frontmatter — when it
cannot: pass `--offline` only when Baton is unreachable and git's word is all there is. It
refuses a ticket that is not available or whose dependencies are not all done — Baton's
position overrides only a false `available`, never `in-progress`, `in-review` or a parked or
closed status — and a ticket another claim holds, naming its holder and its lease. Releasing a
claim (`set <id> available`) keeps every `prs:` entry; its commit is the hand-off — the PRs,
Baton's station and next leg, the branch, and what is left in your words (`--note`).

```sh
node cli/baton.mjs board baton                              # Baton's station for every ready ticket, first
node cli/baton.mjs tickets claim R3-1249 -i ~/.config/baton/worker   # available → in-progress, or the takeover
node cli/baton.mjs tickets set R3-1249 in-review --pr https://github.com/immediately-run/baton/pull/40
node cli/baton.mjs tickets set R3-1249 available --note "review round 2 next" -i ~/.config/baton/worker   # a release: the hand-off
node cli/baton.mjs tickets done R3-1249                   # done, moved to archive/
node cli/baton.mjs tickets claim B-110 --rules-reread R-BTN-33,R-BTN-50   # claim once the amended rules it cites are re-read
node cli/baton.mjs tickets new --title "…" --depends-on R3-1249 --order 1100   # the next B-n
node cli/baton.mjs tickets --help                         # every flag, the tags Baton reads
```

`claim` refuses a ticket that cites a rule `spec/BATON_SPEC_HISTORY.md` amended after the
ticket was filed, naming each; re-read them, rewrite what they contradict, and claim with
`--rules-reread` and the ids it named. A new migration number or scenario id comes from
`node cli/baton.mjs tickets next migration|scenario` — Baton's sequence (B-176, R-BTN-195); with
Baton unreachable the command prints the next free number by the scan and says so, and then the
old rule applies: merge main before merging, and renumber if main took it. A ticket filed from
2026-11-03 carries `### Trust` and `### Invariants`
(`check.sections_since` in `.baton/baton.json`), and every ticket from B-176 on carries the
`_filed` Status line `new` writes, by which CI's shallow clone judges it (`check.sections_from_id`).
