### What to build

1. **The course file (R-BTN-69).** The leg field `on_ticket_changed`, `continue` or `restart`,
   defaulting to `continue`; the validator refuses any other value, naming the leg.
2. **The core (R-BTN-198, §8.1, §14, R-BTN-91, R-BTN-81).**
   - In the transaction that accepts a snapshot: for each held ticket whose posted `version`
     moved and which the snapshot leaves held, log `ticket-changed {from_version, to_version}`
     with the claim, and ring the holder `ticket` after the commit.
   - Each heartbeat claim carries `version`, `snapshot_sha`, `brief` and `last_written_by` from
     the latest accepted snapshot.
   - Accept an end `released:ticket-changed` only from a claim with a `ticket-changed` row
     logged after its running leg started; refuse it otherwise `invalid-params`.
   - `ticket-changed` joins the closed end reasons, which R-BTN-67 refuses as an owner bar's
     `reason`. A migration renames any bar already set with that reason to
     `bar-ticket-changed`, logging the rename.
3. **The runner (R-BTN-198).**
   - Per claim: the last seen and last verified versions, each with its snapshot sha.
   - Hand `ticket.changed` while a leg runs, collapsing several changes into one, none when the
     newest is the last seen.
   - The own-change test: markdown source only, every commit to the ticket's file in the range
     pushed by this claim's legs, from the same reflog reading as the leg-end scope audit.
   - Verification as R-BTN-198 states it: R-BTN-143 on the sha, the source's code from the
     claim's commit, the read where R-BTN-5 reads, `repos`/`course`/`requires` unchanged. A
     source or executor that cannot answer is `unreadable`, never a moved ticket (B-232's
     lesson).
   - Before every leg start, verify a newer version or release `stale-board`.
   - `restart`: stop at once through R-BTN-119's path for `requested`, then end
     `released:ticket-changed`.
   - On every `release` message, hand `release {reason}` first, then act exactly as today.
   - A release and a new version in one heartbeat hand only `release`.
4. **The leg's side (R-BTN-72, R-BTN-106, R-BTN-107).**
   - `ctx.on`, `ctx.events`, `ctx.readTicket`; `baton leg events [--wait <s>]` and `baton leg
     ticket [--version <v>]` on the channel, sharing one cursor per run. The four refusal reasons
     are R-BTN-198's.
   - The executor's brief names the two verbs.
5. **The end table (§9.4).** `released:ticket-changed`.
6. **The agent stubs** (`src/defaults/cli.ts`, after B-227). Pass each event to the agent at its
   next tool boundary where the harness allows it (a hook for Claude Code, the nearest
   equivalent for opencode) as text naming the event's type and the two verbs, never a version
   or ticket text. Under the `session` and `attached` executors the agent polls `baton leg
   events` as its brief says.

**Done when** S-BTN-231 passes as a scenario test, and `npm test` and `npm run typecheck` are
green.

### Out of scope

- **How quickly an external tracker's edits are seen.** Baton learns of a version change at the
  next accepted snapshot. For the markdown source that follows the forge's notification
  (R-BTN-73). An edit in a tracker such as Linear records no want (R-BTN-94) until something
  else does, or until a relay calls `POST /v1/sync/want`. Making that prompt is a separate
  ticket.
- **Other leg events** (an owner bar set, a prerequisite lapsing). Each needs its own rule.

### Trust

- **The version, sha and provenance** come from the sync's post and Baton's own record, as at
  the claim (R-BTN-35, R-BTN-93, R-BTN-194). A forged post (a stolen machine key, the security
  model's reach 7) can tell a leg its ticket changed, or make a `restart` leg release until
  `max_runs` holds the ticket for a person: a denial of service bounded by `max_runs`, the same
  bound every leg has. It cannot hand a leg text from anywhere else: the read is at the posted
  sha, checked on the default branch, for the claim's own ticket and only for a version this
  claim was handed.
- **The new body is as untrusted as the old one.** The read shows its `brief` mark and
  `last_written_by` first, as the claim does (R-BTN-194), so the agent sees whose words it is
  about to read. Its instructions are a task, never authority (`docs/security-model.mdx`,
  reach 3). A version that would widen the claim (`repos`, `course`, `requires`) is refused, and
  the claim's scope never changes by a read.
- **No ticket content crosses Baton**, and an event carries no ticket text. The stub's message
  names only the event's type and the verbs.
- **The own-change test** reads the runner's own reflog, which a hostile leg can falsify
  (§12.9). It can only hide an outside edit from itself.
- **A self-released `ticket-changed` end** is accepted only after a logged change, so a leg
  cannot use it to leave unpenalised at will.

### Invariants

- **R-BTN-33:** nothing new is stored but opaque versions in a history row.
- **R-BTN-5, R-BTN-143 and R-BTN-133:** no leg is handed ticket text that skipped verification,
  and no new code is loaded mid-claim: the source's code comes from the claim's commit.
- **R-BTN-194:** provenance is shown before any new text, as at the claim.
- **R-BTN-119 and §6.9:** a stop's timing and escalation are unchanged. The event is handed
  before the stop, never in place of it.
- **R-BTN-63:** readiness stays the holder's judgement; nothing here re-checks it.
- **R-BTN-160 to R-BTN-163:** conditions, bindings, handlers, Needs you and their quotas are
  untouched. A leg event is never a condition row.
- **Values 4:** versions are compared for equality only.
- **The architecture page, "Replies stay replies":** the ring carries no effect, and delivery
  stays on the heartbeat.
