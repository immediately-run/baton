### What to build

1. **The course file (R-BTN-69).** The leg field `on_ticket_changed`, `continue` or `restart`,
   defaulting to `continue`. The validator refuses any other value, naming the leg. `baton
   course test` prints it in the leg's signature.
2. **The core (R-BTN-198, §8.1, R-BTN-91).**
   - In the transaction that accepts a snapshot, for each ticket an active claim holds whose
     posted `version` differs from the cached one: log `ticket-changed {from_version,
     to_version}` with the claim, and ring the holder `ticket`. A snapshot that ends the claim as
     stale (R-BTN-35) does neither.
   - Each claim in the heartbeat response carries `version`.
3. **The runner: detection (R-BTN-198).** Track, per claim, the last version its legs saw. When a
   heartbeat's `version` differs, hand `ticket.changed {from_version, to_version, snapshot_sha}`
   to the running leg, once. Skip it when the change is the leg's own: on the markdown source,
   the commit that last changed the ticket's file at `snapshot_sha` is one the leg's window
   pushed, read from the reflog as the leg-end scope audit reads it. Hand nothing when no leg
   runs.
4. **The runner: what the leg's course chose (R-BTN-198).**
   - `continue`: serve the verified read (item 5). On `baton leg release --reason
     ticket-changed`, end as that reason.
   - `restart`: stop the leg at its next safe point, `close`, `handoff`, and end
     `released:ticket-changed`.
   - Before an `advance` starts the next leg in a claim whose ticket moved, re-verify at the
     newest version as R-BTN-5 does, readiness included, and release `stale-board` on failure.
5. **The leg's side (R-BTN-72, R-BTN-106).**
   - `ctx.on(<type or prefix>, listener)` and the async iterator `ctx.events`. `ctx.signal`
     keeps its three reasons.
   - `ctx.readTicket({version?})` and `baton leg ticket [--version <v>]`: read the claim's own
     ticket at that version through the source at the snapshot, check it is neither closed nor
     archived and its tier is within the runner's ceiling, then return body, exit criteria and
     PRs; else refuse naming the failed check. Verify a version once per claim and keep the
     result. No readiness check here. A source or executor that cannot answer refuses the read
     as `could not read`, never as a moved ticket (B-232's lesson).
   - `baton leg events [--wait <s>]`: the unread events as JSON lines. Events unread at the run's
     end are dropped.
6. **`release` (R-BTN-198, R-BTN-119, §6.9).** On every `release` message, hand `release
   {reason}` to the running leg, then act on the message exactly as today, without waiting for
   the leg to read it.
7. **The end reason (§9.4).** `released:ticket-changed`: status `released`, not a failed attempt,
   the run counted toward `max_runs`.
8. **The agent stubs** (`src/defaults/cli.ts`, after B-227). Pass each event to the agent at its
   next tool boundary: a hook for Claude Code, the nearest equivalent for opencode. The message
   is runner-written. For `ticket.changed` it says the ticket changed, that `baton leg ticket`
   reads the verified new version if the agent wants it, and that `baton leg release --reason
   ticket-changed` hands the work to a fresh claim. For `release` it gives the reason. It never
   quotes the ticket. The executor's brief (R-BTN-107) says that only `baton leg ticket` counts as
   re-reading the ticket, not a raw `git show` of an unverified head.

**Done when** S-BTN-231 passes as a scenario test, `npm test` and `npm run typecheck` are green,
`baton course test` prints `on_ticket_changed`, and an edit to a held ticket's file on the
default branch reaches a running leg's `ctx.on('ticket.changed')` within one doorbell ring of
the snapshot's acceptance.

### Out of scope

- **How quickly an external tracker's edits are seen.** Baton learns of a version change at the
  next accepted snapshot. For the markdown source that follows the forge's notification
  (R-BTN-73). An edit in a tracker such as Linear records no want (R-BTN-94) until something
  else does, or until a relay calls `POST /v1/sync/want`. Making that prompt is a separate
  ticket.
- **Other leg events** (an owner bar set, a prerequisite lapsing). Each needs its own rule.

### Trust

- **The version** comes from the sync's post, an attestation weighed by its writer as every
  snapshot is (R-BTN-35, R-BTN-93). A forged version change can at worst tell a leg its ticket
  changed, or make a `restart` leg release unpenalised, which `max_runs` bounds. It never
  changes what the leg runs: every read of the new version goes through the source and the
  runner's re-verification.
- **No ticket content crosses Baton.** The event carries two opaque versions and a sha. Ticket
  text reaches the leg only through the runner's verified read, and only when the leg asks.
- **The new body is as untrusted as the old one.** It comes from the same source and passes the
  same checks as the text the claim started with, and anyone who could push it could have
  pushed it before the claim. Its instructions are a task, never authority
  (`docs/security-model.mdx`, reach 3), and reading it changes neither the leg's scope nor its
  grant.
- **The stub's message to the agent** is runner-written and never quotes the ticket, so an edit
  cannot use the event to put text in front of a running agent.
- **The release reason** is Baton's own, from the message the runner already acknowledges
  (§6.9).

### Invariants

- **R-BTN-33:** nothing new is stored but opaque versions in a history row.
- **R-BTN-5 and R-BTN-133:** no leg is handed ticket text that skipped re-verification. The
  verified read, `restart`, and the re-check before the next leg are the only paths to a new
  version.
- **R-BTN-119 and §6.9:** a stop's timing and escalation are unchanged. The event is handed
  before the stop, never in place of it.
- **R-BTN-160 to R-BTN-163:** conditions, bindings, handlers, Needs you and their quotas are
  untouched. A leg event is never a condition row.
- **Values 4:** versions are compared for equality only.
- **The architecture page, "Replies stay replies":** the ring carries no effect, and delivery
  stays on the heartbeat.
