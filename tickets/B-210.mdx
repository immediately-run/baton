**Brief:** the owner, 2026-11-09 (B-191): "A ticket page gathers every read about it: position
(station, path, queued leg), why it can't move (blocks, prerequisites), history with
input/output pointers, children, leg runs with transcripts and log dirs. Its controls live here
too." The mockup's runner cards' claim block (`workers.txt`: leg from → to, running for, lease
reaps at with its bar and minutes left, attempt n of m with backoff, output, earlier attempts
with the failure's text) is this page's claim section; the Output name is text.

### What to build

1. **Sections** (`src/dashboard/screens/tickets/TicketPage.tsx`, one component per section
   under it), all declared to the polling layer together:
   - **Head**: qualified id, title, course, tier, tags, requires as chips, `web_url` as the one
     outward link (host shown), parent linking its page, the state word and mark.
   - **Position**: station, the path as stations and legs run with run ids, the queued leg and
     its `source` (course, route or decision; R-BTN-83) — from `ticket.show`.
   - **Claim**: the mockup's block from `ticket.show.claim` — runner linking its page, leg,
     running for, the lease bar, deadline, attempt n of `max_runs` and `next_backoff_until`,
     `session_url` as a link only where the read passed it (R-BTN-113), `log_dir` as text with
     the `baton leg log <ticket> <leg>` line beside it (R-BTN-128); then the earlier `attempts`
     with their end reason and detail as text.
   - **Why it cannot move**: `blocks` (kind, ref linking a ticket or naming a capability, since,
     until) and `prerequisites` for the queued leg (`met`, `why`, `since`, `until`, `url` where
     given, `found`), as a `<table>`.
   - **Open conditions and scope findings**: condition ids and types linking the Resolve page
     (B-195); scope findings (§12.9) with kind, target and ref as text and their one control.
   - **History**: `history` paged by `?before=` ("earlier" loads more), each row's kind, leg,
     run, reached, next leg, and its `inputs` and outputs as pointers: a `git:` or `s3://` URI
     as text with its digest, an `https://` URI as a link only when the client-side
     `links.mjs` rule passes it with the repository's `web_base` (§12.3).
   - **Children**: `children` with station and blocked, linking each.
   - **Leg runs**: for each leg the path names, `legs/{leg}/runs` — run, run id, runner, mode,
     started, ended, end, session link under R-BTN-113, transcripts as repository paths (text),
     `log_dir` as text.
2. **Controls** by `ui.view` through B-207, context `{repository, ticket_id, claim_id}`:
   hold, unhold (only where `ticket.show` carries `allowed` naming it — an approver's session,
   R-BTN-186), expedite and clear expedite, cancel (the confirm dialog), resolve (where exactly
   one open condition offers restarts, the restart buttons inline; else "resolve on the
   condition's page"), Stop (one click, Decision 3a), the scope finding's acknowledgement
   (`POST /v1/ui/scope/{id}/resolve`, one click, §12.9); for an administrator's session
   force-reap, fence clear (where `fence_pending`), the completion's confirm and release (where
   `unconfirmed`) — each a `202` through the code dialog as R-BTN-155 lists them. Route and
   adopt are not controls (Decision 2a): the page shows `baton ticket route <ticket> <leg>` and
   `baton ticket adopt <ticket> …` as text under Position.
3. **Phone.** The sections stack at 375 px; the controls row wraps under the head.

### What not to do

- No body; no state computed in the client; no control the registry does not place here.
- No route or adopt button (Decision 2a); no dialog on Stop (Decision 3a).
- No log bytes: `log_dir` is text (R-BTN-128).

### Trust

- **Every section** draws its read's text through `Text`; URIs become links only by the shared
  link rule with the read's `web_base`; `session_url` only as the server passed it.
- **Every control** is a registry action through `authorize`; the page sends the context and the
  form, and draws a refusal as text; `allowed` gates unhold on the server's word.

### Invariants

- **R-BTN-155's confirmed list**: unhold, expedite, the completion's confirm and release,
  force-reap and the fence clear go through the code dialog; hold, cancel, Stop, resolve and the
  scope acknowledgement do not.
- **Log directories as text** (R-BTN-128); **session links only from `session_hosts`**
  (R-BTN-113); **text, never markup** (§12.3).
- **Positions are Baton's** (R-BTN-39); **an owner's session, its repositories** (R-BTN-155).

### Tests

Under `test/ui/` with fixture reads and a fixture `GET /v1/actions`: every section draws its
fixture; the owner's entries draw hold, cancel, Stop and not force-reap, the administrator's
force-reap too (B-191's scenario on this screen); unhold appears only with `allowed`; Stop sends
with no dialog; cancel opens the confirm dialog; a `202` opens the code dialog; `log_dir`, a
`git:` URI and an unlisted `session_url` are text; an `https://` URI under `web_base` is a link;
the route and adopt lines are text.

### Exit criteria

- [ ] `/tickets/{ticket}` built with every section and control above, usable on a local Baton
      for both roles at desktop and 375 px.
- [ ] The tests pass; `npm test`, `npm run typecheck`, `npm run check:wiki` and
      `npm run check:tickets` are green.
