### What went wrong

`create-pr` resolves a conflict with the default branch only inside a `merge` leg ("A conflict is resolved by merging the default branch into the PR's branch", `legs/merge.md`). Neither `fix` nor `run-tests` merges the default branch first. So a PR parked anywhere — waiting on a review round, an adjudication, a hold — falls further behind `main` with every merge, and its next `run-tests` tests a tree that is no longer what would land:

- 2026-11-24 (`docs/interventions.mdx`, *the owner merged every mergeable PR*): of 51 open PRs, about 30 runner PRs were already conflicting, and six more that were clean became conflicting while the owner merged 13 by hand.
- 2026-11-24 19:10: "33 conflicting PRs …; every runner PR among them also ends on a `changes` verdict."
- 2026-11-22 13:20: B-282 changed `package-lock.json`, but `run-tests` links the home checkout's `node_modules` (installed from `main`'s lockfile) into the tested tree (`legs/run-tests.mjs`), so the test ran against the wrong dependencies.
- 2026-11-26: B-322's and B-8's `run-tests` ↔ `fix` loops ran on branches whose work had already merged.

A course that leaves its PRs unmergeable needs a person to rebase or merge them: not following the course (criterion 2).

### What to build

1. **`fix` starts from the default branch.** Before its agent runs, the `fix` stub merges the default branch into the PR's branch (never a rebase). On a conflict, the agent's instructions say to resolve it first, regenerating lock and generated files with the repository's own tooling. A merge with no conflict is committed and pushed before the agent's own changes.
2. **`run-tests` tests what would land.** The stub tests the PR's head merged with the current default branch, in a scratch tree. When that merge conflicts, the leg ends at the outcome that sends the ticket to `fix` (its "failed" outcome), with "conflicts with the default branch" as the reason. When the tested tree's lockfile differs from the home checkout's, the stub runs the repository's install (`npm ci` here) in the tested tree instead of linking the home's `node_modules`. This last part waits on decision D4 in the plan; if the owner declines it, leave it out and say so in the PR.
3. **A merged PR is not tested again.** `run-tests` and `fix` first ask the forge whether every PR of the ticket has merged. If they have, they end at the outcome the merge would have reached, with the forge's answer as evidence, instead of testing or fixing.
4. **Regenerate this repository's stubs** in the same PR (`baton repo init --check` clean afterwards).

### Exit criteria

- With B-343's fake forge: a PR behind the default branch with no conflict gets the default branch merged by `fix` and pushed; a conflicting one sends the ticket to `fix` from `run-tests` with the reason; an already-merged PR ends `run-tests` without a test run.
- A PR that changes `package-lock.json` is tested with its own lockfile installed (if D4 is accepted).
- `docs/standard-courses.mdx` states the new behaviour in `create-pr`'s section; `npm test` and `npm run typecheck` green.

### Trust

The default branch is the repository's own reviewed history. Merging it into a PR adds nothing a pusher controls that the PR did not already contain. The forge's "merged" answer is read with the leg's existing forge credential.

### Invariants

- History on a PR branch is never rewritten (`merge.md`'s rule).
- The merge leg still never merges red.
