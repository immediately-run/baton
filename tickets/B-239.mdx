**Used by:** B-243.

**What:** eligibility is computed from JSON on every request: `candidates()` (claims.ts ~528-603) runs ~12 correlated subqueries per ready ticket including `json_each` over grants, allowed capabilities, `person_legs_json` and `leg_capabilities_json`.

- `worker_effective_caps(worker_id, repository_id, capability)` — the set `grantsOf()` already computes, written at heartbeat, grant and credential changes.
- `course_legs(repository_id, course_id, leg, person)` and `course_leg_caps(repository_id, course_id, leg, capability)`, written by the course registry.
- `ticket_repos(ticket_id, repo_lower)`, written by sync; replaces `json_each(t.repos)` in webhook.ts (~540 rows per push) and `repos LIKE` in claims.ts.
- Rule 4 (R-BTN-174, R-BTN-58, R-BTN-120) must match exactly: a test compares the old SQL with the new tables across the scenarios.

**Target:** recommendations and claim ≈ 300 rows; webhook push < 50.

**Why:** on 2026-11-14 production exceeded Cloudflare's free-tier Durable Objects limit of
5,000,000 `rows_read`/day at 21:41Z; every runner call returned 500 until the 00:00Z reset.
Measured on a production-sized local state (180 tickets, 600 claims, ~3k events) with
workerd's `SqlStorageCursor.rowsRead`: `GET /v1/ui/state` ≈ 14.4k rows per 10 s poll
(≈ 3·events + 2–5k), recommendations ≈ 3.7k, claim ≈ 3.8–4k, alarm ≈ 0.8–1.3k per minute,
`POST /v1/sync/board` 4–5k rows over ~2.5k statements. This ticket is one of B-235–B-243,
the owner's 2026-11-15 plan to bound what each read costs.

**Done when:** the named calls' rows_read, measured the same way in a test (cloudflare host),
is at or below the target, `EXPLAIN QUERY PLAN` shows the intended index where one is named,
and behaviour is unchanged (the existing scenarios pass).

### Trust

No new input: indexes, tables and queries over data Baton already stores; no field, file, commit trailer or request is added.

### Invariants

- Rule 4 (R-BTN-174, R-BTN-58, R-BTN-120): eligibility unchanged. The tables are written in the same transaction as their sources, and a test compares the old SQL with the new tables across the scenarios.
