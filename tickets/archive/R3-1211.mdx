### Requires

### Why

Every later piece talks to Baton as a worker: a sidecar registers and heartbeats, hooks
report activities and transcripts, the owner suspends providers and sends messages. This item
builds that surface, with no claims yet (R3-1212). Tier: critical — credentials, secrets and
token binding.

### What to build

1. `POST /v1/worker/heartbeat` with registration, sidecar-generated secret hash, re-key,
   credential binding and capability allow-lists (R-BTN-13/14), the §11 request and response.
2. `POST /v1/worker/activities` and the heartbeat's `transcripts` (§6.8–6.9), with the
   10-minute close-only grace.
3. Messages: `POST /v1/ui/messages`, delivery in the heartbeat, `POST /v1/worker/messages/{id}/ack`.
4. Suspensions: `POST /v1/ui/suspensions`, `/lift`, scheduled start and timed end on the alarm,
   `suspensions[]` in the heartbeat response.
5. `GET /v1/worker/mode` (always `shadow` until R3-1217) and `POST /v1/worker/shadow-report`
   with `shadow-conflict` events.
6. Dashboard: the Workers view, and Suspend / Lift and Send status request actions.

### Architecture — the decisions, named

- **Credentials** are rows in `credentials` (§4) plus a Worker secret `TOKEN_HASHES` (JSON
  map credential id → SHA-256); a token's hostname and `allowed_capabilities` are checked on
  every heartbeat; revocation is deleting the hash. A `credentials` row `test` exists only in
  test bindings, and only it may send `test_harness: true` (R-BTN-32).
- **Validation (§10.4)** is one module `src/validate.ts`: the `session_name` regex, the
  500-character free-text rule, per-kind `detail_json` schemas, the transcript allow-list from
  the synced `baton.json` and the path regex. Every endpoint calls it before any write.
- **Write budget (§3):** capabilities and providers rows are rewritten only when the
  heartbeat's `settings_hash` changes.
- **The alarm** is set once by the object and re-armed every 60 s; this item gives it the
  suspension start/end and message expiry; R3-1212 adds reaping.
- **Do not:** return the worker secret (the server never has it); accept `test_harness` from a
  non-test credential; let one worker's activity id touch another's row (primary key
  `(worker_id, id)`); add claim logic here.
