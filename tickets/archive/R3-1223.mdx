**Brief:** the Baton project; continues [R3-1212](R3-1212.mdx) — its review's round three (baton PR 5, `rg:3-r3-0`).
**Spec:** `docs/content/specs/BATON_SPEC.mdx` §7.1 R-BTN-11 (docs@2dbf1424)
**Depends on:** R3-1212

### Requires

- none — local Worker tests only.

### Why

R3-1212 accepts a held history as a line: a force post against the head the accepted row was
held against becomes the head. Round two closed the backwards move — a once-accepted sha
re-posted after the head moved past it is no longer accepted. Round three found that such a
rewind is held **silently**: `board()` finds the sha's old held row (already accepted, held
against an older head) and treats it as known, so it writes no new row and no
`snapshot-rejected` event; the dashboard's held list, the alarm's 24-hour auto-accept and the
owner's Accept all act only on unaccepted rows. The sync gets `409` on every post until `main`
moves off that sha, and the owner has no way to accept it. The sync stays off until R3-1208
sets `BATON_ENABLED`, so nothing live can reach this before it lands.

Tier: judgement — one branch of the board's compare-and-set.

### What to build

1. In `board()`'s force branch, treat a sha as already held only when its row is unaccepted
   **and** was held against the current head. Otherwise reset the row — `head_sha` the current
   head, `accepted_at` NULL, `received_at` now and a new `auto_accept_at` — and log
   `snapshot-rejected`, exactly as for a first hold.
2. The reset is the only write: a repeat post of the same rewind against the same head stays a
   no-op, as R-BTN-11 requires of the sync's 15-minute re-posts.

### Architecture — the decisions, named

- `held_snapshots` keeps one row per sha (its primary key); a rewind reuses that row rather than
  adding a second.
- **Do not:** accept a rewind automatically because its sha was accepted once; let a held post
  move the head.

### Tests

- `test/unit/claims-gate.test.ts`: extend the rewind case — after the rewind's 409, a
  `snapshot-rejected` event is logged, `/v1/ui/state` lists it under `held`, the owner's Accept
  makes the next force post the head, and with no answer the alarm accepts it 24 h later; a
  repeat post of the rewind changes nothing.
- Scenarios: S-BTN-13 re-run; none new.
