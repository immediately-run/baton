**Brief:** the owner wants to dogfood Baton on a codebase whose organisation has not adopted it:
the code is a GitHub monorepo the owner may push branches to and open PRs on, but may not add a
repository beside it, and may not commit `.baton/` to it. The shape that adopts nothing is a
**home repository that is plain git on the owner's machine** — `.baton/`, the courses and the
tickets — served by a local Baton (`baton server start`, R-BTN-55), with the monorepo as a code
repository its tickets name in `repos:`. Today the spec refuses that shape in five places:

- every repository name a ticket carries is "a forge path on the **home's forge host**"
  (R-BTN-92), and `code_repos` lists "forge repositories on the home forge host" (R-BTN-140); a
  `git` home has no forge host;
- the fact adapter is chosen by `forge`, the home's (R-BTN-96), and `git` has none, so no sync
  reads the monorepo's PRs, reviews or checks — `create-pr` never sees its own PR;
- review rounds go where the **home's** `forge` says (R-BTN-190): on a `git` home, an orphan
  `baton-legs/<ticket>` branch in the home, while the PR they review lives on GitHub;
- `pushers` are forge user ids with no host (R-BTN-139), meaningless on a `git` home;
- `human_identity` is one identity (R-BTN-188): the `pre-receive` pusher on a `git` home, a forge
  user id on a forge — never both.

"A GitLab home with GitHub code repositories" is the same change, so this lands as a general
mechanism, not a dogfood special case (values 11); and it widens values 8 — Baton runs without
GitHub — to a home without a forge whose work is on one.

### What to build

The spec amendment first, in the section files that own each rule, with `npm run spec:index`;
then the code. Every current repository keeps its meaning: an entry or a pusher written without a
host is the home's, exactly as today.

1. **A code repository names its forge** (R-BTN-140, R-BTN-138). A `code_repos` entry is
   `{path, forge?, host?}`; omitted, `forge` and `host` are the home's. On a `git` home both are
   required (`invalid-params` naming the entry). Baton stores `{path, forge, host, repo_id,
   owner_id, web_base}`; `forge` is `github`, `gitlab` or `gitea` — a `git` code repository has no
   PR facts and is refused in this ticket. The ids are read as R-BTN-138 reads a registration's:
   `baton owner settings set` reads them from that forge's API with the operator's token for that
   host (`GITHUB_TOKEN`, `GITLAB_TOKEN`, `GITEA_TOKEN`) or takes `--forge-ids`, and posts them;
   Baton never fetches. **The ids decide** at every read: the fact adapter compares the forge's
   ids for the repository it reads with the entry's and fails the sync on a mismatch, naming the
   entry, so a re-created path never gains reach. Consent (R-BTN-140) is unchanged: it applies to a
   registered repository of the tenant, matched by host and id.
2. **`owner/name` stays the name** (R-BTN-92, §4.4, §12.3, R-BTN-141). A `code_repos` path is
   unique case-insensitively among the home's path and every entry, whatever its host; a list
   with a duplicate is refused `invalid-params`. So `repos:`, the markdown source's `repos` map,
   `git:<owner>/<name>…` URIs and the branch-holder query's `?repo=` keep their grammar and resolve
   without a host. R-BTN-92's sentence becomes: every repository name a ticket carries is a forge
   path naming the home or a `code_repos` entry.
3. **One adapter per repository** (R-BTN-96). The adapter that reads a repository is chosen by
   that repository's `forge`: the home's by the home's (none on `git`), each code repository's by
   its own. The request budget is per host. An unreadable repository fails the sync as today; a
   partial reading is never posted.
4. **Links follow the repository** (R-BTN-92's link rule). A URL is a repository's when it passes
   the link rule for that repository's `web_base`; every forge code repository has one. A `git`
   home still accepts and draws no link of its own; its code repositories' PR URLs in `prs:` and
   a person leg's question `url` (R-BTN-116) pass by their repository's `web_base`.
5. **Pushers are qualified by host** (R-BTN-139). A `pushers` entry is `{host?, id}`; without a
   host it is the home's, and on a `git` home an entry without a host is refused. The forge
   lookup — can this author push to the PR's base — already reads the base repository; it now
   reads it on that repository's forge, with that host's token. Every other R-BTN-139 rule (same
   repository by id, every editor a pusher, fail closed on a missing scope) applies per host.
6. **Leg state follows where the PRs are** (R-BTN-190). The claim response's `leg_state` is
   `forge` when the home is on a forge **or** the claimed ticket's course reads PR facts
   (`facts: ["prs"]`, R-BTN-134); `branch` otherwise. On every forge home nothing changes; on a
   `git` home the `branch` course keeps its orphan leg-state branch, and a PR course's rounds live
   in its PR's conversation, on whichever forge holds the PR.
7. **No human identity across hosts — yet** (R-BTN-188, R-BTN-184). `human_identity` names one
   identity, so a human's merge or verdict on a code repository on another host cannot be told
   from a pusher's. Fail closed both ways: Baton refuses adding a `code_repos` entry on a host
   other than the home's while the repository's policy has a non-null `human_identity` or any
   `floors`, and refuses a policy version that sets either while such an entry exists
   (`invalid-params`, naming the entry or the knob). So the combination runs under `cooperative`,
   where Baton's state is a coordination record (R-BTN-39). Per-host human identities are a
   follow-up ticket.
8. **The single-machine runbook.** `docs/runbooks/local-home.mdx`: a plain home on the operator's
   machine served to local runners as R-BTN-105 requires (a bare repository over SSH with
   `receive.denyNonFastForwards`, `receive.denyDeletes` and `git-shell` for runner keys), a local
   Baton, `code_repos` naming a GitHub repository with the operator's token in the sync's
   environment, and runners polling `git ls-remote` (no webhook reaches a loopback Baton,
   R-BTN-105). It states what this deployment is: one operator's coordination record, not a
   boundary.

### Decision needed

**Should a single-machine deployment be allowed a local-path home remote?** R-BTN-105's plain
repository is reached over SSH with `git-shell`, which on one laptop means a second OS user for
the runners' keys.

- **(a) Keep R-BTN-105 as written** *(recommended)*. The runbook sets up `ssh://localhost` with a
  `git` user. No spec change; slightly fiddly once.
- **(b) Allow a `file://` or absolute-path `remote`** only on the local host bound to loopback,
  with the same `receive.*` settings and no `git-shell` — runners under the operator's own user
  can then write the bare repository directly, which `cooperative` already tolerates. A later
  ticket if (a) proves too awkward in practice.

Default if unanswered by the time the spec PR is ready: (a).

### What not to do

- No ticket tracker here: Linear, Jira and GitHub Issues sources are B-183's and later tickets'.
- No `git` code repository (no PR facts to read), and no change to check courses: check tickets
  and `forge-check` (R-BTN-114, R-BTN-115) stay on the home.
- No per-host `human_identity`, and no loosening of point 7's refusal to make it work.
- No new trust in forge deliveries: a loopback Baton receives none, and a forge Baton keeps
  values 6 (webhooks only trigger syncs).
- No change of meaning for any existing entry or pusher: a migration adds columns defaulted to the
  home's forge and host (append-only, `src/migrations/`).

### Trust

- **A code repository's `forge`, `host` and ids** — written by the repository's owners, signed
  with an owner key, through the one registry and `authorize` (R-BTN-129); the ids are verified
  against the forge by the sync at every read (point 1), so a wrong id fails closed rather than
  widening reach.
- **A pusher's `host`** — owners only, as `pushers` is today; adding one is a loosening governed
  by `approvers.policy` (R-BTN-186), unchanged.
- **PR facts from a second forge** — read by the sync with the operator's token for that host and
  judged by R-BTN-139's rules, unchanged: only pushers' words count, every editor checked.
- **The forge tokens** — the sync's environment, the operator's; never posted, never held by
  Baton (architecture: Baton holds no credential that writes git).

### Invariants

- **Every existing deployment is unchanged:** an entry or pusher without a host is the home's, a
  forge home's `leg_state` is still `forge`, and the full suite passes on both hosts (R-BTN-55).
- **The ids decide** (R-BTN-138): reach is by `{host, id}`, never by a path alone.
- **Only pushers' writes count** (R-BTN-139), on every host.
- **Fail closed where identity is ambiguous** (point 7): no policy names a human or a floor while
  a cross-host code repository exists.
- **Text, never markup; validate before write** (`src/core/validate.ts`): `host` is a lowercased
  DNS name with optional port, validated as `web_base`'s authority is.

### Tests

Each behaviour names a new `S-BTN-n` scenario (numbered at merge), run on both hosts:

- a `git` home with a GitHub code repository: a `create-pr` ticket goes `filed` → `pr-open` →
  `reviewed` → `merged` from fixture GitHub facts, its rounds in the PR's conversation
  (`leg_state: forge`), and a `branch`-course ticket in the same home keeps `leg_state: branch`;
- a duplicate path across hosts, a `git` home entry without `forge`/`host`, a `forge: git` entry
  and a host-less pusher on a `git` home are each refused `invalid-params`;
- the forge reporting different ids for an entry fails the sync and posts nothing;
- a verdict by an author who cannot push to the code repository's base is not read; one by a
  qualified pusher is;
- point 7 refuses in both orders;
- a forge home with host-less `code_repos` and `pushers` behaves byte for byte as before (the
  existing scenarios, unchanged).
