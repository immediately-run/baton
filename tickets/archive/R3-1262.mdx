### Requires

- none — keys and tokens are generated in the harness.

### Why

R-BTN-93 puts every sync credential behind one verifier so R3-1232 and R3-1240 write the check
once; R-BTN-92 makes a repository a forge path, a remote and a forge. Tier: critical —
authentication and per-repository trust.

### What to build

1. A migration: `repositories` gains `forge`, `remote`, `web_base`, `ci_identity`, `dispatch`,
   `unblocked_trigger`, `sync_wanted_at`, `sync_wanted_after`; `sync_workflow` nullable; the
   unique index per forge host; existing rows backfilled as §4's comment says;
   `credentials.kind` accepts `sync`; `sync_key_repositories` with `credential_id` unique.
2. `verifySync(req) → {repository, role}` in `src/core/auth.ts`: a sync key's signature
   (through `verifyRequest`, the Worker's pre-check and the nonce cache), GitHub Actions OIDC
   (today's `verifySyncToken`), and GitLab `id_tokens` (issuer allow-listed, `project_path`,
   `ref_type: branch`, `ref`, audience `#sync`/`#mirror`); every `/v1/sync/*` route uses it.
3. Registration and change of the new fields (`BATON_REPOSITORIES` seed until R3-1240's admin
   route), forge-path grammar and `web_base` validation, sync keys at registration.
4. The one link rule (R-BTN-92) in one function, used by activity detail URLs, decisions'
   `url`, output/input URIs and transcript links (`<forge>:<web_base>` entries).

### Architecture — the decisions, named

- **One key, one repository, one role**: never accept a key for a second repository.
- **Do not**: read a forge; store a forge secret in SQLite.

### Tests

- Integration: S-BTN-55 on both hosts.
- Unit: the link rule's cases (segment boundary, port, userinfo, dot segments, encoded `/`),
  the forge-path grammar, GitLab token claims (tag `ref_type`, wrong audience, unlisted issuer).

### Exit criteria

- [x] S-BTN-55 passes on both hosts
- [x] every `/v1/sync/*` route authenticates only through `verifySync`
- [x] `npm run typecheck` green
