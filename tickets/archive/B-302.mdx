## Plan

1. **Row 2 first: find out what an import does to policy, with a test.** On both hosts: a
   source repository on the `protected` preset with a floor and a human key; freeze, seal,
   export, import into an empty Baton; read `GET …/policy` there. Three outcomes, and the PR
   states which it found:
   - the import carries the policy by a path not in `SECTIONS`: then rows 1 and 2 are wording,
     and R-BTN-88 names that path;
   - the imported repository has the seed preset, no floors and no human key: this is a
     security finding, since moving a tenant silently replaces a protected policy with the
     default and drops every floor. Stop, tell the owner with the test's output, and fix it in
     this ticket: `repository_policies` (every version, chained), `policy_floors` and
     `human_keys` join the export, import validates the chain and refuses an export with a
     repository and no policy, as the rule already says;
   - the import fails: say how, and fix as above.
2. **Row 1: one list.** For each of the nine tables decide with the code, not the rule: a
   table that holds owner state a move must not lose (`capability_capacity`,
   `instance_settings`, the policy tables of step 1, `ticket_stations` and the position rows,
   if they are not rebuilt from the first post) joins `SECTIONS` with its validation in
   `ownerState.ts`; a table of a design that is not built (`check_runners`, `mcp_keys`,
   `registration_tokens`, `ticket_timers`, `conditions` if open conditions are not owner
   state) leaves R-BTN-88 for its proposal. `couriers` goes with B-285 and B-67;
   `instance_readings` is either exported, and R-BTN-88's *Not exported* loses "readings", or
   dropped from `SECTIONS`. After the PR the rule's list and `SECTIONS` are equal, and a unit
   test compares them by reading the rule's list from the section file, so they cannot drift.
3. **Row 3.** §4.4's schema gains `stations` with its shape and the rule that reads it
   (R-BTN-70). The interim shape: R3-1233 is done or it is not; if every poster sends the
   normative shape, delete the branch from `checkPayload` with a test that the old shape is
   `invalid-params`; if one still sends it, name it in §16 as legacy with its ticket.
4. **Row 4: state the clock, or remove it.** B-77 rewrites how a held post is accepted (its
   *Why*: the 24-hour acceptance "could rewind the head by clock"). Until B-77 lands, R-BTN-11
   says what is built: held per sha, accepted by an administrator on the dashboard or by the
   alarm 24 hours after the first post, the head moving at the next post of that sha. The
   sentence "Ordering never depends on a clock" in the same rule is then false as written and
   is reworded to what it means: which of two posts is newer never depends on a clock. Whether
   an unattended acceptance should exist at all is B-77's question and the owner's; this
   ticket only stops the rule being silent about it. `held_snapshots` gets its §13 row in
   B-297.
5. **Row 5.** Drop "*(proposal)*" from the heading; `npm run spec:index`.
6. **Spec mechanics.** History entry with `Rules changed:` R-BTN-88, R-BTN-11; `npm run
   spec:impact` over both ids and the terms `export`, `import`, `held`, `snapshot-rejected`.
7. **Tests.** Step 1's round trip, as cases of S-BTN-50. Step 2's list comparison. Step 3's
   refusal or its legacy note. Row 4 has a test already if S-BTN-13's or R3-1212's cases cover
   the 24 hours; name it in the PR, or add the case: a held sha is not the head at 23 hours 59
   minutes and is accepted by the alarm at 24.

### Trust

New inputs: sections of the import file, if step 1 adds the policy tables. An import is an
administrator's request into an empty Baton (R-BTN-88), and its rows are data the
administrator carries from another instance: each goes through the write path's validation,
the policy versions through `policy.ts`'s document check and hash chain, and a floor or a
human key is imported only for a repository the same file imports. The file's digest proves it
was not altered after export, not that its source was honest: an administrator importing a
file is trusted as the administrator is. The risk this ticket exists to remove is the
opposite direction: an import that loses authority state without saying so. Step 1 is run
against test instances only; reading the reference deployment's export needs an administrator
key the owner supplies, and this ticket changes no live policy, floor or key.

### Invariants

- BATON_SPEC [R-BTN-188](../../spec/BATON_SPEC/12-security.md#sec-12-8): every policy change needs an approver as the list stood. An import
  writes the source's versions as they were, with their hashes and `changed_by`; it adds no
  version of its own and seeds none over them.
- BATON_SPEC [R-BTN-189](../../spec/BATON_SPEC/12-security.md#sec-12-8): a floored guarantee is never broken by a change. After an import
  every floor of the source is in force, or the import was refused.
- BATON_SPEC [R-BTN-185](../../spec/BATON_SPEC/12-security.md#sec-12-8): a repository's `human_key` survives a move, or the gates that need it
  would have no key to open them ([R-BTN-188](../../spec/BATON_SPEC/12-security.md#sec-12-8), *No gate without a key to open it*).
- BATON_SPEC [R-BTN-33](../../spec/BATON_SPEC/01-what-baton-is.md#sec-1): filter fields only. No table added to the export holds a ticket's
  body, a note or a PR list.
- BATON_SPEC [R-BTN-11](../../spec/BATON_SPEC/04-tickets-syncs-board.md#sec-4-3): per repository, a snapshot is accepted only on ancestry and a newer
  observation. Step 4 changes the rule's words, not the compare-and-set.
- Validate before you write: every imported row passes `src/core/validate.ts` or the import
  is refused whole, in its one transaction.
