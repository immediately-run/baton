**Brief:** the owner, 2026-11-22, approved filing this ticket ("OK for me to … file the four tickets" — "Yes"). The facts are from that day's supervision on host bering:
- **B-239's implement leg lost its finished work.** The agent finished (73 focused tests passed, typecheck clean). Full `npm test` hit one failure, which the agent reproduced on an untouched `origin/main`: the masking bug that #354 fixed. The instructions say "Run the repository's checks yourself. Push only once they pass." So it did not push. The sandbox was killed, and the work went with it. FLDH-65 salvages such work; this ticket stops the cause.
- **Two fix legs repaired main's failure inside their own PRs.** The fix legs of B-244 and B-249 each patched `src/runner/mask.ts` in their ticket's PR. That is out of both tickets' scope, and it is a write target the two tickets share, which `docs/context/architecture.mdx` rules out (*Separate tickets never share a write target*).

The `run-tests` leg is the gate (`.baton/courses/create-pr/legs/run-tests.md`). It runs on what is pushed, and red routes to `fix`. An implement leg that holds back a push does not protect anything: the gate would have said red anyway, and the work is lost.

**Spec:** [BATON_SPEC §5.8](../../spec/BATON_SPEC/05-courses.md#sec-5-8) ([R-BTN-131](../../spec/BATON_SPEC/05-courses.md#sec-5-8), the standard courses). What each standard course's legs do is in [the standard courses](../../docs/standard-courses.mdx) and the course's own files, not the spec, so no rule changes.

## Plan

1. **implement.md, §3 *Build it on a branch*** (both copies, `.baton/courses/create-pr/legs/implement.md` and `src/defaults/courses/create-pr/implement.md`, kept identical). Replace "Push only once they pass." with:
   - Run the repository's checks yourself. A failure your change causes is yours to fix before you push.
   - **A failure that also fails on the base is not yours.** Check it on a clean checkout of the base (`git worktree add <tmp> origin/<default branch>`, the same install, the same command), never on your own tree. If it fails there too, push and open the PR anyway. Name it in the PR body under a heading **Pre-existing failures**: the test, its first failing line, and the base commit you reproduced it on.
   - **Never fix an unrelated failure in the ticket's PR**, even a one-line fix. It belongs to the ticket or PR that owns that code. Say in your last lines that main is red and where.
2. **implement.md, *Do not*:** add "Hold back a push because a check fails that fails on the base too: the run-tests leg is the gate, and unpushed work is lost when the leg's environment ends."
3. **fix.md** (both copies). In the *test gate is red* case, before changing anything, check the failure on a clean checkout of the current base:
   - **It fails on the base too:**
     - If the base has moved and the failure is fixed there, merge the default branch into the PR branch (add commits; never rebase) and push.
     - Otherwise, change nothing for it. Comment on the PR naming the failure and the base commit, and end saying main is red, so the gate's red is read as main's.
   - **It passes on the base:** it is the PR's, fixed as now.
   - The same rule holds for a red CI check in another repository.
   - In *Do not*, add: "Fix a failure that also fails on the base inside this PR."
4. **Course version.** `create-pr`'s `protocol_files` is empty (`.baton/baton.json`), so instruction text is not protocol, and R-BTN-22 needs no `version` bump. Say so in the PR.
5. **Test** in `test/unit/standard-courses.test.ts`, beside the B-102 and B-132 cases: create-pr's implement and fix instructions carry the pre-existing-failure rule, and this repository's `.baton` copies carry it with them.

### Trust

This loosens nothing. The PR is still gated by `run-tests` and the review rounds, and a red gate still routes to `fix`. The agent's claim that a failure is pre-existing is checked on the base by the next legs and by the reviewer, who see the named test and commit. An agent that wrongly calls its own failure pre-existing is caught by the gate, because the gate runs on the PR head, not on the claim.

### Invariants

- **Separate tickets never share a write target** (`docs/context/architecture.mdx`). Main's failure is fixed by its own ticket or PR, never by the PRs that meet it.
- The two copies of each instruction file stay identical.

## Exit criteria

- [ ] Both copies of `implement.md` and `fix.md` carry the rule, and the new test checks it.
- [ ] `npm test` and `npm run typecheck` pass.
- [ ] The next time main is red, an implement leg on bering pushes and opens its PR, naming the pre-existing failure, and no fix leg patches it inside its ticket's PR.
