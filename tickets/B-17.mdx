**Brief:** `docs/context/design-brief.mdx`, written in R3-1248's landing for iterating on Baton's web UI with Claude Design: what the dashboard is for, who reads it, what it shows, and the constraints a design must keep.
**Spec:** [BATON_SPEC §11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) (the dashboard: **Needs you** is the debugger — open conditions
with no handler ticket plus the floor, by severity then age, [R-BTN-163](../spec/BATON_SPEC/07-conditions.md#sec-7-3); **Stop leg**, [R-BTN-119](../spec/BATON_SPEC/08-runners.md#sec-8-4), and a
run's log directory shown as text, [R-BTN-128](../spec/BATON_SPEC/08-runners.md#sec-8-5); session links, [R-BTN-113](../spec/BATON_SPEC/08-runners.md#sec-8-3)); [§12.3](../spec/BATON_SPEC/12-security.md#sec-12-3) (text, never markup).

### Why

The brief exists, but no ticket takes it through a design to a dashboard that implements it.

### What to do

1. **Operator.** The owner iterates on a design with Claude Design from the brief, then exports or links the result.
2. Turn the agreed design into implementation tickets with `npm run ticket -- new`, citing §11.4. Each change must keep §12.3: values are set through `textContent`, and the dashboard loads no remote resource.
3. Update the brief with whatever the design settled.

### Do not

- Implement before the owner has agreed a design: the brief is the input, not the design.

### Tests

- The tickets filed cite §11.4 and the design; `npm run check:wiki` is green.

### Exit criteria

- [x] a design agreed by the owner, linked from the brief
- [x] its implementation tickets filed
