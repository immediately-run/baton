**Brief:** the owner, 2026-11-09 (B-191): "its controls the registry actions placed there by
`ui.view` — so 'what I see' and 'what I can do' come from the same definition."

**Spec:** [BATON_SPEC §11.3](../spec/BATON_SPEC/11-people.md#sec-11-3) ([R-BTN-129](../spec/BATON_SPEC/11-people.md#sec-11-3):

[R-BTN-130](../spec/BATON_SPEC/11-people.md#sec-11-3): a delegated key is `unauthenticated` on
`GET /v1/actions`), [§11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) (the root screen, the
strip and the screen-id grammar as B-191 amends them), [§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1)

**Used by:** B-207, B-208; B-206 (`repo.list.session.role`).

### What to build

The §14 rows first, then the code.

1. **`src/core/screens.ts`** is B-193's table; `check:actions` imports it here for `ui.view`'s
   allowed names, so the front, the router (B-221) and the check read one list.
2. **`GET /v1/repositories`** (`repo.list`, read): callers an administrator key, an owner key,
   and `{principal: "session", roles: ["administrator", "owner"], scope: "instance"}`. Rows: the
   registry row's `id`, `github`, `forge`, `web_base`, `default_branch`, `weight`, `tiers`,
   `courses` (ids and versions), `head: {sha, received_at, observation}`, `mode` (`shadow` or
   `cut-over`, R-BTN-28), `running` (live claims), `ready` (ready tickets), `needs_you` (open
   conditions and queued person legs, R-BTN-163 — until B-57 lands this counts conditions only,
   and the strip's label reads "conditions"), `runners_alive`, `runners_total` (runners with an
   accepted grant), `discrepancies_7d` (R-BTN-85's rows of the last 7 days), `exclusive_goal:
   {id, title} | null` (filled by B-122's goals; null until then); and at the top level, once,
   `session: {role: administrator | owner} | null` (the caller's session role, which the
   sidebar and the code dialog need; null for a key), `link_hosts` and `session_hosts` for the
   client's link rule (§12.3). The sidebar's and the strip's counts come from this row and from
   nothing else (B-208). An administrator's answer also carries
   `seed_owners` as `GET /v1/admin/repositories` does (R-BTN-58). From `adminView`, `readyRows`,
   `claims.running` and the conditions count; an owner's answer is its repositories only.
3. **`GET /v1/actions` for a session** (`actions.list`): the caller's entries as the registry
   holds them — `id`, `summary`, `callers` (the matching one), `effect`, `input`, `http`, `ui` —
   minus `delegated`, filtered as `authorize` filters them: an owner's session sees the entries
   listing `session` for owners, and repository-scoped ones only while it still owns a
   repository; an administrator's every entry listing `session`. A delegated key is
   `unauthenticated` (R-BTN-130).
4. **`ui.view` on every session-callable entry**, by B-191's defaults, each placed by the
   ticket that builds or already has the route: here, on the entries whose routes exist today
   or are B-25's — `ticket.hold`, `ticket.unhold`, `ticket.expedite`, `ticket.cancel`,
   `claim.force-reap`, `scope.resolve` (`POST /v1/ui/scope/{id}/resolve`) on
   `repository/tickets/{ticket}`; `leg.stop` (`POST /v1/ui/messages` with `kind: release`, by
   `match`) on `repository/tickets/{ticket}` and `repository/runners/{runner}`;
   `runner.status-request` and `runner.wind-down` (the same route's other kinds, by `match`) on
   `repository/runners/{runner}`; cut over and the adoption confirm on `repository/sync`;
   `attestation.add` on `repository/conditions/{condition}` and `repository/attestations`. The
   rest are placed by their builders: `ticket.resolve` by B-56, `claim.fence-clear` by B-171,
   `claim.confirm` and `claim.release` by B-222, `repo.resync` and `repo.accept-post` by B-201,
   `ui.logout` by B-206 — each on the screens B-191 names. Route, adopt and every administrator
   key action get none (Decisions 1a, 2a).
   `check:actions` fails a `view` naming no screen in `screens.ts` or set on an entry whose
   `callers` list no `session`, and lists every screen without a control.

### What not to do

- No new write caller, no change to R-BTN-155's list: `ui.view` places what a session may already
  call.
- No per-target filtering in `actions.list`: it answers per caller; a target-dependent control
  is gated by the read's `allowed` word (B-191), computed where the target is known.
- No `GET /v1/ui/state` change.

### Trust

- **`repo.list`** — Baton's record, answered to the caller's role; `seed_owners`, `link_hosts`
  and `session_hosts` are administrator configuration, read-only here.
- **`actions.list`** — the registry, filtered by `authorize`'s rule; a drawing instruction for
  the shell, never authority: every call is authorized again on arrival.
- **`ui.view`** — registry data in this repository, written by PR.

### Invariants

- **One check** (R-BTN-129); **a caller is never shown an action it cannot take**.
- **An owner's session, its repositories** (R-BTN-155); an administrator's, every repository.
- **Readable with a key** (R-BTN-179): `repo.list` answers an owner key and an administrator key
  the same rows.
- **Filter fields only** (R-BTN-33): counts and ids, no body.

### Tests

Scenarios numbered at merge, on both hosts:

- `repo.list` as an owner's session lists its repositories with `running`, `ready`,
  `needs_you`, `runners_alive`, `runners_total` and `discrepancies_7d` equal to the board's live
  claims, its ready rows, the open conditions, the granted runners and the history's rows, and
  `session.role` `owner`; as an administrator's, every repository, `seed_owners` and
  `session.role` `administrator`; as an owner key, the rows with `session` null; as a runner
  key, `forbidden`;
- `actions.list` as an owner's session names `ticket.hold` with `ui.view` and not
  `claim.force-reap`; as an administrator's both; as a delegated key `unauthenticated` (B-191's
  scenario, API half);
- `check:actions` fails a fixture entry with `view: ["repository/nowhere"]` and one with a view on
  an entry whose callers list no session.

### Exit criteria

- [ ] `repo.list` and the session's `actions.list` exist with their §14 rows; every
      session-callable entry whose route exists carries `ui.view`; `check:actions` enforces both
      rules against B-193's `screens.ts`.
- [ ] The scenarios pass; `npm test`, `npm run typecheck`, `npm run check:actions`,
      `npm run check:wiki` and `npm run check:tickets` are green.
