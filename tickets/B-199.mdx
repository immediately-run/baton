**Brief:** the owner, 2026-11-09 (B-191): "**Credentials** — `/grants`, `/owners`, `/tokens`,
`/mcp-keys`, `/sync-keys`, `/check-runners` — who may work here (read-only per the spec; changes
by CLI or confirmed action)." The mockup's Limits section ("What agents cannot change. Read-only
here; change them with `baton owner …` or `baton admin …`") is the shape: a table per kind, the
command named beside it.

**Spec:** [BATON_SPEC §11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) ("Repositories, owners,
grants, MCP keys, instrument keys and bars are shown read-only"; R-BTN-155's confirmed-action
list), [§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1) ([R-BTN-179](../spec/BATON_SPEC/12-security.md#sec-12-1):
`GET /v1/owner/{repository}/grants` is the dashboard's limits over one repository; one role per

owners and grants), [§8.2](../spec/BATON_SPEC/08-runners.md#sec-8-2) ([R-BTN-146](../spec/BATON_SPEC/08-runners.md#sec-8-2):

### What to build

The §14 row first, then the code.

1. **Extend `GET /v1/owner/{repository}/grants`** (`owner.grant.list`): beside `owners`,
   `grants`, `mcp_keys`, `settings` and `bars`, answer `tokens` (`id`, `role`, `capabilities`,
   `max_tier`, `expires_at`, `uses_left`, `registered` — the credential ids it registered,
   R-BTN-117), `sync_keys` (`fingerprint`, `role` sync or mirror, `added_by`, `added_at`,
   R-BTN-93), `check_runners` (`fingerprint`, `name`, `capabilities`, `max_tier`, R-BTN-114),
   and on each owner `kind` (ssh or api), `human_only` (R-BTN-185) and `added_at`; on each grant
   `pending` (not yet accepted, R-BTN-146), `sync` and `checker`. One read for the six screens
   (one entity, credentials, six kinds), as R-BTN-179 already frames it; a session of either role
   calls it (B-192).
2. **The six screens**, each a `<table>` from one field of the read, with the kind's CLI command
   named above it as text (R-BTN-127's names: `baton owner grant add …`, `baton owner owner add
   …`, `baton owner token create …`, `baton owner mcp-key create …`, `baton owner sync-key add
   …`, `baton owner check-runner add …`), and a line saying what each is for in one sentence of
   core's vocabulary:
   - `/grants`: fingerprint (short, full on focus), hostname, label, capabilities as chips, max
     tier, role and domain, checker, sync, pending, set by, granted by and at, other
     repositories; pending grants marked;
   - `/owners`: fingerprint, kind, human-only, added at; a repository whose owners are all the
     deploy seed's carries the `seed_owners` notice (R-BTN-58);
   - `/tokens`: id, role, scope, expiry, uses left, what it registered;
   - `/mcp-keys`: name, minter, actions (each id), expiry, last used, client host and address;
   - `/sync-keys`: fingerprint, role, added by and at;
   - `/check-runners`: fingerprint, name, capabilities, max tier.
3. **The controls that are a session's.** Only what R-BTN-155 lists and R-BTN-129's `callers`
   give a session: today none of the credential writes list `session`, so the screens draw no
   control; if B-73's `owner.mcp-key.approve` (an owner's confirmed action) lands, `/mcp-keys`
   places it by `ui.view` through the confirm-code dialog. The screens never draw a control the
   registry does not give them.
4. **Phone.** Each table collapses to one card per row at 375 px, the fingerprint first.

### What not to do

- No credential write from the dashboard: revocations, additions, role changes and flags stay
  the CLI's (`owner.grant.revoke`, …, §12.2), which the screens name.
- No secret: a token's or MCP key's value is returned once at minting and is never in a read.
- No second read: the six screens poll one `owner.grant.list`.

### Trust

- **The extended read** — Baton's rows: fingerprints, hostnames, labels, names, client hosts
  and addresses are untrusted text validated on write (§12.3) and drawn as text; nothing in it
  is a secret (bearers are stored as hashes, §12.1).
- **Who may read it** — an owner's session on its repositories, an administrator's everywhere,
  an owner key as today (R-BTN-179); a runner key is `forbidden`.
- Nothing is written.

### Invariants

- **Read-only** (§11.4): no credential changes from these screens.
- **One role per key** (§12.1): the screens show the role; they never show a key under two.
- **Bearer secrets only as hashes** (§12.1): no value in any read.
- **Text, never markup** (§12.3); **an owner's session, its repositories** (R-BTN-155).

### Tests

A scenario numbered at merge, on both hosts, with a fixture repository holding two owners (one
human-only), an accepted and a pending grant, a registration token that registered one
credential, an MCP key, a sync key and a check-runner:

- `owner.grant.list` returns the six collections with the fields above and no secret; an
  owner's session reads it, a runner key is `forbidden`;
- under `test/ui/`: each screen lists its rows, the pending grant is marked, the command line
  is text, no control is drawn for a session without an entry; a hostile label is text.
