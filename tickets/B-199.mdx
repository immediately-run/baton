**Brief:** the owner, 2026-11-09 (B-191): "**Credentials** — `/grants`, `/owners`, `/tokens`,
`/mcp-keys`, `/sync-keys`, `/check-runners` — who may work here (read-only per the spec;
changes by CLI or confirmed action)." The mockup's Limits block ("What agents cannot change.
Read-only here; change them with `baton owner …` or `baton admin …`"; Owners, Grants, Probes,
Owner bars, Settings) is the shape: a table per kind with the command beside it. Probes are
tenant-wide and move to `/resources` (B-202); bars and settings to Governance (B-200).

**Spec:** [BATON_SPEC §11.4](../spec/BATON_SPEC/11-people.md#sec-11-4) ("Repositories, owners,
grants, MCP keys, instrument keys and bars are shown read-only"), [§12.1](../spec/BATON_SPEC/12-security.md#sec-12-1)
([R-BTN-179](../spec/BATON_SPEC/12-security.md#sec-12-1): the grants read is the limits over one
repository; one role per key; bearers only as hashes), [§11.2](../spec/BATON_SPEC/11-people.md#sec-11-2)
([R-BTN-58](../spec/BATON_SPEC/11-people.md#sec-11-2): owners and grants), [§8.2](../spec/BATON_SPEC/08-runners.md#sec-8-2)
([R-BTN-146](../spec/BATON_SPEC/08-runners.md#sec-8-2): accepted and pending grants, the sync
flag; [R-BTN-117](../spec/BATON_SPEC/08-runners.md#sec-8-2): registration tokens),
[§11.3](../spec/BATON_SPEC/11-people.md#sec-11-3) ([R-BTN-130](../spec/BATON_SPEC/11-people.md#sec-11-3):
MCP keys listed with the credentials; [R-BTN-127](../spec/BATON_SPEC/11-people.md#sec-11-3): the
command tree), [§3.2](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-2) ([R-BTN-93](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-2):
sync keys), [§3.4](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-4) ([R-BTN-140](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-4):

**Used by:** B-200 (the `consents` field), B-203.

### What to build

The §14 row first, then the code (`admin.ts`'s `grantsView`).

1. **Extend `GET /v1/owner/{repository}/grants`** (`owner.grant.list`): beside `owners`,
   `grants`, `settings` and `bars` (what `grantsView` answers today), answer `mcp_keys: [{id,
   name, minter, actions, expires_at, last_used_at, client_host, client_addr}]` (§14 names the
   field and the code lacks it; the keys exist from B-25, in this ticket's closure), `tokens:
   [{id, role, capabilities,
   max_tier, expires_at, uses_left, registered: [credential_id]}]` (R-BTN-117), `sync_keys:
   [{fingerprint, role: sync | mirror, added_by, added_at}]` (R-BTN-93), `check_runners:
   [{fingerprint, name, capabilities, max_tier}]` (R-BTN-114), `consents: [{home, consented,
   by, at, withdrawn_at}]` (R-BTN-140: each home that lists this repository in `code_repos`),
   and on each owner `kind` (ssh or api), `human_only`, `added_at`; on each grant `pending`
   (R-BTN-146), `sync`, `checker`. One read for the credential screens and B-200's `/consents`.
2. **The six screens** (`src/dashboard/screens/credentials/`), each a `<table>` from one field,
   headed by one sentence in core's vocabulary and the exact R-BTN-127 command that changes
   it, copied from the tree in §11.3 (`baton owner grant add <repository> --key <pub>
   --capabilities <a,b> […]` and `… grant revoke …`; `baton owner owner add <repository> <pub>`;
   `baton owner token create <repository> --role runner […]`; `baton owner mcp-key create
   <repository> --name <name> […]`; `baton owner sync-key add <repository> <pub> --role
   sync|mirror`; `baton owner check-runner add <repository> <pub> --name <hostname> […]`) as
   text:
   - `/grants`: fingerprint (short, full on focus), hostname, label, capabilities as chips, max
     tier, role and domain, checker, sync, pending (marked), set by, granted by and at, other
     repositories;
   - `/owners`: fingerprint, kind, human-only, added at; the `seed_owners` notice where
     `repo.list` flags the repository (R-BTN-58);
   - `/tokens`: id, role, capabilities, max tier, expiry, uses left, what it registered;
   - `/mcp-keys`: name, minter, actions (each id), expiry, last used, client host and address;
   - `/sync-keys`: fingerprint, role, added by and at;
   - `/check-runners`: fingerprint, name, capabilities, max tier.
   No control: no credential write lists a session (§12.2, R-BTN-155), and B-73's
   `owner.mcp-key.approve`, when it lands, places itself on `repository/mcp-keys` by `ui.view`
   (the control belongs to the ticket that builds the action).
3. **Phone.** Each table collapses to one card per row at 375 px, the fingerprint first.

### What not to do

- No credential write from the dashboard; no secret in any read (bearers are hashes, §12.1).
- No second read: six screens, one `owner.grant.list`.
- No conditional on B-73.

### Trust

- **The extended read** — Baton's rows: fingerprints, hostnames, labels, names, client hosts
  and addresses are untrusted text validated on write (§12.3), drawn through `Text`; an
  owner's session on its repositories, an administrator's everywhere, an owner key as today
  (R-BTN-179); a runner key `forbidden`. Nothing is written.

### Invariants

- **Read-only** (§11.4); **one role per key** and **bearers only as hashes** (§12.1).
- **Text, never markup** (§12.3); **an owner's session, its repositories** (R-BTN-155).

### Tests

A scenario numbered at merge, on both hosts, with a fixture repository holding two owners (one
human-only), an accepted and a pending grant, a token that registered one credential, an MCP key,
a sync key, a check-runner and one consent: `owner.grant.list` returns every collection with the
fields above and no secret; an owner's session reads it; a runner key is `forbidden`. Under
`test/ui/`: each screen lists its rows, the pending grant is marked, every command line matches
R-BTN-127's tree (a test reads the names from the registry's command table), no control is drawn,
a hostile label is text.

### Exit criteria
