**Brief:** the owner, 2026-10-19, choosing for R3-1254 part 2: "Depth 4 now, ticket for 5".
**Spec:** BATON_SPEC R-BTN-68 (the model report a PR carries); `model/README.md` *Checked how*.
**Depends on:** R3-1254 part 2 (the model with a leg's prerequisites).

### Requires

None: the model and a machine with Java. The proof runs on the author's machine (R-BTN-68).

### Why

Part 2 of R3-1254 added a leg's prerequisites, retries and blocked ends to the model. On its head, Apalache's bounded proof of `safety` on `small` (`npm run model:verify`) is far slower than before:

| Depth | Time, 4 CPUs | Notes |
|---|---|---|
| 1–4 | about 47 minutes | |
| 5 | about 23 minutes per enabled transition | about 26 of them, so roughly 10 hours |
| 5 on main, before part 2 | 49 minutes | |

Part 2 lowered the proof to depth 4 for now, by the owner's choice. This ticket brings depth 5 back within about an hour.

### What to build

1. **Measure where the depth-5 time goes.** Find which transitions and which invariants cost most: Apalache's per-invariant timestamps, and `--write-intermediate`'s transition list.
2. **Make `small` cheaper for the proof without dropping a behaviour the invariants need.** Candidates:
   - fewer prerequisite shapes in `DEP_SHAPES`-style choices on `small` only;
   - fewer leg choices per step;
   - the provisional-row and retry state bounded more tightly on `small`;
   - invariants split so the expensive ones are checked at depth 5 and the rest at 4.

   State the trade-off of each in the README.
3. **Restore depth 5:** `scripts/model-report.mjs`'s `SIZES.depth`, `model/verify.mjs`'s default, the README and the report's tests.

### Tests

- `npm run model:full` on the head passes at depth 5, with the proof under about 60 minutes on 4 CPUs.
- The regression runs and the 10,000-run simulation still pass. Each reduction of `small` is named in the README with what it no longer reaches at depth 5.
- Depth 5 reaches an `unblocked` event on `small` (claim, fail end, two ticks, the backoff clearing), so the proof exercises `unblockedFollowsBlocked` again; a reduction must keep that. `small`'s one ticket keeps a prerequisite on another ticket out of the proof at any depth: say in the README whether this ticket adds a second, and what it costs.

### Exit criteria

- [ ] `SIZES.depth` is 5 again and a passing `model:full` report for the head shows it
- [ ] merged under the review gate

### Status

2026-10-20, a first part (uncommitted, in the working tree; measured on 4 CPUs): `model:verify` now
checks `pverify`, `step` less the actions no state of `small` enables, with `verifyShape` checked
beside `safety` so the reduction cannot silently go stale, and Apalache's
`search.invariant.mode=after` (one invariant check per step, not one per enabled transition).
Same transitions, same invariants. Depth 3: 9.1 → about 7 minutes; depth 4: 127 → 82 minutes
(measured with other proofs running beside it). Tried and not taken: `--smt-encoding=arrays` and
`funArrays` (Apalache 0.62.1 fails an internal assertion at step 0), `--discard-disabled=false`
(slower at depth 3), `MAX_CLAIMS = 2` on `small` (no change), a four-way split of `safety` in
parallel processes (no faster on 4 CPUs: each process pays the whole search; kept opt-in as
`MODEL_VERIFY_SPLIT=1`), and an inductive check of `safety` from an arbitrary bounded state (did
not finish one step in 30 minutes; `safety` is not inductive without strengthening lemmas, and
drawing the 45-field state is itself the cost). Depth 5 is still several hours: at depth 4 the time
is Apalache's per-transition enabledness queries (25 minutes) and the invariant queries at the
last state (53 minutes), both over the whole symbolic path. `SIZES.depth` stays 4; the next steps
need an owner decision: a `small`-only state without the fleet fields (re-stamps every `@model`
marker), TLC for an exhaustive check of `small`, or a newer Apalache whose `arrays` encoding works.
