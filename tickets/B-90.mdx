**Brief:** the gap-analysis run (finding 3): the CLI has no reads. No `repo list`, no grants
list, no board dump — every answer to "what is registered, who is granted, where does the
ticket sit" needs the dashboard, which sits behind a human Cloudflare Access login a
machine cannot pass. The session's probes leaned on `blocked` and `ticket history` because
they were the only readable routes.
**Spec:** §11 (the routes exist: the registry, the grants, the dashboard state), §5 R-BTN-58
(grants), `cli/baton.mjs` (the `plan`).

### Why

An operator or an agent with an admin or owner key should be able to see the instance's
state without a browser; today's answer to a silent runner is guesswork or a human.

### What to build

1. `baton admin repos` (GET the registry), `baton owner grants REPO` (GET its grants and
   settings), and `baton board REPO` (the dashboard state view's repositories and ready
   sections, or a new read route over the same queries) — each one signed request, one
   JSON answer, exit 1 on refusal.
2. The routes they read are the ones the dashboard serves (`/v1/ui/state`'s sources) behind
   the signed principal, no new core queries where an existing one serves.
3. `baton run`'s startup uses `baton board`'s answer for B-86's "why I can never claim"
   line, and for B-86 item 1's declaration: the board answers `granted_capabilities` beside the
   heartbeat, so a granted runner with no `--capabilities` declares its grant's capabilities.

### Tests

- Integration: each command answers for the seeded two-repository instance, and a key
  without the right role is refused with its code.

### Exit criteria

- [x] an operator with a key can see repositories, grants and the board from a terminal

### Where

Built on baton#108. The three routes read the dashboard's own sections (`uiRepo`, `admin.view`'s
rows) behind the signed principal. Two fields are choices the ticket's "no new core queries where
an existing one serves" forces an answer for, and both are kept deliberately:

- `GET /v1/repositories/{repository}/board` carries `course_files`, each course's stored
  `course.json` legs. No dashboard section serves it, but B-86's "why I can never claim" needs the
  clause of a leg with nothing queued — exactly the leg no `queues` row shows.
- The same board carries `granted_capabilities`, which the heartbeat's answer already names, so a
  runner with no `--capabilities` declares its grant's declaration from one read (B-86 item 1).

The tests are two levels on purpose: `test/unit/eligibility.test.ts` pins the clause logic and the
startup default against a board typed to the route's fields, and `S-BTN-166` (both hosts) drives
the real routes and a granted runner's declaration on the heartbeat it makes. The narrowed
`--capabilities llm-call` case is unit-tested: this repository's fixture courses carry no
`Requires:` clause, so no seeded ticket can starve on a narrower declaration.
