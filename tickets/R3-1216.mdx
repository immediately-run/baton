**Brief:** the Baton project.
**Spec:** `spec/BATON_SPEC.md` §16.2 step 2 (exit), §16.1 R-BTN-28 (shadow reports, `shadow-conflict`), §11.1 R-BTN-13 (runner credentials)
**Depends on:** R3-1213, R3-1214, R3-1215

### Requires

- `human-operator` — exit criteria 1–4: the owner registers runner keys on the fleet,
  restarts sessions, and reviews the week's comparison.

### Why

Step 2's exit (§16.2) is one week in which every git claim has a Baton claim, the reaps the
alarm would have made are reviewed against the witness's, and `locate` is recorded for every
live ticket against what sessions did — before Baton decides anything.

### What to build

A one-week observation: runner keys registered per VM, the Mac and the cloud environment; sessions
restarted from a pulled checkout; at the end, a review note
`content/plans/baton/shadow-week.mdx` with the counts.

### Architecture — the decisions, named

- Keys are registered per machine (`credentials` rows, R-BTN-13 §11.1); only the Mac's may
  declare `human-operator`.
- **Do not:** set cutover; fix a mismatch in place — file each as a BUG item in `baton`.

### Tests

None to write.

### Exit criteria

- [ ] **live leg** (`human-operator`): every fleet VM, the Mac and the cloud environment show as alive runners on the dashboard
- [ ] **live leg** (`human-operator`): over 7 days, every `roadmap: claim` commit has a matching shadow claim, and each `shadow-conflict` event is explained in the note
- [ ] **live leg** (`human-operator`): the note lists the alarm's would-be reaps beside the witness's actions, with every difference explained
- [ ] **live leg** (`human-operator`): `locate` is recorded for every live ticket, and the note compares it with what sessions did, every difference explained
- [ ] `npm run verify` green
