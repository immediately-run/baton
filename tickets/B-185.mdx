**Brief:** the owner, 2026-11-08, asked whether each leg attempt has a unique execution id, while
designing salvage of a failed leg's uncommitted work (B-186) and the leg executor (B-184). The
answer was "by composition, with gaps", and the owner agreed to a ticket for a first-class id.

### Why

What exists, and where it falls short:

- `claim_legs` is keyed `(claim_id, seq)` (`src/migrations/0013_stations.sql`); §13.5 says it has
  an `id`, `session_url`, `leg_log_dir` and `head_sha`, none of which a migration adds.
- The run number is a `COUNT` of the ticket's rows for that leg, taken at `advance`
  (`legFacts`, `src/core/claims.ts`) — a position, not an identity.
- `BATON_LEG=<claim id>.<leg>.<run>` (R-BTN-145) and the leg log's `<run>-<claim id>` (R-BTN-128)
  are unique in practice, but:
  1. a context refresh (R-BTN-123) starts a second session — under B-184 possibly on another
     machine — with the same `BATON_LEG`; only `ctx.refresh.n` tells them apart;
  2. a run an adoption added (R-BTN-39) has a null claim and so no `BATON_LEG`;
  3. claim ids are a tenant's integers: production, staging and a local host all issue claim
     412, so anything keyed by them in a shared place — a forge ref, a log bucket — can collide.

### What to build

1. **Baton mints `run_id` when a leg run starts** — in the `advance` that starts it, and, once adoption (R-BTN-39's
   `baton ticket adopt`, unbuilt) adds runs, for an adopted run — as `r_` plus 26 characters of Crockford base32: 48 bits
   of the time read through `this.now` (R-BTN-32) and 80 bits from the core's existing random
   source (`src/core/db.ts`). Opaque to every reader; no rule parses it.
2. **Stored and returned.** A new migration adds `claim_legs.id` (the surrogate §13.5 already
   names) and `claim_legs.run_id`, unique, backfilling existing rows with minted ids; SQLite cannot
   add a primary key or a UNIQUE column in place, so the migration rebuilds the table (create,
   copy, drop, rename) and recreates its indexes. The
   `advance` reply carries `run_id`; the history's leg rows (R-BTN-81), the run list behind
   `baton leg log` (R-BTN-128), `previous_attempts` and the resume record (R-BTN-24) carry it.
   Land the other §13.5 columns this needs (`session_url`, `leg_log_dir`, `head_sha`) in the same
   migration, or record in the PR why one stays out.
3. **The runner exports it.** Every leg process gets `BATON_RUN_ID`; `BATON_LEG` stays unchanged
   (R-BTN-145 keys process stopping on it). Both new names join R-BTN-144's table of the only
   environment names a leg is given.
4. **A refresh's session is `<run_id>.r<n>`.** The runner forms it (Baton knows of a refresh
   only through the `context-handoff` activity, which B-12 adds and which records both session
   ids; until B-12 lands there is no refresh and no suffix but `.r0`), exports it as
   `BATON_SESSION_ID` (`<run_id>.r0` for the first session).
5. **Outside Baton, prefix the tenant.** Anything a runner writes to a place another tenant could
   also write — a forge ref, a bucket path — is keyed `<tenant host>/<run_id>` or a path form of
   it, the tenant host being the host of the tenant's configured origin (R-BTN-135) in
   R-BTN-63's ref-safe form. B-186's refs are the first user.
6. **Leg logs move to the run id.** A run started after this lands writes under
   `<root>/<tenant host>/<repository id>/<local ticket id>/<leg>/<run_id>/` (a bucket may serve
   several tenants, item 5); `baton leg log` reads both forms.

### What not to do

- **No meaning in the id.** No reader sorts, parses or compares run ids except for equality;
  order comes from `started_at` and `seq`.
- **Do not replace `BATON_LEG`** or the run number: the run number stays what `max_runs` and the
  dashboard count.
- **No runner-minted run id.** The runner forms only the `.r<n>` suffix; the run id is Baton's.

### Trust

- **`run_id`** — minted by Baton, returned only to the holder and readers of the ticket's history;
  not secret, not a capability: knowing one grants nothing.
- **`BATON_SESSION_ID`'s suffix** — the runner's word, recorded in the `context-handoff` activity
  like the rest of that activity (R-BTN-46).
- **The tenant prefix** — from the claim response's tenant URL, never from repository files.

### Invariants

- **Migrations are append-only:** one new numbered file; no edit to 0013.
- **One clock** (R-BTN-32): the time half of the id comes from `this.now`; tests fix it with
  `setClock`, and the random half through a seam tests can fix (add one if `db.ts` has none).
- **Filter fields only** (R-BTN-33): an id is a filter field; no body or note is stored.
- **Existing readers keep working:** the history, `baton leg log` and resume records add a field
  and remove none.

### Tests

- Two runs of one leg on one ticket get distinct run ids (an adopted run's, once adoption lands).
- The backfill gives every existing `claim_legs` row a distinct id.
- Once B-12 lands: a refresh exports `<run_id>.r1` to the second session, and the
  `context-handoff` activity names both session ids.
- The `advance` reply, the history row and `previous_attempts` carry the same run id.
- Each behaviour change names its `S-BTN-n` scenario (R-BTN-31).
