**What:** a forge's refusal of a workflow dispatch is never logged. `dispatchWorkflow`
(`src/core/mirror.ts`) catches every error and returns `res.ok`, so the `dispatch-refused`
discrepancy that `src/core/baton.ts` logs in its `catch` can never fire: a 404 or a 422 is a
silent `false`.

From the architecture review of 2026-11-19 (`docs/review/architecture-review-2026-11-19.mdx`, on the branch `review/architecture-2026-11-19` until it lands).

**Spec:** [BATON_SPEC §3.3](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-3) ([R-BTN-94](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-3)): Baton may dispatch a sync run, and a refused dispatch is a
discrepancy an owner can read.

### What to build

`dispatchWorkflow` throws on a non-2xx answer, carrying the status and a reason capped in length
and stripped to text; it keeps returning `false` for a missing token. The caller's existing
`catch` then logs `dispatch-refused`.

**Done when:** a scenario drives the real adapter against a stubbed 422 and reads the event from
the log.

### Trust

The reason is the forge's response body, written by a party Baton does not control. It is capped,
stored as text and rendered as text; it never reaches a log line unbounded and never carries the
request's credential.

### Invariants

- [BATON_SPEC §1](../spec/BATON_SPEC/01-what-baton-is.md#sec-1) ([R-BTN-33](../spec/BATON_SPEC/01-what-baton-is.md#sec-1)): filter fields only. The stored reason is a short status text, not a
  payload.
- A refused dispatch never fails the request that wanted it: the want is recorded, and a runner
  can still pull it.
- Text, never markup, wherever the event is shown.
