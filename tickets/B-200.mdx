### What to build

The §14 row first, then the code.

1. **`GET /v1/repositories/{repository}/attestations`** (`attestation.list`, read; the
   repository reads' principals and a session): the repository's attestations —
   `id`, `type`, `subject`, `value` (the validated JSON, as a blob), `writer` (the credential's
   fingerprint or `mcp:<id>`, and the writer class the policy judged it as: `owner`, `human`,
   `service`, `runner`, `sync`), `domain` and `run_label` where the writer's grant carries them,
   `written_at`, `lapses_at`, `revoked_at`; `?subject=` (a ticket id or commit), `?type=`,
   `?live=1` (not lapsed, not revoked) and `?cursor=`, 100 a page. From the attestations table
   R-BTN-181 defines. `GET …/policy` and `…/policy/log` and the grants read already carry the
   rest; this ticket adds a session to the callers of `…/policy/log` if B-192 did not.
2. **`/repositories/{r}/policy`**: from `GET …/policy`: version, hash, preset if one was
   applied, the policy document pretty-printed as text (§12.3: a blob as JSON), the guarantees
   it meets as a list with a mark per guarantee and the `floors` it must keep marked as such
   (R-BTN-189), `check_app_id`; below, the log from `…/policy/log` as a `<table>` (version,
   hash, previous hash, changed by, approver, preset, at, changed keys), newest first. The CLI
   lines that change it — `baton owner policy set …`, `baton owner policy apply …` — as text; no
   control (the policy's write is never a session's).
3. **`/repositories/{r}/settings`**: the owner settings from the grants read's `settings`
   (§13.1's keys: `code_repos`, `retry`, `transcript_repos`, `api_keys`, `scope_policy`, the
   rest as the data model lists them), each with its value as text and a one-line meaning, and
   the repository's tiers and weight from the registry row; `baton owner settings set …` named.
4. **`/repositories/{r}/bars`**: owner bars in force and scheduled (course, tag, legs, applies,
   starts, ends, release holders, reason, set by — an `mcp:<id>` shown with its key's name) and
   the required bars (course, except legs, tag prefix) from the grants read's `bars` and
   `settings`; `baton owner bar add …`, `… lift …`, `… follow …` named. No control: the lift is
   an approver's by key (R-BTN-186).
5. **`/repositories/{r}/consents`**: the code-repository consents (R-BTN-140): each `repos:`
   home that lists this repository, consented or not, by whom and when, withdrawn when; from the
   grants read (added there if absent: `consents`). `baton owner consent add|withdraw` named.
6. **`/repositories/{r}/attestations`**: the `<table>` from `attestation.list` with its filters
   as URL query (subject, type, live), each row's `value` expandable as pretty-printed JSON,
   lapsed and revoked rows marked; the one control a session has, by `ui.view`: **Add
   attestation** for an owner's session where the policy's `attestations` admits writer `owner`
   for the chosen type (`attestation.add`, R-BTN-181 — the entry's `input` schema is the form:
   type, subject, value, lapses), and nothing where it does not; revocation is the writer's by
   key (`baton attestation revoke`), named as text.
7. **Phone.** Tables collapse to cards at 375 px; the policy document scrolls inside its box.

### What not to do

- No policy, settings, bar or consent write from the dashboard: those are keys' and approvers'
  (R-BTN-186, R-BTN-188); the screens name the commands.
- No guarantee computed in the app: `guarantees` and `floors` are the read's.
- No `human` attestation from a session (R-BTN-185: a session is `owner`, never `human`).

### Trust

- **`attestation.list`** — Baton's rows: `value` and `subject` are validated JSON and
  identifiers (§12.3), drawn as pretty-printed text; `writer` is a fingerprint or `mcp:<id>`,
  text; the policy document is an opaque blob drawn as JSON.
- **`attestation.add` from a session** — writer `owner` (R-BTN-181), bounded by the policy's
  writer list on the server; the form sends what the entry's schema admits; a refusal is text.
- Nothing else is written.

### Invariants

- **The policy is held in Baton, never in git** (R-BTN-188): shown from the read, changed by an
  approver's key.
- **Floors are refusals Baton makes** (R-BTN-189): the screen marks them; it enforces nothing.
- **A session writes as `owner`, never `human`** (R-BTN-185).
- **Text, never markup** (§12.3); **an owner's session, its repositories** (R-BTN-155).

### Tests

A scenario numbered at merge, on both hosts, with a fixture repository under `protected` with two
policy versions, a scheduled owner bar set over MCP, a required bar, one consent and three
attestations (one lapsed, one revoked, one `human`):

- `attestation.list` filters by subject, type and live, pages, and never returns a value a
  session may not read; an owner's session reads it; `…/policy/log` admits the session;
- under `test/ui/`: the policy screen marks the floors; the bars screen shows `mcp:<id>` with
  its name; the attestations screen draws **Add attestation** under a policy admitting an owner
  writer and not under one that does not; a hostile `subject` is text.
