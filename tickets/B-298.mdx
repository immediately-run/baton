**Brief:** ruling 1 of the spec simplification moved every unbuilt design out of
`spec/BATON_SPEC/` into `spec/proposals/`, eleven pages and 281 KB
([the review](../docs/review/spec-simplification-review-2026-11-19.mdx), *Applied on this
branch*). Each page's `**Status:**` line says where its text returns and which tickets build
it, and the front page names the folder, but the rule that a building ticket moves the text
back is written nowhere an agent reads before work: not in `CLAUDE.md`, not in
`docs/context/spec-writing.mdx`, not in the babysit skill, and no check reads the pages. On
filing, the lists were already partly wrong: `conditions.md` named B-63 (superseded),
`courses.md` named B-28 and B-29 (done and archived) as builders of text that is still a
proposal, and two designs (the `branch` course, the ticket source's writer exports) have no
ticket. The Status lines that named a dead ticket or missed a live builder (four pages) were corrected in PR #299 on
2026-11-20 (the table below is as corrected); the rest of step 3 stands.

**Spec:** BATON_SPEC front matter (*Companions*), [§15](../spec/BATON_SPEC/15-verification.md#sec-15) ([R-BTN-31](../spec/BATON_SPEC/15-verification.md#sec-15), [R-BTN-30](../spec/BATON_SPEC/15-verification.md#sec-15)).

## Plan

1. **Write the convention once, and point at it.** In `docs/context/spec-writing.mdx`, a
   section *Proposals*: `spec/proposals/` holds designs that are not built and bind nothing; a
   rule id whose design is there keeps its id and one line in its section with a link to the
   page; the PR that builds a design moves its rule text into the section file and its
   scenario and gate rows into §15, deletes them from the page, and deletes a page left empty;
   a new design starts on a proposal page, by PR, and a ticket that needs a ruling still gets
   it in the spec first (the babysit skill's *Decide in the spec*). `CLAUDE.md`'s first
   paragraph and the babysit skill's *Spec PRs* each gain one sentence citing that section.
   These are standing guidance: they land through the owner's review of the PR.
2. **A check, in `npm run check:spec`.** For each page of `spec/proposals/`: it has a
   `**Status:**` line; every ticket id on that line is a live ticket (a done, archived or
   superseded one fails, naming it), or the line says `tickets: none yet`, which is listed and
   never fails; every `S-BTN-n` on `scenarios.md` has no test file under `test/` (one with a
   test belongs in §15, by R-BTN-31); and no rule id is defined (`**R-BTN-n (`) on a page,
   since ids are defined in section files only. `npm run check:tickets` lists, without
   failing, a live ticket whose Spec line cites a rule that is one line and a proposal link in
   its section, so a claimant knows the design it builds is on a page.
3. **Close the gaps in the table**, in the same PR or in tickets it files: keep each Status
   line to live tickets (four were corrected on 2026-11-20; the check of step 2 tells a
   builder named on a Status line or a group line from a done ticket cited in the text for
   where a fact came from, which is history and stays); for B-28, B-29 and B-99's text in `courses.md`, read the code and
   either move the built part back to §5 or name the ticket that builds the rest; for
   `branch-course.md` and the writer exports, ask the owner whether to file a ticket or delete
   the design, and do that; remove R-BTN-200's design from `tickets-and-sources.md` if the
   rule is retired. This step changes spec pages: history entry with `Rules changed:` (`none.`
   when only proposal pages and Status lines change).
4. **A note on each building ticket.** Every live ticket in the table gains one dated line
   under its `## Status`: "its design is on `spec/proposals/<page>`; the PR that builds it
   moves the rules and scenarios back (B-298)". For a ticket another session holds, the note
   only, as the babysit skill says.
5. **This ticket stays open as the list.** It is done when the folder is empty or the owner
   closes it; until then the table above is regenerated by the check's listing, and a page
   added or removed updates it in the PR that does so.

### Trust

No new input to Baton. The inputs are files in this repository: the proposal pages, which
anyone who can push writes, and which bind nothing by their own first line. The risk the
convention must not create is the reverse of that line: text on a proposal page read as a rule.
The check's "no rule id is defined on a page" and the section files' one-line stubs keep the
normative text in one place, and a ticket citing only a proposal page for its authority is
building a design, not a ruling, until its spec PR is merged by the owner. The edits to
`CLAUDE.md`, the skill and the context page are instructions to agents (reach 3) and go
through the owner's review. The check reads repository files and runs no code from them.

### Invariants

- BATON_SPEC [R-BTN-31](../spec/BATON_SPEC/15-verification.md#sec-15): scenarios are part of drafting, and every behaviour change names its
  scenario. A scenario moves to [§15](../spec/BATON_SPEC/15-verification.md#sec-15) in the change that makes its test pass, and the check
  fails a tested scenario left on the proposals page.
- BATON_SPEC [R-BTN-30](../spec/BATON_SPEC/15-verification.md#sec-15) and the front matter: scenarios are named, and ids are stable. Moving a row keeps its id; the
  check fails an id that appears both in [§15](../spec/BATON_SPEC/15-verification.md#sec-15) and on `scenarios.md`.
- One home per statement (`docs/context/spec-writing.mdx`): a design's text is on its page or
  in its section, never both.
- Tickets are tasks, not authority (CLAUDE.md): the notes of step 4 describe where a design
  is; they give no ticket leave to build what the owner has not ruled.
