**Brief:** the Baton project.
**Spec:** `spec/BATON_SPEC.md` §2.1 (the service, the `baton-staging` tenant), §11.1 (keys), §11.2 R-BTN-57, §11.4 R-BTN-155 (dashboard sign-in), §12.1 (principals), §12.4 R-BTN-16, §12.7 (Baton's GitHub App), §15 (staging)
**Depends on:** R3-1207
**Runbook:** `DEPLOY-RUNBOOK` — every step below from the command line, with the check after each.

### Requires

- `cloudflare-admin` — exit criteria 1–4: the Worker route, Access application and Worker
  secrets live in the owner's Cloudflare account.
- `github-admin` — exit criterion 5: the `CLOUDFLARE_API_TOKEN` repository secret.
- `human-operator` — the Cloudflare and Access consoles are interactive.

### Why

R3-1207's deploy workflow cannot run until the account, route, Access policy and secret
exist, and only the owner holds them.

### What to build

The owner, in one sitting (about 30 minutes):

1. In Cloudflare: the `immediately.run` zone serves the Worker `baton` at
   `baton.immediately.run/*` and the staging Worker `baton-staging` (its own Durable Object
   namespace) at `baton-staging.immediately.run/*` — both declared in
   `immediately-run/baton`'s `wrangler.toml` (baton#2), so the first deploy creates them. Add
   the DNS records both hostnames need (proxied).
2. *(Optional hardening, R-BTN-16.)* In Zero Trust → Access: a self-hosted application for
   `baton.immediately.run` (and one for `baton-staging.immediately.run`) with a policy allowing
   only the owner's email, **covering only** the dashboard's pages `/`, `/login` and
   `/oauth/authorize`, `POST /v1/login` and `/v1/ui/*`, and **bypassed on every other path**:
   keys, webhooks (`/v1/github/webhook`), forge notifications, couriers, instruments, CI
   identities and MCP clients call those without an Access cookie, and each authenticates its
   own requests or is public (adv-4 m5). Baton never requires Access and never reads its
   cookie or JWT.
3. The Worker secret **`BATON_ADMIN_KEYS`** in both environments — the owner's SSH public
   key: `npx wrangler secret put BATON_ADMIN_KEYS < ~/.ssh/id_ed25519.pub` (BATON_SPEC
   R-BTN-57, §11.2). *(2026-10-14, restated 2026-10-20: administrators are these keys and the
   dashboard signs in with a code an administrator confirms (R-BTN-155, §11.4); Access in step
   2 is optional hardening (§12.4). No `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` or `OWNER_EMAILS`
   var is set: Baton reads no Access assertion — B-46 removes the code that still does
   (`verifyOwner` in `src/core/auth.ts`, `src/core/front.ts`).
   Use a separate, touch-required administrator key, `~/.ssh/baton_admin.pub`, never loaded into
   an ssh-agent agent sessions reach — R-BTN-57.)*
3a. The Baton GitHub App (BATON_SPEC §12.7, R-BTN-73 §3.3): create
   it with **Actions: write** and read-only **Contents**, **Pull requests** and **Issues** (the
   permissions its subscriptions need; no Checks), subscriptions to `push`, `pull_request`,
   `pull_request_review`, `issue_comment` and `workflow_run`, webhook URL
   `https://baton.immediately.run/v1/github/webhook` and a generated webhook secret; an
   **organisation owner** of `immediately-run` installs it on `immediately-run/docs` and the
   code repositories docs' tickets change (GitHub's rule; a Baton owner key cannot); then `npx wrangler secret put BATON_GITHUB_APP_KEY` (its
   private key) and `BATON_GITHUB_WEBHOOK_SECRET` in both environments.
4. An API token with **Workers Scripts: Edit** on this account and **Zone: Read** plus
   **Workers Routes: Edit** on the `immediately.run` zone — wrangler resolves the zone and
   writes the two routes on deploy (found in baton#2's review).
5. In GitHub `immediately-run/baton` → Settings → Environments → `production`: the secret
   `CLOUDFLARE_API_TOKEN` (the deploy workflow lives in that repository since the owner moved
   Baton's code there, BATON_SPEC §2.1).
6. Re-run the latest `baton-deploy` workflow on `immediately-run/baton` `main`.
7. In GitHub `immediately-run/docs` → Settings → Variables: `BATON_ENABLED` = `true`, which
   turns on `baton-sync.yml` (off until now, so it never ran against a Worker that was not
   there); dispatch it once and check the run posts the board.

### Architecture — the decisions, named

- One account, one zone; staging shares the Worker code but never the Durable Object.
- The API token is scoped to Workers Scripts on this account and Zone Read plus Workers
  Routes on the one zone, nothing else.
- **Do not:** add the test signing key to any deployed environment (§15); allow any email
  but the owner's in the Access policy; put any path but the dashboard's pages, `POST /v1/login`
  and `/v1/ui/*` behind Access; set the Access vars.

### Tests

None to write: provisioning. The live checks are R3-1209.

### Exit criteria

- [ ] `curl -sI https://baton.immediately.run/` answers with an Access redirect (`302` to the team domain)
- [ ] `curl -s https://baton.immediately.run/v1/sync/head` answers `401` `unauthenticated` (reaches the Worker, not Access), and so do `/v1/owner/x/grants`, `/v1/admin/repositories`, `/v1/actions` and `POST /v1/mcp`; `POST /v1/github/webhook` without a signature is refused by the Worker, not redirected by Access
- [ ] `curl -sI https://baton.immediately.run/v1/ui/state` answers with an Access redirect (Access covers `/v1/ui/*`)
- [ ] `npx wrangler secret list` shows `BATON_ADMIN_KEYS` in both environments
- [ ] the `baton-deploy` run on `main` is green for both environments
- [ ] `wrangler deployments list --name baton` shows the deploy
- [ ] the `production` environment secret `CLOUDFLARE_API_TOKEN` exists in `immediately-run/baton`
- [ ] the docs variable `BATON_ENABLED` is `true` and the dispatched `baton-sync` run is green
- [ ] `npx wrangler secret list` shows `BATON_GITHUB_APP_KEY` and `BATON_GITHUB_WEBHOOK_SECRET`, and the App's recent deliveries page shows a delivery to `/v1/github/webhook` answered 2xx
