## Plan

1. **Row 1: decide who manages sync keys, then make the three places agree.** Recommended:
   build the owners' two routes. R-BTN-93 gives the reason: a sync key is a repository's
   credential, and its owners already manage the repository's grants and owner keys; today
   revoking a leaked sync key needs the tenant's administrator. The routes are owner actions
   under R-BTN-188's `approvers.members` like the other credential changes, with
   `owner.sync-key.revoke` in §12.2's destructive list as the spec has it, and the CLI gains
   `baton owner sync-key add|revoke` (B-157's tree). The other answer is to amend R-BTN-93,
   §12.2, R-BTN-127 and §14 to "an administrator adds and removes sync keys"; then B-199's
   item naming the owner commands is struck. The spec PR records the owner's choice either way.
2. **Row 2: amend the spec to the code, unless the owner wants the general window.** State that
   the 30-second window and its trailing dispatch belong to notification-triggered syncs
   (R-BTN-73's backstop reads the same row), keyed by repository, and that any other dispatch
   is sent once per committing transaction. A general window would need a `webhook_syncs` row
   per workflow and the alarm reading it for every dispatch; nothing reported so far needs it,
   since a forge already queues workflow runs.
3. **Row 3** is B-288's: its plan now names `flushDispatch`'s filter. This ticket only checks,
   when both are open, that R-BTN-94's first paragraph and the code agree after B-288.
4. **Rows 4 to 10: one "Not built" list at the head of §3**, each entry a rule id, the part
   that has no code, and its ticket, restating no design. For row 4 the PR also asks the owner
   which way the rule goes, because two tickets point opposite ways: R3-1270 builds
   machine-key sync, and B-137 with B-189 item 7 remove machine keys from `inputs.board`. Until
   that is ruled, §3.2 says a machine key cannot sync and the `machine` value of `inputs.board`
   admits nobody.
5. **Spec mechanics.** History entry with `Rules changed:` naming R-BTN-93 and R-BTN-94 (and
   any other whose sentence changes); `npm run spec:index`; `npm run spec:impact` over the ids
   and the terms `sync key`, `coalesc`, `dispatch`.
6. **Tests.** If row 1 is built: an owner adds a sync key and the key posts a board; a second
   repository's owner cannot; a key that holds another role is `conflict`; a revoked key is
   `unauthenticated` at its next request; a delegated key is refused the revoke (R-BTN-130).
   Named under the scenario that covers sync keys today (S-BTN-156), or a new one from `node
   cli/baton.mjs tickets next scenario --for B-301`. Rows 2 and 4 to 10 change text only.

### Trust

One new input, if row 1 is built: a request that adds or revokes a sync key, written by an
owner key of that repository and verified as every owner request is (SSH signature, nonce,
`approvers.members` as the policy stood, R-BTN-188), its body validated in
`src/core/validate.ts` before any SQL. A sync key is the credential behind reach 7 of
`docs/security-model.mdx` (whoever holds it posts the board), so the add is a loosening and
needs the same approver class as a grant; a break-glass line must not reach it without being
the repository's `human_key` (B-294's finding applies to this route from its first commit).
Nothing in this ticket reads a sync key's private half, changes a CI workflow or touches a
deployment's secrets; `baton repo init`'s CI configuration is unchanged.

### Invariants

- BATON_SPEC [R-BTN-93](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-2): `verifySync` is the only check on `/v1/sync/*`, and a key holds one
  role. The new routes write `sync_keys` rows through the same uniqueness checks the
  administrator's path uses (`admin.ts:228`).
- BATON_SPEC [R-BTN-57](../spec/BATON_SPEC/11-people.md#sec-11-2): an administrator key is never a sync's. The owners' add refuses one.
- BATON_SPEC [R-BTN-188](../spec/BATON_SPEC/12-security.md#sec-12-8): no list is left without a key to satisfy it; revoking a sync key
  touches no approver list.
- BATON_SPEC [R-BTN-94](../spec/BATON_SPEC/03-repositories-and-forges.md#sec-3-3): a dispatch is recorded in the transaction that causes it and sent after
  the commit. Row 2 changes what the rule says about windows, not when a dispatch is sent.

  nothing.
