<Lede>The durable home for what real runs taught: every entry is dated, names its
evidence, and says what changed. A lesson that a ticket or a PR carries links it; one
still waiting for its fix says so.</Lede>

How to use this page:

- **Before operating** an instance or a runner, read the entries marked *still true*.
- **After a run that surprised you**, append one entry at the bottom: the date, one
  paragraph of what happened with links, one bold sentence carrying the lesson, and what
  changed. Never edit an old entry except to flip its status when its fix lands.
- A lesson is bigger than a bug: it is a way we were wrong about how the system behaves.
  Bugs go to `tickets/`; the lesson is what the bug taught about operating Baton.

## 2026-10-21 — the self-hosting gap analysis and the first acceptance run

The full story is
[`review/gap-analysis-2026-10-21.mdx`](review/gap-analysis-2026-10-21.mdx); the run
registered this repository on `https://baton.immediately.run`, cut it over from its
first ticket, and took B-80 from a claim to a merged PR ([#81](https://github.com/immediately-run/baton/pull/81)).
These are its lessons, newest understanding first.

- **A reverse proxy in front of the machine API breaks every operator command, and a
  client that follows redirects calls the failure success.** Cloudflare Access covered
  everything but `/v1/sync/*` and `/v1/runner/*`; the CLI followed the 302, the login
  page answered `200`, and `baton admin repo add` printed `null`, **exit 0**. Fixed
  both ways: twelve bypass apps for the six self-authenticated machine paths (the
  dashboard keeps Access — it is its principal), and the CLI refuses redirects and
  non-JSON 2xx answers ([B-80](https://github.com/immediately-run/baton/pull/81)).
  *Status: fixed; re-verify with the probes in the report if the Access config ever
  changes.*

- **The leg stub trusts the agent's exit code, not its outcome.** B-71's implement
  agent finished with exit 0 having committed nothing and opened no PR; the stub
  returned `pr-open`, the claim advanced to a review of nothing, and the round burned
  half an hour before a human stopped it. The board cannot fence this: no sync ever
  showed `pr-open`, so there was nothing to regress from. **A leg's `run` must verify
  its own outcome before returning its position** — for `create-pr`'s implement, that a
  PR of the branch pattern exists. *Status: filed as [B-81](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-81.mdx);
  the instructions alone did not enforce it.*

- **A machine reads the agent's last line; the agent must be told so, in the place it
  reads.** The first review round was refused — verdict prose around the word — and the
  claim released cleanly (`cannot-finish:transient`), which is the design working; the
  failure was the prompt's. [PR #82](https://github.com/immediately-run/baton/pull/82)
  spells the contract out in the leg instructions and `agent_command`. **Result-dependent
  legs say "a machine parses your last line: exactly the value word, optionally one URL,
  nothing after."** *Status: instructions hardened ([PR #82](https://github.com/immediately-run/baton/pull/82)); the tolerant parser is filed as [B-85](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-85.mdx).*

- **The backstop sync's cron does not fire.** In three hours of a 15-minute schedule,
  GitHub ran it zero times; every board refresh came from a push or a manual dispatch.
  The measurement since is no better: 14 scheduled runs in the 51 hours to 2026-10-24
  13:34, gaps of two to five hours, against the 96 a day a 15-minute cron implies. A stale
  board is not just missing news — it is what the regression fence needs to do its work.
  **Between pushes, dispatch `baton-sync.yml` when freshness matters.** *Status: the cron
  still is not the backstop. Baton's webhook receives the App's `pull_request` deliveries
  again (§7.1), so a merge dispatches the sync itself (one per merge, inside R-BTN-73's 30-second window), and
  the alarm dispatches one when the repository's last is over 10 minutes old — a run of
  the fifteen-minute cron alone would now leave the board at most that far behind. The
  delivery half waits on B-92's verified App; the channel itself is
  [PR #107](https://github.com/immediately-run/baton/pull/107).*

- **A failed sync leaves its observation outstanding, and the next sync within ten
  minutes goes `busy` — exit 0, nothing posted.** The 10:34 failure (the `repos: [docs]`
  404) cascaded `busy` through the next two pushes; the filing of B-80 waited two syncs
  for no visible reason. This is R-BTN-62 voiding as designed, but it looks like
  success. **After a failed sync, expect one silent `busy`; check the outcome line, not
  the green check.** *Status: never silent, in
  [B-89](https://github.com/immediately-run/baton/pull/107): every run ends with its
  outcome line, and the workflow's annotation step reads it — a notice for a post, a
  warning saying nothing was posted, an error for any other outcome or none. Not every
  silent case is red: a `busy` or `held` run ends green under a CLI that exits 0 for it
  (this repository's pinned CLI's `busy`), and its warning is what says the board was held.
  The retry that makes a `busy` run post (`--busy-retry`, exit 1 when it is busy too) lands
  when the workflow's pin carries the new CLI. The board is held for up to R-BTN-62's ten
  idle minutes either way.*

- **A repository's own tickets name it in `repos:`, and `repo init` writes an empty
  `repos` map.** The default source refuses the whole board until the map resolves every
  short name; and any `.mdx` with an `id` under `items` boards as a ticket, including
  Grove project pages. **Self-hosting needs the map filled and the source scoped** —
  ours is `.baton/tickets.mjs`, top-level `*.mdx` plus `archive/` (PRs
  [#77](https://github.com/immediately-run/baton/pull/77),
  [#80](https://github.com/immediately-run/baton/pull/80)). *Status: fixed for this
  repository; the defaults remain a trap for the next self-hoster.*

- **`--harness` is telemetry; `agent_command` is the runner.** `baton run` reports the
  harness in its heartbeat and spawns nothing with it — the legs run
  `.baton/baton.json`'s `agent_command`, whose init default is `echo`: a first run
  "succeeds" every leg with a no-op agent. **Set a real `agent_command` before the
  first claim, pin its model, and redirect its stdin** — the stub's `sh -c` environment
  hangs `opencode run` deterministically without `< /dev/null` (root cause still
  unexplained; ruled out: signals, trust prompts, the service). *Status: filed as
  [B-83](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-83.mdx) (the command) and
  [B-84](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-84.mdx) (the spawn).*

- **The runner declares `--capabilities agent-venue` and nothing else, whatever the
  grant allows.** The first acceptance runner registered, recommended, and idled — the
  gate had no `create-pr` capability to match the course's legs; the silence was total.
  **Pass `--capabilities` to match the grant.** *Status: filed as
  [B-86](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-86.mdx).*

- **A seeded second repository changes what tests mean, not just what they read.** The
  transcript allow-list is a union over registered repositories; a bare claim's refusal
  code flips with `anyCutOver()`; state views gain a row. Sixteen assertions across
  eight files assumed one registered repository. **When `BATON_REPOSITORIES` changes,
  run the suite before anything else** (PRs
  [#78](https://github.com/immediately-run/baton/pull/78),
  [#79](https://github.com/immediately-run/baton/pull/79) — and read the failed list
  without truncation; the sixteenth failure hid behind a `head -15`). *Status: fixed;
  the lesson is the reading habit.*

- **One repository, one Baton.** The owner's decision: a git repository is served by a
  single Baton, because two boards drift and contradict; staging does not register this
  repository, and the seed lives in the top-level (production) vars only. Registration
  is live now but survives fresh deployments only through that seed agreeing with what
  `admin repo add` wrote. *Status: policy.*

## 2026-10-21 — the resumed loop: B-71's review rounds

- **A leg's close can outlive its claim — and silence the runner with it.** B-83's
  implement agent finished at 16:09; the runner's heartbeats stopped at 17:28 with the
  process alive; the leg's result landed at 18:09 — a two-hour close; the server reaped
  the claim (`reaped:silent`); the runner then died with no log line and no crash
  report. The morning's identical `reaped:silent` (then "unexplained") was the same
  thing. The close's `git push` is unbounded — no timeout, no terminal to answer an ssh
  prompt — and whatever blocked the runner's loop beside it, the heartbeat timer is
  independent by design, so silence means the loop itself was blocked. **Bound every git
  call (`GIT_TERMINAL_PROMPT=0`, ssh BatchMode, a kill on timeout), and never accept a
  traceless death: a runner's shutdown must log.** Filed as
  [B-94](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-94.mdx).

- **The client's exit is not the agent's word.** `opencode run` is a client of a
  background service. In B-71's first review round, subagent launches on other providers
  errored; the client exited at 14:55 mid-review; the stub read truncated stdout, found
  no verdict, refused the round and released the claim — while the service kept the
  session running, finished it twelve minutes later, and posted the complete review (five
  inline comments, a protocol-perfect last line) to a claim that no longer existed. The
  verdict protocol was never violated; the completion signal was. **A leg's completion
  must be the agent's, not the client process's** — for opencode, run `--standalone`
  (in-process; the client cannot exit ahead of its session). And when diagnosing a
  refused round, read the session store, not the stub's error: the work may exist.
  *Status: filed as
  [B-84](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-84.mdx)
  (the completion contract), bounding
  [B-85](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-85.mdx)
  (the parser).*

- **B-84's "unexplained" hang is explained: it was `execFile`'s stdin, not the shell.**
  Building B-84 reproduced the hang with no harness at all: `execFile('cat')` never
  returns, because execFile leaves the child's stdin an open pipe it never writes and
  never closes — the `stdio: ['ignore', …]` option is not honoured for fd 0 (`spawn`
  honours it; that, not the shell, is why "direct spawn works and `sh -c` hangs" — the
  two tests differed in API, not only in shell). An agent that reads stdin (opencode's
  client does) blocks on that pipe forever: zero output, idle, the claim burning until
  reap — and `--standalone` and signal traps change nothing, exactly as observed.
  **When a child must not wait on stdin, use `spawn` with `'ignore'`, or close
  `child.stdin` the moment `execFile` returns it** — the stub now does the latter,
  reproducible in the suite. *Status: fixed with
  [B-84](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-84.mdx);
  the reproduction and diagnosis are in its PR.*

- **A grammar borrowed for its checker is not a grammar for prose.** B-111's ticket check
  compared each ticket body's `**Depends on:**` line with its `depends_on` by matching the
  board's own id pattern — `LOCAL_ID`, `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` — un-anchored over the
  line, which is right for a `depends_on` list and wrong for a sentence: `**Depends on:** none.
  (the store) and B-3` named `none.`, `the`, `store`, `and` and `B-3` as dependencies, and on a
  copy of this repository's tickets the setting produced 1250 findings across 67 tickets. The
  first round of review found it before release; fieldhouse's own pattern (`[A-Z]+-\d+`) never
  had the fault. **A check over prose matches an id-SHAPED token, never the list grammar,** and
  `none` is the empty list. *Status: fixed with
  [B-111](https://immediately.run/present/github/immediately-run/baton/main/bundle/tickets/B-111.mdx).*

## 2026-10-27 — a ticket that names a private repository turns the sync red

- **A ticket's `repos:` is a read the sync's token must be able to make.** B-130 named
  `fieldhouse` and `docs`; the map lacked `fieldhouse` (fixed in #123), and then the run on
  `e082b9f` failed `404 — immediately-run/fieldhouse is named in repos: by B-130; the sync's
  token cannot read it` — the workflow's `GITHUB_TOKEN` reads this repository alone, and both
  siblings are private. The failure is right (no partial reading), and it lands on whoever pushes
  next, not on the ticket that caused it. **Before a live ticket names a private repository, the
  sync's token must read it** — here `BATON_GITHUB_READ_TOKEN`, a fine-grained read-only token
  (docs/standard-courses.mdx). The token was in use at once — `fieldhouse`'s answer went from
  404 (run 40542988875, the Actions token) to 403 (40558126421, the first run after #125; the
  public `baton` and `baton-board` read either way) — and that run logged `…/fieldhouse/pulls…: 403 — … the sync's token
  cannot read it, or it does not exist` (the sync prints the status, never GitHub's body; the
  same text follows a 404). The body, read by hand with the token, was `Resource not accessible
  by personal access token`: the token reached the repository without the permission listing
  PRs needs, and four runs failed so until the owner granted it. An expired token should instead
  be a 401 on the home repository's PR list, which is read first and passed through unwrapped
  (`list` in src/defaults/cli.ts) — not yet seen. `docs` is still never read: `.baton/tickets.mjs`
  drops it from every ticket's `repos:` (b2a70cd) until the token can read it. *Status: fixed for
  `fieldhouse` — run 40572091880 on `dd7a2f0` read it and posted the board.*
