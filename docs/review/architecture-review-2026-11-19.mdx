## Verdict, one line per question

| Question | Answer |
|---|---|
| Is code duplicated? Would an inheritance tree help? | Duplication is real but local: helper-sized copies, not parallel class families. No inheritance tree is warranted — the core is already 26 services over explicit context objects, which is the right shape. The fixes are one shared helper per cluster, and moving three concerns out of `src/core/baton.ts`. |
| Are units doing too much? | Three are: `src/core/baton.ts` (composition root, router, auth, board post and dashboard read model in 2,227 lines), the `Runner` class (2,440 lines, 103 members, per-claim state reached through `AsyncLocalStorage` proxies) and `src/defaults/cli.ts` (four modules in one file, 515 lines of JavaScript held in template strings). `claims.ts` is large but well factored. |

| Is the Quint model earning its cost? | It earned it in its first six days and has found nothing since. Nothing is proved (the bounded check reaches depth 4 on one ticket), no Quint runs in CI or `npm test`, and one invariant now contradicts the spec. | Is formatting, commenting and naming consistent? | Formatting is uniform by habit with no tool enforcing it (two exceptions: code line length, trailing commas). | Can spec and code evolve without diverging? | The spec's own consistency is well guarded. Almost nothing ties it to the code: no artifact says which rules are built, 90 of 192 scenarios have no test, and the route table, schema and command tree in the spec each differ from the code by dozens of entries with no check. |

## 1. Duplication and decomposition

### The core is composed well; one file is not

`BatonCore` is a composition root over 26 service classes, each constructed with a context object
(`constructor(private readonly c: Ctx)`). There are no mixins, no prototype augmentation and no
value-import cycles; hosts are wiring only (55 lines for Cloudflare, about 320 for local); no
platform import reaches core, and `Date.now()` appears once, as the clock's default. An
inheritance tree would add nothing: the services share no behaviour beyond a private `rows`
wrapper, which 21 of them define identically — a helper in `db.ts`, not a base class.

The exception is `src/core/baton.ts`. Beside the composition root it holds:

- **the HTTP router and all per-route authentication** — about 800 lines and 72 dispatch sites
  across `route`, `runnerRoute` (266 lines), `adminRoute`, `courierRoute`, `blocksRoute` and
  `sequenceRoute`, with `front.ts` keeping a second hand-written path list that must mirror it;
- **the board post**, the most intricate transaction in the system (`boardPost`, 179 lines, and
  its helpers) — every other domain has a service, this one has none;
- **the dashboard read model** (`uiState` and its helpers).

`docs/context/architecture.mdx` says "one registry, one check … generated from it behind one
`authorize`" in the present tense. That is the target (B-25, `available`), not the code:
`src/shared/actions.mjs` does not exist and `authorize` appears nowhere in `src/` or `cli/`. The
retired-repository bug fixed above is what hand-dispatch costs — a new route copied five of the
six checks its siblings make.

What looks like duplication and is not: the five large leg scripts under
`.baton/courses/create-pr/legs/` share 89–97% of their lines because they are esbuild bundles
that `repo init` wrote, one standalone file per leg by design.

### The runner

`Runner` (`src/runner/runner.ts:365–2806`) moved per-claim *state* to a `Slot` but left the
*behaviour* on the class, which reaches the state through 17 getter and setter pairs over
`AsyncLocalStorage`. Which claim a line touches depends on the ambient async context, not on a
receiver; `runClaim` is 370 lines threading about 15 mutable locals. The smaller runner modules
(`mask`, `audit`, `channel`, `executor`, `state`, `protocol`) are each one job in 85–310 lines,
and the runner re-implements no server rule — it imports `core/graph` and `core/conditionTypes`.

## 3. The Quint model

**What it found.** Two spec defects and two core defects, all between 2026-10-15 and 2026-10-20:
overlapping sync runs flagged as a regression (R-BTN-62, amended to `sync-busy`); an end that
blocked a ticket silently; a regression judged by a reading older than the latest advance
(S-BTN-36); `done` not confirmed at an end station (S-BTN-40). Both code defects came from the
model-drawn *replay*, not from the checker. Of the 75 runs in `model/regressions.qnt`, about four
trace to a defect the tooling surfaced; the rest are back-ported review findings and scripted
examples.

**What it proves.** Nothing unbounded. The Apalache run is depth 4 on a one-ticket instance and
takes 48–127 minutes; at that depth it reaches no judged snapshot, no reap and no second ticket.
Liveness formulas "have not been run" (`model/README.md`). Everything else is random sampling,
which already missed one real trace at 1,000 samples.

**What it costs and where it stands.**

- No Quint runs in CI or in `npm test` (removed in five steps between 2026-10-14 and 2026-11-10).
  The last full report on a PR is 2026-10-20; of 53 PRs since 2026-11-06 that changed checked
  paths, two carry a report.
- `model/` took 55 commits in October and 8 in November while `src/core` took 135 and 106. B-188
  changed the claim cardinality with no model change: `oneClaimPerRunner`
  (`model/properties.qnt:81`) asserts what R-BTN-4 no longer says, and `model:links` stayed green
  because its hashes cover model edits only, never code edits.
- `model/lightQuestion.qnt` (586 lines) models a rule retired on 2026-11-01 and no script runs it.
- The report gate caused two operational incidents recorded in `docs/lessons.mdx`.
- About 5,300 lines of model, scripts and tests against 19,580 in `src/core`.

**Recommendation: shrink, do not retire outright.** Keep `baton.qnt`, `properties.qnt`,
`regressions.qnt`, `witnesses.qnt` and the `sim` instance as a design instrument for the lease,
fence and observation core: `npm run model:quick` (typecheck plus the 75 runs, about a minute) in
CI when `model/` changes, and `npm run model` on demand when a ticket amends the lease rules.
Retire the bounded proof, liveness, `lightQuestion`, the scenario trace check, the report gate and
the `@model` stamps. Replace the one part that found code bugs — the replay — with a property test
that drives the real core with random action sequences under `setClock` and asserts the nine
non-trivial invariants. This amends values 10 and R-BTN-68, so it is the owner's decision
(ticket 1).

## 4. Replacing SQLite

**The contract.** `Store` is `exec(query, ...params)`, `script(sql)` and `transaction(fn)`, all
synchronous, with positional `?` and raw SQL strings. That is true of both hosts today and of no
Postgres driver.

| Obstacle | Size |
|---|---|
| The synchronous port: about 512 functions reach the store without `await`, through chains up to 14 frames deep; about 2,000 call sites and every `transaction` body would change | large |
| No data-access layer: 894 SQL literals in 29 of 50 core files (claims 213, blocks 103, admin 98, runnerApi 87) | large to confine, medium to translate in place |
| Tests assert on the schema: 1,451 SQL literals in 126 test files | medium to large |
| Dialect semantics: bytewise `ORDER BY` on text (161 uses), `rowid` as an insertion-order tiebreak (5), a unique violation caught inside a transaction that then continues (2), booleans as integers, `int8` returned as strings | medium |
| Migration history: 59 files with table rebuilds and JSON rewrites; a second dialect needs a squashed baseline and then two trees | medium |
| Single-writer assumption: sequences, observations, capacity seats and claim eligibility are read-then-write with no lock; only "one active claim per ticket" has a database constraint behind it | small for one instance (keep the request queue), large for several |

The dialect itself is mostly mechanical: no `datetime()`, `strftime()`, `AUTOINCREMENT`, `STRICT`,
`GLOB` or `INSERT OR REPLACE` anywhere; every `ON CONFLICT` names its target; time is always bound
from `this.now`.

So: one instance on Postgres is a large but bounded port, and the cheap steps that keep it open
are worth taking now (ticket 8). Several instances on one database is a different system — the
spec states the single writer as a rule (§2) — and should be recorded as a non-goal rather than
left implied.

## 5. Spec and code

What works: one home per statement, a generated index, `check:spec` failing on unknown rule ids,
stale indexes and patch notes, and a history file the stale-rule guard reads.

What is missing is any link from a rule to the fact of its being built.

- **No per-rule status.** The only markers are 17 free-text section headings, several already
  wrong (§6.11 is marked a proposal for B-106, which is done and cited in 11 source files).
  Citation is not implementation: R-BTN-129 is cited in two source files and the registry does
  not exist.
- **Scenarios.** R-BTN-30 says every scenario passes; 90 of 192 have no test anywhere, and
  `check:spec` checks only test file → spec, never spec → test.
- **Retired ids** are a warning, not an error: 94 citations in `src/`, 30 in `model/`. Of 275
  section-qualified citations (`§x R-BTN-n`) in code, 96 name a section that no longer holds the
  rule.
- **Three second sources of truth, unchecked.** §14 lists 113 paths, the code serves about 73
  (51 spec-only, 11 code-only). §13 calls itself "the current schema"; 19 tables in the
  migrations are not in it and about 20 in it have no migration. R-BTN-127's command tree has 59
  rows; nine of its nouns are not built and three built commands are not in it.
- **The spec names checks that do not exist**: `npm run check:actions` (§14, §11) and
  `npm run test:load` (§2, §15) are not in `package.json`.
- **`spec:impact`** lists tickets and context pages, not code or tests, so "an amendment reaches
  every citation" stops at the documentation.

## 6. Consistency

- **Formatting.** No formatter, linter or lint step exists. The code is uniform anyway: two-space
  indent, no tabs, single quotes about 99%, semicolons always, no loose equality, no `var`, zero
  `as any` and zero `@ts-ignore` in `src/`. Two real inconsistencies: comments wrap at 100 with
  discipline while code does not wrap at all (12% of code lines exceed 120 characters, 333 exceed
  200), and trailing commas are mixed. A formatter at width 100 would rewrite about 14,000 lines;
  that is a decision, not a cleanup.
- **Type coverage.** About 7,400 hand-written lines of `.mjs` are unchecked (`cli/`, `scripts/`,
  `src/shared/`), eleven modules are declared bare so every import from them is `any`, and twelve
  test files are in no tsconfig because coverage is two hand-kept lists of about 75 paths.
- **Comments.** 66% of comment blocks carry an id. Rule ids (the rule that holds) age well;
  ticket ids (who changed it) duplicate `git blame`, and about 9% of blocks are change narrative
  ("moved", "round 1", "renumbered at the merge"). A dozen name files or functions that no longer
  exist.
- **Names.** Identifiers follow one unwritten rule consistently — snake_case is data (wire,
  database, file), camelCase is code — and error codes, routes and table names are uniform. File
  names are not: `src/core` is camelCase, `src/defaults` and `scripts` kebab-case, and near-twins
  confuse (`core/course.ts` and `core/courses.ts`; `baton.ts` twice; `defaults/cli.ts` and
  `cli/`). `src/shared` is called vendored and is 5 vendored files among 12.
- **The dashboard** is an 18-line shell; the previous one was deleted on 2026-11-13 and its
  replacements (B-206–208, B-194, B-195) are `available`. The README still describes screens that
  do not exist.
