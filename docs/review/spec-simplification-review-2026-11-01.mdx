decisions: "start a fable review agent which reviews the entire baton spec … and assess it" for
needless complexity, user experience, and whether the security guarantees are truly guaranteed
and matter. A fresh review agent read `spec/BATON_SPEC.md` at `main` (`b0d7b9b`) on its own,
without the history, tickets or earlier reviews. The findings are its claims, checked against
the spec's text where cited; the tickets filed from them (B-155 to B-165) decide each one.</Lede>

Scope: `spec/BATON_SPEC.md` at `main` (7,897 lines, ~190 live rule ids), read whole and on its own, with `docs/context/*`, `docs/security-model.mdx`, `docs/standard-courses.mdx` and `node cli/baton.mjs --help` for what the CLI exposes today. History, reviews, lessons, tickets and git log were not consulted. Every claim below cites a rule id or a quoted phrase so it can be checked.

A note on method: where I say a mechanism "protects nothing", I mean against the actors and reaches `docs/security-model.mdx` names (a pusher, a compromised runner, an injected owner session, forge admin, a compromised Baton), not that it has no organisational value.

## Summary

Ranked by how much the owner should care.

1. **The `protected` preset, as written, deadlocks or ceremonialises ordinary operation (class d).** Five independent problems compound: `merge.checks: required` plus "nothing merges until `std:checks@1` is set" (R-BTN-188), where the "trusted executor" that writes `std:checks@1` is an actor the spec never defines or registers; `tickets.created: proposed` makes every handler ticket, including the `announce` notification of a `baton.*` condition, "not claimable until it lands with a `std:approval@1`" (R-BTN-161) — the human must approve the notification before being notified; `std:decision@1` "admits `human` alone" (R-BTN-191), so the standard `ask` course, whose person answers "in the ask's own file" attested by the sync (R-BTN-169), is inert and every question expires after 48 h; `adopt` needs "under `protected`, a `human` key" (R-BTN-39), so each in-flight ticket after a course rename costs a hardware-key ceremony; and a trusted-runner deliverer "marks every git entry `failed` with `refused`" on a repository with its own `tickets.mjs` (R-BTN-171). Separately, any repository with `starts_from: request` courses loses `baton request` as a one-liner ("opens a PR, not a push", R-BTN-180).

2. **Under `cooperative`, Baton's "owned" state is exactly as mutable as git — the owner's suspicion is correct.** Position and course history (R-BTN-39), holds (R-BTN-12), `max_runs` counts (R-BTN-63) and owner bars are all escapable by any pusher: re-file under a new id (admitted in R-BTN-12), change the ticket's `course:`, add an edge or an `arrives` leg to the course file ("An agent can change every byte of a registered repository", R-BTN-66), or rename a leg to dodge a bar (R-BTN-142). The apparatus built around this ownership — eleven `next_source` kinds, `position-disagrees`, `std:git.implied@1`, `history-adopted`, held snapshots with 24-hour auto-accept, `pending_owner_state`, `machine-loosened` — earns its keep only under `protected`, where control paths and tickets are human-landed. The spec should say that, and the cooperative-only parts should shrink.

3. **Too many actors that are all "a key whose host holds a credential Baton does not".** Courier ×3 classes, trusted runner, merge runner, fact reader, protection checker, check-runner, instrument, sync key, mirror key, CI identity, dispatch App, check App. Collapses that cost no guarantee: courier → trusted runner (R-BTN-171 already admits `trusted-runner` as a deliverer, and `protected` uses it); fact reader → the sync (under `protected` the sync's workflow and `.baton/` are human-landed control paths, and the fact reader's `pr-verdict` inherits R-BTN-139's push-based trust anyway); check-runner → a grant role like `trusted-runner`; instrument → a `service:` key; dispatch courier → delete, since it guards only reach 0 (see 4) and "the runners alone answer wants" (R-BTN-94) already works; mirror, shadow mode, legacy runners, adoption requests, cutover → an adoption appendix (the baton repository "runs none", §16.3).

4. **A large share of the security machinery guards a compromised Baton (reach 0), which §12.8 places "outside every guarantee".** Ed25519-signed outbox entries and `GET /v1/keys/signing`, the dispatch courier's workflow pins ("a compromised Baton could otherwise start any workflow"), signed policy reads verified against keys "pinned in its own configuration, never fetched from Baton", `base_sha` no-roll-back (R-BTN-143), and the trusted runner's policy-hash pin with `baton.policy-unpinned`. Either reach 0 is in scope (then add it to R-BTN-189 and keep these) or it is not (then these are class b: real, protecting little). Today the spec says both.

5. **Five ways to ask a person, three places an answer can live.** A person leg (R-BTN-116), a posted decision (R-BTN-78, which additionally raises `hitl.decision` so one question is listed twice on Needs you), a `hitl` condition with a handler ticket (R-BTN-160/161), a light question with Baton-held tickets, `refs/baton/questions/*`, promotion, two outbox kinds and a Quint model (R-BTN-173), and a `baton.*` condition answered only on the resolve page (R-BTN-163). One primitive would do: a person leg, answered by a `std:decision@1` attestation from the CLI, dashboard or MCP, which under `cooperative` the sync may also attest from `answer:`. Light questions alone are ~150 lines, the `handler`/`answer` outbox kinds, the `baton_held` ticket state and the `recorded`/`promoted_at`/`ignored` bookkeeping, to save one git commit per question.

6. **MCP is specified twice and contradictorily; the CLI cannot be learned from its help today, and the spec's own command tree disagrees with itself.** R-BTN-130 ("its only writes add a hold and stop a leg", echoed by R-BTN-154, §12.2, §14's overrides route and G-BTN-144) and R-BTN-186 ("Tightening ... is open to any owner credential, MCP keys included. This replaces R-BTN-130's closed list") are both in force; R-BTN-163 already assumes 186 ("an MCP key allowed `owner.resolve`"). An MCP agent can hold but not unhold, stop but not restart, see why a ticket is stuck (`leg.why`) but neither route nor adopt it. The built CLI prints one line per noun and answers `--help` on a subcommand with "not a flag of this command"; `runner`, `repo`, `leg`, `course` are not nouns of `cli/baton.mjs`; `test-course` and `request` are top-level verbs although R-BTN-127 says "the only top-level verbs are `help` and `version`"; the spec names the runner both `baton run` (R-BTN-131) and `baton runner start` (R-BTN-72, R-BTN-127); `baton attest` (R-BTN-181) and `baton owner policy …` (R-BTN-188) are not in R-BTN-127's tree.

7. **The route-choice/ontology stratum (R-BTN-174 to R-BTN-177, ~270 lines) puts a stratified ASP evaluator with a clingo conformance suite inside the core to compute advice** that R-BTN-98 already assigns to the runner ("runners rank", `rank.mjs` fed from the fleet and instance views). It is the single largest departure from values 3 ("The core is small and knows no course"). Keep holdings → derived capability as a gate input if wanted; move route choices, hysteresis (`route_last`), `meters`, `atoms_from`, field atoms and `BATON_ADVICE`/`BATON_TAKEN` to `rank.mjs` and course instructions.

8. **"Trusted" means six things.** Forge push access (R-BTN-139 "A trusted person ... someone the forge reports can push"), a grant's trust level (R-BTN-180), the trusted-runner role (R-BTN-182), `trusted_identities`, `trusted_sources` (R-BTN-134) and trust domain. The overload has a concrete consequence: under `protected` runners still push their branches, so the forge reports them as able to push, so a runner's review comment is a "trusted author's verdict" for the `pr-verdict` fact kind (R-BTN-192), and the fact reader — introduced to keep runner-sourced arrivals out — moves the ticket to `reviewed` on a runner's say-so. Not a landing (the merge leg re-checks `std:review@1`), but the opposite of the actor's purpose.

### 1.3 The handler-ticket pipeline for Baton's own conditions

This deserves its own paragraph because it is the root of several nouns above. R-BTN-163 says a `baton.*` condition's handler "only delivers": a link to `/conditions/<id>` where a signed-in owner picks a restart. To deliver that link, Baton queues a `handler` outbox entry, a courier writes a ticket file (or, under `proposed`, a branch and an approval), the sync posts it, a runner with `channel:push` claims `announce`'s `send` leg, and when the condition closes Baton queues a `withdraw` entry. `baton decision list --watch` already polls `GET …/conditions?open=1&person=1` once a minute. A delivery runner that polls that route and pushes/emails needs no ticket file, no outbox, no courier, no `withdraw`, no `outbox-collision` hold, no flapping rule and no proposal branch. The `handler` kind would remain only for leg-raised `suspend` conditions, which the raising runner already writes itself (R-BTN-161).

### 1.4 Policy knobs that may never leave their preset value

From R-BTN-188's table, with the only value each preset gives:

- `human_key` — `any`/`any`/`hardware`: only `protected-signed` moves it; and under `any` the spec admits the human-only key is "a promise" ("a human-only key an agent session can use (always possible while ... `human_key` is `any`)").
- `authorship` — `any`/`any`/`signed`: see guarantee `signed-authorship` below.
- `grants.trusted_domain`, `grants.default_trust`, `grants.one_per_domain` — declarations with no enforcer but a counter.
- `outbox.*.min_release` — "declared, not proven ... holds nothing against a compromised one".
- `refs.baton` — "which GitHub cannot restrict"; `refs.legs` — "which nothing merges".
- `leg_state` — "unset means `forge` on a repository with a forge and `branch` on one whose `forge` is `git`, where `forge` is refused": the knob is a function of `forge`.
- `merge.checks` — `optional`/`required`; see finding 1.
- Owner settings (R-BTN-66): `api_keys`, `required_independence` (duplicates `no_chain_from`), `artifact_buckets`, `transcript_repos`, `leg_log_root`, `unblocked_trigger`, `trigger_workflows`, `weight`, `report_horizon_h`, `atoms_from`, `checks`, `check_runners`.

A knob with one realistic value is a constant. Each of the above costs a row in R-BTN-188's table, a validation rule, a loosening rule under R-BTN-186, an export section and a test.

## 2. User experience

### 2.1 Can Baton be learned from `baton help` or the MCP schema?

**Today, no.** `node cli/baton.mjs --help` prints `baton: baton admin … | baton owner … | baton board REPO`; `baton owner --help` prints one line of verbs; `baton owner grant --help` and `baton admin repo --help` answer "not a flag of this command". The nouns `runner`, `repo`, `leg`, `course` do not exist in `cli/baton.mjs` (the runner is `baton run` in `src/runner/main.ts`; `test-course` and `request` are top-level verbs). Only `baton tickets --help` and `baton request` print real help.

**By design, unlikely.** R-BTN-129's promise that `baton help` and `tools/list` show "the caller's own entries, each with its `input` schema" is good. But the vocabulary a caller then meets is: ~25 `why` codes across 10 prerequisite kinds (R-BTN-120), 8 block kinds (R-BTN-75), 11 `next_source` values, 22 end reasons (§9.4), 14 gate rules with "12 is unused", 24+ `baton.*` conditions, 3 dispositions, restarts, `hold_reason` with 10 values, discrepancy subs, and the four-noun boundary. An MCP agent given `leg_why`, `ticket_blocked`, `ticket_history`, `decision_list`, `board`, `ticket_hold`, `leg_stop` (R-BTN-130) can diagnose but, by rule, not act: it may hold but not unhold, stop but not restart, read a `course-changed` wait but not `adopt` ("never a delegated key, so not MCP", R-BTN-39), and, depending on which of R-BTN-130/186 is read, may or may not `resolve`, `expedite` or `cancel`.

The spec's own command tree is inconsistent: `baton run` (R-BTN-131, `standard-courses.mdx`) vs `baton runner start` (R-BTN-72, R-BTN-127); `baton owner key grant` (R-BTN-146) vs `owner grant` (today's CLI) vs `POST /v1/owner/{repository}/grants`; `baton owner override` (R-BTN-12) vs actions `ticket.hold/unhold/expedite/cancel`; `baton attest`, `baton owner policy set|apply|show|diff|log|floor add`, `baton owner courier add`, `baton admin courier add`, `baton repo protect --print|--check`, `baton courier start`, `baton owner ticket adopt`, `baton owner route`, `baton owner token create`, `baton owner mcp-key create`, `baton admin github-app create` — none in R-BTN-127's table. Two further binaries (`baton-sidecar`, `baton-activity`) appear only in §8.1 and §9.9.

### 2.2 Journeys, walked as a new user with one GitHub repository

**Set up a repository.** (1) The administrator: `baton key create`, put the line in `BATON_ADMIN_KEYS` through the secret sink (R-BTN-136); `baton admin repo add` with forge ids (read from the API or `--forge-ids`), remote, web base, default branch, tiers, the first owner key (R-BTN-47). (2) The owner: `baton repo init` writes the course entry, the sync workflow, `HOW-TICKETS-WORK.md`, `.baton/leg-wrapper.example`; add a sync key or rely on the CI identity (R-BTN-93); set `BATON_GITHUB_READ_TOKEN` as a fine-grained read token for PR facts (`standard-courses.mdx`). (3) A runner: `baton key create`; owner `grant`; runner `accept-grant` (R-BTN-146: every grant "is pending and gives nothing until the holder runs `baton runner accept-grant`"), at which the hostname binds; `baton run --home`. (4) Optional but needed for sub-15-minute freshness: `baton admin github-app create` (manifest flow), an organisation owner installs it, the private key goes to a dispatch courier's host, `baton admin courier add --delivers dispatch`, `baton courier start --github-app-key` (R-BTN-57, R-BTN-171). (5) If `--bind-conditions`: a git courier too (finding 1.1), or notifications never leave the outbox. Count: nine commands over three roles plus GitHub settings, before any ticket runs. The owner-and-runner-are-one-person case still does grant-then-accept.

**Run a ticket on the default course.** `baton tickets new --title …` refuses without `--project` naming "a `kind: project` page in the items folder's `projects/`" — "There is no hard-coded project: `new` without one it can name refuses" (R-BTN-74). A new user has no projects folder. Then: push; wait for the sync (cron every 15 minutes, or a runner's `ls-remote` poll, or the App); the runner claims `implement`, the agent opens the PR; `review` (max 3), `fix` (max 2), `adjudicate`, `merge` by the runner under `cooperative`. Works, and the course is sensible. Surprises: the ticket needs a `**Depends on:**` body line that matches `depends_on` or `baton tickets check` fails (opt-in, but `new` enforces it); `repos:` entries "reach nothing unless the home's owners list them in `code_repos`" and, if the second repository is also registered, "need that repository's consent" (R-BTN-140) even when the same person owns both.

**Answer a person leg** (`decision` course). Under `cooperative`: the ticket sits at `asked`; the owner edits `answer: b` in the ticket file on the default branch, pushes, waits for the sync; `carry-out` runs; then the owner must *also* merge the PR that holds the record (`merged-by-hand`, R-BTN-131) — two human acts for one decision, and under `protected` both must be done by the human-only identity (the answer as a `human` `std:decision@1`, since `sync` is not admitted; the merge as "the human-only identity", R-BTN-185). The attestation path (`baton attest`) is named in R-BTN-181 but has no CLI entry and no documented argument shape; "The dashboard may only prepare an approval that the CLI signs" (R-BTN-185), so no answer from a phone. Meanwhile Needs you shows the posted decision and its `hitl.decision` twin.

**Recover a stuck ticket.** The owner must first classify the stuckness: a `retry` block (`baton leg why` → `backing-off`) is cleared by `baton owner override` unhold, which also "resets the leg's attempt and blocked-end counts"; a `baton.retries`/`baton.contract`/`baton.stalled` condition by `baton owner resolve <ticket> retry|route:<leg>|park`; a wrong queued leg by `baton owner route`; a `course-changed` wait only by `baton owner ticket adopt --at --next` (R-BTN-83), which must name stations and is refused `nothing-implied` without `--at`; a hung runner by `leg stop`, Cancel, `wind-down`, or an administrator's force-reap with a confirmation code typed from browser to CLI (R-BTN-155); an unconfirmed completion (6 h) by an administrator's confirm/release, again with a code; a held history by `board accept`; a renamed-leg bar by `bars follow`. Eleven verbs, three roles, two of them hardware-key gates under `protected` (`adopt`, and any unhold if the owner's keys are human-only), and the dashboard, "no standalone console" (§11.4), can do only hold, cancel, stop, resync and resolve without a code.

**Move from `cooperative` to `protected`.** In order, as the spec requires: set a trust domain, level and family on every live grant and courier through `approvers.trust` (R-BTN-180), because `apply protected` "is refused while a live grant or courier would break" `one_per_domain`/`trusted_domain: separate` (R-BTN-188); register a trusted-runner grant with the role; name a protection checker (R-BTN-180) and run it hourly with a credential that "could also rewrite" the ruleset; register a human-only key — a *host* configuration line `BATON_HUMAN_KEYS`, so the operator, not the owner (R-BTN-185); create a second GitHub identity and an organisation (a personal account "cannot name a person as a bypass actor"); `baton owner policy apply protected`; `baton repo protect --print github` and apply rulesets, environments and bypass teams by hand; wait for the checker's match, else `no-runner-lands` is broken and "Baton offers and accepts no claim or advance on any ticket that reaches the repository" (R-BTN-189); name the trusted executor's `service:` key for `std:checks@1`, else "nothing merges"; name the fact reader's key, else `baton.fact-reader-missing` and fact legs "arrive only by adopt"; make `outbox.git` deliverable (a trusted-runner process running a pinned CLI from a tarball with shrinkwrap, which "does not ship yet" per Open questions); pin the policy hash in that runner's configuration and re-pin after every change (`baton.policy-unpinned`); move secrets per FLDH-37; then `baton owner policy floor add`. From here every policy edit, grant, owner change, courier registration, adopt, `std:approval@1` and ticket-filing request (`baton request` "opens a PR, not a push") is a human-only act, and the dashboard cannot perform any of them. Expected outcome on day one: the merge runner refuses everything (`std:checks@1` unset), notifications wait for approval (finding 1), and the `ask` course's answers do not count. The preset needs a dry-run that lists what will stop.

### 2.4 Unintuitive limitations and surprising refusals

- A ticket "names tickets of the same repository" (R-BTN-47, R-BTN-120); a cross-repository dependency is a `**Waits on:**` prose line nobody reads.
- `human-operator` is "a runner's own statement, which Baton cannot verify" (R-BTN-121); the `OP` tag on a ticket therefore routes to whichever runner says it is a human.
- `max_queue` "closes" a course but "a claim of a new ticket by id is accepted" (R-BTN-79); an operator sees `course-closed` and nothing changes.
- A machine key granted on two repositories stops syncing both until an owner confirms flags (R-BTN-146 span).
- `baton request` refuses "a course without `starts_from: request`" (R-BTN-131) although the same ticket written by hand is accepted.
- Owner bars do not follow `renamed_from` (R-BTN-142); a rename holds the course file until `bars follow`.
- Lease timeout is clamped to ≥ 15 minutes (R-BTN-9): a crashed runner blocks its ticket for a quarter of an hour, by rule.
- Leg logs are off unless `leg_log_root` names a bucket (R-BTN-128); `baton leg log` reads the bucket with the user's own credentials; the dashboard "reads no log".
- Check courses are "GitHub only" and need `session` isolation (R-BTN-114, R-BTN-115).
- A hold "outlives the board" by id (R-BTN-12); withdrawing and re-filing with a new id escapes it, and the dashboard lists the dead id's hold "beside the new ticket" as the remedy.
- `api_keys: false` disables MCP keys too (R-BTN-130), though an MCP key is "not a `credentials` row".
- An owner's dashboard session cannot see Instances or Capacity (§11.4); an owner on a one-repository tenant is the administrator too and must sign in twice.
- Switching the instance to `human_key: hardware` "suspends every `human_only` key registered before the switch that does not meet it" (R-BTN-185); the recovery is the host's break-glass line.
- The three `conflict`s of registering a key that holds another role never name the role (§12.1), so a user who reused a key gets no hint which role it already has.
- Two retention clocks the user never set: `request_nonces` 11 min, `webhook_deliveries` 24 h, history 90 days, `route_last` 24 h, `runner_derived` 30 days, `forge-check` 7 days, `open_world_bars` 24 h, `held_snapshots` 24 h, `observation` 5/10/30 min, unconfirmed 6 h, fence 30 min notice, `baton.stalled` 72 h — a table of magic numbers that will each generate a support question.

### 3.2 Detailed findings

**F1. The guarantees that matter are the forge's, and Baton's part is to print settings and stop the repository.** `no-runner-lands` and `control-paths-human` are enforced by rulesets or a `pre-receive` hook; Baton "prints it, the protection checker checks it". That is a sound division, and the spec says it. What follows is that most of the machinery Baton adds on top — signed outbox entries, pinned policy hashes, the fact reader, `board-from-trusted`, trust levels separate from roles — defends layers behind a wall whose only real breach (forge admin, reach 2) none of them sees. The owner should decide whether forge admin is in the threat model. If yes, the one useful addition is a push ruleset that also covers the ruleset's own bypass team (and FLDH-37); if no, the detection-only protection checker can be the merge runner's hourly self-check.

**F2. `human-gates` under `protected` is a custody promise, and the spec says so in two places while the preset table says it holds.** R-BTN-189: "The `protected` preset holds all of them but `signed-authorship` and `human-gates-hardware`." §12.8: outside every guarantee is "a human-only key an agent session can use (always possible while the repository's `human_key` is `any`)". `docs/security-model.mdx`: "Owner gates are not human gates ... A gate is human only when it needs a credential no agent session holds". Under `protected`, `human_key` is `any`. So `human-gates` holds by definition over the policy and not in the world. The honest fix is to drop `human-gates` from what `protected` "holds" and let only `protected-signed` claim it, or to make `human_key: hardware` part of `protected`.

**F3. Position ownership protects a design, not a boundary (the owner's example).** Under `cooperative`, R-BTN-66 grants every pusher the course file, the ticket source, tiers and requirements. With that, moving a ticket where you like is: add `"arrives": {"fact": "pr-opened"}` to a leg leaving its station and open a PR; or change `course:` to a course whose `start` suits you (the claim ends `course-changed`, the ticket waits for adopt — a DoS, not a move, but it also stops the ticket); or re-file. R-BTN-147's `machine-loosened` notice fires only for machine-key posts, so a sync-key post after a human-looking push is silent. The parts of the position apparatus that exist to catch an adversary — `position-disagrees` as a Needs-you item, `std:git.implied@1`, held snapshots that "only tighten" — are therefore theatre under `cooperative` and belong, if anywhere, under `protected`, where they are redundant because control paths are human-landed. Keep the single-authority design (it removes replay and makes `max_runs` deterministic); delete the adversary-facing trimmings.

**F4. `tickets-approved` and `proposed` collide with Baton's own outbox.** R-BTN-161, R-BTN-165, R-BTN-171 and R-BTN-173 each carry the italic rider "Under the policy's `tickets.created: proposed` … not claimable until it lands with a `std:approval@1`". For a leg's children that is the intended cost. For Baton's own `baton.*` handler tickets, whose job is to deliver a link, it means a human-only approval per notification, and the flapping rule (20 handlers an hour) still queues them. Even granting an exemption, the approval covers "the protected paths changed, their blob ids, and the digest of the computed view" — a human on a phone cannot produce it ("The dashboard may only prepare an approval that the CLI signs"). The approval ceremony is right for a spec file; it is wrong for a one-line ticket a runner filed to ask a question.

**F5. `independent-review` is correctly described as not a security gate, so its cost should match.** §12.8's first exclusion and R-BTN-183 ("Checks ... are not a security gate", "Baton records this; the deployment makes it true") are candid. What is left is "two claims from two labelled domains approved". That justifies `merge.reviews.count` and a domain label; it does not justify trust levels separate from roles, `model_family` as a distinct field, `trust_set_by` clearing on approver changes, or `std:ran@1` as an attestation type Baton signs about something it cannot observe.

**F6. Signed authorship protects against the wrong writer.** The key that signs is in the runner's process (R-BTN-14, R-BTN-144), so a compromised leg signs. The signature distinguishes "this runner" from "another pusher on the same branch", which continuity ranges plus the foreign-commit reset already do. The open-question race ("a reset can discard an honest leg's unreported pushes, and any runner can trigger one through the shared forge identity until B-131") means the reset is itself a denial-of-service lever. Until the host-side signer exists, `authorship: signed` buys a knob and a key-type restriction. Recommend: leave `signed-authorship` out of the spec until the signer is designed, and keep continuity.

**F7. The trusted executor is an undefined actor on which `protected` depends.** `std:checks@1`'s writer is "`service:<the trusted executor's key>`: the course's check commands, from protected course data, passed at `head` in a sandbox holding no credential" (R-BTN-181). Nothing registers, grants, heartbeats or schedules it; §10's check-runner posts forge check runs, not `std:checks@1` attestations; "Checks are GitHub only". With `merge.checks: required` in the `protected` column, the preset cannot merge until an actor the spec does not define exists. Either define it (plausibly: the check-runner of §10 also posts a `std:checks@1` as its `service:` key) or make `protected`'s `merge.checks` `optional` and accept the forge's required checks.

**F8. The overloaded word "trusted" leaks push-based trust into the protected path.** R-BTN-139 marks forge content `trusted` when its author "can push to the PR's base". Under `protected`, runners push their own branches, so they can push. R-BTN-192's `pr-verdict` is "a trusted author's verdict (R-BTN-139) on the PR's head that no claim of the ticket wrote" — a runner's review comment on a peer's PR, posted outside any claim, qualifies, and the fact reader attests it as a `service:` arrival that R-BTN-39 applies: `reviewed-by-hand` fires, `merge` is queued. The merge runner then refuses for want of `std:review@1` attestations, so nothing lands; but the actor whose purpose is to exclude runner-sourced arrivals accepts one. Fix: under `protected`, `pr-verdict` and `trusted_identities` should mean the human-only identity, i.e. `human`, and the word "trusted" in R-BTN-139 should be renamed (`pusher`).

**F9. Reach 0 is both excluded and defended.** Listed as outside every guarantee: "a compromised Baton server or Cloudflare account (reach 0 ...), recovered by B-125's runbook". Defended by: outbox signatures and `GET /v1/keys/signing`; the dispatch courier's pins; the signed policy read verified against keys "never fetched from Baton at the time of use"; the trusted runner pinning "the hash of the whole policy document and of its floors" and acting on nothing while a pin differs; `base_sha`. Each is individually reasonable; together they are the largest single source of actors and knobs after §12.8 itself. A one-line decision ("Baton's server is trusted; its compromise is recovered, not resisted") would remove them; the opposite decision should add reach 0 to R-BTN-189 so the machinery has a named guarantee to justify it.

**F10. Several "limits" are constants with a validation rule.** `min_release` ("holds nothing against a compromised one"), `refs.baton` ("which GitHub cannot restrict"), `refs.legs` ("which nothing merges"), `leg_state` (a function of `forge`), `human_key` and `authorship` outside `protected-signed`. Each is a row in the policy table, a loosening rule in R-BTN-186, a guarantee condition, and a floor check. Removing them weakens nothing.

## 4. What is good and should stay

- **The four-noun boundary** (attestation, command, outbox entry, reply; R-BTN-191, architecture page): it makes "who may tell Baton this?" one question. Keep it; it is what makes the simplifications above possible.
- **Git first, position recorded at once, confirmation by evidence** (R-BTN-8, R-BTN-10, R-BTN-39, R-BTN-83): one authority for where a ticket is, no replay, deterministic counts.
- **Observation numbers and compare-and-set heads** (R-BTN-11, R-BTN-62): the correctness core, precisely stated.
- **The lease, the fence, and "advice never refuses"** (R-BTN-4, R-BTN-6, R-BTN-19, R-BTN-26, R-BTN-45): the product's reason to exist, scoped honestly to cooperating runners.
- **Baton runs no repository code; runners rank** (R-BTN-98, R-BTN-133, R-BTN-143): the right place for the boundary. The ontology is the one exception and should be judged against this rule.
- **One action registry, one `authorize`, one validator** (R-BTN-129, R-BTN-108): once MCP's two rules are reconciled this gives every surface for free.
- **The policy as one versioned document with compare-and-set and an append-only log** (R-BTN-188): the right shape; it needs fewer knobs, not a different shape.

- **"Outside every guarantee, stated exactly"** (§12.8), **"Baton records this; the deployment makes it true"**, and the end-reason and gate tables: the spec is unusually honest about its limits. The recommendations above mostly ask it to act on its own honesty.
- **`baton leg why`, the blocks index, `baton tickets check`, the course test kit** (R-BTN-75, R-BTN-120, R-BTN-64): the diagnostic surface is the best part of the user experience and deserves a CLI whose help matches it.
- **Tenant isolation and the same-site rules** (R-BTN-135 to R-BTN-137, R-BTN-16): cheap, complete, correct.
