A course is the route a ticket takes: its stations, and the legs an agent runs between them. A
repository can write its own, as the docs repository did with `roadmap-pr`, but most need one of
a handful of routes. Baton's CLI ships six, and a repository adopts each with one command. They
are specified in BATON_SPEC R-BTN-131 and started from the docs repository's skills.

| course | what it does | legs | where it ends |
|---|---|---|---|
| `create-pr` | builds a ticket in a PR, reviews it in up to three rounds, fixes, adjudicates what the last round leaves open, merges | implement, review, fix, adjudicate, merge | `merged` |
| `review-pr` | reviews a PR someone else opened, in rounds, and concludes with a summary | review, conclude | `approved` or `concluded` |
| `bug-report` | traces a reported bug to its cause and the artifact that seeded it, dedupes it by cause, files the fix ticket or folds the report into the one that covers it, weighs prevention | trace, origin, dedupe, file or fold, prevent | `closed` |
| `draft-ticket` | researches, drafts and files a ticket that prescribes its architecture, tests and requirements | research, draft, check | `filed` |
| `decision` | turns a question only the owner can settle into a one-letter packet, then carries the answer out | prepare, carry-out | `decided` |
| `build-app` | takes a one-line request to a verified application: a product definition, a design with mock-ups, an architecture and a plan, each approved by the owner, then the plan's tickets on `create-pr`, and a verification against the definition | define, design, architect, plan, file, verify | `shipped` |

`create-pr` is the default. It replaced the `pr` course, which a repository scaffolded before
keeps until it switches.

## Adopting one

```
npx baton repo init                       # create-pr, the settings (agent_command among them) and the sync workflow
npx baton repo init --course bug-report   # a second course beside the first
```

Each `init --course` writes `.baton/courses/<course>/`: the course file, one stub per leg, and
one Markdown file of instructions per leg. It also adds the course to `.baton/baton.json`. A
ticket picks its course with `course:` in its frontmatter, and the repository's `default_course`
covers the rest.

A runner serves one course, since a claim does not say which course its ticket is on. A
repository on several courses runs one runner for each, each in its own clone, because a
runner's legs work in its checkout's working tree (a second runner on a checkout is refused):

```
npx baton run --course create-pr  --home ~/src/repo
npx baton run --course bug-report --home ~/src/repo-bug-report
```

## The agent that runs the legs

Each leg's stub runs the command `.baton/baton.json` names in `agent_command` — a shell string,
with the ticket id, the leg and the checkout as `$1`, `$2` and `$3`, and the leg's briefing in
the environment (`BATON_COURSE`, `BATON_LEG`, `BATON_TICKET_FILE`, `BATON_INSTRUCTIONS`, and
`BATON_ANSWER` on a leg whose last line is read). `baton repo init` names it for the harness you
run, and prints the command for the unfamiliar:

```
npx baton repo init --agent opencode      # the default
npx baton repo init --agent claude-code
npx baton repo init --agent-command '<your own command>'
```

The two shipped commands, both validated on real runs (opencode on the acceptance runs of the
self-hosting gap analysis; claude-code headless on a checkout, following the instructions file
and editing the tree):

```
opencode run --auto --model zai-coding-plan/glm-5.3 "You are the $BATON_LEG leg of the $BATON_COURSE course for ticket $1. Read the file named by $BATON_INSTRUCTIONS and follow it exactly. The ticket file is $BATON_TICKET_FILE. Work in the current repository checkout. $BATON_ANSWER — when that answer rule is set, a machine parses the LAST line of your output: exactly the value word (optionally followed by one PR URL) and nothing else after it." < /dev/null
```

```
claude -p --permission-mode bypassPermissions --model sonnet "You are the $BATON_LEG leg of the $BATON_COURSE course for ticket $1. Read the file named by $BATON_INSTRUCTIONS and follow it exactly. The ticket file is $BATON_TICKET_FILE. Work in the current repository checkout. $BATON_ANSWER — when that answer rule is set, a machine parses the LAST line of your output: exactly the value word (optionally followed by one PR URL) and nothing else after it." < /dev/null
```

Three details carry weight:

- **The model is pinned.** An unpinned agent runs whatever the machine defaults to, and the
  default moves under you. Change the pin in the command when your repository should run another
  model.
- **`< /dev/null` closes stdin.** The stub spawns the command through `sh -c`, an environment
  that hangs `opencode run` deterministically with an open stdin (root cause unexplained; filed
  as B-84, whose fix is to spawn without the shell). Until B-84 lands, keep the redirection.
- **The prompt spells the last-line contract.** A result-dependent leg's answer is read from the
  agent's last line; the prompt says so in the words the machine enforces.

A runner refuses to start for a settings file whose `agent_command` is exactly `echo` — the
no-op stub whose every leg "succeeds" while nothing happens. It is for tests, and tests pass
`--test-harness` (which also declares `test_harness` on the heartbeat, so Baton refuses it from
any credential but the test one). When the settings name no `agent_command` at all, `baton run
--harness opencode|claude-code` runs that harness's command — the flag is the runner's word for
its harness, and with no command named, it is the command.

## How each course finds where a ticket is

- **`create-pr` and `review-pr` read the forge.** A ticket's PRs are the ones its branch pattern
  or its `prs:` names. Each review's verdict is a review state or a comment whose first line is
  `<!-- baton:verdict approve -->` or `<!-- baton:verdict changes -->`. `create-pr`'s adjudication
  and `review-pr`'s conclusion are comment lines of the same kind. The leg's `close` writes each
  of these lines from the agent's answer, so the agent never writes them itself.
- **A ticket's PRs may be in other repositories.** A ticket that names repositories in its
  `repos:` (docs' roadmap items name the code repositories they change) gets one PR in each, on
  a branch of the same name; its home may get none. The sync reads every repository a live
  ticket names, and reads the ticket's PRs together, as one change: a verdict on any of them
  stands for all of them, and the ticket is merged when every PR is. A leg whose line goes on a
  PR names it after its answer (`approve https://github.com/<owner>/<name>/pull/<n>`) when the
  checkout's branch has none. The workflow's token reads public repositories; a private one
  needs a token that can read it.
- **`bug-report`, `draft-ticket`, `decision` and `build-app` open no PR.** Their legs commit their work to the
  default branch, and each leg's `close` appends a line to `.baton/markers.jsonl` saying where the
  ticket got to and which leg comes next. The sync reads that file, so these courses need no forge
  token at all.
- **`decision` waits on the owner.** After `prepare` writes the packet into the ticket, the claim
  ends and `carry-out` waits until the owner sets the ticket's `answer:` to their letter. Nothing
  answers for them. `review-pr` waits the same way on the author after asking for changes, and
  `create-pr` on the owner after an `owner` adjudication.

## Where a course comes from

Each course `init` scaffolds names its source in `.baton/baton.json`, in immediately.run's own
form: provider, owner, repository, commit, then the course.

```
"source": "github/immediately-run/baton/<commit>/create-pr"
```

The commit is the CLI's own, the one that wrote the files, so the name always means one graph.
The sync holds the course to it: if `.baton/courses/create-pr/course.json` differs from that
commit's, nothing is posted until `npx baton repo init --course create-pr --force` restores it.
Upgrading is re-running `init` with a newer CLI: it moves the workflow's pin and every course's
source together, rewriting the course files and leg scripts and keeping your instructions and
overrides. For now a source names the CLI's own repository; a course from another repository is
refused as not supported yet.

## Overriding a leg

When your repository does a leg differently in code, not just in prose, replace that leg's run
and keep everything else:

```
npx baton repo init --course create-pr --override review
```

This writes `.baton/courses/create-pr/legs/review.run.mjs`, yours from then on:

```js
export async function run(ctx, standard) {
  return standard(ctx); // the course's own run: your agent_command with the leg's instructions
}
```

The leg's script loads it from the claim's snapshot and calls it in place of its own run. It
keeps its own `close`, so the line the course reads (the review's verdict, the adjudication, a
marker) is always written the standard way, and the course places the ticket as it would without
the override. Return the same shape `standard` returns; the file's header says what that is for
the leg. It is loaded alone, so import only Node built-ins. A difference that is only prose
belongs in the leg's `.md` instead.

## Changing one

The instructions are yours once scaffolded. Edit `.baton/courses/<course>/legs/<leg>.md` to
match how your repository works: its checks, its review rubric, where its tickets live. A
release of the CLI never touches them. Each leg's stub runs the command `.baton/baton.json`
names in `agent_command` — [the two shipped ones are above](#the-agent-that-runs-the-legs) —
with the ticket, the leg and the checkout as its arguments. It hands
the agent the instructions, read at the claim's snapshot, through `BATON_INSTRUCTIONS`, so a
branch under review cannot rewrite its reviewer's instructions.

To change how a course places tickets, `npx baton repo init --course <course> --eject stations`
copies its station function into `.baton/courses/<course>/sync.mjs`, where you can edit it. The
course is then yours, not the source's: remove its `source` from `.baton/baton.json` first.

## `build-app`, step by step

`build-app` is for a whole application, or a large feature of one. Adopt it beside `create-pr`,
which its tickets run on:

```
npx baton repo init                       # create-pr
npx baton repo init --course build-app
```

A request is one ticket, `course: build-app`, saying what to build, often in a sentence. Each
of the first four legs drafts one document in `product/<ticket id>/` and stops for the owner:

| leg | writes | the owner approves with |
|---|---|---|
| `define` | `PRODUCT.md`: who it is for, the rules, what is in and out, numbered acceptance criteria | `answer: define` |
| `design` | `DESIGN.md` and a self-contained HTML mock-up of each screen in `mockups/` | `answer: design` |
| `architect` | `ARCHITECTURE.md`: hosting, state, sign-in, abuse, operations, cost, testing, the walking skeleton | `answer: architect` |
| `plan` | `PLAN.md`: every ticket, complete, and which acceptance criteria each one makes pass | `answer: plan` |

Each draft ends with its open questions, each with a recommendation, and the ticket gets a
`## Your turn` section. The owner settles them in a conversation: they open an interactive agent
session in a checkout and ask it to follow `## The conversation` in that leg's instructions. The
session asks the questions one at a time, rewrites the document as answers come, and sets
`answer:` only when the owner says it is right. Nothing moves until then. Then `file` writes the
plan's tickets as children of the request (`parent:`), each on `create-pr`, and the request waits
until every one has merged and closed. `verify` then tests every acceptance criterion against
the running build. It either closes the request, or files a fix ticket per failure and waits
again, up to three rounds.

Until interactive legs are built (B-34), the conversation is a session the owner starts
themselves, and `answer:` is the approval.
