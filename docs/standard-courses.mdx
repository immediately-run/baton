A course is the route a ticket takes: its stations, and the legs an agent runs between them. A
repository can write its own, as the docs repository did with `roadmap-pr`, but most need one of
a handful of routes. Baton's CLI ships seven, and a repository adopts each with one command. They
are specified in BATON_SPEC R-BTN-131 and started from the docs repository's skills.

| course | what it does | legs | where it ends |
|---|---|---|---|
| `create-pr` | builds a ticket in a PR, reviews it in up to three rounds, fixes, adjudicates what the last round leaves open, merges | implement, review, fix, adjudicate, merge | `merged` |
| `review-pr` | reviews a PR someone else opened, in rounds, and concludes with a summary | review, conclude | `approved` or `concluded` |
| `bug-report` | traces a reported bug to its cause and the artifact that seeded it, dedupes it by cause, files the fix ticket or folds the report into the one that covers it, weighs prevention | trace, origin, dedupe, file or fold, prevent | `closed` |
| `draft-ticket` | researches, drafts and files a ticket that prescribes its architecture, tests and requirements | research, draft, check | `filed` |
| `decision` | turns a question only the owner can settle into a one-letter packet, then carries the answer out | prepare, carry-out | `decided` |
| `build-app` | takes a one-line request to a verified application: a product definition, a design with mock-ups, an architecture and a plan, each approved by the owner, then the plan's tickets on `create-pr`, and a verification against the definition | define, design, architect, plan, file, verify | `shipped` |
| `create-spec` | designs a specification in conversation with the owner, reviews it adversarially, addresses blocking findings in a second conversation, adjudicates what three rounds leave open, merges | converse, review, address, adjudicate, merge | `merged` |

`create-pr` is the default. It replaced the `pr` course, which a repository scaffolded before
keeps until it switches.

## Adopting one

```
npx baton repo init                       # create-pr, the settings (agent_command among them) and the sync workflow
npx baton repo init --course bug-report   # a second course beside the first
npx baton tickets check                   # check the tickets as the sync reads them; exit 1 naming every finding (B-111)
```

Each `init --course` writes `.baton/courses/<course>/`: the course file, one stub per leg, and
one Markdown file of instructions per leg. It also adds the course to `.baton/baton.json`. A
ticket picks its course with `course:` in its frontmatter, and the repository's `default_course`
covers the rest.

A runner serves every course its home checkout declares — any course its capabilities can serve —
since the claim answer names the ticket's `course_id` and the runner loads that course from the
claim's snapshot. One checkout on two courses is one runner on two courses; `--course` narrows it
to one, for a machine that should serve only part of what the checkout declares. Its only limit
is one leg at a time (at least for now): a runner's legs work in its checkout's working tree, so
a second runner on the same checkout is still refused:

```
npx baton run                    --home ~/src/repo   # every course .baton/baton.json declares
npx baton run --course create-pr --home ~/src/repo   # narrowed to create-pr
```

## The agent that runs the legs

Each leg's stub runs the command `.baton/baton.json` names in `agent_command` — a shell-style
string the stub splits into words and spawns with **no shell between it and the agent** (B-84),
with the ticket id, the leg and the checkout appended as its last three arguments, and the leg's
briefing in the environment (`BATON_COURSE`, `BATON_LEG`, `BATON_TICKET_FILE`,
`BATON_INSTRUCTIONS`, and `BATON_ANSWER` on a leg whose last line is read). `baton repo init`
names it for the harness you run, and prints the command for the unfamiliar:

```
npx baton repo init --agent opencode      # the default
npx baton repo init --agent claude-code
npx baton repo init --agent-command '<your own command>'
```

The two shipped commands. The shape is the one this repository runs in production (opencode —
its legs run under exactly these words now); the earlier `sh -c` form was validated on real runs
(opencode on the acceptance runs of the self-hosting gap analysis; claude-code headless on a
checkout, following the instructions file and editing the tree):

```
opencode run --auto --model zai-coding-plan/glm-5.3 "You are a Baton leg agent. The file named by the BATON_INSTRUCTIONS environment variable holds your instructions for this leg: read them and follow them exactly. The environment names your course (BATON_COURSE), your leg (BATON_LEG), the ticket's file (BATON_TICKET_FILE) and the answer rule for your last line (BATON_ANSWER, when one is set); the arguments after this message are the ticket id, your leg and the repository checkout. Work in the current repository checkout. When BATON_ANSWER is set, a machine parses the LAST line of your output: exactly the value word (optionally followed by one PR URL) and nothing else after it. Your process's exit is the leg's completion: when the leg is done — the work pushed, the checks green, the final line printed — exit immediately, never waiting for further input."
```

```
claude -p --permission-mode bypassPermissions --model sonnet "You are a Baton leg agent. The file named by the BATON_INSTRUCTIONS environment variable holds your instructions for this leg: read them and follow them exactly. The environment names your course (BATON_COURSE), your leg (BATON_LEG), the ticket's file (BATON_TICKET_FILE) and the answer rule for your last line (BATON_ANSWER, when one is set); the arguments after this message are the ticket id, your leg and the repository checkout. Work in the current repository checkout. When BATON_ANSWER is set, a machine parses the LAST line of your output: exactly the value word (optionally followed by one PR URL) and nothing else after it. Your process's exit is the leg's completion: when the leg is done — the work pushed, the checks green, the final line printed — exit immediately, never waiting for further input."
```

Three details carry weight:

- **The model is pinned.** An unpinned agent runs whatever the machine defaults to, and the
  default moves under you. Change the pin in the command when your repository should run another
  model.
- **No shell, and stdin is already closed.** The stub splits the command itself and spawns the
  words as argv (B-84): a redirection like `< /dev/null` is refused — nothing executes it, and
  the agent's stdin is closed by the stub — and `$BATON_INSTRUCTIONS` would stay those literal
  characters, never the path. That is why the prompt names the `BATON_*` environment variables
  for the agent to read itself, and the ticket id, the leg and the checkout ride as the
  arguments after the message.
- **The prompt spells the last-line contract.** A result-dependent leg's answer is read from the
  agent's last line; the prompt says so in the words the machine enforces.

A runner refuses to start for a settings file whose `agent_command` is exactly `echo` — the
no-op stub whose every leg "succeeds" while nothing happens. It is for tests, and tests pass
`--test-harness` (which also declares `test_harness` on the heartbeat, so Baton refuses it from
any credential but the test one). When the settings name no `agent_command` at all, `baton run
--harness opencode|claude-code` runs that harness's command — the flag is the runner's word for
its harness, and with no command named, it is the command.

## How each course finds where a ticket is

- **`create-pr`, `review-pr` and `create-spec` read the forge.** A ticket's PRs are the ones its branch pattern
  or its `prs:` names. Each review's verdict is a review state or a comment whose first line is
  `<!-- baton:verdict approve -->` or `<!-- baton:verdict changes -->`. `create-pr`'s adjudication
  and `review-pr`'s conclusion are comment lines of the same kind. The leg's `close` writes each
  of these lines from the agent's answer, so the agent never writes them itself.
- **A ticket's PRs may be in other repositories.** A ticket that names repositories in its
  `repos:` (docs' roadmap items name the code repositories they change) gets one PR in each, on
  a branch of the same name; its home may get none. The sync reads every repository a live
  ticket names, and reads the ticket's PRs together, as one change: a verdict on any of them
  stands for all of them, and the ticket is merged when every PR is. A leg whose line goes on a
  PR names it after its answer (`approve https://github.com/<owner>/<name>/pull/<n>`) when the
  checkout's branch has none. The workflow's token reads public repositories; a private one
  needs a token that can read it. This repository's workflow takes it from the
  `BATON_GITHUB_READ_TOKEN` secret (never `BATON_SYNC_TOKEN`, which the CLI sends to Baton as its
  bearer): a fine-grained token, read-only (Pull requests, Checks, Contents, Metadata), over every
  repository its `repos` map names, this one included — the home's own PR list and a
  collaborator's permission (R-BTN-139) are read through it too. The token expires: an expired
  one fails the sync with a 401 on the home repository's PR list, and the remedy is a new token
  in the same secret.
- **`bug-report`, `draft-ticket`, `decision` and `build-app` open no PR.** Their legs commit their work to the
  default branch, and each leg's `close` appends a line to `.baton/markers.jsonl` saying where the
  ticket got to and which leg comes next. The sync reads that file, so these courses need no forge
  token at all.
- **`decision` waits on the owner.** After `prepare` writes the packet into the ticket, the claim
  ends and `carry-out` waits until the owner sets the ticket's `answer:` to their letter. Nothing
  answers for them. `review-pr` waits the same way on the author after asking for changes,
  `create-pr` on the owner after an `owner` adjudication, and `create-spec`'s two interactive
  legs — the design conversation and the one that answers a round's findings — from the moment
  their claims end until the PR they work on moves. Those two are PR courses' legs that still need
  a record, because nothing on the PR says a conversation is under way: each one's `close` pushes
  its marker line to `.baton/markers.jsonl` itself (the marker courses' own commit and push), so a
  checkout whose close ran always leaves the line on the default branch the sync reads.

## Where a course comes from

Each course `init` scaffolds names its source in `.baton/baton.json`, in immediately.run's own
form: provider, owner, repository, commit, then the course.

```
"source": "github/immediately-run/baton/<commit>/create-pr"
```

The commit is the CLI's own, the one that wrote the files, so the name always means one graph.
The sync holds the course to it: if `.baton/courses/create-pr/course.json` differs from that
commit's, nothing is posted until `npx baton repo init --course create-pr --force` restores it.
Upgrading is re-running `init` with a newer CLI: it moves the workflow's pin and every course's
source together, rewriting the course files and leg scripts and keeping your instructions and
overrides. For now a source names the CLI's own repository; a course from another repository is
refused as not supported yet.

## Overriding a leg

When your repository does a leg differently in code, not just in prose, replace that leg's run
and keep everything else:

```
npx baton repo init --course create-pr --override review
```

This writes `.baton/courses/create-pr/legs/review.run.mjs`, yours from then on:

```js
export async function run(ctx, standard) {
  return standard(ctx); // the course's own run: your agent_command with the leg's instructions
}
```

The leg's script loads it from the claim's snapshot and calls it in place of its own run. It
keeps its own `close`, so the line the course reads (the review's verdict, the adjudication, a
marker) is always written the standard way, and the course places the ticket as it would without
the override. Return the same shape `standard` returns; the file's header says what that is for
the leg. It is loaded alone, so import only Node built-ins. A difference that is only prose
belongs in the leg's `.md` instead.

## Changing one

The instructions are yours once scaffolded. Edit `.baton/courses/<course>/legs/<leg>.md` to
match how your repository works: its checks, its review rubric, where its tickets live. A
release of the CLI never touches them. Each leg's stub runs the command `.baton/baton.json`
names in `agent_command` — [the two shipped ones are above](#the-agent-that-runs-the-legs) —
with the ticket, the leg and the checkout as its arguments. It hands
the agent the instructions, read at the claim's snapshot, through `BATON_INSTRUCTIONS`, so a
branch under review cannot rewrite its reviewer's instructions.

The agent itself is the repository's too: `.baton/baton.json`'s `agent_command`. So is
everything around it. When you want every leg's output tee'd to a log, uploaded, timed or
prefixed, name an `agent_wrapper` beside it — one command, split into words as `agent_command`
is, whose words run in front of the agent's:

```json
"agent_command": "opencode run --auto --model <provider>/<model> \"…\"",
"agent_wrapper": ".baton/leg-wrapper"
```

The stub runs `[.baton/leg-wrapper, opencode, run, …, <ticket>, <leg>, <checkout>]`: the wrapper
receives the whole leg command as `"$@"` and owns its stdio, timing and log. Baton builds nothing
around it — no capture, upload, retention or redaction is built in. `npx baton repo init` writes
`.baton/leg-wrapper.example`, a `tee` to `.baton/logs/<ticket>-<leg>.log`; copy it to
`.baton/leg-wrapper`, make it executable, and name it. The repository's setting applies wherever
the leg runs; `BATON_AGENT_WRAPPER` in the runner's own environment overrides it, so one host can
wrap while the repository stays unwrapped (it wins over the file, and it is read from the host,
not the branch).

Two rules, both B-84's contract: the wrapper must pass stdin through untouched — one that reads
or buffers it holds the agent's stdin open, the hang B-84 closed — and its stdout is what the
stub reads the answer from, so it must pass the agent's stdout through byte for byte and keep
stderr off it. A wrapper that loses or mangles the last line fails the leg: it owns that failure.

To change how a course places tickets, `npx baton repo init --course <course> --eject stations`
copies its station function into `.baton/courses/<course>/sync.mjs`, where you can edit it. The
course is then yours, not the source's: remove its `source` from `.baton/baton.json` first.

**Land course changes yourself, outside Baton, for now.** A change to `.baton/` (instructions,
overrides, `agent_command`, the wrapper, a course's merge criteria) changes what every runner
executes and how its work lands. The practice (the owner, 2026-10-28): push it to the default
branch directly, or open a PR and merge it by hand. Under the [security model](security-model.mdx)'s
core guarantee the merge runner never merges a PR that touches `.baton/`, and stops it at
`human-merge` for you to land. Once human-in-the-loop support is built, a course may change
courses with a human approval, as ticket-creating courses already land tickets.

## `build-app`, step by step

`build-app` is for a whole application, or a large feature of one. Adopt it beside `create-pr`,
which its tickets run on:

```
npx baton repo init                       # create-pr
npx baton repo init --course build-app
```

A request is one ticket, `course: build-app`, saying what to build, often in a sentence. Each
of the first four legs drafts one document in `product/<ticket id>/` and stops for the owner:

| leg | writes | the owner approves with |
|---|---|---|
| `define` | `PRODUCT.md`: who it is for, the rules, what is in and out, numbered acceptance criteria | `answer: define` |
| `design` | `DESIGN.md` and a self-contained HTML mock-up of each screen in `mockups/` | `answer: design` |
| `architect` | `ARCHITECTURE.md`: hosting, state, sign-in, abuse, operations, cost, testing, the walking skeleton | `answer: architect` |
| `plan` | `PLAN.md`: every ticket, complete, and which acceptance criteria each one makes pass | `answer: plan` |

Each draft ends with its open questions, each with a recommendation, and the ticket gets a
`## Your turn` section. The owner settles them in a conversation: they open an interactive agent
session in a checkout and ask it to follow `## The conversation` in that leg's instructions. The
session asks the questions one at a time, rewrites the document as answers come, and sets
`answer:` only when the owner says it is right. Nothing moves until then. Then `file` writes the
plan's tickets as children of the request (`parent:`), each on `create-pr`, and the request waits
until every one has merged and closed. `verify` then tests every acceptance criterion against
the running build. It either closes the request, or files a fix ticket per failure and waits
again, up to three rounds.

Until interactive legs are built (B-34), the conversation is a session the owner starts
themselves, and `answer:` is the approval.


## `create-spec`, step by step

`create-spec` takes a request for a specification — what a thing must be, decided — from the
owner's design conversation to a merged PR. Its review and adjudication are `create-pr`'s; its
two conversations are the course's own, and Baton neither runs them nor waits inside a claim for
them.

```
npx baton repo init --course create-spec
```

A request is one ticket, `course: create-spec`. It starts at `requested` with `converse` queued:
the owner opens an interactive agent session in a checkout, following that leg's instructions, and
the two design one new specification file — under `spec/` by convention, wherever the repository
keeps them — and open its PR on the course's branch pattern. The leg's own `close` appends its
marker — `{"ticket": "<id>", "leg": "converse", "reached": "requested", "next": "review"}` — to
`.baton/markers.jsonl`, commits it and pushes it, and the claim ends. The marker
is the leg's own record that the conversation is under way: from it, every sync offers `converse`
waiting on the owner rather than ready, so there is one session, not one per sync. When the PR
appears the ticket moves to `spec-open` and
`review` runs: adversarial, non-interactive, against the corpus the specification joins — live
cross-references, security holes inherent in the design, decisions an implementer cannot be left
to make, the product's values and vocabulary — with `create-pr`'s severity ladder and its verdict
line. An `approve` queues `merge`. A `changes` verdict queues `address`: a second conversation, in
which the owner and an agent decide how each blocking finding is answered — fixed, argued, or
split into another ticket — and push the amendment. That round's claim ends with an `address`
marker, so `address` waits on the owner too, until the push lands and the ticket goes back to
`spec-open` for the next round. `review` runs four times and `address` three: the fourth review is
the one that finds the rounds spent, and queues `adjudicate` on what is left, as in `create-pr`.
`merge` lands the specification and closes the ticket.

As with `build-app`, until Baton launches interactive sessions itself (B-34), the conversation is
a session the owner starts; the runner then sends the link to the session instead. The course is
otherwise unchanged.
