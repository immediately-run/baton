<Lede>Whoever can push a home repository is a legitimate user of the fleet that serves it.
The owner keeps that decision (2026-10-27). This page states it as a security model: who
holds push, what a push can reach, the blast radius when a pusher is compromised, and the
mitigations, with what each costs.</Lede>

## The decision

- **The perimeter is push.** Whoever can push a registered repository's default branch, or
  is in its `trusted_identities`, is a legitimate user of it (BATON_SPEC R-BTN-66, §12
  "Pushers are legitimate"). Baton does not fortify git: people without push gain nothing,
  and people with push are trusted with everything git controls.
- **What agents must not change lives in Baton, not in git** (R-BTN-66): keys, grants and
  capabilities, owner bars and required bars, holds and cancels, `retry`,
  `trusted_identities`, `code_repos`, tiers and weights. No push changes them.
- **Fieldhouse adds trust levels** (*What Fieldhouse is*, Axioms 4 and 6). A sandbox VM is the
  least trusted level, the host above it, humans at the top, and a credential never crosses
  downward. Agents in VMs write the home repository without approval.

Put together: **push is held at the VM level, so everything git controls is controlled at
the VM level.** A compromised VM, a prompt-injected leg, a leaked worker token or a careless
pusher has the whole of that power. The rest of this page is what that power is.

Two corrections from the adversarial review (2026-10-27, *Review* below) bound that statement:

- **Push is not the only door.** A push to `baton` deploys Baton's server (reach 0), and any
  runner's machine key can post a board (reach 7). Neither is a push to a home's tickets.
- **Owner gates are not human gates.** The owner's agent sessions hold the owner's GitHub
  account and keys, so every gate that asks for "the owner" (ruleset bypass, code-owner
  approval, environment approval, an owner pusher, an owner signature) is passable by an
  injected session (reach 3). A gate is human only when it needs a credential no agent session
  holds: a touch-required hardware key and an approval identity in no session (B-136). On this
  page, "owner-approved" and "owner-signed" mean that human-only identity.

## The core guarantee

The owner, 2026-10-28: one simple model, implemented differently per forge, with the same
guarantee everywhere. Engineers reason about protected branches and rejected pushes, so the model
is that an unauthorised change never lands, not that it lands and is ignored.

1. **Runners propose, trusted runners land.** Runners write only their own branches. Only trusted
   runners (the merge runner first) and the human-only identity update the default branch and
   tags. The specification is BATON_SPEC §12.8 (baton#134), which supersedes this page where they
   differ.
2. **No runner change to Baton's state lands without a human.**
   - **Courses and leg logic** (`.baton/**`, agent configuration, `.github/workflows/**`): for
     now, changed outside Baton. A human pushes to the default branch or merges the PR by hand,
     as the human-only identity (B-136); the merge runner never merges them. That is also the
     best practice for working on courses (the owner, 2026-10-28). Later, with human-in-the-loop
     support, a course may change courses with a human approval, as tickets do.
   - **Tickets** (`tickets/**`, goals): created through Baton courses like code (`draft-ticket`,
     spec-to-tickets), with their own stages and reviews. The merge runner lands one only with a
     human approval at its exact head (a `std:approval@1` attestation, R-BTN-181), or, until that exists, a human merging the PR.
     One exception: a claim's branch may append its leg's progress to its own ticket's
     `## Status` section, frontmatter and everything above untouched, which the merge runner
     checks from git. The brief and frontmatter stay human-approved, since a brief reads as the
     owner's instruction.
3. **Status is Baton's.** Runners never write a ticket's status, claims or course history; those
   live in Baton (R3-1266, B-120). What runners write about tickets is a proposal on a branch,
   landed under rule 2.

**The merge runner** (B-140) is a runner type that runs only deterministic code: a pinned
released CLI, never anything from the repository. It merges a PR at its exact approved head when
Baton's own records hold independent approvals (runner keys, R-BTN-106, never PR comments), the
required checks passed, and every changed path is outside the protected paths, except a ticket
change with a human approval at that head. A PR touching a control path ends at a `human-merge`
station with a notice, for a human to land. Its criteria are course data,
so each course and home tailors its merge leg; since they live under `.baton/**`, only a human
lands a change to them, and a floor of protected paths held in Baton cannot be removed by a
course.

| Environment | What makes the default branch accept the merge runner only |
|---|---|
| GitHub, public or private | a branch ruleset restricting updates to the merge runner |
| GitLab | a protected branch: allowed to push and merge, the merge runner |
| Gitea, Forgejo | a protected branch with the merge runner alone on its whitelist |
| Plain git | a `pre-receive` hook on the server's repository, or gitolite's per-branch rules (never a client-side hook, which a runner skips) |

Rule 2 needs no forge feature beyond rule 1: the merge runner checks the paths itself and
declines, the same everywhere, and only the human can update the default branch otherwise.
The merge runner runs as a GitHub Actions workflow on the default branch, its credential in an
environment limited to that branch, or as a process above the VM level.

**The precondition**: no repository-level secrets anywhere runners push (FLDH-37). Agent branches
live in the same repository, and a workflow pushed to one runs with whatever secrets the
repository exposes. Per-worker forks would close that by GitHub's design; they stay the fallback.

**Where Baton ends and Fieldhouse begins.** Baton is cooperative (BATON_SPEC §12): on one machine
with runners you trust, it needs no merge runner, protected branch, proxy or sandbox, and runners
may land their own work. Baton's part of the guarantee is never to require a runner to write
protected state, to hold the policy (protected paths, who lands), and to print each forge's
setting for it. Fieldhouse, where runners are untrusted, sets that policy, registers the
guarantees it relies on as a floor (BATON_SPEC R-BTN-188, R-BTN-189), and supplies what Baton
cannot observe: the VMs, their resets and where keys live.

## Who holds push

For irfldhv1's homes (`fieldhouse`, `docs`, `baton`, `hq`), as of 2026-10-27:

| Holder | Level | How |
|---|---|---|
| The owner | human | their own account |
| `immediately-run-worker` | VM | an org member with `write`: every VM's SSH key and `gh` token |
| Claude Code sessions | host (`local`) or below (`cloud`) | the owner's account, or the Claude GitHub App. That puts human-level credentials in sessions below the human level: a credential crossing downward under Axiom 6, and the root of reach 3 (B-136) |
| GitHub Actions workflows | the workflow's | `GITHUB_TOKEN` and the repository's secrets |
| Any other org member or installed App with `write` | theirs | their grant |
| Any runner's Baton machine key | VM | not push, but a board post (R-BTN-102, the `cooperative` policy's `inputs.board` admits `machine`): reach 7 |

Every VM shares one GitHub identity, so a push cannot be traced to a slot from git alone,
and revoking that identity stops every VM at once.

## What a push can reach

Ordered by blast radius, largest first.

### 0. Baton's server, through its deploy

`baton`'s `.github/workflows/baton-deploy.yml` runs `wrangler deploy` on every push to `main`,
with `CLOUDFLARE_API_TOKEN` (Workers Scripts edit on the whole Cloudflare account) from the
`production` environment. The worker identity pushes `baton`, which is public, so no push ruleset
can protect it. One push, to `src/` or to the lockfile the deploy job installs, deploys the server
every tenant trusts:

- its database of keys, grants, bars, holds and settings: everything *What a push cannot reach*
  lists;
- `BATON_GITHUB_APP_KEY` (Actions write on every installed repository, so it can dispatch any
  `workflow_dispatch` workflow, the deploy included), the webhook secrets and the cursor key;
- every answer runners act on: claims, snapshot shas, recommendations, the message of the day.

The token also reaches every other Worker on the account. Whether `production` requires a
reviewer was not verified; even if it does, the reviewer is the owner's account (see *The
decision*). **Rated critical: the largest reach on this page.** B-135 makes a production deploy
a human act. A compromised server or Cloudflare account is recovered by rotating the App key,
the webhook secrets and the administrator keys, and redeploying a known commit (B-125).

### 1. Code execution on every runner that serves the home

A runner executes what the home repository names:

- `.baton/baton.json`'s `agent_command` and `agent_wrapper`, run for every leg;
- a course's `legs/<leg>.run.<ext>` overrides (R-BTN-131) and `rank.mjs` (R-BTN-98), loaded
  from the default branch's head;
- the course `source` pin, which picks the leg stubs and instructions;
- a course's `sync.mjs`, run by the sync;
- **the leg scripts of a sourced course, copied into the home** (found 2026-10-28). The spec
  (R-BTN-134) says a sourced course's code is the source's, at its pinned and verified commit, and
  the home holds only overrides. The code does otherwise: `baton repo init` copies every
  `legs/<leg>.mjs` into the home, the runner executes those copies (`src/runner/home.ts`), and the
  sync checks only `course.json`. Source fetching is not built. So an edited
  `.baton/courses/create-pr/legs/implement.mjs` runs on every runner at the next leg, unreported,
  and the pin to a reviewed Baton commit binds nothing. B-139 makes homes refer to the source
  instead of copying it, and runners run only the source's code.

So one push runs code on every runner granted on that home, at the next leg. Bounded by the
runner's level, that is the VM: its keys and the output repositories. **Unless a runner runs
above the VM level.** A runner on an owner's machine (`scripts/start-runner.sh` on a laptop)
runs that code with the owner's credentials. A VM-level push then executes at the human level,
which is the upward crossing Axiom 6 forbids.

**Agent configuration does the same in the owner's own sessions** (found in the OWASP review,
2026-10-27). Claude Code loads and executes what a repository carries:
- `.claude/settings.json` hooks (docs runs `.claude/hooks/session-context.sh` at every session
  start, and `archive-transcript.sh` at every stop);
- the plugins it enables (docs enables one from `immediately-run/claude-plugins`);
- `.claude/skills/`, `.claude/memory/` and every `CLAUDE.md`.

A push to docs' session hook is code execution with the owner's credentials in their next
session on docs, and runners push docs' main (6 commits by "OpenCode Agent" between
2026-10-21 and 2026-10-27). **Rated critical, with reach 3's privileged case.**

**And the repository's ordinary code runs too** (review findings 5 and 6). Agents and owners
execute far more than `.baton/` and `.claude/`:
- the Baton CLI itself: owners and administrators are told to run `node cli/baton.mjs owner|admin
  -i KEY` from a `baton` checkout the worker pushes, and runners run the CLI from the leg
  checkout. Pushed code then reads the owner's and administrator's keys (B-138);
- tests, `package.json` scripts, `.husky/`, `.envrc`, `.vscode/tasks.json`, `.mcp.json` servers,
  nested `CLAUDE.md`, `.claude/agents` and `.claude/commands`, in any checkout a leg or an owner
  session works in.

So mitigations on control paths close only the configuration half of this reach. Only option 1
(no runner above the VM level) closes the upward crossing for code.

### 2. CI secrets

A pushed workflow file runs on `push` to any branch with the repository's Actions secrets. A
token without the `workflow` scope cannot push a workflow over HTTPS, but SSH pushes are not
scope-limited, and every VM pushes over SSH. A workflow that has run once can also be dispatched
against any branch through the API, and runs for same-repository PRs receive repository secrets.

The worst example (review finding 2, confirmed): docs keeps `DEPLOY_APP_ID` and
`DEPLOY_APP_PRIVATE_KEY` as **repository** secrets (`process-dashboard.yml`), and the deploy App
holds Administration write. One pushed workflow reads the key, and with it an attacker deletes
the rulesets, branch protection and environment rules that mitigations A and B and tickets
B-128 and B-130 rely on, on every repository the App is installed on. **Rated critical: an
Administration-write credential reachable from a pushable workflow defeats every GitHub-side
mitigation.** `baton-sync.yml` holds `BATON_GITHUB_READ_TOKEN` the same way. FLDH-37 moves every
such secret into an environment with human-only reviewers, narrows the App and rotates.

### 3. Instructions to agents

A ticket's body and a leg's instructions are the task an agent carries out. BATON_SPEC §12.3
keeps forge and runner text as quoted data, but the ticket is not quoted data: it is the
instruction. A pushed ticket can direct the next runner that claims it to do anything that
runner's credentials allow. In effect it is a prompt injection laundered through the ledger,
and Baton cannot tell it from real work.

**The worst case is a privileged reader** (the owner's question, 2026-10-27). Runners are not
the only readers of tickets: the owner's own interactive sessions read them too. Every
repository's CLAUDE.md says to read the ticket before changing anything, and the sweeping
skills (`next-roadmap-item`, `witness`) read the board in bulk. Such a session holds human-level
credentials (the owner's GitHub account, Baton owner and administrator keys, deploy and publish
rights), often runs without approval per action, and is bound by no Baton grant. A ticket a
compromised runner wrote, read there, lifts the attacker from the VM level to the human level
with text rather than code: the upward crossing Axiom 6 forbids, untouched by signing, fences
or rulesets. Tickets also carry authority by convention: a `**Brief:** the owner, …,
verbatim:` line reads as the owner's instruction, and a runner can write that line as easily
as any other. **Rated critical.** And because the injected session holds the owner's
credentials, it passes every owner gate on this page (*The decision*), signing included.

**The message of the day (B-123) is this reach at fleet scale**: one injected owner session, or
a compromised server, instructs every leg of a repository for up to seven days.

### 4. Reviews and merges

A verdict counts from anyone who can push (R-BTN-139, B-119). The worker can push, so a
compromised leg can post the approving verdict on its own PR, and the `merge` leg merges it.
Baton's independence rule (R-BTN-106) binds runner keys inside claims, not comments posted
outside them. Branch protection on the output repositories is then the only stop.

### 5. Scheduling

Every scheduling input in git can be set by a push:

- `EXPEDITE` (R-BTN-12, from the snapshot) and `order`;
- a goal's `priority` and `exclusive` (B-122, not built). An `exclusive` goal starves
  every other ticket in its home;
- `tier` and requirements: a judgement ticket marked routine reaches runners granted only
  routine work, and a ticket marked `critical` reaches whichever runners serve that tier. If
  those run on owner machines (Claude Code runners, R-FH-21), a pushed ticket's body reaches the
  human level by frontmatter (review finding 12; B-127's tier decision depends on option 1);
- `depends_on`: blocks any ticket;
- new tickets, and re-filing a held ticket under a new id to escape its hold (R-BTN-12's
  stated residual risk).

The damage here is denial of service and misdirection, not data access. It also hides
whatever 1 to 4 do.

### 6. The record

A push can rewrite where a ticket is and how it got there (B-120, open), and the evidence
git holds: markers, ticket records, changelogs.

### 7. Board posts

Any runner's machine key can post its repository's board (R-BTN-102, while the policy's
`inputs.board` admits `machine`, as the `cooperative` preset does), and any leg can read its runner's key file (R-BTN-14, R-BTN-144). Baton never reads
repository content itself, so what a board post says is what Baton believes. A compromised leg
can post a board that marks its own verdicts and approvals trusted (R-BTN-139's marking runs in
the CLI), reports no control change (so G and B-126 stay silent), and names an older commit as
the one runners load (a rollback). B-127's signature check, as first specified, ran in that
same sync. None of this needs a push. B-137 and the policy's `inputs.board` (BATON_SPEC R-BTN-188) take `machine` out below the human level and
moves what Baton must trust (changed paths, signatures) to the server and the runners.

### 8. Denial of service by a key

A machine key can take observation numbers and post boards repeatedly; an outstanding number
blocks other syncs until it lapses after ten idle minutes (R-BTN-62), so one key can freeze a
board. It can also claim every leg its grant allows and hold the leases. B-137 adds per-key
limits; B-125's runbook starts by revoking the key.

### What a push cannot reach

Baton's own state (R-BTN-66), so a push cannot:

- grant itself a capability or a tier its key does not hold;
- lift an owner bar, clear a hold or an owner's cancel;
- add a trusted identity;
- make Baton act on a repository outside `code_repos`;
- mint a key.

Three limits on that list (review findings 1, 10 and 11):
- **It bounds what Baton lets a key do, not the GitHub identity.** The worker can push any
  repository its organisation grants allow, whatever `code_repos` says.
- **It holds only while Baton's server holds.** A push to `baton` deploys the server (reach 0).
- **It holds only against pushes.** The owner's agent sessions and delegated MCP keys (B-124) can
  change this state; B-124 keeps R-BTN-66's protected settings out of delegated keys, and B-136
  separates the human from the agent sessions.

## Mitigations

Each mitigation names what it closes, what it costs, and where it works.

### A. Push rulesets on control paths

A GitHub **push ruleset** can reject any push that changes listed paths, with a bypass list of
roles, teams or Apps. Candidate paths: `.baton/**`, `.github/workflows/**`, `**/goals/**`,
`.claude/**`, `**/CLAUDE.md` and `.github/CODEOWNERS`. Only the human-only identity bypasses
(B-136); `immediately-run-worker` and the account the owner's agent sessions use do not.

- **Closes:** the configuration half of 1, and 2, for pushes by the worker, and goals in 5. It
  is enforced at the push, so direct pushes are covered too. It does not close the code half of
  1, and an Administration-write credential deletes it (reach 2, FLDH-37).
- **Cost:** no Baton change. Changing a course or a workflow becomes an owner's push, or a
  PR an owner merges.
- **Where:** GitHub Team plans or above, on private and internal repositories only (GitHub
  Docs, *About rulesets*). That covers `fieldhouse`, `docs` and `hq`, but not `baton`, which is
  public. Path rules cannot see inside a file: `EXPEDITE`, `tier` and `depends_on` in a
  ticket's frontmatter stay open.

### B. Required reviews on control paths

CODEOWNERS plus a ruleset requiring code-owner review on the default branch. The code owner is
the human-only identity (B-136), and `.github/CODEOWNERS` is itself under code-owner review.

- **Closes:** the configuration half of 1, and 2, when changes arrive by PR.
- **Cost:** it binds only merges. Direct pushes must then be blocked, and the ticket commands
  push straight to main. That makes an approval queue, which Axiom 4 rejects, unless it is
  scoped to control paths only.
- **Where:** every plan and visibility. A complement to A, not a replacement.

### C. Owner-signed control (a Baton change)

The sync accepts control inputs only from a commit **signed by an owner key of that
repository**: `.baton/`, goals and `EXPEDITE`, and ticket `tier` if the owners choose. Owner
keys are SSH keys Baton already holds, and git's SSH commit signatures use the SSHSIG format
Baton already verifies for signed requests (R-BTN-13).
Runners load `agent_command`, overrides and `rank.mjs` only from such a commit, by extending
the verified tree they already check (R-BTN-133, R-BTN-134). An unsigned change keeps the
last signed version and raises a notice under Needs you.

- **Closes:** the configuration half of 1, and 5, on every forge and visibility, `baton`
  included, **provided** the signature is verified by Baton and by each runner rather than by the
  sync that posts it (reach 7, B-137), history is read along first parents so a crafted merge
  cannot roll a control input back to an older signed version (B-127, reproduced in the review),
  and the key is the human-only one (B-136). Without those, it is computed by the attacker.
- **Cost:** a Baton ticket; owners sign their commits; agents can no longer improve courses
  unreviewed (R-BTN-66 says they may today), so an agent's course change becomes a proposal
  an owner signs.

### D. Control as Baton state

Goals, expedite and exclusivity become owner actions (`baton owner goal set`). Git may carry a
proposal that an owner adopts, the way B-120's `adopt` takes git's course history.

- **Closes:** 5 completely.
- **Cost:** these fields leave the ledger. B-120 already makes that trade for course history.

### E. A separate control repository

`.baton/` and goals live in a repository only owners can write, as Fieldhouse did for host
state (FLDH-25, `immediately-run/runner-hosts`). The home keeps the tickets.

- **Closes:** 1 and 5, on any plan.
- **Cost:** Baton reads courses from a second repository, so a ticket's home and its course
  diverge. More moving parts than C.

### F. Trust-level hygiene (no Baton change)

- **No runner above the VM level on a home the VM level can push.** Owner-machine runners
  serve only homes whose pushers are all human-level, or stop. This is the only mitigation that
  closes the upward crossing in 1 for code, not only configuration. Its cost is real: with
  R-FH-21, it removes local Claude Code runners from every home the VMs push.
- **Actions secrets in environments** with human-only required reviewers and a
  deployment-branch policy. Before B-130 the worker can push `main`, so "main only" alone does not
  protect a secret; with human-only reviewers it does. This closes reach 2 for agent branches once
  B-130 lands, and until then only for secrets behind such reviewers (FLDH-37).
- **One GitHub identity per slot**, so a push is attributable and revocable per VM (FLDH-17's
  open item).
- **Branch protection on every output repository**: required checks, and no merge without
  them. This bounds 4.

### G. Detection

The sync raises a notice when a board post changes a control input (`.baton/`, goals,
`EXPEDITE`, a ticket's tier) and the push's pusher is not an owner. The pusher comes from the
forge's push event, not the commit author, which anyone can set.

- **Closes:** nothing. It gives after-the-fact visibility of control changes on the default
  branch, at the next sync, after the next leg may already have run them. It does not see ticket
  bodies (B-126's provenance does), workflows on agent branches, or code run in a PR-branch
  checkout. And it is only as good as the board post (reach 7): B-137 computes the changed paths
  server-side.
- **Cost:** a small Baton change.

## Hardening against a compromised runner

Assume a runner will be compromised sooner or later (the owner, 2026-10-27). Baton already
bounds its key: it claims only what its grant allows, and it cannot touch keys, bars, holds or
trusted identities. What is unbounded is the GitHub identity. Every VM shares one, with `write`
on the home and every output repository, so one compromised runner is all of them and has
everything in *What a push can reach* (the table cites its sections as reach 0 to 8). One weak
point is one identity that both writes the control plane and lands code. The review added two
more: Baton's server deploys from a push, and the owner's agent sessions hold the owner's
credentials.

## Should runners write the home repository at all?

The owner, 2026-10-27, questioned giving VM runners write access to the home repository. The line
that matters is not home versus code repository but the **default branch versus agent
branches**. Baton's sync reads only the default branch (R-BTN-105), so a change that has not
reached it is neither claimable nor in force on Baton's board. It is in force in any leg that
checks out the PR branch: a review or fix leg loads that branch's agent configuration and runs its
code (B-128 item 6, B-132). Three versions were weighed:

- **(a) Protected main, agent branches.** The worker identities push only agent refs, and the
  default branch changes only by merge. Code is merged by the reviewer identity (B-128).
  Tickets, goals, `.baton/` and workflows are merged only with an owner's approval, because a
  model reviewing a ticket's text is reading a payload whose danger is its meaning. Closes
  reaches 1, 5 and 6 on main, and reach 3 against runners. It needs ticket claims in Baton
  (R3-1266) and the second identity (B-128).
- **(b) Fork-only.** The worker reads org repositories and pushes only to its own forks. Workflows
  on fork PRs get no secrets, so this also closes reach 2. It needs Baton to trust a registered
  worker's fork PRs, and forking of private repositories.
- **(c) Quarantine by provenance.** Writes stay, but Baton holds any ticket a VM identity last
  wrote until an owner releases it. Cheap, but it leaves reaches 1 and 2 open.

**Chosen: (a), directly (B-130), implemented by the merge runner (B-140, 2026-10-28)**:
the default branch accepts only the merge runner, which replaces the reviewer identity as the
lander, so no second GitHub identity is needed. (c) is not built as a bridge: its one strength, an owner in
front of every agent-written ticket, is kept inside (a) by the owner-approval rule for
`tickets/**`. (b) stays in reserve for a repository whose CI holds secrets that cannot move into
protected environments.

**This amends Fieldhouse's axioms** (review finding 8). Axiom 4 says agents update the home
"without human approval … never by an approval queue", and (a) puts every agent-filed ticket,
memory promotion and corpus change in front of the owner. B-130's implementing PR amends Axiom 4
(and Axiom 1 for tickets) first, citing the owner's choice, with an estimate of the queue.

**The interim is accepted** (the owner, 2026-10-27). Until B-130 lands, VM runners, vm0 among
them, hold `write` on the default branch of the homes they serve, with everything in *What a push
can reach*. Baton is early, and its runners mostly work Baton's own tickets. Meanwhile:

- the CLAUDE.md rule (baton#122, fieldhouse#5, docs#223) stops the most dangerous instructions.
  It lives in files the worker can push, so owners keep a copy in their user-level
  `~/.claude/CLAUDE.md` (review finding 20);
- privileged sessions check who introduced a ticket from the forge, not from `git log`, whose
  author and committer anyone can set: the PR that brought the commit to the default branch
  (`gh api repos/{owner}/{repo}/commits/{sha}/pulls`) and its author.

## Authority and data

The owner asked (2026-10-27) whether memory written by a compromised runner and read by a
privileged session is the ticket-body problem again. It is, and worse:

- **Authority.** A ticket is a task the reader judges. A memory reads as the session's own
  prior learning ("we decided", "always", "the owner prefers"), which models trust more than a
  stranger's request.
- **Scope.** A ticket steers the session working it. A memory steers every later session.
- **Loading.** A ticket is read when picked up. Memory loads at the start of a session, before
  any task is known.
- **Persistence and review.** A ticket closes and has an owner. A poisoned memory stays until an
  audit finds it, among a hundred real ones nobody reviewed.

Provenance (B-126) helps a reader judge what they chose to read; it does nothing for what is
injected before judgement starts. Tickets were one case of a general rule, the dual of
Axiom 6:

> **Credentials never cross downward; content never crosses upward without a gate.** A
> privileged session takes authority only from owner-gated content. Everything else is data.

What privileged sessions read as authority, and who writes it today:

| Read as authority | Written by today | Gate (B-130) |
|---|---|---|
| agent memory (`.claude/memory/`) | any session, runners included | owner tier: owner-approved |
| the context corpus (values, threat model, ways of working, vocabulary) | sessions and runners, by PR | owner-approved |
| `lessons.mdx` ("read before operational work") | whoever operated Baton | owner-approved |
| `CLAUDE.md`, skills, hooks, settings | sessions and runners | owner-approved; B-127 signs |
| the specs' decision sections | sessions and runners, by PR | owner-approved |
| ticket bodies and briefs | anyone who pushes | owner-approved tickets; B-127 signs briefs |
| decision packets | agents | B-133 shows the computed action |
| archived session transcripts (`claude-sessions`) | every owner session, by a hook, unmasked | data, never authority; masked and human-only (FLDH-38) |

"Owner-approved" in this table means the human-only identity (B-136). The owner's agent
sessions, and delegated MCP keys (B-124), are writers like any other.

**Two memory tiers.**
- **The owner tier** is loaded by privileged sessions and written only through an owner-approved
  PR or an owner-signed commit. It lives with the skills, in the owner-only plugin repository,
  once docs is decomposed.
- **The fleet tier** is written by runners freely, at a path outside every owner-gated one
  (proposed: `hq`'s `memory/fleet/**`). No privileged session's configuration loads it; a
  privileged session may read it deliberately, as data with provenance.
- **Promotion is a gate.** A runner's lesson reaches the owner tier only as a PR the owner merges,
  as agent-filed tickets do under B-130. Most runner learnings are operational and stay in the
  fleet tier, so the queue is small.

**Until B-130 lands**, privileged sessions treat memory, lessons and the context corpus in a
repository runners push as unverified claims, as they treat tickets.
