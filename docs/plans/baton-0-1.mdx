# Plan — Baton 0.1: three days unattended

## The criterion

The owner, 2026-11-27: "Baton's 0.1 release criteria is that the runner can execute tasks without
interventions for 3 days such that:

1. It is working on the correct issues (most important first)
2. It follow the course as expected
3. It operates at full capacity

That is in order of importance, most important first."

What counts as an intervention is already written down: `AGENTS.md`, *The supervising agent* —
"anything you or the owner, through you, had to do before the runners could make progress".
Answering a question the course asks (a person leg, an `adjudicate`, an approval) is following the
course, not an intervention. Filing tickets is not one either.

The criterion is decided by a check, not by judgement. N9 builds `baton report soak`, which reads
Baton's own record over a window and reports the four measures: interventions, order inversions,
course deviations and idle capacity. The window passes when it prints `PASS` and the log has no
entry inside it. N10 is the operator ticket that runs the window and makes the release.

Two things this table shows:

- **Criterion 3 has the most entries**, and its fixes come first in the order below even though it
  is the least important criterion. A runner that is stuck works on no ticket at all, in order or
  not. Each fix also removes a recurring job from the supervising agent, which frees the runner to
  build the rest itself.
- **Criterion 1 is mostly data.** Baton's default order already puts expedited work first, then
  work closest to an end, then the ticket's `order`. What fails is that the order is missing or
  wrong, and that a ticket which cannot move is offered at all. N6 and N7 are small tickets. The
  ranks below fix the order for this plan's own tickets now.

## The work, in order

The first column is the rank each ticket's `order` should carry; lower ranks are offered first.
New tickets are filed with theirs. An existing ticket keeps its old `order`, or has none, until
D7 is answered: Dibber 0.4.0 refuses to change `order` after filing ("`--field` cannot write
Dibber-owned key `order`"), and has no command that does. Until then the existing 0.1 tickets
without an `order` (B-324, B-244, B-318, B-336, B-347, B-337, B-249, B-352 to B-357) sort after
every ranked ticket. Tickets the same number of legs from an end are offered by rank (*The default
order*, [BATON_SPEC §6.6](../../spec/BATON_SPEC/06-prerequisites-blocks-advice.md#sec-6-6)).
Tickets marked N are new in this PR.

## Decisions for the owner

Each has a default that this plan assumes until answered.

- **D1 — The default order.** Today `to_end` (fewest legs to an end) decides before `order`.
  - (a) Keep it, and write it down (N6, item 5). **Default.** Finishing in-flight work first keeps PRs from going stale.
  - (b) Put `order` first, so the most important ticket always goes first, even over finishing one that is nearly merged.
- **D2 — Is the selector (phase B) in 0.1?**
  - (a) Yes. The release soak runs on the mechanism 0.1 ships, and phase A's rehearsal is the cheap early signal. **Default.**
  - (b) No. Release on phase A alone, and the selector is 0.2's.
- **D3 — The pass thresholds for `baton report soak`.**
  - (a) Zero interventions, zero inversions, zero course deviations, idle capacity at most 5% of each runner's live time, no ticket stale for more than 24 hours. **Default.**
  - (b) Other numbers.
- **D4 — `run-tests` installs a PR's own lockfile.** Asked in the 2026-11-22 13:20 entry and not answered.
  - (a) Yes, when the PR's lockfile differs from the home's (N8, item 2). **Default.**
  - (b) No: N8 leaves it out.
- **D5 — B-240 and B-250** (dashboard query counts) are at `order` 2 and 3, ahead of all of phase A.
  - (a) Move them after phase A (ranks 85 and 86). **Default.** This plan's PR does not move them until answered.
  - (b) Keep them first. Choose this if their read cost threatens the soak, as the 2026-11-15 read-quota outage did.
- **D6 — While phase A is open, the 61 available tickets that cite a design in `spec/proposals/`.**
  - (a) Leave their ranks as they are: they sort after every rank above. **Default.**
  - (b) Mark them `deprioritized`, so no runner takes one before 0.1.
- **D7 — Re-ranking existing tickets**, which Dibber 0.4.0 cannot do.
  - (a) The owner authorizes a one-off hand edit of `order:` on the tickets ranked here, in this plan's PR. Dibber gains a re-rank command afterwards (a Dibber ticket). **Default.**
  - (b) Wait for the Dibber command, and accept that the existing 0.1 tickets sort last until it exists.

### People

The owner's message of 2026-11-24 asked for "ticket leg X is waiting on input from user Y or
user group Z", and for per-user notification preferences. The owner's rulings of 2026-11-26 and
2026-11-27, in
[people and dashboard §5](../../spec/proposals/people-and-dashboard.md#5-people-identities-and-the-roster)
and [personal secrets and notification](../../spec/proposals/personal-secrets.md), answer most of
it:

- **Who may answer** a person leg: the keys holding its labels (R-BTN-204's members, B-338), or
  an owner. A label is "group Z" for answering.
- **Who is told:** the ticket's assignee, resolved to a person. Baton keeps no groups, and a
  person carries no authority.
- **How:** each person's own channels and preferences, sent by a notifier outside Baton that
  never shows Baton a plaintext secret.

One gap is left. A person leg waiting on a label, on a ticket with no assignee, reaches nobody: it
is shown on Needs you and not sent. N14 (rank 270) moves both proposals into the spec under the
owner's 2026-11-27 ruling, files their build tickets, and puts that gap to the owner as one
question: keep it, or let an arena map a label to one shared channel (no membership, no
authority).
