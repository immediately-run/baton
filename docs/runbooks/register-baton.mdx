<Lede>How the baton repository becomes a repository that the Baton at
`https://baton.immediately.run` serves: its tickets on the dashboard, claimed by `baton run`
instead of `npm run ticket`.</Lede>

Commands run from a checkout of this repository on the owner's machine. The CLI is
`node cli/baton.mjs`; it talks to `https://baton.immediately.run` unless `--url` or `BATON_URL`
says otherwise. Do each step on staging first (`--url https://baton-staging.immediately.run`, and
`--env staging` for wrangler), then on production.

## What can be done today, and what waits

| Step | Ready? |
|---|---|
| 1. Keys | yes |
| 2. Make yourself administrator | yes |
| 3. Register the repository | yes |
| 4. The sync | **waits on R3-1249** (`baton sync` and a ticket source for `tickets/*.mdx`); a sync key works today, from a laptop (see below); its webhook half (4a) is ready — its smoke needs only the App's secret and the token (B-92) |
| 5. Workers | the grant is ready; `baton run` waits on the `pr` course's legs (R3-1249's `baton init`) |
| 6. Cut over | after 4 and 5 |

Until step 6, tickets are claimed with `npm run ticket` (git is the lock), and registering the
repository changes nothing about that.

## 1. Keys

Three roles, three keys: a key holds one role, and Baton refuses a key used in a second
(`conflict`).

```sh
ssh-keygen -t ed25519-sk -f ~/.ssh/baton_admin -C "baton admin"     # administrator; a touch-required
                                                                     # hardware key if you have one,
                                                                     # else -t ed25519
ssh-keygen -t ed25519 -f ~/.ssh/baton_owner_baton -C "owner of baton" # owner of this repository
```

Never load the administrator key into an ssh-agent an agent session can use. Worker keys are made
on each worker machine (step 5).

## 2. Make yourself administrator

Production has no administrator yet: `npx wrangler secret list` is empty.

```sh
npx wrangler secret put BATON_ADMIN_KEYS < ~/.ssh/baton_admin.pub
npx wrangler secret put BATON_ADMIN_KEYS --env staging < ~/.ssh/baton_admin.pub
node cli/baton.mjs admin -i ~/.ssh/baton_admin open     # prints a one-time login link (5 minutes)
```

Check: the link opens the dashboard (a session for 12 hours). From now on the dashboard needs a
login link: Cloudflare Access still stands in front, but on its own it opens the dashboard only
while `BATON_ADMIN_KEYS` lists no key.

## 3. Register the repository

```sh
node cli/baton.mjs admin -i ~/.ssh/baton_admin repo add immediately-run/baton --id baton \
  --owner-key ~/.ssh/baton_owner_baton.pub --default-branch main \
  --sync-workflow .github/workflows/baton-sync.yml --ci-identity github-actions
```

- Leave out `--cut-over`: step 6 cuts over from the dashboard once a sync and a worker work.
- `--weight N` sets the share of claims among repositories; the default is fine to start.
- Registration is insert-only. To make a fresh deployment know the repository too, add the same
  entry to `BATON_REPOSITORIES` in `wrangler.toml` (both environments) in a PR, `--owner-key` and
  all — the entry carries `owner_keys`, the owner keys `admin repo add` wrote, so a rebuilt
  instance serves the owner CLI with no manual re-add (B-91):
  `{"id":"baton","github":"immediately-run/baton","default_branch":"main","sync_workflow":".github/workflows/baton-sync.yml","owner_keys":["<~/.ssh/baton_owner_baton.pub, as one line>"]}`.
  The key this repository's entry names is the owner key the owner
  actually signs with — this runbook's `~/.ssh/baton_owner_baton`, whose fingerprint
  `ssh-keygen -lf ~/.ssh/baton_owner_baton.pub` prints — not a key another run left behind: on
  a rebuilt instance it is the only key that registers anything, so the entry is the one place
  the owner CLI is served without a read of the deployed record, and a key the owner does not
  hold is a failure nothing on the rebuilt instance can repair by hand.

→ Check, in the same PR: every entry of `BATON_REPOSITORIES` that this step registered carries
`owner_keys`, and `node cli/baton.mjs admin -i ~/.ssh/baton_admin repos` names that repository
under `seed_owners`. That name alone does not tell a seeded repository from one seeded without its
keys — `seed_owners` names every registration whose live owner keys are all the deploy's, or that
has none at all — so check each of this step's repositories for itself:

```sh
node cli/baton.mjs admin -i ~/.ssh/baton_admin repos > /tmp/repos.json
node -e 'const a = JSON.parse(require("fs").readFileSync("/tmp/repos.json")); for (const id of process.argv.slice(1))
  console.log(id, JSON.stringify((a.owners ?? []).filter((o) => o.repository_id === id)), (a.seed_owners ?? []).includes(id) ? "seed_owners" : "its own owners")' baton
```

Each repository this step registered must list exactly the keys its entry carries, each as
`<type> <base64>` (an `owners` entry carries the key's `SHA256:` fingerprint, not the line), or
the same line a build adds beside it, should one need it too — an owner added later is real, and
the entry is not the whole answer, only what a rebuild would have; and it is named in
`seed_owners` while every one of those owners is `admin:seed`. An empty list means the repository serves nobody: its
owner CLI fails after every rebuild, and no `admin repo add` can re-add it there — the rebuilt
instance knows the entry, and its `owner_keys` are checked against the role rules on that start.
A key in the list the entry does not name is the other way: the instance's history owns that
repository and the deploy would not. The PR is not ready until every repository this step
registered passes both.

Check: the dashboard lists `baton` under the repositories, with no board yet.

## 4. The sync (waits on R3-1249)

The sync posts the board: every ticket's frontmatter from `tickets/` at `main`'s head. It
authenticates with GitHub Actions OIDC from the workflow registered in step 3, so it needs no
secret.

1. A ticket source for this repository's MDX tickets: `.baton/tickets.mjs` over `tickets/` and
   `tickets/archive/`, or R3-1249's default source taught `.mdx` and the folder (R3-1266).
2. `.github/workflows/baton-sync.yml`: on a push to `main`, on `workflow_dispatch` — which
   Baton's webhook path dispatches for a merge and the alarm for a stale board — and every 15
   minutes; `permissions: id-token: write`; it runs `baton sync` at the CLI version it pins.
   `baton init` (R3-1249) writes it.

Check: `gh workflow run baton-sync.yml -R immediately-run/baton` goes green, and the dashboard
shows the `baton` board with the live tickets and the next available one. A run that posted
nothing is never silent (B-89): a failed post fails its step, and a `busy` run — another run's
reading in flight — ends with a warning saying the board is held, never a silent pass. Not every
one of those is red: a `busy` or `held` run ends green whenever the CLI it runs exits 0 for it —
this repository's pin does for `busy` — and its warning is what says nothing was posted. Read
the outcome line (`baton: advanced|confirmed at …`), not just the check mark. A run that waits a
minute and retries once arrives with the CLI release the workflow pins; until the pin carries
`--busy-retry`, a `busy` run over the old CLI still exits 0, and the annotation is what tells
you.

The schedule is the backstop, and it is not assumed to fire (§7.1): the App's `pull_request`
deliveries reach Baton, so a merge of `main` dispatches this workflow (at most one per
R-BTN-73's 30-second window, and so one per merge at most — `main` moves itself a dozen times a
day), and Baton's alarm dispatches one when the repository's last webhook-driven sync is ten
minutes old: the alarm is armed for that instant, so a quiet repository sees one an interval and
not one a tick. A dispatch that fails is not silently dropped: its stamp stands, and the alarm's
ten-minute backstop sends it again — the schedule adds only an attempt of its own. Both are
visible as `workflow_dispatch` runs in the list beside the `schedule` ones; a day with no dispatch
at all is the webhook path down, as a day with no scheduled run is GitHub's cron not firing.

A repository with no Actions — or a first board to post before any workflow exists — needs no
CI identity: register a sync key and sign the sync by hand. The key holds one role, so it can be
neither a worker's nor an administrator's.

```sh
ssh-keygen -t ed25519 -f ~/.ssh/baton_sync -C "sync of baton"
node cli/baton.mjs admin -i ~/.ssh/baton_admin repo add immediately-run/baton --id baton \
  --owner-key ~/.ssh/baton_owner_baton.pub --sync-key ~/.ssh/baton_sync.pub   # or, on a registered repository:
node cli/baton.mjs admin -i ~/.ssh/baton_admin repo set baton --add-sync-key ~/.ssh/baton_sync.pub
BATON_SYNC_KEY=~/.ssh/baton_sync node cli/baton.mjs repo sync --root <a checkout of immediately-run/baton>
```

`--sync-key FILE` (or `BATON_SYNC_KEY`) signs the sync's observation, head and board calls with
the file's key, exactly as a worker signs (R-BTN-93; B-88); it is the no-CI path, and a CI token
beside it is never spent. The file is normally the **private** key (`~/.ssh/baton_sync`); a `.pub`
whose private half an `ssh-agent` holds signs just as well — `ssh-add ~/.ssh/baton_sync` first —
as does a passphrase-protected key loaded in the agent. A file that is no SSH key at all is
refused before the first call; a key ssh-keygen cannot sign with is named by the first
signature's own reason, before any request leaves. The sync workflow stays as it is — in Actions
the OIDC token is the credential, and no key secret is needed.

## 4a. The GitHub App's webhook (B-92)

The App is the trigger that runs a sync on its own: a push, a review, a comment or a workflow's
end in a repository whose tickets name another dispatches that repository's sync, windowed to one
per 30 seconds plus one trailing (R-BTN-73). Configure it once, then check it with one delivery.

1. In the App's settings: **Webhook URL** `/v1/github/webhook` on this instance's origin.
   **Webhook secret**: a `openssl rand -hex 32` value, never a password. **SSL verification**
   on. Events: **Push**, **Pull requests**, **Pull request reviews**, **Issue comments**,
   **Workflow runs**, and nothing else — Baton drops anything outside these five. "Active"
   ticked. Permissions: **Actions: write** (the dispatch it makes), **Contents**, **Pull
   requests** and **Issues** read-only — the four its events need, and no Checks (§12.7). If no
   App exists yet, these are the values to create it with (`tickets/R3-1208.mdx` step 3a); an
   **organisation owner** of `immediately-run` installs it on `immediately-run/baton` and on the
   code repositories its tickets name — GitHub's rule, and no Baton key can.

   ```sh
   (umask 077; openssl rand -hex 32 > ~/baton_github_webhook_secret)   # mode 600; the same file both commands below read
   npx wrangler secret put BATON_GITHUB_WEBHOOK_SECRET < ~/baton_github_webhook_secret
   npx wrangler secret put BATON_GITHUB_WEBHOOK_SECRET --env staging < ~/baton_github_webhook_secret
   ```

1b. **`GITHUB_DISPATCH_TOKEN`**, in both environments — every dispatch the webhook path makes is
   sent with it (`src/cloudflare/baton.ts`; without it the dispatch fails and the ten-minute
   backstop retries into the same missing token). A delivery dispatches not only its own
   repository but every registered repository whose tickets name it, and this one token sends
   them all — so its **Actions: write** must cover every registered repository the delivery may
   dispatch: `baton` and `docs` in production, `docs` on staging:

   ```sh
   npx wrangler secret put GITHUB_DISPATCH_TOKEN        # Actions: write on baton AND docs (production); docs alone on staging
   npx wrangler secret put GITHUB_DISPATCH_TOKEN --env staging
   ```

2. The secret must also be the App's *current* webhook secret: GitHub signs every delivery with
   it, and Baton answers `401 unauthenticated` to every unsigned one when the secret is set
   (`403` only when it is not). If step 1's file is not what the App holds, rotate it in the
   App's settings to the same value.

→ Check, before any delivery, on each instance — the body's `code` and `message` say which fault
   it is, so keep them:

```sh
curl -s -w '\n%{http_code}\n' -X POST -H 'content-type: application/json' -d '{}' \
  https://baton.immediately.run/v1/github/webhook    # forbidden: the GitHub App webhook secret is not configured
```

The unsigned probe is refused before anything is read, so its answer names where the operator is
stuck: `forbidden` with *the GitHub App webhook secret is not configured* is step 1 not done (or
not yet deployed — `npx wrangler secret list` names it); `unauthenticated` with *X-Hub-Signature-256
is required* is step 1 done and the route reachable. Read either as done only when the
`forbidden` is gone. A `302`, or an HTML page, is Cloudflare Access in front instead: that is
`.local/access-paths.py` (finding 1 of the 2026-10-21 gap analysis), not this step.

3. One live smoke. Push a throwaway branch to the repository the App is installed on; the App
   delivers the push to this Baton.

→ Check, in the App's **Advanced → Recent Deliveries** (or its *Redeliver* page): the delivery
   answers **`204`**. `401` is the App's secret differing from step 1's; `403` is step 1 not
   deployed; a green `204` is the plumbing.

→ Check, in Baton, that the delivery was *acted on*, which is what the `204` alone does not say.
   A delivery writes its own trace — its id for 24 hours and its window (`webhook_deliveries`,
   `webhook_dispatch`) — and that row is not reachable from outside: there is no route for it, and
   the store is the Durable Object's, not a D1 the CLI can query. What Baton does with the delivery
   is:

   - **Either side of the cutover:** the delivery dispatches the sync (§7.1 R-BTN-73: the sync
     posts the board snapshot whatever the mode, and a snapshot under 15 minutes old is what the
     cutover needs when its day comes) — no other step of this runbook needs to happen first.
     The `204` plus this step's `401 unauthenticated` on an unsigned probe is all a live
     delivery proves on its own.
   - **The dispatch's evidence is the sync workflow's run**: a **fresh push or PR merge** in the
     repository (GitHub's Redeliver reuses the delivery id, which Baton drops as a repeat for
     24 hours — a redelivery can only count more than a day after the original) makes Baton
     dispatch the repository's `baton sync` workflow within a minute — once per 30 seconds plus
     one trailing. Read it where it ran:

     ```sh
     gh run list --repo immediately-run/baton --workflow baton-sync.yml --limit 10 --json event,createdAt,headBranch -q '.[] | select(.event == "workflow_dispatch") | .createdAt'   # the dispatch's runs; staging reads the registered repository's (docs)
     ```

     A claim's own syncs read in its ticket history (`baton ticket … history`).

   So the smoke is: push, then the line above. A `204` with no dispatch after a minute is
   the token (step 1b covers every registered repository the delivery may dispatch — a push that
   names another registered repository's tickets dispatches that one too), a second delivery
   inside the 30-second window (suppressed into the trailing one), or a repository no ticket
   names — in that order; the App's secret, its events or its Active flag were already answered
   by the `204` itself.

## 5. Workers

On each machine that will work baton tickets:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/baton_worker -C "$(hostname)"   # on the worker
```

Then, as the repository's owner, grant that key (copy its `.pub` over first):

```sh
node cli/baton.mjs owner -i ~/.ssh/baton_owner_baton grant baton --key worker.pub \
  --hostname <the worker's hostname> --capabilities create-pr,llm-call,agent-venue --max-tier judgement
```

The hostname must be what the machine reports (`hostname`, or `BATON_HOSTNAME`), or its heartbeats
are refused. Capabilities are from `src/shared/vocabulary.mjs` (`authentication`, `llm-call`,
`create-pr`, `drivable-browser`, `agent-venue`); only an administrator grants `human-operator`.

The grant *is* the machine's capability declaration (B-86): `baton run` with no `--capabilities`
declares what the grant allows on the repositories it serves, so the runner and the grant cannot
disagree. `--capabilities` exists to **narrow** — a machine without a browser passes
`--capabilities authentication,llm-call,create-pr` — never to enable: a name the grant does not
allow is refused at the heartbeat (`forbidden`). A runner whose declaration misses a capability a
leg requires says so in one line at startup (`missing-capability`) rather than idling.

Once the `pr` course's legs exist (R3-1249), the worker runs:

```sh
BATON_KEY_FILE=~/.ssh/baton_worker BATON_REPOSITORY=baton \
  node cli/baton.mjs run --harness claude-code --home <a checkout of immediately-run/baton>
```

Check: the dashboard's Workers view shows the machine heartbeating, and the log's first lines say
what it declares (`baton: declaring … — the grant's capabilities`).

## 6. Cut over

On the dashboard, under the `baton` repository, choose **Cut over** and confirm twice. From then
on Baton holds the claims for this repository, and git is not a fallback (R-BTN-18).

Then, in a PR (R3-1266): retire `scripts/ticket.mjs`'s `claim` and `set`, and say in
`tickets/home.mdx` and the README that tickets are claimed by `baton run`.

Check: `baton run` on a granted worker claims the next available ticket and takes it through the
`pr` course to merged.

## Break-glass

When Baton itself is down, agents cannot claim the ticket that fixes it. Then:

- a person (never an agent) may push a fix to `main` without a claim; the deploy workflow deploys
  it;
- `npx wrangler rollback` puts the previous version back, but only to a version at the same
  migration number (`npx wrangler deployments list`): the schema does not roll back.
