<Lede>A push can no longer change what every runner executes or how work is scheduled: with
`require_signed_control` on, a control input counts only at a commit an owner's human-only key
signed, an unsigned change keeps the last signed version in force, and each runner verifies the
signature itself before loading anything (B-127, security model mitigation C).</Lede>

## What counts, and who may sign

The control inputs are `.baton/**` (the settings, `agent_command`, course sources, overrides,
`rank.mjs`, `sync.mjs`), goal files, the `EXPEDITE` tag, and agent configuration (`.claude/**`,
every `CLAUDE.md` and `AGENTS.md`, `.mcp.json`, plugin manifests). A ticket's `tier` is
deliberately not one: a tier routes work by quality, not privilege, so a changed tier sends a
ticket to no runner whose credentials it could not already reach through its body.

Only a key of the repository's owners that **no agent session holds** counts — the human-only
register (R-BTN-185): a key registered with the tenant (`BATON_HUMAN_KEYS` on the host, or
`POST /v1/human-keys`), then made an owner of the repository (`baton owner owners REPO --add
PUB`). An ordinary owner key an agent session can reach does not count (an injected session
could sign with it), and an API key cannot sign a commit at all. Until B-136's hardware
attestation lands, the register is a custody promise; the strictest available rule is to keep
the key on a hardware token that touches on every signature.

## Configure git once

```sh
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519_owner   # the owner key's private file
```

Any commit made with `git commit -S` after that carries an SSHSIG in the namespace `git` —
exactly what Baton verifies. `baton owner -i KEY sign -- <paths>` wraps the same commit (it
configures both settings for the one call and refuses to commit no path), and either is equally
good:

```sh
baton owner -i ~/.ssh/id_ed25519_owner sign -m "the agent the fleet runs" -- .baton/baton.json
# or, the same thing by hand:
git commit -S -m "the agent the fleet runs" -- .baton/baton.json
```

## Turning it on

```sh
baton owner -i OWNER_KEY settings REPO --require-signed-control
```

The setting tightens: any owner may turn it on, and turning it **off** is a loosening an
`approvers.policy` approver signs for (R-BTN-186). With it off, today's behaviour stands and
only the marks post (briefs are marked `signed`/`unsigned` either way).

**Sign the current state once when opting in.** A control input counts only from a commit that
*changed it* and is signed, so turn the setting on only after signing one real change per
control file — a comment bump is enough; an empty `--allow-empty` signature signs nothing the
walk can see. Until then each group fails closed: runners refuse claims
(`released:cannot-finish:spec`) and the `unsigned-control` notice under Needs you names what to
sign. After the one-time signing, an unsigned change keeps the last signed version in force —
the runners keep loading it, the notice names the paths and commits, and the owner signs or
reverts at leisure.

An agent's change to a control input becomes a proposal an owner signs (that is the point of
the gate — R-BTN-66's "agents may improve it" narrows to this). The everyday shape: the agent
lands its `.baton/` change on a branch, the owner reviews and merges, then re-makes the change
signed — or merges with `-S` — so the default branch's first-parent history carries the
signature on the commit that changed the path.

## The notice and the marks

An unsigned change to a control input raises one `unsigned-control` notice under Needs you,
naming the paths and the commits — the push alone is never silent. A ticket's `**Brief:** the
owner …` line is marked `signed` or `unsigned` with its provenance whether or not the setting is
on: the mark is served with the ticket, printed at the claim, and the standing `CLAUDE.md` rule
reads an unsigned owner quote as a claim, not the owner.

## The verifier privileged sessions run

Baton cannot stop a harness loading an unsigned `.claude/settings.json` hook, and a check kept
inside the repository is rewritten by the very push it guards. For those paths the deliverable
is a verifier installed **outside** the repository:

```sh
baton owner -i OWNER_KEY verify-config REPO --checkout ~/work/REPO
```

It reads the repository's owner signing keys from Baton, walks the checkout's first-parent
history, and exits 1 naming every agent-configuration path whose last change no owner key
signed. Install it where your privileged sessions start — user-level settings, never the
repository's:

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "baton owner -i ~/.ssh/id_ed25519_owner verify-config REPO --checkout \"$CLAUDE_PROJECT_DIR\""
          }
        ]
      }
    ]
  }
}
```

(That is `~/.claude/settings.json` — the user-level file — for Claude Code; the equivalent
startup hook for other harnesses. The hook's non-zero exit is the refusal to open; how strictly
your harness enforces it is its own setting.)

## What each part refuses

| Part | Refuses |
|---|---|
| the sync | nothing — it computes what counts and posts it, marking briefs and the record |
| Baton | silently missing it: a post that moves the head onto unsigned control inputs raises the notice (while the setting is on) |
| each runner | loading what a post named without verifying: a forged or non-owner signature on a named commit ends the claim `cannot-finish:spec` |
| the runner (fail closed) | a group with no signed version: no claim runs until an owner signs the state once |
| `verify-config` | a privileged session on a checkout whose agent configuration was last changed unsigned |
| the merge runner | nothing new — control paths land by the policy's `paths.control` as ever (R-BTN-184) |

## Bounds, honestly

- The walks read the default branch's **first parents**, bounded (2000 commits, 200 changers,
  256 verifications a sync): a merge whose result differs from its first parent on a control
  path is that merge's change, so a crafted rollback to an older signed version never counts;
  burying a change past the bound takes that many accepted head moves, each flagged while in
  memory. B-137's server-side read of the push deliveries is the memory-free answer.
- `EXPEDITE` gating and the notice are the sync's computation until B-137 moves them
  server-side; the runner-loaded groups are verified by every runner, so a lying post changes
  what a runner refuses, not what it runs.
- `sync.mjs` and `.baton/tickets.mjs` still run at the head the sync reads (their unsigned
  changes raise the notice); gating their execution joins B-139's sourced-course work.
