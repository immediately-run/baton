<Lede>Baton's dashboard is the operator's live view of an AI coding factory: who is working,
on what, what is stuck, and what needs a person. It should read in five seconds and act in
two clicks.</Lede>

**The agreed design (the owner, 2026-11-09):** the Claude Design mockup
[`docs/design/baton-dashboard-v2.html`](../design/baton-dashboard-v2.html) (self-contained; its
overview in [`baton-dashboard-v2-overview.png`](../design/baton-dashboard-v2-overview.png)),
built by the BATON-UI-V2 project ([`tickets/projects/baton-ui-v2.mdx`](../../tickets/projects/baton-ui-v2.mdx)).
The mockup draws the *content* of the screens and their visual language; the dashboard's
*organization* is the entity tree below, which the owner set when handing the mockup over.

## Who uses it

- **The operator**, an instance administrator, most often on a laptop, sometimes on a phone.
  They check in a few times a day, want the exceptions first and rarely browse.
- **A repository owner**, reading their course's record: what waits longest, which legs
  fail.

## The questions it answers, in priority order

1. **Does anything need me?** Unconfirmed completions, held tickets, open decisions, tickets
   nobody can take, git overruling Baton.
2. **What is running?** Each active claim: ticket, worker, leg, how long, when its lease runs
   out, and whether it is stalled.
3. **Who is working?** Runners alive or dead, what each can do, what each holds.
4. **What happened today?** A 24-hour timeline: one lane per worker, claims as bars,
   activities nested inside them.
5. **What is ready?** The queue in Baton's order, and, separately, what nobody can take and why.
6. **How does a course perform?** Each course drawn as stations and legs, with tickets on
   it, wait and run times, and the legs that back up. Each leg is an edge with a state —
   ready, running, blocked by an unmet prerequisite (whether found before a start or during a
   run), backing off — and a blocked leg is a marked edge, never a station of its own
   (R-BTN-126). A leg's log, live or finished, opens from its edge (R-BTN-128).
7. **Where did git overrule Baton?** Discrepancies by kind and age: what Baton had, what git
   showed.
8. **Is the instance healthy?** Capacity — request rate and live counts against the
   envelope — and the instance view runners rank from (shared resources and their readings).

These are answered on the entity screens of [BATON_SPEC §11.4](../../spec/BATON_SPEC/11-people.md#sec-11-4):
the overview strip on every repository screen — running now · ready · needs you — and Conditions
(1); Board (2); Runners (3); a runner's page (4); Board and Tickets (5); Courses (6); Sync (7);
the tenant screens `/state`, `/instances` and `/resources` (8). Running, Ready and Needs you
are no longer screens of their own (the owner, 2026-11-09): the task answers stay one glance
away on the strip, and each screen is one entity.

## What it does

Expedite, hold, cancel (a hold plus a release message), stop a leg, request a worker's status,
resync a repository, resolve a condition and answer a person's leg (where the policy admits an
`owner` writer; else the entry names `baton decision answer`) — an owner's session on its
repositories, an administrator's everywhere; force-reap (with confirmation), confirm an adoption,
confirm or release an unconfirmed completion, force a resync onto a rewritten head, and cut over a
repository — an administrator's only (BATON_SPEC [R-BTN-155](../../spec/BATON_SPEC/11-people.md#sec-11-4)). Every control is a registry action
behind the same `authorize` as the CLI and the API ([R-BTN-129](../../spec/BATON_SPEC/11-people.md#sec-11-3)). Repositories, owners, grants,
probes, owner bars and required bars are shown read-only, each screen naming the CLI command
that changes it.

## Constraints a design must keep

- **Text, never markup.** Everything from tickets and runners is untrusted text. It is shown
  as a text node, never rendered as HTML or Markdown — no `innerHTML`, no
  `dangerouslySetInnerHTML` ([BATON_SPEC §12.3](../../spec/BATON_SPEC/12-security.md#sec-12-3)).
- **Polling, not push.** Each screen polls its entity's reads every 10 seconds with
  `If-None-Match`, paused while the page is hidden; show how fresh the data is. The one
  exception is the confirmation-code dialog, which polls every 5 seconds for its two minutes
  ([BATON_SPEC §11.4](../../spec/BATON_SPEC/11-people.md#sec-11-4)).
- **One entity per screen.** The dashboard is a walk down the tree the REST API, the CLI and MCP
  already draw: sign in (`/login`), pick a repository (`/`), then one entity per screen under
  `/repositories/{r}/…` — Board, Tickets, Goals, Courses, Conditions, Runners, the credentials,
  the governance knobs, Sync — and the tenant screens for an administrator. Every screen is
  drawn from that entity's REST reads, and its controls are the registry actions `ui.view`
  places there (R-BTN-129), so what a session sees and what it can do come from one definition.
  A control whose answer depends on the repository's policy is drawn only where the read says
  the session may take it; the page never reads the policy to decide.
- **React and TypeScript, one built bundle.** The owner's choice (2026-11-09) replaces the earlier
  dependency-free rule: React with no other runtime dependency, TypeScript, one esbuild bundle
  built from this repository, no external fonts or scripts, nothing loaded from another origin.
- **Accessible.** Real tables for tabular data, headings per section, keyboard reachable,
  never colour alone for state.
- **Light and dark.** Follow the system setting.
- **Course-agnostic.** Station, leg and tag names are data. Nothing in the layout may assume
  `roadmap-pr`'s names.
- **Phone-readable.** The overview strip, Conditions and the Resolve page, and Board must work
  at 375 px wide.

## The feel

Calm, dense and factual — closer to a status board than a product page. Temporal's UI is the
owner's reference for the timeline and worker views. Status by shape and label first, colour
second. Exceptions stand out; the normal case recedes.

## Where to look

`src/dashboard/` — React 19 and TypeScript, built by `npm run build:ui` into the one bundle both

page is `tickets/projects/baton-ui-v2.mdx`); its data is the entity reads of

The screens are [BATON_SPEC §11.4](../../spec/BATON_SPEC/11-people.md#sec-11-4).
