<Lede>Software is now built by people, deterministic tools and AI agents together. Baton
combines them into one explicit process, with each trusted for what it is, so a team can change
how it builds software and know whether the change worked.</Lede>

## The problem

Three kinds of actor build software today, and they differ in exactly the ways that matter:

| | Cost and availability | How far it can be trusted | Predictability |
|---|---|---|---|
| **People** | Scarce, slow, available only at certain hours | Accountable, but cannot review everything | Variable |
| **Deterministic tools** — CI, compilers, deploy scripts | Cheap and fast | Trusted to do the same thing every time, but only check what they were built to check | Reproducible |
| **AI agents** — coding, review, manager and debug agents | Cheaper than people, but limited by tokens and rate limits | Capable, but not trusted by default | Noisy |

Most teams combine them through habits and ad-hoc pipelines. That costs them four things:

- **A process nobody can see or change.** The way work moves lives in conventions, so it cannot be
  tested, compared or improved, and assumptions that no longer fit — "my pull request" against
  "yours", when agents write every pull request from the same specs — stay because nobody wrote
  them down.
- **Trust that does not match the actor.** An agent's claim, a test result and a person's sign-off
  get treated alike. A person skimming a generated pull request is not a security control, least
  of all at today's volume, and once agents can push, a record kept only in git can be rewritten by
  the agent it is meant to constrain — a compromised runner included.
- **Opinions instead of measurements.** Which model, which harness, a manager agent or not, how
  many review rounds: these are measurable questions, but nobody can say which change made things
  better when the process was never recorded.
- **Scarce resources spent by accident.** People's attention, compute and tokens are limited, and
  how much of each there is changes by the hour. Without one view of what is waiting on whom, a
  person's time goes where an agent would do and a dead claim blocks a ticket for days.

## What Baton gives a team

Baton puts people, tools and agents on one course, under the same leases, rules and record.

- **An explicit process.** A course is the team's workflow written down: the stations a ticket
  rests at and the legs it runs between them, and which kind of actor runs each. Each repository
  keeps its courses in its `.baton/` folder and changes them with a commit, not a Baton deploy.
  Baton ships standard courses that cover the simple end; a team writes its own for the rest. A
  ticket belongs to whoever holds its lease, and a suspended or released claim leaves a hand-off
  for whoever comes next, so ownership moves from who wrote a change to who owns the ticket and
  the course.
- **People, tools and agents as peers.** Agents run legs. A person takes part by working a leg at
  a runner that declares `human-operator`, or by answering a person leg, the one way a course
  waits on a person (R-BTN-116). Tools take part through the attestations they write — a check
  run, a build, a provider's remaining quota — and through the legs runners run with them.
- **Trust that matches the actor.** An attestation counts for what its writer is worth, and the
  repository's policy says whose count: a review only from an independent domain, a human gate
  only by a human-only key. Course history, attestations, the policy, grants and owner bars live
  in Baton, where no push can write them. Some of it is copied into git for people to read, and
  some of it is in git nowhere. If Baton loses that state, it fails closed: the work is reviewed
  and approved again, never restored from git (the owner, 2026-10-28).
- **Measurable change.** Because the course is versioned and every leg's history is recorded where
  the agents being measured cannot rewrite it, a change to one leg — another model, another
  harness, a linter in place of a review — can be tied to what happened next. Baton makes such
  experiments possible and attributable; running them, and judging when a result is significant,
  is the factory's work, not Baton's.
- **Scarce resources, scheduled on purpose.** One fenced lease per ticket: a runner claims a ticket
  and keeps it by heartbeat, a runner that goes silent loses the claim when its lease runs out, and
  a fence stops a revived one from writing. Capabilities and their seats say who can take what, so
  no runner finds out after claiming that it could not do the work. *Needs you* lists everything
  waiting on a person, so attention goes only where nothing cheaper will do.
- **Gates protect the lock; the rest is advice.** Baton refuses only what would make cooperating
  runners collide, or take work they have said they cannot do: a second holder, a missing
  capability or seat, a tier above the runner's ceiling, a barred tag. Everything else it offers
  in a default order that a runner may override, and every override is logged.
- **A live view.** Workers, claims, timelines, what is ready, what is blocked and what needs a
  person, all on one dashboard, along with the course's own record of how long things take. Advice
  is never older than the last write Baton accepted for the runner reading it. Fleet-wide views
  catch up within one alarm cycle.

**Baton coordinates the work, and holds the record no push may change.** It does not do, verify
or confine the work: it runs no repository code, its permissions cover its own state, and its
gates protect the lock. The ticket source — git by default — holds every ticket and its body, and
git the work's evidence. A repository can opt into one exception through its policy: Baton's
trusted runners decide what lands, and the forge lets only them and a human land it
([BATON_SPEC §12.8](../../spec/BATON_SPEC/12-security.md#sec-12-8)).

## From one machine to a factory

Baton scales from one person running a few agents on their own machine to a software factory with
a threat model of its own. Both ends run the same core. What differs is the repository's
**policy**: one versioned document, held in Baton and never read from git, that decides who lands
on which refs, who approves what, and whose attestations count (BATON_SPEC [R-BTN-188](../../spec/BATON_SPEC/12-security.md#sec-12-8)).

- **The simple end.** The `cooperative` preset and the standard courses: leases, courses and the
  live view, for runners that cooperate. At this end, owner bars and positions are a
  coordination record, not a boundary, and no guarantee is required.
- **The strict end.** The `protected` and `protected-hardware` presets turn the same state into a
  boundary. Trusted runners land only what the policy's attestations allow. Reviews count only
  from independent domains (where the policy lists a credential's runs as domains of their own, by
  run label), and human gates are satisfied only by a human-only key. A deployment
  that depends on Baton requires named **guarantees**, such as `no-runner-lands`,
  `independent-review`, `tickets-approved` and `human-gates`, and lists them as **floors**. Baton
  then refuses any policy change that would break one of them, and stops the repository while one
  is broken (R-BTN-189).
- **Everything between.** A preset is a starting point, not a mode: an owner applies one, then
  tunes it knob by knob. No rule reads a preset's name.

The courses Baton ships assume no particular architecture, and they serve the simpler end. A
factory whose guarantees rest on its own architecture writes the courses that rely on it and keeps
them itself: immediately.run's courses are Fieldhouse's (the owner, 2026-10-29).

## Who it is for

Teams of people, agents or both that work on the same repositories, from a solo developer with a
handful of agents to a factory of several dozen runners. It also serves the operator, who needs
to see at a glance what the team is doing and what it needs from a person.

## What it is not

- **Not the record of the work.** The ticket source holds every ticket and git its evidence, and
  Baton's board is a cache of them, rebuilt by each sync. Baton holds the live leases, the course history,
  attestations and the limits agents cannot change. When Baton and git disagree about what Baton
  owns, Baton wins; about anything else, the ticket source and git win.
- **Not a gatekeeper of the work.** Baton never verifies or confines what a runner does. A
  capability, `human-operator` included, is the runner's own statement, which Baton records and
  matches but never grants or checks. A threat that needs a runner stopped belongs to the
  sandbox, the forge or the credential proxy. The one exception is the trusted-runner merge a
  policy opts into. A repository chooses to adopt Baton; once it has, Baton's refusals bind every
  runner that uses it, and a runner that ignores them is outside the factory, not stopped by it
  (the owner, 2026-10-22).
- **Not a workflow engine.** A course says where a ticket may go next; runners decide how to run
  each leg. Baton runs no repository code. For durable execution of your own code, use something
  like Temporal ([compared](../compared-to-temporal.mdx)).
- **Not tied to GitHub.** Any git forge, or a plain git server, will do.
