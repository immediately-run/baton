## 15. Verification: the model, the harness, scenarios and gates *(partly built — B-50)*

- **R-BTN-29 (the harness).** `test/integration/` runs the real Worker and Durable Object locally
  on a fake clock the test advances: R-BTN-32's injected clock, plus a `clock-offset` file the
  test sidecars honour (G-BTN-38). It drives:
  - a local bare git repository per home, with fixture tickets, so the sync, the mirror and the
    CLI run as plain Node on real history;
  - simulated runners: the real runner, sidecar, harness hooks and activity reporter under a
    scripted fake harness that can be paused, killed and resumed, so fencing, spools and
    process-group kills run for real;
  - stub reviewer agents, fake OIDC tokens signed by a test key, and test keys of every
    R-BTN-13 type, trusted only by the test bindings in `vitest.config.ts` and never by the
    deployed Worker;
  - fixture courses, among them a toy course with no reviews (S-BTN-28).
- **Where it runs.** `npm test` runs on every PR and nightly on `main`. Every scenario runs in
  the Workers runtime and again on the local host; none runs against a deployed Worker.
- **The load test.** `npm run test:load` drives R-BTN-87's envelope on the local host in CI. It
  fails on any error or any route over its latency budget, and reports the figures it reached
  (G-BTN-77).
- **R-BTN-30 (scenarios are named and required).** A scenario is `S-BTN-<n>`: a fixed script with
  assertions, in a test file named for it (`test/integration/S-BTN-<n>.*.test.ts`). A gate
  `G-BTN-<n>` is an invariant the implementation must establish, proved by the scenarios or
  tests its row names. Every scenario that has a test passes on the hosts it runs on (G-BTN-37).
- **R-BTN-31 (scenarios are part of drafting).** Every ticket that changes Baton's behaviour
  names, under **Tests**, the scenarios it adds or makes pass. A new scenario's number comes from
  `baton ticket next scenario` (R-BTN-199), taken before the branch names it anywhere. Its row
  lands in the table below in the same change, and the ticket's exit criteria require `npm test`
  green with it. A behaviour change without a scenario is incomplete. Legacy, removed with its
  code (R-BTN-193): a session without Baton takes the next free number at merge.
- **R-BTN-68 (the core is a checked model).**
  - The core's state machine — claims, fencing, stations and legs, observations, ends and their
    confirmation, bars and gates — is a Quint model (`model/baton.qnt`), with the sync's output
    nondeterministic within its contract, so its properties hold for every course.
  - Safety: one live holder per ticket; no end confirmed by an earlier observation;
    observations only increase; a claim goes stale only when git takes the ticket back; every
    gate holds at claim and advance. Liveness: every end is confirmed or flagged; every fence
    clears; a ready leg with an eligible idle runner is eventually taken.
  - Every scenario's event log is checked against the model. A change to a requirement the
    model cites changes the model in the same PR.
  - CI and the deploy check only the `@impl`/`@model` links (`npm run model:links`); hosted CI
    runs no Quint. A PR that changes what the checks read carries `npm run model:pr`'s report
    for its head when a machine to run it is available. The report is advisory, never a merge
    requirement: the CI job `model-report` is red only for a pasted report that shows a failed
    check.
  - `npm run model:full` (simulation, witnesses, model-drawn traces, the proof, the scenario
    traces) is run by hand. Running it weekly as a Baton series is not built (B-50).

### Scenarios

Each row says what its scenario establishes and names the rules it tests. The test file is the
script: setups, values and refusal codes are there and in the rules, not here. A row marked
*no test* has no test file yet (R-BTN-30). Scenarios for designs that are not built are in
[the proposed scenarios](../proposals/scenarios.md).
